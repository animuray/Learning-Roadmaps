# Сломанный сервер — логи

Логи ломаются на трёх участках: приложение пишет не туда (или в удалённый файл), сборщик не читает или не может отправить, хранилище не принимает. Начинайте с конца, который ближе к приложению, и проверяйте каждое звено отдельно.

## Алгоритм «логов нет»

1. **Пишет ли приложение?** `ls -l` и `tail -f` файла; `lsof -p PID | grep log` — в какой файл оно пишет на самом деле (после ротации это может быть `app.log.1` или `(deleted)`).
2. **Видит ли сборщик файл?** Путь в конфиге (`__path__`, `path`, `paths`) и смонтирован ли каталог в контейнер сборщика.
3. **Отправляет ли?** Журнал сборщика: `docker logs promtail` — ошибки `connection refused`, `no such host`, `429`/`400` от Loki.
4. **Принял ли Loki?** `curl localhost:3100/loki/api/v1/labels`, запрос `{job="..."}` в Grafana Explore или через API.
5. **Метки:** поток мог прийти, но с другими метками, чем вы ищете.

## logrotate

- Конфиги — `/etc/logrotate.d/*`, запуск — таймер `logrotate.timer` раз в сутки. Проверка без изменений: `logrotate -d файл`, принудительно: `logrotate -f файл`.
- Приложение держит файл открытым. После переименования оно **продолжает писать в старый файл** (теперь `app.log.1`), пока не переоткроет его. Варианты: сигнал приложению в `postrotate` (`systemctl kill -s HUP`, `nginx -s reopen`) или `copytruncate` (копия и обнуление; возможна потеря строк на стыке).
- logrotate отказывается работать с каталогом, доступным на запись группе или всем («parent directory has insecure permissions»): исправьте права или укажите `su пользователь группа`.

## Лаборатория

```bash lib
# Логи: Loki (порт 3100) и Promtail — контейнеры в сети Docker «logging».
# lab_loki — запустить Loki со стандартным конфигом образа (если ещё не работает)
lab_loki() {
  docker network inspect logging >/dev/null 2>&1 || docker network create logging >/dev/null
  if [ "$(docker inspect -f '{{.State.Running}}' loki 2>/dev/null)" != true ]; then
    docker rm -f loki >/dev/null 2>&1
    docker run -d --name loki --network logging -p 3100:3100 grafana/loki:3.3.0 >/dev/null
  fi
  for i in $(seq 60); do curl -s localhost:3100/ready 2>/dev/null | grep -q ready && return 0; sleep 1; done
}
# lab_logq 'LogQL' — строки за последний час (JSON-ответ Loki)
lab_logq() { curl -s --get localhost:3100/loki/api/v1/query_range --data-urlencode "query=$1" --data-urlencode "limit=${2:-1000}" --data-urlencode "start=$(( $(date +%s) - 3600 ))000000000"; }
# lab_loglines 'LogQL' — число строк в ответе
lab_loglines() { lab_logq "$1" | jq '[.data.result[]?.values[]?] | length'; }
# lab_bsapp — приложение bs-app: пишет заказы в /var/log/bs-app/app.log, по SIGHUP переоткрывает файл
lab_bsapp() {
  systemctl stop lab-bsapp 2>/dev/null; systemctl reset-failed lab-bsapp 2>/dev/null
  mkdir -p /opt/lab /var/log/bs-app && rm -f /var/log/bs-app/*
  cat > /opt/lab/bsapp.py <<'EOF'
import signal, time, random
PATH = "/var/log/bs-app/app.log"
f = open(PATH, "a", buffering=1)
def reopen(*_):
    global f
    f.close(); f = open(PATH, "a", buffering=1)
signal.signal(signal.SIGHUP, reopen)
n = 0
while True:
    n += 1
    lvl = random.choice(["INFO"] * 8 + ["WARN", "ERROR"])
    f.write(f"{time.strftime('%Y-%m-%dT%H:%M:%S')} {lvl} order {n} processed\n")
    time.sleep(0.3)
EOF
  systemd-run -q --unit=lab-bsapp python3 /opt/lab/bsapp.py
}
```

### Логи не доходят до Loki

Логи приложения bs-app (`/var/log/bs-app/app.log`) должны попадать в Loki с меткой `job="bsapp"`. Сборщик — контейнер **`promtail-bs`**, его конфиг `~/logging/promtail-bs.yml`, запускается скриптом `~/logging/run-promtail-bs.sh`. Контейнер работает, но в Loki по `{job="bsapp"}` пусто.

Почините так, чтобы свежие логи bs-app появлялись в Loki.

```bash setup
lab_img grafana/loki:3.3.0 grafana/promtail:3.3.0
docker rm -f promtail-bs loki >/dev/null 2>&1
lab_loki
lab_bsapp
d=/home/student/logging
mkdir -p $d
cat > $d/promtail-bs.yml <<'EOF'
server:
  http_listen_port: 9080
positions:
  filename: /tmp/positions.yaml
clients:
  - url: http://localhost:3100/loki/api/v1/push
scrape_configs:
  - job_name: bsapp
    static_configs:
      - targets: [localhost]
        labels:
          job: bsapp
          __path__: /var/log/bsapp/*.log
EOF
cat > $d/run-promtail-bs.sh <<'EOF'
#!/bin/sh
docker rm -f promtail-bs >/dev/null 2>&1
docker run -d --name promtail-bs --network logging \
  -v "$HOME/logging/promtail-bs.yml:/etc/promtail/config.yml:ro" \
  -v /var/log/bs-app:/var/log/bs-app:ro \
  grafana/promtail:3.3.0 -config.file=/etc/promtail/config.yml
EOF
chmod +x $d/run-promtail-bs.sh
chown -R student:student $d
su - student -c "$d/run-promtail-bs.sh" >/dev/null
```

```bash check
[ "$(docker inspect -f '{{.State.Running}}' loki 2>/dev/null)" = true ] || fail "Loki не работает — нажмите «Начать задачу» заново"
[ "$(systemctl is-active lab-bsapp)" = active ] || fail "Приложение bs-app не работает"
[ "$(docker inspect -f '{{.State.Running}}' promtail-bs 2>/dev/null)" = true ] || fail "Контейнер promtail-bs не запущен: $(docker logs promtail-bs 2>&1 | tail -1 | cut -c1-150)"
for i in $(seq 25); do n=$(lab_loglines '{job="bsapp"} |= "processed"' 200); [ "${n:-0}" -gt 3 ] && break; sleep 1; done
[ "${n:-0}" -gt 3 ] || fail "В Loki нет строк {job=\"bsapp\"}"
last=$(tail -1 /var/log/bs-app/app.log | grep -oE 'order [0-9]+' | cut -d' ' -f2)
got=$(lab_logq '{job="bsapp"}' 5 | jq -r '[.data.result[]?.values[]?[1]] | map(capture("order (?<n>[0-9]+)").n | tonumber) | max // 0')
[ $(( last - got )) -le 60 ] || fail "В Loki старые строки: последний заказ в Loki — $got, в файле — $last"
ok "логи bs-app доходят до Loki (последний заказ $got)"
```

```text hint
1. Начать с журнала сборщика: что он пишет про файлы и про отправку.
2. Сравнить путь, который сборщик ищет, с тем, где приложение реально пишет и что смонтировано в контейнер.
3. Подумать, что значит «локальный адрес» внутри контейнера, и по какому имени контейнеры одной сети находят друг друга. После правки конфига перезапустить сборщик.
```

```bash solution
docker logs promtail-bs 2>&1 | tail -5
ls /var/log/bs-app/
docker network inspect logging -f '{{range .Containers}}{{.Name}} {{end}}'
sed -i 's#/var/log/bsapp/\*\.log#/var/log/bs-app/*.log#; s#http://localhost:3100#http://loki:3100#' ~/logging/promtail-bs.yml
~/logging/run-promtail-bs.sh
sleep 15
curl -s --get localhost:3100/loki/api/v1/query_range --data-urlencode 'query={job="bsapp"}' --data-urlencode limit=3 | jq -r '.data.result[].values[][1]'
```

```text review
Две поломки:

1. `__path__: /var/log/bsapp/*.log` — каталог называется `bs-app`. Promtail не ругается на маску без совпадений — просто ничего не читает.
2. `url: http://localhost:3100` — внутри контейнера `localhost` — это сам контейнер Promtail, Loki там нет: в журнале `connection refused`. Контейнеры одной сети Docker обращаются друг к другу **по имени** (`loki`).

- `docker exec promtail-bs ls /var/log/bs-app` — видит ли сборщик файлы; на странице `:9080/targets` Promtail показывает, какие файлы он читает.
- Начальная позиция чтения хранится в `positions.yaml`. Если её потерять, Promtail перечитает файлы с начала — получите дубли; если положить её на том, переживёт пересоздание контейнера.
- В Kubernetes те же ошибки выглядят как неверный `hostPath` в DaemonSet сборщика и неверное имя сервиса Loki.
```

```text notes
--network\s+host => Сборщик запускали в сети хоста — он работает, но ломает изоляцию; контейнеры одной сети находят друг друга по имени.
```

### logrotate не помогает

Лог bs-app `/var/log/bs-app/app.log` растёт без ограничений. Для него есть конфиг `/etc/logrotate.d/bs-app` (ежедневно, 5 сжатых копий), но ротация не происходит, а когда коллега запускал её вручную, приложение «пропадало» из `app.log`.

Почините так, чтобы ротация проходила без ошибок, после неё приложение продолжало писать в **новый** `app.log`, а старые копии сжимались. Права в каталоге должны быть безопасными.

```bash setup
lab_bsapp
chmod 777 /var/log/bs-app
cat > /etc/logrotate.d/bs-app <<'EOF'
/var/log/bs-app/*.log {
    daily
    rotate 5
    compress
    delaycompress
    missingok
    notifempty
}
EOF
chmod 644 /etc/logrotate.d/bs-app
rm -f /var/lib/logrotate/lab-bs.status
```

```bash check
[ "$(systemctl is-active lab-bsapp)" = active ] || fail "Приложение bs-app не работает"
[ -f /etc/logrotate.d/bs-app ] || fail "Нет /etc/logrotate.d/bs-app"
m=$(stat -c %a /var/log/bs-app); [ $(( 0$m & 2 )) -eq 0 ] || fail "Каталог /var/log/bs-app доступен на запись всем"
sleep 1
st=/var/lib/logrotate/lab-bs.status
for round in 1 2; do
  out=$(logrotate -f -s $st /etc/logrotate.d/bs-app 2>&1) || fail "Ротация завершается с ошибкой: $(echo "$out" | grep -iE 'error|skipping' | head -1 | cut -c1-200)"
  echo "$out" | grep -qi 'skipping' && fail "logrotate пропускает лог: $(echo "$out" | grep -i skipping | head -1 | cut -c1-200)"
  sleep 2
done
s1=$(stat -c %s /var/log/bs-app/app.log 2>/dev/null || echo 0)
o1=$(stat -c %s /var/log/bs-app/app.log.1 2>/dev/null || echo 0)
sleep 2
s2=$(stat -c %s /var/log/bs-app/app.log 2>/dev/null || echo 0)
o2=$(stat -c %s /var/log/bs-app/app.log.1 2>/dev/null || echo 0)
[ "$s2" -gt "$s1" ] || fail "После ротации в /var/log/bs-app/app.log не появляются новые строки"
[ "$o2" = "$o1" ] || fail "После ротации приложение продолжает писать в app.log.1"
ls /var/log/bs-app/app.log.*.gz >/dev/null 2>&1 || fail "Нет сжатых копий app.log.N.gz"
grep -qE '^\s*rotate\s+5\b' /etc/logrotate.d/bs-app || fail "Число хранимых копий изменено"
ok "ротация проходит, приложение пишет в новый app.log, старые копии сжаты"
```

```text hint
1. Запустить ротацию этого конфига в режиме отладки или принудительно и прочитать, почему лог пропускается.
2. Когда ротация прошла, посмотреть, в какой файл приложение пишет на самом деле (какой из файлов растёт и какой файл держит открытым процесс).
3. Добавить в конфиг действие после ротации, которое просит приложение переоткрыть файл (приложение умеет это по сигналу HUP), — или способ ротации, при котором файл не переименовывается.
```

```bash solution
sudo logrotate -d /etc/logrotate.d/bs-app 2>&1 | grep -iE 'skipping|error' | head -3
ls -ld /var/log/bs-app
sudo chmod 755 /var/log/bs-app
sudo tee /etc/logrotate.d/bs-app >/dev/null <<'EOF'
/var/log/bs-app/*.log {
    daily
    rotate 5
    compress
    delaycompress
    missingok
    notifempty
    postrotate
        systemctl kill -s HUP lab-bsapp
    endscript
}
EOF
sudo logrotate -f /etc/logrotate.d/bs-app
sleep 2
ls -l /var/log/bs-app/
sudo lsof -p "$(systemctl show -p MainPID --value lab-bsapp)" | grep bs-app
```

```text review
Две поломки:

1. `chmod 777` на каталоге логов — logrotate отказывается: «skipping ... because parent directory has insecure permissions». Это защита: в каталог, куда может писать кто угодно, можно подложить ссылку и заставить logrotate (root) перезаписать чужой файл.
2. После переименования `app.log` → `app.log.1` приложение держало открытым старый файл и писало в него. Новый `app.log` оставался пустым — «приложение пропало».

- `postrotate` + сигнал — правильный способ для программ, умеющих переоткрывать журналы (nginx — `USR1` или `nginx -s reopen`, многие демоны — `HUP`). Без `sharedscripts` скрипт выполняется для каждого файла по маске.
- `copytruncate` работает с любой программой, но между копированием и обнулением строки могут потеряться, а файл копируется целиком — тяжело для больших логов.
- `delaycompress` оставляет `app.log.1` несжатым до следующей ротации — на случай, если программа ещё дописывает в него.
- Если ротации нет вовсе, проверьте `systemctl status logrotate.timer` и `/var/lib/logrotate/status` (когда что ротировалось).
```

```text notes
chmod\s+[^\n]*(777|o\+w|a\+w) => Каталог логов открывали на запись всем — logrotate прав, отказываясь с таким каталогом работать.
```

## Тест

### Promtail в контейнере отправляет логи на http://localhost:3100, а Loki — в соседнем контейнере. Что не так?
- [ ] Ничего, localhost — это хост
- [x] Внутри контейнера localhost — сам контейнер Promtail; к Loki нужно обращаться по имени в общей сети
- [ ] Loki не принимает HTTP
- [ ] Нужен порт 9080
> Каждый контейнер — свой сетевой namespace со своим loopback.

### Promtail работает без ошибок отправки, но строк в Loki нет. Что проверить?
- [ ] Версию Loki
- [x] Совпадает ли __path__ с реальным расположением файлов и смонтирован ли каталог в контейнер
- [ ] Права на Grafana
- [ ] Метку level
> Маска без совпадений — не ошибка: сборщику просто нечего читать.

### Как узнать, в какой файл процесс пишет на самом деле?
- [ ] cat /proc/cpuinfo
- [x] lsof -p PID (или ls -l /proc/PID/fd)
- [ ] df -h
- [ ] journalctl -k
> Открытые дескрипторы показывают реальные файлы, включая удалённые и переименованные.

### После ротации app.log пустой, а app.log.1 продолжает расти. Почему?
- [ ] logrotate сломан
- [x] Приложение держит открытым старый файл; его нужно попросить переоткрыть журнал (postrotate) или использовать copytruncate
- [ ] Не хватает места
- [ ] Включён compress
> Переименование не меняет дескриптор, открытый процессом.

### logrotate пишет «skipping … because parent directory has insecure permissions». Что делать?
- [ ] Запускать logrotate с -f
- [x] Убрать запись в каталог для группы и всех (например, 755) или указать директиву su пользователь группа
- [ ] chmod 777 на файлы логов
- [ ] Удалить конфиг
> Защита от подмены файлов в каталоге, куда могут писать посторонние.

### Как проверить конфиг logrotate, ничего не меняя?
= logrotate -d
= logrotate -d /etc/logrotate.d/bs-app
> -d (debug) показывает, что было бы сделано.

### Что делает delaycompress?
- [ ] Сжимает лог через сутки после создания
- [x] Не сжимает самую свежую копию (app.log.1) до следующей ротации
- [ ] Откладывает ротацию
- [ ] Отключает сжатие
> На случай, если программа ещё пишет в только что переименованный файл.

### Чем copytruncate хуже postrotate с сигналом?
- [ ] Ничем
- [x] Строки между копированием и обнулением могут потеряться, а большой файл копируется целиком
- [ ] Не работает с gzip
- [ ] Требует перезапуска приложения
> copytruncate — компромисс для программ, не умеющих переоткрывать журнал.

### Где обычно смотреть, когда logrotate последний раз ротировал файлы?
- [ ] /etc/logrotate.conf
- [x] /var/lib/logrotate/status
- [ ] /var/log/syslog.1
- [ ] /proc/logrotate
> Файл состояния хранит дату последней ротации для каждого лога.

### Promtail перезапустили без сохранения positions.yaml. Что произойдёт?
- [ ] Ничего
