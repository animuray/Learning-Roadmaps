# Централизованное логирование

Пока сервер один, хватает `journalctl` и `tail -f`. Когда серверов десять, а подов сотни, которые живут минуты и переезжают между узлами, искать логи по SSH невозможно. **Централизованное логирование** — все логи стекаются в одно хранилище с поиском, фильтрами и графиками.

Зачем:

- искать по всем сервисам сразу: «что происходило везде в 14:05»;
- логи **переживают** под, контейнер и сервер (удалённый под уносит свои логи с собой);
- права: разработчик видит логи без SSH на прод;
- алерты и графики по логам («ошибок оплаты больше 10 в минуту»);
- аудит и расследования безопасности.

## Источники логов

| Источник | Где лежит | Как читать локально |
| --- | --- | --- |
| Службы systemd | **journald** | `journalctl -u nginx -f` |
| Классические файлы | `/var/log/nginx/access.log`, `/var/log/syslog`, `/var/log/auth.log` | `tail -f`, `less`, `grep` |
| Контейнеры Docker | stdout/stderr → драйвер логов (по умолчанию json-file в `/var/lib/docker/containers/...`) | `docker logs -f app` |
| Поды Kubernetes | stdout/stderr → файлы на узле `/var/log/pods/`, `/var/log/containers/` | `kubectl logs -f deploy/app`, `--previous` |
| Компоненты Kubernetes | journald (kubelet) или поды (apiserver и др.) | `journalctl -u kubelet` |
| Облако и сеть | Аудит облака, логи балансировщиков, WAF | Консоль провайдера |

**Правило для контейнеров**: приложение пишет логи в **stdout/stderr**, а не в файлы внутри контейнера. Сбор и ротацию берёт на себя платформа. Логи остановленного контейнера на узле живут недолго, а при удалении пода — пропадают.

## Архитектура

```
 источники                 сборщик (агент)          буфер (опционально)     хранилище + поиск        интерфейс
 /var/log/*.log  ─┐
 journald        ─┼──►  Fluent Bit / Alloy / ──►  Kafka / Redis    ──►  Elasticsearch / OpenSearch ──►  Kibana / Dashboards
 stdout подов    ─┘     Filebeat / Vector         (сглаживает пики)     Loki / ClickHouse              Grafana
                        парсинг, метки, фильтры
```

- **Сборщик** на каждом узле (в Kubernetes — **DaemonSet**) читает файлы и journald, добавляет метаданные (хост, namespace, под), отправляет дальше.
- **Обработка**: парсинг строк в поля, удаление лишнего, маскировка секретов, маршрутизация.
- **Хранилище**: полнотекстовый индекс (Elasticsearch/OpenSearch) или индекс только по меткам (Loki).
- **Интерфейс**: поиск, графики, алерты.

В Kubernetes есть три варианта: агент на узле (DaemonSet, основной), sidecar-контейнер в поде (для приложений, пишущих только в файлы), отправка из приложения напрямую (редко).

## Структурированные логи

Сравните:

```
2026-11-27 14:05:12 ERROR Payment failed for user 42 order 1001: timeout after 30s
```

```json
{"ts":"2026-11-27T14:05:12Z","level":"error","msg":"payment failed","user_id":42,"order_id":1001,"error":"timeout","duration_ms":30000,"request_id":"a1b2c3","service":"payments"}
```

JSON-логи не нужно парсить регулярками: поиск `level=error AND service=payments`, график по `duration_ms`, фильтр по `request_id` работают сразу.

Рекомендации:

- **уровни**: `debug` (выключен в проде), `info`, `warn`, `error`, `fatal`; ошибки — с причиной и контекстом;
- время в **UTC** и ISO 8601;
- **request_id / trace_id** во всех сервисах: по нему собирается вся цепочка одного запроса;
- одно событие — одна строка (многострочные трейсбеки — головная боль сборщиков);
- не логировать каждый успешный запрос на огромной нагрузке без нужды — для этого метрики.

## Безопасность и данные

- **Никаких паролей, токенов, номеров карт** в логах. Персональные данные — минимально и с маскировкой (требования 152-ФЗ, GDPR).
- Доступ к системе логов — по ролям; аудит доступа.
- Логи — тоже данные: шифрование при передаче (TLS), ограничение срока хранения.

## Хранение и ротация

- На серверах — **logrotate** и лимиты journald (`SystemMaxUse=`), иначе логи забьют диск.
- В Docker — ротация драйвера: `"log-opts": {"max-size": "50m", "max-file": "3"}` в `daemon.json`.
- В центральном хранилище — политика срока (7–30 дней «горячих», дольше — в дешёвое хранилище S3), иначе стоимость растёт бесконечно.
- Логи аудита и безопасности часто нужно хранить дольше — по требованиям регуляторов.

## Как читать логи при инциденте

1. **Сузить время**: когда началось (по алерту или графику метрик).
2. **Сузить источник**: какой сервис, какой хост или под.
3. Отфильтровать **уровень** error/warn и посмотреть, что изменилось относительно «нормы».
4. Найти **первую** ошибку в цепочке, а не самую частую: часто это «таймаут к базе», а остальное — следствия.
5. Пройти по **request_id** через все сервисы.
6. Сопоставить с событиями: деплой, изменение конфигурации, рост нагрузки.

## Практика

- [ ] Найти логи одной службы через journalctl по времени и приоритету, затем те же события в файлах /var/log
- [ ] Посмотреть, где Docker хранит логи контейнера, и настроить ротацию драйвера json-file в daemon.json
- [ ] В Kubernetes посмотреть логи пода через kubectl logs, логи предыдущего контейнера после падения и файлы в /var/log/pods на узле
- [ ] Перевести своё приложение на JSON-логи с уровнем, временем в UTC, сервисом и request_id
- [ ] Прокинуть request_id через два сервиса и найти по нему всю цепочку запроса
- [ ] Проверить, что в логах приложения нет паролей и токенов
- [ ] Нарисовать схему сбора логов для своего проекта: источники, сборщик, хранилище, интерфейс, срок хранения

## Тест

### Зачем нужно централизованное логирование?
- [x] Чтобы искать по логам всех сервисов и серверов в одном месте
- [x] Чтобы логи сохранялись после удаления пода, контейнера или сервера
- [x] Чтобы выдавать доступ к логам без SSH на продакшен-серверы
- [ ] Чтобы приложение работало быстрее
> Плюс алерты и графики по логам.

### Куда приложение в контейнере должно писать логи?
- [ ] В файл внутри контейнера
- [x] В stdout и stderr — их собирает и ротирует платформа
- [ ] В базу данных
- [ ] В /dev/null
> Файлы внутри контейнера пропадают вместе с ним и не видны через docker logs и kubectl logs.

### Как в Kubernetes обычно разворачивают агент сбора логов?
= DaemonSet
> Так на каждом узле работает один агент, который читает логи всех подов узла.

### Что происходит с логами пода при его удалении без централизованного сбора?
- [ ] Они сохраняются навсегда в etcd
- [x] Они пропадают вместе с подом
- [ ] Они переносятся на другой узел
- [ ] Они отправляются в Prometheus
> Поэтому логи нужно собирать в отдельное хранилище.

### Чем полезны структурированные JSON-логи?
- [ ] Они занимают меньше места всегда
- [x] Поля уже выделены, поэтому фильтры, поиск и графики работают без регулярных выражений
- [ ] Их нельзя прочитать человеку
- [ ] Они заменяют метрики
> Например, сразу можно отфильтровать level=error и service=payments.

### Зачем во всех сервисах логировать request_id или trace_id?
- [ ] Для красоты
- [x] Чтобы по одному идентификатору собрать все записи одного запроса, прошедшего через несколько сервисов
- [ ] Чтобы увеличить кардинальность
- [ ] Для авторизации пользователей
> Это связывает логи разных сервисов в одну историю.

### Что нельзя писать в логи?
- [x] Пароли и токены доступа
- [x] Номера банковских карт
- [x] Лишние персональные данные без маскировки
- [ ] Уровень и время события
> Логи читают многие люди и системы, и они хранятся долго.

### Чем грозит отсутствие ротации логов на сервере?
- [ ] Ничем
- [x] Логи заполнят диск, и службы начнут падать
- [ ] Логи будут удалены
- [ ] Сервер перезагрузится
> logrotate, лимиты journald и ротация драйвера Docker.

### Как ограничить размер логов контейнеров Docker с драйвером json-file?
- [ ] Это невозможно
- [x] Настроить log-opts max-size и max-file в daemon.json или для конкретного контейнера
- [ ] Удалять каталог /var/lib/docker вручную
- [ ] Перезапускать контейнер раз в день
> Например, max-size 50m и max-file 3.

### С чего начинать разбор логов при инциденте?
- [ ] С самой частой ошибки за весь месяц
- [x] Сузить время и источник, затем найти первую ошибку в цепочке и сопоставить с изменениями, например деплоем
- [ ] Прочитать все логи подряд
- [ ] Перезапустить все сервисы
> Самая частая ошибка часто оказывается следствием, а не причиной.

### Какой командой посмотреть логи предыдущего (упавшего) контейнера пода?
- [ ] kubectl logs pod --all
- [x] kubectl logs pod --previous
- [ ] kubectl describe logs
- [ ] kubectl get logs
> Полезно при CrashLoopBackOff.

### Какой уровень логирования обычно выключен в продакшене?
= debug
> Он слишком подробный и дорогой в хранении; включают временно для диагностики.
