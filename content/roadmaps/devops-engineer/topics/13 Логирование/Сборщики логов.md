# Сборщики логов

**Сборщик** (агент, шиппер) читает логи там, где они появляются, и надёжно доставляет в хранилище. Задачи:

- **читать** файлы (как `tail -f`, с запоминанием позиции), journald, syslog, stdout контейнеров;
- **парсить** строки в поля (JSON, регулярки, форматы nginx);
- **обогащать** метаданными: хост, namespace, под, метки;
- **фильтровать** и маскировать: выбросить healthcheck, скрыть токены;
- **буферизовать** и повторять отправку, если хранилище недоступно;
- **маршрутизировать**: ошибки — в одно место, аудит — в другое.

## Fluentd и Fluent Bit

Оба — проекты CNCF (graduated), лицензия Apache 2.0, общая модель: **input → parser → filter → buffer → output**, маршрутизация по **тегам**.

| | Fluentd | Fluent Bit |
| --- | --- | --- |
| Язык | Ruby + C | C |
| Память | Десятки МБ и больше | Около 1 МБ |
| Плагины | Более 1000 внешних | Более 100 встроенных |
| Роль | **Агрегатор**: сложная обработка и маршрутизация | **Агент** на каждом узле, высокая производительность |
| Сигналы | Логи | Логи, метрики, трейсы |

Классическая схема — Fluent Bit на узлах → Fluentd-агрегатор → хранилища. Сейчас многие обходятся только Fluent Bit; облачные провайдеры перешли на него ради производительности.

Конфигурация Fluent Bit (YAML-формат):

```yaml
service:
  flush: 1
  log_level: info

pipeline:
  inputs:
    - name: tail
      path: /var/log/containers/*.log
      tag: kube.*
      multiline.parser: docker, cri
      db: /var/lib/fluent-bit/tail.db
      mem_buf_limit: 50MB

  filters:
    - name: kubernetes
      match: kube.*
      merge_log: on
    - name: grep
      match: kube.*
      exclude: log /healthz

  outputs:
    - name: loki
      match: kube.*
      host: loki
      port: 3100
      labels: job=fluent-bit, namespace=$kubernetes['namespace_name'], app=$kubernetes['labels']['app']
    - name: opensearch
      match: audit.*
      host: opensearch
      port: 9200
      tls: on
```

- `tail` + `db` — файл позиций: после перезапуска агент продолжит с того места, где остановился, без дублей и пропусков.
- `kubernetes` filter — добавляет namespace, под, контейнер и метки пода из API Kubernetes; `merge_log` разбирает JSON-строку приложения в поля.
- `multiline.parser` — склейка многострочных записей (stack trace Java/Python) в одно событие.

Fluentd (классический формат):

```
<source>
  @type forward
  port 24224
</source>

<filter app.**>
  @type parser
  key_name log
  <parse>
    @type json
  </parse>
</filter>

<match app.**>
  @type opensearch
  host opensearch
  port 9200
  logstash_format true
  <buffer>
    @type file
    path /var/log/fluentd/buffer
    flush_interval 5s
    retry_max_times 10
  </buffer>
</match>
```

## Filebeat

Лёгкий агент Elastic на Go (семейство **Beats**). Для каждого файла запускает **harvester**, отправляет в Elasticsearch или Logstash. Есть **модули** для nginx, system, postgresql и др. — с готовым парсингом и дашбордами Kibana.

```yaml
filebeat.inputs:
  - type: filestream
    id: nginx-access
    paths:
      - /var/log/nginx/access.log
    fields:
      service: nginx

  - type: filestream
    id: app
    paths:
      - /var/log/app/*.log
    parsers:
      - ndjson:
          target: ""
      - multiline:
          type: pattern
          pattern: '^\d{4}-\d{2}-\d{2}'
          negate: true
          match: after

processors:
  - add_host_metadata: ~
  - drop_event:
      when:
        contains:
          message: "/health"

output.logstash:
  hosts: ["logstash:5044"]
```

Elastic развивает **Elastic Agent** (централизованное управление через Fleet), внутри которого работают те же Beats.

## Другие сборщики

- **Vector** (Datadog, Rust) — быстрый, с языком преобразований VRL; источники, трансформы, приёмники.
- **Grafana Alloy** — агент Grafana на базе OpenTelemetry Collector: логи (в Loki), метрики, трейсы; замена Promtail.
- **OpenTelemetry Collector** — вендор-нейтральный стандарт для всех сигналов (OTLP); набирает популярность как единый агент.
- **rsyslog / syslog-ng** — классика Linux для syslog, пересылка по сети.

## Надёжность доставки

- **Позиции чтения** (registry/db): без них при рестарте агент перечитает файлы (дубли) или пропустит строки.
- **Буфер** в памяти и на диске: хранилище недоступно — логи копятся и отправляются позже. Буфер в памяти без ограничения → OOM агента.
- **Backpressure**: если хранилище не успевает, агент замедляет чтение; при переполнении буфера часть логов теряется — это нужно мониторить.
- **Ротация**: агент должен корректно обрабатывать переименование и усечение файлов (logrotate `copytruncate` может привести к потере строк).
- **Мониторинг самого агента**: у Fluent Bit, Vector, Alloy есть метрики для Prometheus (ошибки отправки, ретраи, размер буфера).
- Между агентами и хранилищем для больших объёмов ставят **Kafka** как буфер.

## Как выбрать

| Ситуация | Выбор |
| --- | --- |
| Kubernetes + Loki/Grafana | Grafana Alloy или Fluent Bit |
| Elastic Stack | Filebeat / Elastic Agent |
| Много разных назначений, сложная маршрутизация | Fluent Bit (+ Fluentd или Vector как агрегатор) |
| Единый агент для логов, метрик и трейсов | OpenTelemetry Collector / Alloy |
| Минимум ресурсов на узле | Fluent Bit, Vector |

## Лаборатория

Loki работает в Docker (контейнер `loki`, сеть `logging`, порт 3100). Приложение `jsonapp` пишет **структурированный JSON-лог** в `/var/log/jsonapp/app.log` — по объекту на строку: `{"time": ..., "level": "info|debug|warn|error", "msg": ..., "user": ...}`.

```bash lib
# Логи: Loki (порт 3100) и Promtail — контейнеры в сети Docker «logging».
# lab_loki — запустить Loki со стандартным конфигом образа (если ещё не работает)
lab_loki() {
  docker network inspect logging >/dev/null 2>&1 || docker network create logging >/dev/null
  if [ "$(docker inspect -f '{{.State.Running}}' loki 2>/dev/null)" != true ]; then
    docker rm -f loki >/dev/null 2>&1
    docker run -d --name loki --network logging -p 3100:3100 grafana/loki:3.3.0 >/dev/null
  fi
  for i in $(seq 60); do curl -s localhost:3100/ready 2>/dev/null | grep -q ready && return 0; sleep 1; done
}
# lab_logq 'LogQL' — строки за последний час (JSON-ответ Loki)
lab_logq() { curl -s --get localhost:3100/loki/api/v1/query_range --data-urlencode "query=$1" --data-urlencode "limit=${2:-1000}" --data-urlencode "start=$(( $(date +%s) - 3600 ))000000000"; }
# lab_loglines 'LogQL' — число строк в ответе
lab_loglines() { lab_logq "$1" | jq '[.data.result[]?.values[]?] | length'; }
lab_drm() { docker rm -f "$@" >/dev/null 2>&1; true; }
# образ есть локально или скачивается (если ученик почистил образы через prune)
lab_img() { for i in "$@"; do docker image inspect "$i" >/dev/null 2>&1 || docker pull -q "$i" >/dev/null; done; }
# lab_wait_http URL [строка] — дождаться ответа
lab_wait_http() { for i in $(seq 60); do curl -s --max-time 1 "$1" 2>/dev/null | grep -q "${2:-.}" && return 0; sleep 0.25; done; return 1; }
```

### Разобрать JSON и отсечь шум

Запустите Promtail в контейнере **`promtail-json`** (сеть `logging`) с конфигом `~/logging/promtail-json.yml`, который:

- читает `/var/log/jsonapp/*.log` с меткой `job="jsonapp"`;
- **разбирает JSON** и делает **метку `level`** из поля `level`;
- **отбрасывает** строки уровня `debug` — их в Loki быть не должно.

```bash setup
lab_img grafana/loki:3.3.0 grafana/promtail:3.3.0
lab_loki
docker rm -f promtail-json >/dev/null 2>&1
systemctl stop lab-jsonapp 2>/dev/null; systemctl reset-failed lab-jsonapp 2>/dev/null
mkdir -p /var/log/jsonapp /opt/lab && rm -f /var/log/jsonapp/*.log
cat > /opt/lab/jsonapp.py <<'EOF'
import json, random, time
users = ["anna", "boris", "vera", "gleb"]
with open("/var/log/jsonapp/app.log", "a", buffering=1) as f:
    while True:
        lvl = random.choice(["debug"] * 5 + ["info"] * 3 + ["warn", "error"])
        f.write(json.dumps({"time": time.strftime("%Y-%m-%dT%H:%M:%S"), "level": lvl, "msg": f"{lvl} event {random.randint(1, 999)}", "user": random.choice(users)}) + "\n")
        time.sleep(0.5)
EOF
systemd-run -q --unit=lab-jsonapp python3 /opt/lab/jsonapp.py
mkdir -p /home/student/logging && chown student:student /home/student/logging
rm -f /home/student/logging/promtail-json.yml
```

```bash check
[ "$(docker inspect -f '{{.State.Running}}' promtail-json 2>/dev/null)" = true ] || fail "Контейнер promtail-json не запущен: $(docker logs promtail-json 2>&1 | tail -1 | cut -c1-150)"
for i in $(seq 30); do n=$(lab_loglines '{job="jsonapp"}' 100); [ "${n:-0}" -gt 3 ] && break; sleep 1; done
[ "${n:-0}" -gt 3 ] || fail "В Loki нет строк {job=\"jsonapp\"}"
lv=$(curl -s --get localhost:3100/loki/api/v1/label/level/values --data-urlencode 'query={job="jsonapp"}' | jq -r '.data // [] | join(" ")')
for l in info error; do echo " $lv " | grep -q " $l " || fail "У потоков jsonapp нет метки level=\"$l\" (значения level: ${lv:-нет})"; done
d=$(lab_loglines '{job="jsonapp"} |= "\"level\": \"debug\""' 100)
d2=$(lab_loglines '{job="jsonapp", level="debug"}' 100)
[ "${d:-0}" = 0 ] && [ "${d2:-0}" = 0 ] || fail "В Loki попали строки уровня debug: $((d + d2))"
ok "jsonapp: метка level ($lv), debug отброшен"
```

```text hint
1. В задании сбора Promtail есть этапы конвейера обработки строк: разбор JSON с выражениями для нужных полей, превращение поля в метку, отбрасывание строк по значению поля.
2. Порядок важен: сначала разобрать, потом использовать поле.
3. Запустить контейнер в сети logging с конфигом и каталогом логов только на чтение.
```

```bash solution
cat > ~/logging/promtail-json.yml <<'EOF'
server:
  http_listen_port: 9080
positions:
  filename: /tmp/positions.yaml
clients:
  - url: http://loki:3100/loki/api/v1/push
scrape_configs:
  - job_name: jsonapp
    static_configs:
      - targets: [localhost]
        labels:
          job: jsonapp
          __path__: /var/log/jsonapp/*.log
    pipeline_stages:
      - json:
          expressions:
            level: level
      - drop:
          source: level
          value: debug
      - labels:
          level:
EOF
docker run -d --name promtail-json --network logging \
  -v ~/logging/promtail-json.yml:/etc/promtail/config.yml:ro -v /var/log/jsonapp:/var/log/jsonapp:ro \
  grafana/promtail:3.3.0 -config.file=/etc/promtail/config.yml
sleep 15
curl -s --get localhost:3100/loki/api/v1/label/level/values | jq
```

```text review
Эталон: `pipeline_stages` — `json` → `drop` (source: level, value: debug) → `labels: level`.

- Отбрасывать шум **на сборщике** выгоднее всего: debug-логи — часто половина объёма, а платят за хранение и трафик.
- `level` — хорошая метка (несколько значений), `user` — плохая (кардинальность): его оставляют в строке и ищут `| json | user = "anna"`.
- Логи в JSON — лучший подарок эксплуатации: не нужны хрупкие регулярки, поля разбираются однозначно.
- Другие сборщики: Fluent Bit (лёгкий, стандарт в Kubernetes), Vector (быстрый, удобный язык преобразований VRL), Logstash (мощный, тяжёлый), Grafana Alloy. Принцип у всех одинаковый: вход → разбор/фильтры → выход.
```

## Тест

### Какие задачи решает сборщик логов?
- [x] Читает логи из файлов, journald и stdout контейнеров
- [x] Парсит строки и обогащает их метаданными
- [x] Буферизует и повторяет отправку, если хранилище недоступно
- [ ] Хранит логи годами и строит по ним индекс
> Хранение и поиск — задача Elasticsearch, OpenSearch или Loki.

### Чем Fluent Bit отличается от Fluentd?
- [x] Fluent Bit написан на C и потребляет около мегабайта памяти — подходит как агент на каждом узле
- [x] Fluentd на Ruby и C, с тысячей внешних плагинов, чаще используется как агрегатор со сложной обработкой
- [ ] Fluent Bit не умеет отправлять в Elasticsearch
- [ ] Fluentd — платный продукт
> Оба — проекты CNCF под Apache 2.0.

### Зачем сборщику файл позиций (db или registry)?
- [ ] Для хранения паролей
- [x] Чтобы после перезапуска продолжить чтение с того же места — без дублей и пропусков
- [ ] Для сжатия логов
- [ ] Для авторизации в хранилище
> Без него агент перечитает файлы с начала или пропустит строки.

### Что делает фильтр kubernetes во Fluent Bit?
- [ ] Перезапускает поды
- [x] Добавляет к логам метаданные из API Kubernetes: namespace, имя пода, контейнер, метки
- [ ] Удаляет логи системных подов
- [ ] Отправляет логи в etcd
> С merge_log он ещё и разбирает JSON-строку приложения в поля.

### Как правильно обработать многострочный stack trace?
- [ ] Каждая строка трейсбека — отдельное событие
- [x] Настроить многострочный парсер, который склеит строки трейсбека в одно событие по шаблону начала записи
- [ ] Удалить трейсбеки
- [ ] Логировать только первую строку
> Иначе ошибка разлетится на десятки бессвязных записей.

### Какой агент из семейства Beats предназначен для доставки файлов логов в Elastic Stack?
= Filebeat
> Для каждого файла он запускает harvester.

### Что произойдёт, если хранилище логов недоступно, а у агента настроен буфер?
- [ ] Логи сразу теряются
- [x] Логи накапливаются в буфере в памяти или на диске и отправляются после восстановления — пока буфер не переполнится
- [ ] Агент удаляет исходные файлы
- [ ] Приложение останавливается
> Размер буфера нужно ограничивать и мониторить.

### Какой вендор-нейтральный агент собирает логи, метрики и трейсы по стандарту OTLP?
- [ ] Filebeat
- [x] OpenTelemetry Collector
- [ ] Logstash
- [ ] rsyslog

- [ ] Как Job

- [ ] Для красивых дашбордов

- [ ] Для замены хранилища
- [ ] Для парсинга grok

- [ ] Не нужно, он всегда работает
- [x] Ошибки отправки, переполнение буфера и отставание означают потерю логов именно тогда, когда они нужны
- [ ] Чтобы считать число пользователей
- [ ] Чтобы ускорить приложение

= Vector
