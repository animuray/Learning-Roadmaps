# Managed-сервисы

**Managed-сервис** — облако разворачивает и обслуживает за вас сложную систему: базу данных, Kubernetes, Kafka, Redis/Valkey, OpenSearch, ClickHouse. Вы получаете **endpoint** и настройки, а установка, обновления, репликация, бэкапы и замена упавших серверов — на провайдере.

## Что берёт на себя провайдер, а что остаётся вам

| Провайдер | Вы |
| --- | --- |
| Установка и обновления ОС и ПО (минорные версии автоматически, мажорные — по кнопке) | Выбор размера, числа хостов и зон |
| Репликация и автоматическое переключение на реплику | Схема БД, индексы, запросы, миграции |
| Автоматические бэкапы и восстановление на момент времени | Проверка восстановления, сроки хранения, свои дампы |
| Мониторинг «железа», замена вышедших из строя хостов | Мониторинг своих метрик и алерты |
| Окна обслуживания | Пользователи, права, сетевой доступ, группы безопасности |

Самое ценное — **вы не дежурите за отказы инфраструктуры** и не пишете свою автоматизацию failover и бэкапов.

## Managed PostgreSQL

На примере Yandex Managed Service for PostgreSQL (у Selectel, Cloud.ru, VK Cloud, AWS RDS — так же):

- **Кластер** из одного или нескольких **хостов** в разных **зонах доступности**: один мастер, остальные — реплики. Мастер упал → автоматически повышается реплика.
- **Класс хоста** (vCPU/RAM), тип и размер диска; диск можно расширять, часто — с автоувеличением.
- **Бэкапы** — ежедневно автоматически + архив WAL → **PITR**: восстановление в **новый** кластер на любой момент в пределах срока хранения. Бэкап снимается с реплики, чтобы не нагружать мастер.
- **Подключение**:
  - особые FQDN: «текущий мастер» и «наименее отстающая реплика» — приложение не нужно перенастраивать после failover;
  - **TLS обязательно**, сертификат провайдера (`sslmode=verify-full`);
  - встроенный пулер соединений (Odyssey/PgBouncer) — режимы session/transaction;
  - публичный доступ к хостам выключен по умолчанию — держите базу во внутренней сети.
- **Ограничения**: нет SSH на хосты и **нет суперпользователя**; часть настроек PostgreSQL меняется только через API/консоль; расширения — из разрешённого списка. Пользователи и базы создаются через консоль, CLI или Terraform.
- **Мониторинг**: встроенные графики, логи, `pg_stat_statements`; метрики экспортируются в Prometheus.

```bash
yc managed-postgresql cluster create \
  --name app-db \
  --environment production \
  --network-name app-net \
  --host zone-id=ru-central1-a,subnet-name=app-a \
  --host zone-id=ru-central1-d,subnet-name=app-d \
  --resource-preset s3-c2-m8 \
  --disk-type network-ssd --disk-size 50 \
  --postgresql-version 17 \
  --user name=app,password=<пароль> \
  --database name=app,owner=app \
  --security-group-ids <id_db_sg>

psql "host=c-<id_кластера>.rw.mdb.yandexcloud.net port=6432 sslmode=verify-full dbname=app user=app"
```

Версии и классы хостов меняются — смотрите актуальные значения в документации провайдера (`yc managed-postgresql resource-preset list`).

## Managed Kubernetes

- **Мастер (control plane)** — API-сервер, etcd, scheduler — обслуживает провайдер, часто в **высокодоступном** варианте по трём зонам. Вы не видите его ВМ, но платите за него.
- **Группы узлов** (node groups) — ВМ-воркеры из шаблона: размер, число, зоны, прерываемые узлы для дешёвых нагрузок, метки и taints.
- **Автомасштабирование узлов** (cluster autoscaler): поды не помещаются → добавляются узлы; узлы пустуют → удаляются. Вместе с HPA для подов.
- **Обновления** версии Kubernetes — по кнопке или автоматически в окно обслуживания; версии поддерживаются ограниченное время, отставать нельзя.
- **Интеграции**:
  - `Service type: LoadBalancer` → облачный балансировщик;
  - PersistentVolumeClaim → облачный диск через CSI;
  - Ingress / Gateway API → контроллер, ALB провайдера;
  - образы из **Container Registry** провайдера;
  - IAM ↔ RBAC, workload identity: поды получают права в облаке без статических ключей.
- Доступ: `yc managed-kubernetes cluster get-credentials app-k8s --external` дописывает контекст в kubeconfig.
- Ваша зона ответственности: всё внутри кластера — приложения, RBAC, сетевые политики, Ingress, мониторинг, логи, обновление узлов (или его настройка), бэкапы (Velero).

## Другие managed-сервисы

Kafka, Valkey/Redis, ClickHouse, OpenSearch, MySQL, MongoDB-совместимые, GitLab, Container Registry, Lockbox/KMS (секреты и ключи), Certificate Manager, Monitoring и Logging, serverless-функции. Принцип тот же: платите за удобство и надёжность, теряете часть контроля.

## Плюсы и минусы

| Плюсы | Минусы |
| --- | --- |
| Отказоустойчивость, бэкапы, обновления «из коробки» | Дороже аналогичных ВМ «в лоб» |
| Быстрый старт — минуты вместо дней | Нет полного доступа (суперпользователь, SSH, любые расширения) |
| Не нужна узкая экспертиза для дежурств | Зависимость от провайдера и его окон обслуживания |
| Интеграция с IAM, сетью, мониторингом облака | Не все параметры настраиваются |

Частое разумное решение: **stateful-сервисы (базы, очереди) — managed**, а stateless-приложения — в Managed Kubernetes или на ВМ. Самостоятельно поднимать базу в Kubernetes оправдано, когда есть опыт и операторы (CloudNativePG, Patroni).

## Практика

- [ ] Создать managed PostgreSQL из двух хостов в разных зонах, подключиться по TLS с verify-full через FQDN мастера
- [ ] Посмотреть автоматические бэкапы и восстановить кластер на момент времени в новый кластер
- [ ] Выполнить ручное переключение мастера и убедиться, что приложение продолжает работать через FQDN текущего мастера
- [ ] Найти в документации, каких прав и расширений нет в managed-базе по сравнению с собственной установкой
- [ ] Создать Managed Kubernetes с группой узлов из двух узлов, получить kubeconfig и задеплоить своё приложение
- [ ] Создать Service типа LoadBalancer и PVC и посмотреть, какие облачные ресурсы появились
- [ ] Включить автомасштабирование группы узлов, нагрузить кластер и пронаблюдать добавление узла
- [ ] Посчитать стоимость: managed PostgreSQL против двух ВМ с PostgreSQL и Patroni с учётом времени инженера
- [ ] Удалить кластеры и проверить, что не остались диски и балансировщики

- [ ] По IP-адресу конкретного хоста

### Куда восстанавливается managed PostgreSQL из бэкапа на момент времени?
- [ ] Поверх текущего кластера с потерей данных

- [ ] На локальный ноутбук
- [ ] Восстановление невозможно
> Затем переключают приложение или переносят нужные данные.

### Почему к managed-базе подключаются с sslmode=verify-full?
- [ ] Так быстрее
- [x] Трафик шифруется, а клиент проверяет сертификат сервера и имя хоста — защита от перехвата и подмены
- [ ] Без этого база не принимает пароли
- [ ] Это отключает пулер
> Сертификат провайдера скачивают из документации.

### Что обслуживает провайдер в Managed Kubernetes?
- [ ] Все приложения внутри кластера
- [x] Мастер (control plane): API-сервер, etcd, планировщик — часто в высокодоступном варианте
- [ ] Только Ingress
- [ ] RBAC пользователей приложения
> Узлы — ВМ в группах узлов, которыми управляете вы.

### Что произойдёт при создании Service типа LoadBalancer в Managed Kubernetes?
- [ ] Ничего
- [x] Облако автоматически создаст облачный балансировщик и направит трафик на узлы кластера
- [ ] Будет создана новая база данных
- [ ] Кластер перезапустится
> PVC аналогично создаёт облачный диск через CSI.

### Что делает автомасштабирование группы узлов?
- [ ] Меняет число реплик подов
- [x] Добавляет узлы, когда поды не помещаются, и удаляет пустующие
- [ ] Увеличивает диски
- [ ] Обновляет Kubernetes
> Число подов меняет HPA, число узлов — cluster autoscaler.

### Что остаётся в зоне ответственности клиента в Managed Kubernetes?
- [x] Приложения, RBAC, сетевые политики
- [x] Мониторинг, логи и бэкапы ресурсов кластера
- [ ] Работа etcd
- [ ] Железо дата-центра
> Провайдер обслуживает control plane и инфраструктуру.

### Какой главный минус managed-сервисов?
- [ ] Их нельзя масштабировать
- [x] Выше стоимость и меньше контроля: нет полного доступа, не все параметры настраиваются, зависимость от провайдера
- [ ] Они не делают бэкапы
- [ ] Они работают только в одной зоне
> Взамен — экономия времени на эксплуатации и дежурствах.

### Почему версии Kubernetes в managed-кластере нужно регулярно обновлять?
- [ ] Чтобы сбросить данные
- [x] Каждая версия поддерживается ограниченное время; устаревшие версии перестают получать исправления и в итоге обновляются принудительно
- [ ] Новые версии бесплатны
- [ ] Обновления не нужны
> Планируйте обновления и проверяйте устаревшие API заранее.

### Какой подход к размещению часто выбирают в облаке?
- [ ] Всё на одной ВМ
- [x] Базы и очереди — managed-сервисы, stateless-приложения — в Managed Kubernetes или на ВМ
- [ ] Базы обязательно в Kubernetes без операторов
- [ ] Только serverless
