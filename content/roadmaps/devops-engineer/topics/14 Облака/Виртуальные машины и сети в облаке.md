# Виртуальные машины и сети в облаке

Примеры — на Yandex Cloud и его CLI `yc`, но у Selectel (OpenStack), Cloud.ru, VK Cloud и AWS всё устроено похоже: другие названия, те же идеи.

## Ресурсы и доступ

- Иерархия Yandex Cloud: **организация → облако → каталог (folder) → ресурсы**. Каталоги разделяют окружения (dev, prod) и команды.
- **IAM**: пользователи и **сервисные аккаунты** (для программ, CI, Terraform) получают **роли** на облако, каталог или ресурс (`viewer`, `editor`, `vpc.admin`, `compute.admin`…). Принцип наименьших привилегий: CI не нужен `admin` на всё облако.
- Ключи сервисных аккаунтов — секреты: в хранилище секретов или CI-переменных, не в Git.

```bash
yc init
yc config list
yc resource-manager folder list
yc iam service-account create --name terraform
```

## Виртуальная машина

Из чего состоит:

| Параметр | Что это |
| --- | --- |
| **Образ** | Ubuntu, Debian, Rocky и др. из публичного каталога (`standard-images`) или свой |
| **Платформа и vCPU** | Поколение процессоров, число ядер, **гарантированная доля vCPU** (`core-fraction` 20/50/100%) — дешёвые ВМ с 20% подходят для учёбы, не для нагрузки |
| **Память** | Гигабайты RAM |
| **Загрузочный и дополнительные диски** | HDD, SSD, нереплицируемые; размер можно увеличить, уменьшить — нет |
| **Сетевой интерфейс** | Подсеть, приватный IP, опционально публичный IP (NAT), группы безопасности |
| **Метаданные** | SSH-ключи, **cloud-init** (`user-data`) — настройка при первом запуске |
| **Прерываемость** | Дешевле, но может быть остановлена |

```bash
ssh-keygen -t ed25519 -f ~/.ssh/cloud -C "me@laptop"

yc compute instance create \
  --name web-1 \
  --zone ru-central1-d \
  --platform standard-v3 \
  --cores 2 --memory 2 --core-fraction 20 \
  --create-boot-disk image-folder-id=standard-images,image-family=ubuntu-2404-lts,size=20 \
  --network-interface subnet-name=app-d,nat-ip-version=ipv4,security-group-ids=<id_web_sg> \
  --ssh-key ~/.ssh/cloud.pub

yc compute instance list
ssh -i ~/.ssh/cloud yc-user@<публичный_IP>
```

- Флаг `--ssh-key` создаёт пользователя **yc-user** с вашим ключом через cloud-config. Вход по паролю в публичных образах отключён.
- Список семейств образов: `yc compute image list --folder-id standard-images`.

**cloud-init** — стандарт первичной настройки ВМ во всех облаках:

```yaml
#cloud-config
users:
  - name: deploy
    groups: sudo
    shell: /bin/bash
    sudo: ALL=(ALL) NOPASSWD:ALL
    ssh_authorized_keys:
      - ssh-ed25519 AAAA... me@laptop
package_update: true
packages:
  - nginx
  - fail2ban
runcmd:
  - systemctl enable --now nginx
```

Передаётся через `--metadata-from-file user-data=cloud-init.yaml`. Логи: `/var/log/cloud-init-output.log`.

**Снапшоты** дисков — точка восстановления перед рискованными изменениями и способ клонировать ВМ; **расписания снапшотов** — простой бэкап. **Группы ВМ** (instance groups) — несколько одинаковых ВМ из шаблона с автомасштабированием и автовосстановлением.

> [!tip] ВМ — это «скот, а не питомцы»
> Всё, что настроено вручную на ВМ, потеряется при её пересоздании. Настраивайте через cloud-init, Ansible или образы (Packer), а инфраструктуру описывайте в Terraform.

## Облачная сеть (VPC)

```
 Облачная сеть app-net (общая на все зоны)
 ├── подсеть app-a  10.10.1.0/24  ru-central1-a
 ├── подсеть app-b  10.10.2.0/24  ru-central1-b
 └── подсеть app-d  10.10.3.0/24  ru-central1-d
        web-1 (10.10.3.5, публичный 51.250.x.x) ──┐
        db-1  (10.10.3.10, без публичного IP)      │  трафик между подсетями сети — по приватным адресам
```

- **Облачная сеть (VPC)** — изолированная частная сеть; внутри неё ВМ общаются по **приватным** адресам (RFC 1918).
- **Подсеть** привязана к **зоне доступности** и имеет CIDR. Планируйте адреса заранее, без пересечений с офисом и VPN.
- **Публичный IP**: динамический (меняется после остановки ВМ) или **статический** (резервируется отдельно, платный, даже если не используется).
- Принцип: **публичный адрес — только у того, что должно быть доступно из интернета** (балансировщик, бастион). Базы, бэкенды, воркеры — только приватные адреса.
- **NAT-шлюз** — исходящий доступ в интернет (обновления пакетов, внешние API) для ВМ без публичного IP; входящие соединения из интернета через него невозможны.
- **Бастион (jump host)** — единственная ВМ с SSH из интернета (и только с ваших IP); к остальным: `ssh -J yc-user@bastion deploy@10.10.3.10`. Альтернатива — VPN (WireGuard) в сеть.
- **Таблицы маршрутизации** — статические маршруты (например, весь трафик через ВМ-шлюз).
- **Cloud DNS** — внутренние и публичные зоны; внутри сети ВМ резолвятся по имени.

```bash
yc vpc network create --name app-net
yc vpc subnet create --name app-d --zone ru-central1-d --range 10.10.3.0/24 --network-name app-net
yc vpc address create --name web-ip --external-ipv4 zone=ru-central1-d
```

## Группы безопасности

**Группа безопасности (Security Group)** — облачный файрвол на уровне сетевого интерфейса ВМ (и других ресурсов: managed-баз, узлов Kubernetes, балансировщиков). Правила — **разрешающие**, всё, что не разрешено, запрещено. Работают с **состоянием** (stateful): ответный трафик на разрешённое соединение пропускается автоматически.

| Группа | Входящие (ingress) | Исходящие (egress) |
| --- | --- | --- |
| `web-sg` | 443, 80 от `0.0.0.0/0`; 22 только от `bastion-sg` | всё |
| `bastion-sg` | 22 только от IP офиса/дома `/32` | всё |
| `db-sg` | 5432 только от `web-sg` | всё |

Правило может ссылаться не на CIDR, а на **другую группу** («от всех ВМ из web-sg») — не нужно перечислять IP, которые меняются.

```bash
yc vpc security-group create --name web-sg --network-name app-net \
  --rule "direction=ingress,port=443,protocol=tcp,v4-cidrs=[0.0.0.0/0]" \
  --rule "direction=ingress,port=80,protocol=tcp,v4-cidrs=[0.0.0.0/0]" \
  --rule "direction=egress,protocol=any,v4-cidrs=[0.0.0.0/0]"
```

Группы безопасности не отменяют файрвол внутри ВМ (ufw/nftables) — это два уровня защиты. Частая ошибка: «всё открыто `0.0.0.0/0` на любой порт для теста», которое забыли закрыть.

## Балансировщики

- **Network Load Balancer** (L4) — TCP/UDP, распределяет соединения между ВМ целевой группы с проверками здоровья.
- **Application Load Balancer** (L7) — HTTP(S): маршрутизация по хосту и пути, TLS-сертификаты, HTTP/2, WebSocket.
- Балансировщик + ВМ в нескольких зонах + health checks = сервис переживает падение ВМ и зоны.

## Как работать с облаком

1. **Консоль** — изучать и смотреть.
2. **CLI** (`yc`, `openstack`, `aws`) — скрипты и быстрые операции.
3. **API и SDK** — интеграции.
4. **Terraform** — основной способ для всего постоянного (тема дальше): инфраструктура в Git, ревью изменений, воспроизводимость.

## Тест

### Для чего нужны сервисные аккаунты в облаке?
- [ ] Для входа людей в консоль
- [x] Для программ, CI и Terraform, которые работают с API облака; им выдают роли с минимально нужными правами
- [ ] Для оплаты счетов
- [ ] Для SSH на ВМ
> Их ключи — секреты, их не хранят в Git.

### Что такое cloud-init?
- [ ] Консоль облака
- [x] Стандартный механизм первичной настройки ВМ при первом запуске: пользователи, ключи, пакеты, команды
- [ ] Балансировщик
- [ ] Тип диска
> Конфиг передаётся через метаданные user-data.

### Чем облачная сеть (VPC) отличается от подсети?
- [x] Облачная сеть — изолированная частная сеть, общая для всех зон доступности
- [x] Подсеть привязана к конкретной зоне и имеет свой диапазон адресов (CIDR)
- [ ] Это синонимы
- [ ] Подсеть всегда публичная
> ВМ в разных подсетях одной сети общаются по приватным адресам.

### Какой ВМ нужен публичный IP-адрес?
- [ ] Всем ВМ всегда
- [x] Только тому, что должно принимать соединения из интернета, — балансировщику, бастиону, публичному веб-серверу
- [ ] Только базе данных
- [ ] Никакой
> Базы и бэкенды держат только на приватных адресах.

### Как ВМ без публичного IP может скачивать обновления пакетов?
- [ ] Никак
- [x] Через NAT-шлюз, который даёт исходящий доступ в интернет без возможности входящих подключений
- [ ] Через группу безопасности
- [ ] Через статический публичный IP на базе данных
> Это безопаснее, чем выдавать каждой ВМ публичный адрес.

### Что такое бастион (jump host)?
- [ ] Балансировщик нагрузки
- [x] Единственная ВМ с SSH-доступом из интернета (с ограниченных IP), через которую заходят на остальные ВМ по приватным адресам
- [ ] Резервный диск
- [ ] Сервисный аккаунт
> Пример: ssh -J user@bastion deploy@10.10.3.10.

### Как работают группы безопасности?
- [x] Это облачный файрвол на уровне сетевого интерфейса с разрешающими правилами — всё, что не разрешено, запрещено
- [x] Ответный трафик на разрешённое соединение пропускается автоматически (stateful)
- [ ] Они шифруют трафик
- [ ] Они действуют только на исходящий трафик
> В правиле можно указать другую группу безопасности вместо диапазона адресов.

### Как правильно разрешить доступ к базе только с веб-серверов?
- [ ] Открыть 5432 для 0.0.0.0/0
- [x] В группе безопасности базы разрешить порт 5432 только от группы безопасности веб-серверов
- [ ] Выдать базе публичный IP
- [ ] Отключить группы безопасности
> Не нужно перечислять IP-адреса, которые могут меняться.

### Какого пользователя создаёт флаг --ssh-key у команды yc compute instance create?
= yc-user
> Ключ добавляется через cloud-config.

### Зачем делать снапшоты дисков?
- [ ] Чтобы ускорить ВМ
- [x] Как точку восстановления перед рискованными изменениями, для простого бэкапа по расписанию и клонирования ВМ
- [ ] Чтобы уменьшить размер диска
- [ ] Для балансировки трафика
> Снапшоты тоже стоят денег — удаляйте ненужные.

### Чем Application Load Balancer отличается от Network Load Balancer?
- [x] Network Load Balancer работает на уровне L4 — распределяет TCP/UDP-соединения
- [x] Application Load Balancer работает на уровне L7 — маршрутизирует HTTP(S) по хосту и пути, терминирует TLS
- [ ] Network Load Balancer понимает URL
- [ ] Разницы нет
> Оба используют проверки здоровья целей.

### Почему важно не настраивать ВМ только вручную?
- [ ] Ручная настройка запрещена провайдером
- [x] При пересоздании ВМ ручные изменения теряются; настройку описывают в cloud-init, Ansible или образах, а инфраструктуру — в Terraform
- [ ] Вручную нельзя установить nginx
- [ ] ВМ не поддерживают SSH
> Принцип «скот, а не питомцы».
