# Сломанный сервер — S3

Бэкап в S3 — классическое место тихих аварий: скрипт работает по таймеру, никто не смотрит его вывод, а в бакете месяцами лежат пустые архивы. Две вещи важнее всего: понятная ошибка, когда загрузка не удалась, и проверка, что из бэкапа можно восстановиться.

## Алгоритм «не грузится в S3»

1. **Достучаться:** `curl -sI http://endpoint` — отвечает ли хранилище вообще. `Connection refused` — не тот адрес или порт.
2. **Аутентификация:** `s3cmd ls` (или `aws s3 ls --endpoint-url ...`). Ошибки:
   - `InvalidAccessKeyId` — нет такого ключа доступа;
   - `SignatureDoesNotMatch` — неверный секретный ключ (или часы сервера сильно убежали);
   - `AccessDenied` — ключ верный, но прав на это действие нет.
3. **Бакет:** `NoSuchBucket` — опечатка в имени или другой регион/аккаунт.
4. **Конфиг клиента:** `s3cmd --dump-config`, переменные `AWS_*` в окружении (они сильнее файла у AWS CLI).

## Надёжный скрипт бэкапа

- `set -euo pipefail` — скрипт падает на первой же ошибке, в том числе внутри конвейера.
- Не прятать ошибки (`2>/dev/null`, `|| true`) у шагов, от которых зависит результат.
- Секреты — не в скрипте: в конфиге клиента с правами `600`, в переменных окружения из `EnvironmentFile` или в роли сервера (IAM role).
- Проверять результат: размер, контрольная сумма, **пробное восстановление** по расписанию.
- Алерт на «последний успешный бэкап старше N часов» — по метрике или по дате объекта в бакете.

## Лаборатория

S3-совместимое хранилище работает на стенде (контейнер `s3`). Клиент — `s3cmd`.

```bash lib
lab_drm() { docker rm -f "$@" >/dev/null 2>&1; true; }
# образ есть локально или скачивается (если ученик почистил образы через prune)
lab_img() { for i in "$@"; do docker image inspect "$i" >/dev/null 2>&1 || docker pull -q "$i" >/dev/null; done; }
# lab_wait_http URL [строка] — дождаться ответа
lab_wait_http() { for i in $(seq 60); do curl -s --max-time 1 "$1" 2>/dev/null | grep -q "${2:-.}" && return 0; sleep 0.25; done; return 1; }
# lab_s3 — S3-совместимое хранилище на 127.0.0.1:7480 (данные в /srv/s3)
lab_s3() {
  lab_img versity/versitygw:v1.0.10
  if [ "$(docker inspect -f '{{.State.Running}}' s3 2>/dev/null)" != true ]; then
    docker rm -f s3 >/dev/null 2>&1; mkdir -p /srv/s3
    docker run -d --name s3 --restart unless-stopped -p 127.0.0.1:7480:7480 -v /srv/s3:/data \
      -e ROOT_ACCESS_KEY=labkey -e ROOT_SECRET_KEY=labsecret123 versity/versitygw:v1.0.10 --port :7480 posix /data >/dev/null
  fi
  mkdir -p /var/lib/lab
  printf '[default]\naccess_key = labkey\nsecret_key = labsecret123\nhost_base = localhost:7480\nhost_bucket = localhost:7480\nuse_https = False\nbucket_location = us-east-1\n' > /var/lib/lab/s3cfg
  for i in $(seq 40); do s3cmd -c /var/lib/lab/s3cfg ls >/dev/null 2>&1 && return 0; sleep 0.25; done
}
lab_s3cmd() { s3cmd -c /var/lib/lab/s3cfg "$@" 2>/dev/null; }
lab_s3rb() { lab_s3cmd del -r --force "s3://$1" >/dev/null; lab_s3cmd rb "s3://$1" >/dev/null; true; }
# lab_s3n префикс — число объектов
lab_s3n() { lab_s3cmd ls -r "$1" | grep -c 's3://'; }
```

### Бэкап перестал уходить

Скрипт `~/bin/backup-to-s3.sh` (его запускает таймер) архивирует `/srv/app/data` и загружает архив в бакет **`backups`** под префикс `app/`. После того как на прошлой неделе «обновили доступы к хранилищу», новых архивов в бакете нет.

Действующие параметры доступа выданы в `~/s3-credentials.txt`. Почините так, чтобы скрипт успешно загружал архивы. Ключи в сам скрипт не записывайте.

```bash setup
lab_s3
lab_s3rb backups; lab_s3rb bakups
lab_s3cmd mb s3://backups >/dev/null
mkdir -p /srv/app/data && echo "id,total" > /srv/app/data/orders.csv && chmod -R a+rX /srv/app
h=/home/student
mkdir -p $h/bin
cat > $h/bin/backup-to-s3.sh <<'EOF'
#!/bin/bash
set -euo pipefail
f=/tmp/app-$(date +%F-%H%M%S).tar.gz
tar czf "$f" -C /srv/app data
s3cmd put "$f" "s3://bakups/app/$(basename "$f")"
rm -f "$f"
echo "uploaded $(basename "$f")"
EOF
chmod +x $h/bin/backup-to-s3.sh
printf '[default]\naccess_key = labkey\nsecret_key = oldsecret-2025\nhost_base = localhost:7481\nhost_bucket = localhost:7481\nuse_https = False\nbucket_location = us-east-1\n' > $h/.s3cfg
chmod 600 $h/.s3cfg
printf 'endpoint:   http://localhost:7480\nregion:     us-east-1\naccess_key: labkey\nsecret_key: labsecret123\n' > $h/s3-credentials.txt
chmod 600 $h/s3-credentials.txt
chown -R student:student $h/bin $h/.s3cfg $h/s3-credentials.txt
```

```bash check
s=/home/student/bin/backup-to-s3.sh
[ -x $s ] || fail "Нет исполняемого ~/bin/backup-to-s3.sh"
grep -q 'labsecret123' $s && fail "Секретный ключ записан в скрипт"
[ "$(stat -c %a /home/student/.s3cfg 2>/dev/null)" = 600 ] || fail "~/.s3cfg отсутствует или доступен не только владельцу"
before=$(lab_s3n s3://backups/app/); sleep 1.1
out=$(su - student -c "$s" 2>&1) || fail "Скрипт завершается с ошибкой: $(echo "$out" | grep -iE 'error|denied|refused|exist' | head -1 | cut -c1-200)"
after=$(lab_s3n s3://backups/app/)
[ "$after" -gt "$before" ] || fail "Скрипт отработал, но в s3://backups/app/ новых архивов нет"
k=$(lab_s3cmd ls s3://backups/app/ | sort | tail -1 | awk '{print $4}')
lab_s3cmd get --force "$k" /tmp/lab-bk.tgz >/dev/null
tar tzf /tmp/lab-bk.tgz 2>/dev/null | grep -q 'data/orders.csv' || fail "Последний архив в бакете не содержит data/orders.csv"
rm -f /tmp/lab-bk.tgz
ok "скрипт загрузил $k"
```

1. Запустить скрипт руками и прочитать ошибку клиента дословно. Затем проверить связь клиента с хранилищем отдельно от скрипта.
2. Сравнить настройки клиента (адрес и ключи) с выданными параметрами доступа.
3. Когда клиент подключается, снова запустить скрипт: следующая ошибка укажет на место назначения.

```bash solution
~/bin/backup-to-s3.sh || true
s3cmd ls || true
cat ~/s3-credentials.txt
sed -i 's/^secret_key = .*/secret_key = labsecret123/; s/7481/7480/g' ~/.s3cfg
s3cmd ls
~/bin/backup-to-s3.sh || true
sed -i 's#s3://bakups/#s3://backups/#' ~/bin/backup-to-s3.sh
~/bin/backup-to-s3.sh
s3cmd ls s3://backups/app/
```

```text review
Три поломки:

1. `host_base = localhost:7481` — не тот порт: `Connection refused`.
2. `secret_key = oldsecret-2025` — ключи сменили, а конфиг клиента — нет: `SignatureDoesNotMatch`.
3. `s3://bakups/` в скрипте — опечатка в имени бакета: `NoSuchBucket`. Она была и раньше, но маскировалась первыми двумя ошибками.

- После смены ключей обновляют **все** места, где они используются: конфиги на серверах, переменные CI, секреты в Kubernetes, Vault. Хорошо, когда такое место одно — менеджер секретов.
- Благодаря `set -euo pipefail` скрипт честно падал. Если бы ошибку прятали, сломанный бэкап заметили бы только при попытке восстановления.
- Таймер с бэкапом должен сообщать о неудаче: `OnFailure=` в юните, алерт на возраст последнего объекта в бакете или на метрику из Pushgateway.
```

### Бэкап «успешный», но пустой

Скрипт `~/bin/backup-shop.sh` каждую ночь пишет «backup ok», а при попытке восстановления оказалось, что в архивах нет данных магазина. Данные магазина сейчас лежат в `/srv/shop/data` (их перенесли с прежнего места месяц назад).

Почините скрипт так, чтобы:

- в архиве были данные магазина (`data/…`);
- если архивирование не удалось, скрипт завершался **с ошибкой** и **ничего не загружал** в бакет.

```bash setup
lab_s3
lab_s3rb backups
lab_s3cmd mb s3://backups >/dev/null
rm -rf /var/lib/shop /srv/shop
mkdir -p /srv/shop/data && printf 'id,total\n1,100\n2,250\n' > /srv/shop/data/orders.csv && chmod -R a+rX /srv/shop
h=/home/student
mkdir -p $h/bin
cat > $h/bin/backup-shop.sh <<'EOF'
#!/bin/bash
f=/tmp/shop-$(date +%F-%H%M%S).tar.gz
tar czf "$f" -C /var/lib/shop data 2>/dev/null
s3cmd put "$f" "s3://backups/shop/$(basename "$f")" >/dev/null
rm -f "$f"
echo "backup ok"
EOF
chmod +x $h/bin/backup-shop.sh
cp /var/lib/lab/s3cfg $h/.s3cfg && chmod 600 $h/.s3cfg
chown -R student:student $h/bin $h/.s3cfg
```

```bash check
s=/home/student/bin/backup-shop.sh
[ -x $s ] || fail "Нет исполняемого ~/bin/backup-shop.sh"
[ -d /srv/shop/data ] || mv /srv/shop/data.lab-hidden /srv/shop/data 2>/dev/null
b1=$(lab_s3n s3://backups/shop/); sleep 1.1
out=$(su - student -c "$s" 2>&1); rc=$?
a1=$(lab_s3n s3://backups/shop/)
k=$(lab_s3cmd ls s3://backups/shop/ | sort | tail -1 | awk '{print $4}')
mv /srv/shop/data /srv/shop/data.lab-hidden
sleep 1
su - student -c "$s" >/dev/null 2>&1; rc2=$?
a2=$(lab_s3n s3://backups/shop/)
mv /srv/shop/data.lab-hidden /srv/shop/data
[ $rc = 0 ] || fail "Скрипт завершается с ошибкой при доступных данных: $(echo "$out" | tail -1 | cut -c1-200)"
[ "$a1" -gt "$b1" ] || fail "Скрипт отработал, но новых архивов в s3://backups/shop/ нет"
lab_s3cmd get --force "$k" /tmp/lab-shop.tgz >/dev/null
tar tzf /tmp/lab-shop.tgz 2>/dev/null | grep -q 'data/orders.csv' || { rm -f /tmp/lab-shop.tgz; fail "В свежем архиве нет data/orders.csv"; }
rm -f /tmp/lab-shop.tgz
[ $rc2 != 0 ] || fail "Когда каталог с данными недоступен, скрипт завершается успешно"
[ "$a2" = "$a1" ] || fail "Когда каталог с данными недоступен, скрипт всё равно загружает архив"
ok "архив с данными магазина загружается; при ошибке архивирования — код $rc2 и ничего не загружено"
```

```text hint
1. Запустить команды скрипта по одной без подавления ошибок и посмотреть, что на самом деле попадает в архив.
2. Сделать так, чтобы оболочка прерывала скрипт на первой же неудачной команде, и не прятать вывод ошибок архиватора.
3. Исправить путь к данным. Проверить и удачный случай, и случай, когда данных нет.
```

```bash solution
f=/tmp/test.tar.gz; tar czf $f -C /var/lib/shop data; echo "код: $?"; tar tzf $f; rm -f $f
cat > ~/bin/backup-shop.sh <<'EOF'
#!/bin/bash
set -euo pipefail
f=/tmp/shop-$(date +%F-%H%M%S).tar.gz
trap 'rm -f "$f"' EXIT
tar czf "$f" -C /srv/shop data
s3cmd put "$f" "s3://backups/shop/$(basename "$f")" >/dev/null
echo "backup ok: $(basename "$f")"
EOF
~/bin/backup-shop.sh
s3cmd ls s3://backups/shop/
```

```text review
Причина: данные переехали в `/srv/shop/data`, а скрипт архивировал `/var/lib/shop`. `tar` падал с ошибкой, но:

- `2>/dev/null` прятал сообщение;
- без `set -e` скрипт шёл дальше и загружал пустой (битый) архив;
- последней командой был `echo "backup ok"` — код выхода скрипта всегда 0, и таймер считал бэкап успешным.

- `set -euo pipefail`: `-e` — выход на первой ошибке, `-u` — ошибка на неопределённой переменной, `-o pipefail` — конвейер падает, если упала любая его часть (иначе `pg_dump | gzip` «успешен», даже если `pg_dump` упал).
- `trap '…' EXIT` убирает временный файл при любом исходе.
- Бэкап без проверки восстановления — это надежда, а не бэкап. Минимум — проверять размер и содержимое архива сразу после создания; лучше — регулярное восстановление на тестовой машине.
```

## Тест

### s3cmd ls отвечает «Connection refused». Что проверить?
- [ ] Секретный ключ
- [x] Адрес и порт хранилища (host_base / endpoint)
- [ ] Имя бакета
- [ ] Права на файл
> До аутентификации дело не дошло: по этому адресу никто не слушает.

### Ошибка SignatureDoesNotMatch. Что вероятнее всего?
- [ ] Нет бакета
- [x] Неверный секретный ключ (реже — сильно сбитые часы сервера)
- [ ] Неверный ключ доступа (access key)
- [ ] Хранилище перегружено
> Подпись запроса считается из секретного ключа и времени.

### Ошибка NoSuchBucket при загрузке. Причина?
- [ ] Неверный пароль
- [x] Бакета с таким именем нет — опечатка, другой аккаунт или регион
- [ ] Переполнен диск
- [ ] Файл слишком большой
> Хранилище доступно и ключи верны — не найден сам бакет.

### Что делает set -o pipefail?
- [ ] Ускоряет конвейеры
- [x] Код выхода конвейера — ошибка, если упала любая его часть, а не только последняя команда
- [ ] Запрещает конвейеры
- [ ] Печатает каждую команду
> Без него `pg_dump | gzip > file` «успешен», даже если `pg_dump` упал.

### Скрипт бэкапа заканчивается строкой `echo "backup ok"` без set -e. Какой у него будет код выхода при ошибке tar?
- [ ] Код ошибки tar
- [x] 0 — код последней команды echo
- [ ] 1 всегда
- [ ] Не определён
> Код выхода скрипта — код последней выполненной команды.

### Где хранить ключи доступа к S3 для скрипта на сервере?
- [ ] Прямо в скрипте
- [x] В конфиге клиента или EnvironmentFile с правами 600, а в облаке — в роли сервера (IAM role)
- [ ] В README репозитория
- [ ] В имени бакета
> Секрет в скрипте попадёт в Git, бэкапы и чужие руки.

### Как убедиться, что бэкапы действительно рабочие?
- [ ] Посмотреть, что скрипт пишет «ok»
- [x] Регулярно восстанавливать из них на тестовой машине и проверять данные
- [ ] Проверить, что бакет не пустой
- [ ] Сравнить имена файлов
> Только восстановление доказывает, что из бэкапа можно восстановиться.

### Какой алерт поймает тихо сломавшийся бэкап?
- [ ] Загрузка CPU сервера
- [x] Возраст последнего успешного бэкапа больше N часов
- [ ] Число бакетов
- [ ] Свободная память
> Так ловятся и падения скрипта, и выключенный таймер.

### После смены ключей хранилища что нужно сделать в первую очередь?
- [ ] Ничего, клиенты обновятся сами
- [x] Обновить ключи во всех местах использования: серверы, CI, секреты кластера
- [ ] Пересоздать бакеты
- [ ] Перезагрузить хранилище
> Хорошо, когда такое место одно — менеджер секретов.

### Зачем в скрипте `trap 'rm -f "$f"' EXIT`?
- [ ] Чтобы скрипт не завершался
- [x] Чтобы временный файл удалялся при любом исходе, в том числе при ошибке
- [ ] Чтобы перехватить Ctrl+C и продолжить
- [ ] Чтобы загрузка шла в фоне
> EXIT срабатывает при любом завершении оболочки.

### Как посмотреть итоговые настройки s3cmd (какой endpoint и ключ он использует)?
= s3cmd --dump-config
> Выводит все параметры с учётом конфига и ключей командной строки.

### Почему `2>/dev/null` у команды архивации в скрипте бэкапа — плохая идея?
- [ ] Это ускоряет скрипт
- [x] Ошибки архиватора пропадают — в журнале таймера не будет причины неудачи

- [ ] Это запрещено в bash
> Вывод ошибок — единственная подсказка при разборе ночной аварии.
