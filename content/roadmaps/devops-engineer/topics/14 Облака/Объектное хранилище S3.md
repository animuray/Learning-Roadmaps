# Объектное хранилище S3

**Объектное хранилище** хранит данные как **объекты** (файл + метаданные) в **бакетах** и отдаёт их по HTTP API. Протокол **S3** придумал Amazon, и он стал стандартом: Yandex Object Storage, Selectel S3, Cloud.ru, VK Cloud и самостоятельные решения (Ceph RGW, SeaweedFS, Garage) совместимы с S3 API — одни и те же инструменты работают везде.

## Три вида хранения

| | Блочное | Файловое | Объектное |
| --- | --- | --- | --- |
| Что это | «Голый диск» для одной ВМ | Общая ФС по сети | Объекты по HTTP |
| Примеры | Диски ВМ, PV в Kubernetes | NFS, SMB, облачные файловые хранилища | S3 |
| Доступ | Монтируется как устройство | `mount`, пути, POSIX | API: PUT/GET/DELETE по ключу |
| Масштаб | Гигабайты–терабайты | Терабайты | Практически без предела |
| Для чего | Базы данных, ОС | Общие файлы нескольким серверам | Бэкапы, статика, логи, артефакты, медиа |

Объект нельзя изменить «на месте» или дописать в середину — только записать заново. Зато хранение дешёвое, надёжное (данные реплицируются провайдером) и доступно отовсюду.

## Бакеты и объекты

- **Бакет** — контейнер для объектов. Имя **уникально во всём хранилище** провайдера (не только в вашем аккаунте), строчные латинские буквы, цифры, дефисы.
- **Объект** — данные + **ключ** (имя) + метаданные (Content-Type, свои заголовки).
- Папок нет: ключ `backups/2026/11/db.dump` — просто строка с `/`. **Префиксы** имитируют каталоги в интерфейсах и используются в политиках и правилах.
- Адрес: `https://storage.yandexcloud.net/<бакет>/<ключ>` или `https://<бакет>.storage.yandexcloud.net/<ключ>`.
- Большие файлы загружают **multipart upload** — частями, параллельно, с докачкой.

## Инструменты

```bash
aws configure --profile yc
aws --profile yc --endpoint-url=https://storage.yandexcloud.net s3 mb s3://my-app-backups-7f3a
aws --profile yc --endpoint-url=https://storage.yandexcloud.net s3 cp db.dump s3://my-app-backups-7f3a/postgres/2026-11-27/db.dump
aws --profile yc --endpoint-url=https://storage.yandexcloud.net s3 ls s3://my-app-backups-7f3a/postgres/ --recursive --human-readable
aws --profile yc --endpoint-url=https://storage.yandexcloud.net s3 sync ./public s3://my-site-static --delete
aws --profile yc --endpoint-url=https://storage.yandexcloud.net s3 presign s3://my-app-backups-7f3a/report.pdf --expires-in 3600
```

- **aws cli** с `--endpoint-url` работает с любым S3-совместимым хранилищем (регион для Yandex — `ru-central1`).
- **s3cmd**, **rclone** (синхронизация и монтирование, десятки облаков), **mc** (клиент MinIO), SDK (boto3 для Python и др.).
- У Yandex также `yc storage` (бакеты и s3api-команды).

## Доступ

| Механизм | Что это |
| --- | --- |
| **IAM-роли** | Сервисному аккаунту выдают роль на каталог или бакет: `storage.viewer`, `storage.uploader`, `storage.editor`… |
| **Статические ключи** | Access key + secret key сервисного аккаунта для инструментов S3 (aws cli, приложения). Это секрет! |
| **Политика бакета** (bucket policy) | JSON-правила: кто, какие действия (`s3:GetObject`, `s3:PutObject`), на какие ключи/префиксы, с каких IP |
| **ACL** | Устаревший простой механизм прав на бакет/объект |
| **Presigned URL** | Временная ссылка на один объект с подписью и сроком действия — дать скачать или загрузить файл без ключей |
| **Публичный доступ** | Чтение объектов без авторизации — только для действительно публичной статики |

> [!warning] Публичные бакеты — частая причина утечек
> Бэкапы баз, логи и документы в бакете с публичным доступом находят сканерами. По умолчанию бакеты должны быть **закрытыми**; для раздачи файлов пользователям — presigned URL или CDN перед бакетом.

Для бэкапов полезна схема «только запись»: у сервера с базой ключ с правом **загружать**, но не удалять — взломщик не сможет стереть бэкапы. Ещё надёжнее — **блокировка версий объектов** (object lock): объект нельзя удалить или перезаписать до заданной даты.

## Версионирование, жизненный цикл, классы

- **Версионирование** — при перезаписи и удалении старые версии сохраняются; защищает от случайного удаления и шифровальщиков (но версии тоже занимают место и стоят денег).
- **Жизненный цикл (lifecycle)** — правила по префиксу и возрасту: перевести в холодный класс через 30 дней, удалить через 90, удалять незавершённые multipart-загрузки и старые версии.
- **Классы хранения**: стандартное (частый доступ), холодное (редкий доступ, дешевле хранение, дороже операции), ледяное/архивное (ещё дешевле, для долгого хранения).
- **Шифрование** на стороне сервера (ключами KMS) и клиента.
- Платят за: объём, класс хранения, **число запросов** и **исходящий трафик**.

## Где S3 встречается у DevOps

- **Бэкапы**: pg_dump, pgBackRest, WAL-G, snapshots Elasticsearch, Velero (бэкап Kubernetes).
- **Хранилище для систем**: Loki, Thanos/Mimir, Tempo — чанки и блоки в S3.
- **Terraform state** — backend `s3` (тема Terraform).
- **Артефакты CI**, кэш сборок, бинарники и пакеты.
- **Статические сайты** и фронтенд (+ CDN), загрузки пользователей.
- Хранилище образов для некоторых registry, датасеты для ML.

## S3 у себя

Для локальной разработки и on-premise используют S3-совместимые серверы. Долгое время стандартом был **MinIO**, но с 2025 года его бесплатная версия урезана: из веб-консоли убрали управление, перестали публиковать готовые бинарники и образы, а в декабре 2025 года репозиторий перевели в режим поддержки без новых функций. Для новых проектов рассматривают **Ceph RGW** (большие кластеры), **SeaweedFS**, **Garage** (лёгкий, для небольших инсталляций) и другие — проверяйте актуальный статус и лицензию.

## Лаборатория

Облака на стенде нет, но есть **S3-совместимое хранилище** (versitygw в контейнере `s3`): адрес **`http://localhost:7480`**, регион `us-east-1`, ключ доступа **`labkey`**, секретный ключ **`labsecret123`**. Клиент — **`s3cmd`** (работает и с AWS S3, и с любым совместимым хранилищем).

```bash lib
lab_drm() { docker rm -f "$@" >/dev/null 2>&1; true; }
# образ есть локально или скачивается (если ученик почистил образы через prune)
lab_img() { for i in "$@"; do docker image inspect "$i" >/dev/null 2>&1 || docker pull -q "$i" >/dev/null; done; }
# lab_wait_http URL [строка] — дождаться ответа
lab_wait_http() { for i in $(seq 60); do curl -s --max-time 1 "$1" 2>/dev/null | grep -q "${2:-.}" && return 0; sleep 0.25; done; return 1; }
# lab_s3 — S3-совместимое хранилище на 127.0.0.1:7480 (данные в /srv/s3)
lab_s3() {
  lab_img versity/versitygw:v1.0.10
  if [ "$(docker inspect -f '{{.State.Running}}' s3 2>/dev/null)" != true ]; then
    docker rm -f s3 >/dev/null 2>&1; mkdir -p /srv/s3
    docker run -d --name s3 --restart unless-stopped -p 127.0.0.1:7480:7480 -v /srv/s3:/data \
      -e ROOT_ACCESS_KEY=labkey -e ROOT_SECRET_KEY=labsecret123 versity/versitygw:v1.0.10 --port :7480 posix /data >/dev/null
  fi
  printf '[default]\naccess_key = labkey\nsecret_key = labsecret123\nhost_base = localhost:7480\nhost_bucket = localhost:7480\nuse_https = False\nbucket_location = us-east-1\n' > /var/lib/lab/s3cfg
  for i in $(seq 40); do s3cmd -c /var/lib/lab/s3cfg ls >/dev/null 2>&1 && return 0; sleep 0.25; done
}
lab_s3cmd() { s3cmd -c /var/lib/lab/s3cfg "$@" 2>/dev/null; }
lab_s3rb() { lab_s3cmd del -r --force "s3://$1" >/dev/null; lab_s3cmd rb "s3://$1" >/dev/null; true; }
```

```bash setup
lab_s3
```

### Бэкап в бакет

1. Настройте `s3cmd` для этого хранилища — конфиг клиента в **`~/.s3cfg`**.
2. Создайте бакет **`backups`**.
3. Загрузите архив `~/db-2026-11-28.tar.gz` в бакет по ключу **`postgres/daily/db-2026-11-28.tar.gz`**.

```bash setup
lab_s3rb backups
rm -f /home/student/.s3cfg
head -c 300000 /dev/urandom > /home/student/db-2026-11-28.tar.gz
chown student:student /home/student/db-2026-11-28.tar.gz
```

```bash check
[ -f /home/student/.s3cfg ] || fail "Нет ~/.s3cfg"
su - student -c 's3cmd ls' >/dev/null 2>&1 || fail "s3cmd с конфигом ~/.s3cfg не подключается к хранилищу: $(su - student -c 's3cmd ls' 2>&1 | tail -1 | cut -c1-120)"
lab_s3cmd ls | grep -q 's3://backups' || fail "Бакета backups нет"
o=$(lab_s3cmd ls s3://backups/postgres/daily/ | awk '{print $3, $4}')
echo "$o" | grep -q 's3://backups/postgres/daily/db-2026-11-28.tar.gz' || fail "В бакете нет объекта postgres/daily/db-2026-11-28.tar.gz (есть: $(lab_s3cmd ls -r s3://backups | awk '{print $4}' | tr '\n' ' '))"
[ "$(echo "$o" | awk '{print $1}')" = "$(stat -c %s /home/student/db-2026-11-28.tar.gz)" ] || fail "Размер объекта не совпадает с архивом"
ok "s3://backups/postgres/daily/db-2026-11-28.tar.gz"
```

```text hint
1. Конфиг s3cmd — INI-файл в домашнем каталоге: ключи доступа, адрес хранилища (для обращения к бакетам — тот же адрес), без HTTPS, регион. У s3cmd есть и интерактивная настройка.
2. Команды s3cmd похожи на привычные: «создать бакет», «положить», «показать».
3. «Каталоги» в S3 — просто часть ключа объекта с косыми чертами.
```

```bash solution
cat > ~/.s3cfg <<'EOF'
[default]
access_key = labkey
secret_key = labsecret123
host_base = localhost:7480
host_bucket = localhost:7480
use_https = False
bucket_location = us-east-1
EOF
chmod 600 ~/.s3cfg
s3cmd mb s3://backups
s3cmd put ~/db-2026-11-28.tar.gz s3://backups/postgres/daily/db-2026-11-28.tar.gz
s3cmd ls -r s3://backups
```

```text review
Эталон: `~/.s3cfg` → `s3cmd mb s3://backups` → `s3cmd put ... s3://backups/postgres/daily/...`.

- В S3 нет каталогов: есть бакет и объекты с ключами; `postgres/daily/` — просто префикс, по которому удобно листать и задавать правила.
- Ключи доступа — как пароль: в файле с правами 600, в CI — в защищённых переменных, на сервере в облаке — роль инстанса (IAM role), а не ключи.
- Для бэкапов: lifecycle-правила (через 30 дней — в дешёвый класс хранения, через год — удалить), версионирование и Object Lock (защита от удаления — спасение от шифровальщиков).
- AWS CLI делает то же: `aws s3 cp file s3://bucket/key --endpoint-url http://localhost:7480`; restic и rclone умеют S3 из коробки.
```

### Зеркало каталога сайта

Каталог `~/site` — статический сайт. Синхронизируйте его в бакет **`site`** так, чтобы бакет был **точной копией** каталога: при повторной синхронизации передаются только изменения, а файлы, удалённые локально, **удаляются и из бакета**. В каталоге уже удалён файл `old-promo.html`, который ещё лежит в бакете.

```bash setup
lab_s3rb site
lab_s3cmd mb s3://site >/dev/null
rm -rf /home/student/site && mkdir -p /home/student/site/css /home/student/site/img
echo '<h1>Главная</h1>' > /home/student/site/index.html
echo 'body{margin:0}' > /home/student/site/css/main.css
head -c 50000 /dev/urandom > /home/student/site/img/logo.png
echo '<h1>Старая акция</h1>' > /tmp/old-promo.html
lab_s3cmd put /tmp/old-promo.html s3://site/old-promo.html >/dev/null
lab_s3cmd put /home/student/site/index.html s3://site/index.html >/dev/null
chown -R student:student /home/student/site
lab_s3 >/dev/null
[ -f /home/student/.s3cfg ] || { cp /var/lib/lab/s3cfg /home/student/.s3cfg; chown student:student /home/student/.s3cfg; chmod 600 /home/student/.s3cfg; }
```

```bash check
want=$(cd /home/student/site && find . -type f | sed 's#^\./##' | sort)
got=$(lab_s3cmd ls -r s3://site | awk '{print $4}' | sed 's#^s3://site/##' | sort)
echo "$got" | grep -qx 'old-promo.html' && fail "В бакете остался old-promo.html, удалённый из каталога"
[ "$got" = "$want" ] || fail "Содержимое бакета не совпадает с ~/site: в бакете $(echo $got), в каталоге $(echo $want)"
lab_s3cmd get --force s3://site/img/logo.png /tmp/lab-logo.png >/dev/null
cmp -s /tmp/lab-logo.png /home/student/site/img/logo.png || fail "img/logo.png в бакете отличается от локального"
rm -f /tmp/lab-logo.png
ok "s3://site — зеркало ~/site ($(echo "$want" | wc -l) файлов)"
```

```text hint
1. У s3cmd есть команда синхронизации каталога с префиксом в бакете — она передаёт только новые и изменённые файлы.
2. По умолчанию синхронизация ничего не удаляет; есть ключ «удалять в назначении то, чего нет в источнике».
3. Сначала полезно запустить с ключом «пробный прогон».
```

```bash solution
s3cmd sync --dry-run --delete-removed ~/site/ s3://site/
s3cmd sync --delete-removed ~/site/ s3://site/
s3cmd ls -r s3://site
```

```text review
Эталон: `s3cmd sync --delete-removed ~/site/ s3://site/` (сначала с `--dry-run`).

- Как и в rsync, слеш в конце `~/site/` важен: синхронизируется содержимое, а не сам каталог.
- `--delete-removed` делает зеркало; ошибка в пути (`s3://site/` вместо `s3://site/assets/`) удалит лишнее — поэтому сначала `--dry-run`.
- Так деплоят статические сайты (фронтенд после `npm run build`) в S3 + CDN; в CI — `aws s3 sync dist/ s3://bucket --delete` и сброс кэша CDN.
```

## Тест

### Чем объектное хранилище отличается от блочного?
- [x] Объектное хранит объекты по ключу и отдаёт их по HTTP API, масштабируется практически без предела
- [x] Блочное — это диск, который монтируется к одной ВМ как устройство, подходит для баз данных и ОС
- [ ] Объектное хранилище монтируется как обычный диск по умолчанию
- [ ] Блочное хранилище доступно по HTTP всем
> Файловое хранилище (NFS) — третий вид: общая ФС по сети.

### Что такое бакет?
- [ ] Тип диска ВМ
- [x] Контейнер для объектов в объектном хранилище с уникальным именем
- [ ] Папка на сервере
- [ ] Резервная копия базы
> Имя бакета уникально во всём хранилище провайдера, а не только в вашем аккаунте.

### Есть ли в S3 настоящие папки?
- [ ] Да, как в файловой системе
- [x] Нет: ключ вроде backups/2026/db.dump — это просто строка, а префиксы только имитируют папки
- [ ] Только у Yandex
- [ ] Папки обязательны
> Префиксы используются в политиках и правилах жизненного цикла.

### Как работать aws cli с S3-совместимым хранилищем другого провайдера?
- [ ] Это невозможно
- [x] Указать endpoint провайдера через --endpoint-url и использовать статические ключи сервисного аккаунта
- [ ] Только через веб-консоль
- [ ] Нужно установить отдельную версию aws cli для каждого облака
> Для Yandex Object Storage endpoint — storage.yandexcloud.net.

### Как дать человеку скачать закрытый файл на час, не выдавая ключи и не делая бакет публичным?
- [ ] Сделать бакет публичным на час
- [x] Сгенерировать presigned URL с ограниченным сроком действия
- [ ] Отправить секретный ключ
- [ ] Скопировать файл на ВМ
> Подпись в ссылке действует только для одного объекта и только до истечения срока.

### Почему публичные бакеты опасны?
- [ ] Они медленные
- [x] Бэкапы, логи и документы в публичном бакете находят сканерами, и данные утекают
- [ ] Их нельзя удалить
- [ ] Они дороже закрытых
> По умолчанию бакеты должны быть закрытыми.

### Что даёт версионирование бакета?
- [ ] Ускоряет загрузку
- [x] При перезаписи и удалении сохраняются предыдущие версии объектов — можно восстановиться после ошибки
- [ ] Уменьшает стоимость хранения
- [ ] Шифрует данные
> Старые версии занимают место — их чистят правилами жизненного цикла.

### Для чего нужны правила жизненного цикла (lifecycle)?
- [ ] Для авторизации
- [x] Чтобы автоматически переводить объекты в более дешёвые классы хранения и удалять старые по возрасту и префиксу
- [ ] Для ускорения CDN
- [ ] Для создания бакетов
> Например, удалять бэкапы старше 90 дней.

### Как защитить бэкапы в S3 от удаления злоумышленником, взломавшим сервер базы?
- [x] Дать серверу ключ с правом только загружать объекты, без права удаления
- [x] Включить версионирование или блокировку версий объектов (object lock)
- [ ] Хранить секретный ключ с полными правами прямо в скрипте на сервере
- [ ] Сделать бакет публичным
> Бэкап, который можно стереть тем же доступом, — плохая защита от шифровальщиков.

### За что обычно платят в объектном хранилище?
- [x] За объём хранимых данных и класс хранения
- [x] За число запросов
- [x] За исходящий трафик
- [ ] За число папок
> Холодные классы дешевле в хранении, но дороже в операциях.

### Какие системы из стека DevOps используют S3 как хранилище?
- [x] Loki и Thanos для чанков логов и метрик
- [x] Terraform для хранения state
- [x] pgBackRest, WAL-G и Velero для бэкапов
