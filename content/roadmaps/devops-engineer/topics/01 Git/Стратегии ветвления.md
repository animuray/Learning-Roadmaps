# Стратегии ветвления

**Стратегия ветвления** — это договорённость команды: какие ветки живут всегда, как называть временные ветки, откуда их создавать и когда и как сливать. Без неё в репозитории быстро появляется хаос, а CI/CD не понимает, что и куда деплоить.

## Pull request и merge request

Почти все стратегии строятся вокруг **pull request** (GitHub, Bitbucket) или **merge request** (GitLab) — это одно и то же. Это предложение влить изменения из одной ветки в другую. Внутри — diff, обсуждение, ревью построчно и автоматические проверки CI. Ветку `main` обычно **защищают**: прямой push запрещён, влить можно только через одобренный PR или MR с зелёным пайплайном.

## GitFlow

Модель, которую в 2010 году описал Vincent Driessen. Она стала очень популярной.

**Постоянные ветки:**

- `main` (раньше `master`) — только то, что ушло в продакшен; каждый коммит здесь — релиз, помеченный тегом;
- `develop` — ветка интеграции, куда собираются готовые фичи для следующего релиза.

**Временные ветки:**

| Ветка | Создаётся от | Вливается в | Зачем |
| --- | --- | --- | --- |
| `feature/*` | `develop` | `develop` | Новая функциональность |
| `release/*` | `develop` | `main` и `develop` | Подготовка релиза: стабилизация, версия, мелкие исправления. Новые фичи сюда не идут |
| `hotfix/*` | `main` | `main` и `develop` | Срочное исправление продакшена |

**Минусы:** много долгоживущих веток, сложные слияния и «ритуалы» релиза. Сам автор позже добавил к статье примечание: модель стали воспринимать как догму, а для веб-приложений с непрерывной доставкой лучше подходит более простой процесс вроде GitHub Flow. GitFlow уместен там, где выпускают явные версии продукта и поддерживают несколько версий одновременно.

## GitHub Flow

Лёгкий процесс вокруг одной ветки:

1. `main` всегда в рабочем состоянии и готова к деплою.
2. На любую задачу создаётся ветка с понятным именем: `add-nginx-config`, `fix-timeout`.
3. Коммиты, push, открывается pull request.
4. Ревью, обсуждение, проверки CI.
5. Слияние в `main` → деплой.
6. Ветка удаляется.

Подходит большинству команд, которые часто деплоят веб-сервисы.

## GitLab Flow

GitHub Flow плюс правила о том, как изменения доезжают до окружений:

- **Ветки окружений:** изменения сначала вливаются в `main` (деплой на staging), затем через MR — в `pre-production`, потом в `production`. Код всегда течёт «вниз по течению».
- **Ветки релизов** (`2-3-stable`, `2-4-stable`) — если нужно поддерживать несколько версий. Исправление сначала делают в `main`, а затем переносят в стабильную ветку через `cherry-pick`.

## Trunk-Based Development

Все разработчики часто — минимум раз в день — интегрируют изменения в общую главную ветку (trunk, то есть `main`). Если ветки и используются, то **короткоживущие**: от нескольких часов до пары дней, с обязательным ревью и CI.

- Незаконченную функциональность прячут за **feature flags** — переключателями в конфиге, — а не держат в отдельной долгой ветке.
- Это необходимая практика для настоящей непрерывной интеграции. Исследования DORA связывают её с более высокой скоростью и стабильностью поставки.

## Как выбрать

| Ситуация | Стратегия |
| --- | --- |
| Веб-сервис, деплой несколько раз в день, небольшая команда | GitHub Flow или Trunk-Based |
| Нужны отдельные окружения staging и production с ручным продвижением | GitLab Flow с ветками окружений |
| Коробочный продукт, мобильное приложение, несколько поддерживаемых версий | GitFlow или GitLab Flow с ветками релизов |

## Именование веток

Частое соглашение — префикс по типу работы: `feature/login-page`, `fix/nginx-timeout`, `hotfix/1.2.1`, `release/1.3.0`. Иногда добавляют номер задачи: `feature/DEVOPS-142-add-monitoring`. CI-системы умеют запускать разные пайплайны в зависимости от имени ветки — подробнее в разделе CI-CD.

## Практика

- [ ] Включить защиту ветки main в своём репозитории на GitHub или GitLab: запретить прямой push
- [ ] Выполнить небольшое изменение по GitHub Flow: ветка → коммиты → pull request → самопроверка diff → merge → удаление ветки
- [ ] Нарисовать (на бумаге или в draw.io) схему GitFlow с ветками main, develop, feature, release и hotfix
- [ ] Узнать, какая стратегия принята в открытом проекте, которым вы пользуетесь (README или CONTRIBUTING.md)

## Тест

### Что такое стратегия ветвления?
- [ ] Алгоритм, по которому Git хранит ветки на диске
- [x] Договорённость команды о том, какие ветки постоянные, как называть временные и когда и как их сливать
- [ ] Команда git branch с особыми флагами
- [ ] Настройка доступа к репозиторию
> Это правила процесса, а не возможность Git. Поэтому их бывает много разных.

### Какие две ветки живут постоянно в GitFlow?
- [ ] main и feature
- [x] main (master) и develop
- [ ] develop и release
- [ ] main и hotfix
> main — то, что в продакшене, develop — интеграция следующего релиза.

### От какой ветки в GitFlow создаётся hotfix и куда он вливается?
- [ ] От develop, вливается в develop
- [x] От main, вливается в main и develop
- [ ] От release, вливается в main
- [ ] От feature, вливается в main
> В develop hotfix вливают, чтобы исправление не потерялось в следующем релизе.

### От какой ветки в GitFlow создаются feature-ветки?
- [ ] От main
- [x] От develop, и в develop же вливаются
- [ ] От release
- [ ] От hotfix
> В main фичи попадают только через release.

### Какое главное правило GitHub Flow?
- [ ] Каждая фича живёт в отдельной ветке не меньше месяца
- [x] Ветка main всегда готова к деплою; любая работа идёт через короткую ветку и pull request
- [ ] Коммитить можно только в develop
- [ ] Релизы делаются раз в квартал
> Слили PR в main — можно деплоить.

### Что характерно для Trunk-Based Development?
- [ ] Каждый разработчик работает в своей ветке неделями
- [x] Все часто интегрируют изменения в общую главную ветку; если ветки и есть, то живут часы или пару дней
- [ ] Ветки main не существует
- [ ] Слияния делаются раз в релиз
> Короткие ветки — меньше расхождений и конфликтов, быстрее обратная связь от CI.

### Как в Trunk-Based Development поступают с незаконченной функциональностью?
- [ ] Держат её в долгоживущей ветке до готовности
- [x] Сливают в main, но прячут за feature flag, пока она не готова
- [ ] Не коммитят, пока не закончат
- [ ] Удаляют и пишут заново
> Флаги отделяют «код в main» от «функция включена для пользователей».

### Что такое pull request или merge request?
- [ ] Команда git pull, выполненная на сервере
- [x] Запрос на слияние изменений из одной ветки в другую с обсуждением, ревью и проверками CI
- [ ] Запрос на доступ к репозиторию
- [ ] Автоматическое слияние без проверки
> PR в GitHub и MR в GitLab — одно и то же понятие.

### Что GitLab Flow добавляет к GitHub Flow?
- [ ] Ветку develop
- [x] Ветки окружений (staging, pre-production, production) или ветки релизов для поддержки нескольких версий
- [ ] Запрет на pull request
- [ ] Обязательный rebase
> Код течёт из main в ветки окружений через merge request.

### Почему классический GitFlow плохо подходит для непрерывной доставки?
- [ ] Он не поддерживает теги
- [x] В нём много долгоживущих веток и церемоний релиза: изменения долго не попадают в main, а слияния становятся сложными
- [ ] Он работает только на GitHub
- [ ] Он запрещает code review
> Об этом пишет и сам автор модели в примечании к оригинальной статье.

### Что верно для короткоживущих веток?
- [x] Снижают количество и сложность конфликтов
- [x] Ускоряют интеграцию и обратную связь от CI
- [ ] Должны жить несколько недель
- [ ] Заменяют code review
> Чем дольше живёт ветка, тем сильнее она расходится с main.

### Зачем в GitFlow ветка release/1.4?
- [ ] Для разработки новых фич версии 1.4
- [x] Для подготовки релиза: стабилизация, правка версии и мелкие исправления; новые фичи в неё не добавляют
- [ ] Для хранения копии продакшена
- [ ] Для экспериментов
> Пока идёт стабилизация release, команда продолжает добавлять новые фичи в develop.

### Команда из трёх человек деплоит веб-сервис несколько раз в день. Какая стратегия подойдёт лучше?
- [ ] GitFlow с release-ветками
- [x] GitHub Flow или Trunk-Based Development
- [ ] Отдельная долгоживущая ветка на каждого разработчика
- [ ] Работа без веток и без ревью
> Простые процессы с короткими ветками хорошо сочетаются с частыми деплоями.
