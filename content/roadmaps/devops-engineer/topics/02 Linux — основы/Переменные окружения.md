# Переменные окружения

**Переменная окружения** — пара «имя=значение», которую процесс получает от родителя при запуске. Так программам передают настройки: где искать команды, какой язык использовать, адрес базы, режим работы. Docker, Kubernetes и CI/CD передают конфигурацию приложениям тоже через переменные окружения — так делают по методологии 12-factor app.

## Переменные оболочки и окружения

```bash
NAME=world          # переменная ОБОЛОЧКИ — видна только в текущем bash
echo "Hello $NAME"
export NAME         # теперь это переменная ОКРУЖЕНИЯ — её унаследуют дочерние процессы
export APP_ENV=prod # создать и экспортировать сразу
unset NAME          # удалить
```

- Вокруг `=` **не должно быть пробелов**: `NAME = world` bash поймёт как запуск команды `NAME`.
- Переменная только для одной команды: `APP_ENV=test ./run.sh`.
- Дочерний процесс получает **копию** окружения. Изменить переменные родителя он не может. Поэтому `./set-vars.sh` не поменяет переменные вашей оболочки, а `source set-vars.sh` — поменяет.

```bash
env                 # все переменные окружения
printenv PATH       # одна переменная
set | less          # всё, включая переменные оболочки и функции
```

## Важные переменные

| Переменная | Значение |
| --- | --- |
| `PATH` | Каталоги, где оболочка ищет команды |
| `HOME` | Домашний каталог |
| `USER` | Имя пользователя |
| `SHELL` | Оболочка входа |
| `PWD` | Текущий каталог |
| `LANG`, `LC_*` | Язык и локаль |
| `EDITOR` | Редактор по умолчанию (git, crontab, visudo) |

## PATH

Когда вы пишете `python3`, оболочка ищет исполняемый файл с таким именем по очереди в каталогах из `PATH` (через двоеточие) и запускает первый найденный.

```bash
echo $PATH
# /usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
which python3
export PATH="$HOME/.local/bin:$PATH"   # добавить свой каталог в начало
```

- «command not found» для установленной программы обычно значит, что её каталога нет в PATH.
- Текущего каталога в PATH нет специально (из соображений безопасности), поэтому свой скрипт запускают как `./script.sh`.
- Перезаписывать PATH без `$PATH` нельзя: `export PATH=/opt/bin` «сломает» все команды в этой оболочке.

## Где задавать переменные надолго

Bash при запуске читает файлы, и какие именно — зависит от типа оболочки:

| Тип оболочки | Когда | Что читает |
| --- | --- | --- |
| Login | Вход по SSH, вход в консоль, `su -`, `bash -l` | `/etc/profile`, затем **первый найденный** из `~/.bash_profile`, `~/.bash_login`, `~/.profile` |
| Интерактивная non-login | Новое окно терминала на десктопе, просто `bash` | `/etc/bash.bashrc` (в Debian/Ubuntu), `~/.bashrc` |
| Неинтерактивная (скрипт) | `bash script.sh`, cron, службы | Обычно ничего из этого |

Практическое правило:

- переменные окружения (PATH и т. п.) — в `~/.profile` или `~/.bash_profile`;
- алиасы, приглашение, функции для работы в терминале — в `~/.bashrc`;
- в Ubuntu `~/.profile` сам подключает `~/.bashrc`, поэтому многие пишут всё в `.bashrc`.

Применить изменения без перелогина: `source ~/.bashrc` (или `. ~/.bashrc`).

Системно для всех пользователей: `/etc/environment` (простые `KEY=value` без команд) или скрипты в `/etc/profile.d/*.sh`.

## Почему служба «не видит» переменную

Служба systemd, задача cron или процесс через `sudo` **не читают** ваш `~/.bashrc`:

- в systemd переменные задают в unit-файле: `Environment=APP_ENV=prod` или `EnvironmentFile=/etc/app/env`;
- в cron — прямо в crontab или внутри скрипта;
- `sudo` по умолчанию очищает окружение и подставляет свой безопасный PATH (`secure_path`). Сохранить переменные: `sudo -E` (если разрешено политикой).

## Секреты в переменных

Переменные окружения процесса можно прочитать в `/proc/PID/environ` (своих процессов или под root), они попадают в дампы и иногда в логи. Это лучше, чем пароль в коде, но для серьёзных секретов используют хранилища (Vault, Kubernetes Secrets) — об этом в конце роадмапа.

## Лаборатория

### Свои команды в PATH

Создайте каталог `~/bin` и скрипт `~/bin/hello`, который печатает `Привет, <имя пользователя>!` (имя — из переменной окружения). Скрипт должен запускаться **просто по имени** `hello` из любого каталога в новом сеансе.

```bash setup
rm -rf /home/student/bin
```

```bash check
f=/home/student/bin/hello
[ -f $f ] || fail "Нет файла ~/bin/hello"
[ -x $f ] || fail "~/bin/hello нельзя запустить: у файла нет права на выполнение"
head -1 $f | grep -q '^#!' || fail "В первой строке скрипта не указан интерпретатор"
p=$(su - student -c 'command -v hello' 2>/dev/null)
[ "$p" = /home/student/bin/hello ] || fail "В новом сеансе оболочка не находит команду hello по имени"
out=$(su - student -c 'cd /tmp && hello' 2>&1)
[ "$out" = "Привет, student!" ] || fail "hello печатает «$out», а нужно «Привет, student!»"
grep -q 'student' $f && fail "Имя пользователя вписано в скрипт: у другого пользователя он напечатает «student»"
ok "$out"
```

```text hint
1. Создать каталог и файл скрипта: первая строка — указание интерпретатора, дальше — вывод приветствия с переменной, в которой хранится имя пользователя.
2. Сделать файл исполняемым.
3. Чтобы команда находилась по имени, каталог должен быть в PATH. Посмотрите в ~/.profile — возможно, в Ubuntu об этом уже позаботились, и достаточно открыть новый сеанс.
```

```bash solution
mkdir -p ~/bin
printf '#!/bin/bash\necho "Привет, $USER!"\n' > ~/bin/hello
chmod +x ~/bin/hello
```

```text review
Эталон: `mkdir -p ~/bin`, скрипт с `#!/bin/bash` и `echo "Привет, $USER!"`, `chmod +x`.

- В Ubuntu `~/.profile` уже содержит `if [ -d "$HOME/bin" ] ; then PATH="$HOME/bin:$PATH"`: каталог попадает в PATH при следующем входе. В текущем сеансе — `source ~/.profile` или `export PATH="$HOME/bin:$PATH"`.
- Добавлять каталог в **начало** PATH — значит ваши команды перекроют системные с тем же именем. Удобно, но опасно: свой `ls` в `~/bin` сломает чужие скрипты.
- Без shebang скрипт запустится текущей оболочкой — в cron или systemd это может быть `sh`, где не работают bash-конструкции.
- Права: `chmod +x` (или `chmod 755`). `chmod 777` здесь лишний — запись остальным не нужна.
```

```text notes
chmod\s+0?777 => 777 даёт право изменять ваш скрипт всем пользователям системы — а его запускают из PATH. Хватит chmod +x.
echo\s+[^\n]*Привет,\s*student => Имя пользователя вписано в скрипт. Скрипт должен работать у любого пользователя — берите имя из $USER.
```

### Переменная для всех сеансов

Сделайте так, чтобы в **каждом новом сеансе** пользователя `student` была доступна переменная окружения `APP_ENV` со значением `staging` — и чтобы её видели запущенные из оболочки программы.

```bash setup
sed -i '/APP_ENV/d' /home/student/.profile /home/student/.bashrc /home/student/.bash_profile 2>/dev/null; true
rm -f /etc/profile.d/app-env.sh
```

```bash check
v=$(su - student -c 'bash -c "echo \$APP_ENV"' 2>/dev/null)
[ "$v" = staging ] || fail "В новом сеансе дочерний процесс видит APP_ENV=«$v»"
vi=$(su - student -c 'bash -ic "echo \$APP_ENV"' 2>/dev/null | tail -1)
[ "$vi" = staging ] || fail "В интерактивной оболочке APP_ENV=«$vi»"
ok "APP_ENV=$v"
```

```text hint
1. Переменная должна быть экспортирована, иначе её не увидят дочерние процессы.
2. Чтобы она появлялась при каждом входе, строку нужно дописать в файл настроек оболочки пользователя, который читается при входе в систему.
3. Проверьте в новом сеансе: запустите дочернюю оболочку и выведите переменную.
```

```bash solution
echo 'export APP_ENV=staging' >> ~/.profile
```

```text review
Эталон: `echo 'export APP_ENV=staging' >> ~/.profile`.

- `export` делает переменную частью окружения: её наследуют дочерние процессы. `APP_ENV=staging` без export видна только самой оболочке.
- Куда писать: `~/.profile` читают login-оболочки (вход по SSH, `su -`), `~/.bashrc` — интерактивные. В Ubuntu `.profile` сам подключает `.bashrc`, поэтому переменные окружения кладут в `.profile`, а алиасы и приглашение — в `.bashrc`.
- Для всех пользователей — файл в `/etc/profile.d/` или `/etc/environment` (там без `export`, просто `KEY=value`).
- Службы systemd эти файлы **не читают** — для них `Environment=` в unit-файле. Об этом — в теме [[systemd и unit-файлы]].
```

```text notes
^\s*APP_ENV=staging\s*$ => Переменная задана без export — дочерние процессы её не увидят. Добавьте export.
>\s*~?/?(home/student/)?\.(profile|bashrc)\b(?!.*>>) => Похоже, файл настроек перезаписан через одиночный «>»: всё, что в нём было, удалено. Для добавления строки нужен «>>».
```

### Секрет из окружения процесса

От root запущен процесс `sleep`, которому при старте передали переменную окружения `LAB_TOKEN`. Найдите значение токена и запишите его (только значение) в `~/token.txt`.

```bash setup
pkill -f 'sleep 7777' 2>/dev/null; true
token="tok-$(head -c 6 /dev/urandom | od -An -tx1 | tr -d ' \n')"
echo "$token" > /var/lib/lab/token
LAB_TOKEN="$token" setsid nohup sleep 7777 >/dev/null 2>&1 < /dev/null &
rm -f /home/student/token.txt
```

```bash check
[ -f /home/student/token.txt ] || fail "Нет ~/token.txt"
want=$(cat /var/lib/lab/token)
got=$(tr -d '[:space:]' < /home/student/token.txt)
[ "$got" = "$want" ] || fail "В ~/token.txt «$got» — не то значение"
ok "токен найден: $want"
```

```text hint
1. Узнать PID процесса sleep, запущенного от root.
2. Окружение любого процесса лежит в специальном файле внутри /proc/<PID>/. Переменные там разделены нулевым байтом — замените его переводом строки.
3. Файл чужого процесса читается только с правами администратора. Найдите нужную строку и оставьте только значение после «=».
```

```bash solution
pid=$(pgrep -f 'sleep 7777' | head -1)
sudo cat /proc/$pid/environ | tr '\0' '\n' | grep '^LAB_TOKEN=' | cut -d= -f2 > ~/token.txt
```

```text review
Эталон: `sudo cat /proc/$(pgrep -f 'sleep 7777')/environ | tr '\0' '\n' | grep LAB_TOKEN | cut -d= -f2`.

- `/proc/<PID>/environ` — окружение процесса **на момент запуска**. Если процесс потом сам поменял переменную, здесь этого видно не будет.
- Вывод: секреты в переменных окружения видны root и самому пользователю процесса, попадают в `docker inspect`, дампы и логи падений. Это приемлемо, но не секретно «по-настоящему» — поэтому их держат в Vault или Kubernetes Secrets и монтируют файлами.
- Именно так отлаживают «служба не видит переменную»: смотрят environ работающего процесса, а не своё окружение.
- `ps eww -p PID` показывает то же одной строкой.
```

### Алиас

Добавьте пользователю `student` постоянный алиас `ll` для `ls -lah`, работающий в каждой новой интерактивной оболочке.

```bash setup
sed -i "/alias ll=/d" /home/student/.bashrc /home/student/.bash_aliases 2>/dev/null; true
```

```bash check
a=$(su - student -c 'bash -ic "alias ll"' 2>/dev/null | tail -1)
echo "$a" | grep -q "ls -lah" || fail "В новой интерактивной оболочке alias ll — «$a»"
ok "$a"
```

```text hint
Алиасы относятся к интерактивной оболочке — допишите определение алиаса в файл её настроек в домашнем каталоге. Чтобы применить в текущем сеансе, перечитайте этот файл.
```

```bash solution
echo "alias ll='ls -lah'" >> ~/.bashrc
```

```text review
Эталон: `echo "alias ll='ls -lah'" >> ~/.bashrc`, затем `source ~/.bashrc`.

- Алиасы живут только в интерактивной оболочке: в скриптах они не работают (и не должны). Для скриптов пишут функции или отдельные файлы в `~/bin`.
- В Ubuntu `.bashrc` подключает `~/.bash_aliases`, если он есть: алиасы удобно держать там отдельно.
- Кстати, в Ubuntu `ll` уже определён как `ls -alF` — свой алиас его переопределил.
```

## Тест

### Что делает export VAR?
- [ ] Сохраняет переменную в файл
- [x] Делает переменную частью окружения, чтобы её унаследовали дочерние процессы
- [ ] Удаляет переменную
- [ ] Выводит значение переменной
> Без export переменная видна только в текущей оболочке.

### Почему команда NAME = value не создаёт переменную?
- [ ] Имя переменной должно быть в нижнем регистре
- [x] Вокруг = не должно быть пробелов; иначе bash пытается запустить команду NAME
- [ ] Нужно писать set NAME value
- [ ] Значение должно быть в кавычках
> Правильно: `NAME=value`.

### Как выполнить ./run.sh с переменной APP_ENV=test, не меняя окружение текущей оболочки?
= APP_ENV=test ./run.sh
> Переменная, указанная перед командой, действует только на эту команду.

### Для чего нужна переменная PATH?
- [ ] В ней хранится домашний каталог
- [x] В ней перечислены каталоги, где оболочка ищет исполняемые файлы команд
- [ ] Это путь к текущему каталогу
- [ ] Это путь к логам
> Каталоги перебираются по порядку, запускается первый найденный файл.

### Как правильно добавить каталог ~/.local/bin в PATH?
- [ ] export PATH=~/.local/bin
- [x] export PATH="$HOME/.local/bin:$PATH"
- [ ] PATH+=~/.local/bin
- [ ] set PATH ~/.local/bin
> Без `$PATH` в значении вы потеряете все стандартные каталоги, и перестанут находиться даже `ls` и `cat`.

### Почему свой скрипт из текущего каталога запускают как ./script.sh, а не просто script.sh?
- [ ] Так быстрее
- [x] Текущего каталога нет в PATH (из соображений безопасности), поэтому путь нужно указать явно
- [ ] Без ./ скрипт запустится от root
- [ ] script.sh — зарезервированное имя
> Если бы `.` был в PATH, злоумышленник мог бы подложить в каталог файл `ls` и дождаться, пока его запустят.

### Какой файл читает интерактивная non-login оболочка bash, например новое окно терминала?
- [ ] ~/.profile
- [x] ~/.bashrc
- [ ] /etc/environment
- [ ] ~/.bash_logout
> Login-оболочка (вход по SSH) читает `/etc/profile` и `~/.bash_profile` или `~/.profile`.

### Как применить изменения в ~/.bashrc в текущей оболочке без перелогина?
- [x] source ~/.bashrc
- [x] . ~/.bashrc
- [ ] bash ~/.bashrc
- [ ] export ~/.bashrc
> `bash ~/.bashrc` выполнит файл в дочерней оболочке, и изменения пропадут вместе с ней.

### Почему ./set-vars.sh не меняет переменные вашей оболочки, а source set-vars.sh — меняет?
- [ ] source запускает скрипт от root
- [x] ./set-vars.sh выполняется в дочернем процессе, который не может изменить окружение родителя; source выполняет команды в текущей оболочке
- [ ] ./ игнорирует export
- [ ] Это одно и то же
> Окружение наследуется только «вниз» — от родителя к потомку.

### Приложение, запущенное как служба systemd, не видит переменную из ~/.bashrc. Почему и как исправить?
- [ ] Нужно перезагрузить сервер
- [x] systemd не читает .bashrc; переменные задают в unit-файле через Environment= или EnvironmentFile=
- [ ] Переменные окружения не работают со службами
- [ ] Нужно выполнить source ~/.bashrc от root
> Так же поступают cron и другие неинтерактивные запуски.

### Какие команды покажут переменные окружения?
- [x] env
- [x] printenv
- [ ] export -d
- [ ] ls $ENV
> `set` покажет ещё и переменные оболочки и функции.

### Какая переменная задаёт редактор, который откроют git commit и crontab -e?
= EDITOR
> Некоторые программы смотрят ещё на `VISUAL`.

### Где хранятся переменные окружения уже запущенного процесса с PID 1234?
- [ ] /etc/environment
- [x] /proc/1234/environ
- [ ] /var/run/1234.env
- [ ] ~/.bashrc
> Значения разделены нулевыми байтами; удобно читать через `tr '\0' '\n'`.
