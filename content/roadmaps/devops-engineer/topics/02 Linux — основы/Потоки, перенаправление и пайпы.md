# Потоки, перенаправление и пайпы

У каждого процесса есть три стандартных потока — **файловых дескриптора**:

| Номер | Имя | По умолчанию |
| --- | --- | --- |
| 0 | **stdin** — стандартный ввод | Клавиатура |
| 1 | **stdout** — стандартный вывод | Экран |
| 2 | **stderr** — поток ошибок | Экран |

Ошибки идут отдельным потоком, поэтому их можно отделить от полезного вывода. Без этого невозможно писать скрипты, однострочники и разбирать логи.

## Перенаправление вывода

```bash
ls -l > files.txt          # stdout в файл (файл перезаписывается!)
echo "line" >> log.txt     # дописать в конец файла
find / -name x 2> errors.txt   # stderr в файл
find / -name x 2>/dev/null     # выбросить ошибки
command > out.log 2>&1     # и stdout, и stderr в один файл
command &> out.log         # то же короче (только bash)
command > /dev/null 2>&1   # полностью «тихий» запуск, например в cron
```

`/dev/null` — «чёрная дыра»: всё, что туда записано, исчезает.

### Порядок важен

Перенаправления обрабатываются **слева направо**. `2>&1` значит «направь stderr туда же, куда **сейчас** указывает stdout».

```bash
cmd > file 2>&1   # stdout → file, затем stderr → туда же (file). Оба в файле
cmd 2>&1 > file   # stderr → экран (куда тогда указывал stdout), stdout → file
```

## Ввод из файла

```bash
wc -l < access.log        # stdin из файла
mysql db < dump.sql
```

**Here-document** — многострочный ввод прямо в скрипте, удобно для создания конфигов:

```bash
cat > /etc/app.conf <<EOF
port=8080
host=$HOSTNAME
EOF
```

С `<<'EOF'` (кавычки вокруг метки) переменные внутри **не** подставляются.

**Here-string:** `grep error <<< "$OUTPUT"`.

## Пайпы

`|` передаёт stdout одной команды на stdin следующей. Так из маленьких утилит собирают мощные цепочки:

```bash
ps aux | grep nginx
cat access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head
journalctl -u app | grep -i error | tail -20
```

- Через пайп идёт **только stdout**. Чтобы пустить и ошибки: `cmd 2>&1 | grep x` или в bash — `cmd |& grep x`.
- `tee` — «тройник»: пишет и в файл, и дальше на экран или в пайп:
  ```bash
  ./build.sh 2>&1 | tee build.log
  echo "127.0.0.1 app.local" | sudo tee -a /etc/hosts
  ```
  Почему не `sudo echo ... >> /etc/hosts`? Перенаправление выполняет **ваша** оболочка без root, и вы получите Permission denied. `sudo tee` открывает файл уже с правами root.

## Код возврата и цепочки команд

Каждая команда завершается с **кодом возврата**: `0` — успех, всё остальное — ошибка. Код последней команды хранится в `$?`.

```bash
ls /nope; echo $?          # 2
mkdir app && cd app        # cd выполнится, только если mkdir успешен
ping -c1 host || echo "недоступен"   # выполнить, если первая команда упала
cmd1; cmd2                 # просто по очереди, независимо от результата
```

У пайплайна код возврата по умолчанию берётся у **последней** команды. В скриптах включают `set -o pipefail`, чтобы ошибка в середине цепочки не терялась.

## Подстановка команды

```bash
echo "Сегодня $(date +%F)"
tar czf backup-$(date +%F).tar.gz /etc
kill $(pgrep -f old-app)
```

## Тест

### Какой номер файлового дескриптора у stderr?
= 2
> 0 — stdin, 1 — stdout, 2 — stderr.

### Чем > отличается от >>?
- [ ] `>` дописывает в конец, `>>` перезаписывает
- [x] `>` перезаписывает файл, `>>` дописывает в конец
- [ ] `>>` перенаправляет ошибки
- [ ] Ничем
> Одна лишняя стрелка или её отсутствие может стереть важный лог.

### Как отправить и stdout, и stderr команды в файл out.log?
- [x] cmd > out.log 2>&1
- [x] cmd &> out.log
- [ ] cmd 2>&1 > out.log
- [ ] cmd | out.log
> В третьем варианте stderr уйдёт на экран: перенаправления обрабатываются слева направо.

### Что делает 2>/dev/null?
- [ ] Удаляет файл с ошибками
- [x] Выбрасывает сообщения об ошибках, не показывая их
- [ ] Перенаправляет вывод на второй терминал
- [ ] Отключает команду при ошибке
> Удобно для `find /`, где много «Permission denied».

### Что передаёт пайп | следующей команде?
- [ ] stdout и stderr
- [x] Только stdout
- [ ] Только stderr
- [ ] Код возврата
> Чтобы через пайп пошли и ошибки, добавьте `2>&1` или используйте `|&`.

### Почему sudo echo "x" >> /etc/hosts выдаёт Permission denied?
- [ ] echo нельзя запускать через sudo
- [x] Перенаправление выполняет текущая оболочка без прав root; sudo получает только echo
- [ ] Файл /etc/hosts защищён от записи даже для root
- [ ] Нужно использовать >, а не >>
> Правильно: `echo "x" | sudo tee -a /etc/hosts`.

### Что делает команда tee?
- [ ] Сортирует строки
- [x] Пишет входные данные одновременно в файл и на stdout
- [ ] Удаляет дубликаты
- [ ] Создаёт пайп между двумя терминалами
> Название — от T-образного соединения труб.

### Какой код возврата означает успешное завершение команды?
= 0
> Любое ненулевое значение — ошибка; конкретное число зависит от программы.

### В какой переменной хранится код возврата последней команды?
= $?
> Сразу после проверки значение перезапишется кодом самой проверки.

### Когда выполнится вторая команда в mkdir app && cd app?
- [ ] Всегда
- [x] Только если mkdir завершился успешно
- [ ] Только если mkdir завершился с ошибкой
- [ ] Параллельно с первой
> `||` — наоборот, при ошибке первой команды.

### Как сохранить в имя архива текущую дату через подстановку команды?
- [ ] tar czf backup-{date}.tar.gz /etc
- [x] tar czf backup-$(date +%F).tar.gz /etc
- [ ] tar czf backup-date.tar.gz /etc | date
- [ ] tar czf backup-${date}.tar.gz /etc
> `$(...)` подставляет вывод команды. `${date}` — это переменная date, а не команда.

### Чем cat <<'EOF' отличается от cat <<EOF в here-document?
- [ ] Ничем
- [x] С кавычками переменные и подстановки внутри не раскрываются, текст вставляется как есть
- [ ] С кавычками текст пишется в файл EOF
- [ ] Без кавычек here-document не работает
> Удобно, когда в шаблоне нужен буквальный `$` — например, для конфигов nginx.

### Зачем в скриптах включают set -o pipefail?
- [ ] Чтобы пайпы работали быстрее
- [x] Чтобы пайплайн возвращал ошибку, если упала любая команда в цепочке, а не только последняя
- [ ] Чтобы запретить пайпы
- [ ] Чтобы ошибки шли в stdout
> Без pipefail `false | true` считается успешным.
