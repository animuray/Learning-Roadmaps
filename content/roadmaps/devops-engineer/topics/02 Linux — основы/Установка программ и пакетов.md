# Установка программ и пакетов

В Linux программы обычно не скачивают с сайтов вручную, а ставят **из репозиториев** через менеджер пакетов. Он сам скачает нужные **зависимости** (библиотеки), проверит подписи, разложит файлы по местам и потом обновит всё одной командой.

## Пакеты и репозитории

- **Пакет** — архив с программой, метаданными (версия, зависимости) и скриптами установки: `.deb` в семействе Debian, `.rpm` в семействе Red Hat.
- **Репозиторий** — сервер с пакетами и подписанным индексом.
- Низкоуровневые утилиты (`dpkg`, `rpm`) ставят один файл пакета и не умеют скачивать зависимости. Высокоуровневые (`apt`, `dnf`) работают с репозиториями и сами разрешают зависимости.

## apt (Debian, Ubuntu)

```bash
sudo apt update                 # обновить списки пакетов из репозиториев (ничего не ставит!)
sudo apt install nginx git      # установить
sudo apt install -y htop        # без вопроса «Продолжить?» — для скриптов
sudo apt upgrade                # обновить установленные пакеты
sudo apt full-upgrade           # обновить, разрешая удаление и замену пакетов
sudo apt remove nginx           # удалить, оставив конфиги
sudo apt purge nginx            # удалить вместе с конфигами
sudo apt autoremove             # удалить ненужные больше зависимости
apt search postgres             # поиск
apt show nginx                  # описание, версия, зависимости
apt list --installed
dpkg -l | grep nginx            # установлен ли пакет
dpkg -L nginx                   # какие файлы поставил пакет
dpkg -S /usr/sbin/nginx         # какому пакету принадлежит файл
sudo dpkg -i package.deb        # поставить скачанный .deb (зависимости потом: apt -f install)
```

Репозитории описаны в `/etc/apt/sources.list` и `/etc/apt/sources.list.d/`. Сторонние репозитории (Docker, PostgreSQL, Grafana) добавляют вместе с их **GPG-ключом**: APT проверяет подпись и не поставит подменённый пакет.

## dnf (Fedora, RHEL, Rocky, AlmaLinux)

```bash
sudo dnf install nginx
sudo dnf upgrade                # обновить всё (dnf update — то же самое)
sudo dnf remove nginx
dnf search postgres
dnf info nginx
dnf provides /usr/sbin/nginx    # какой пакет даёт файл
rpm -qa | grep nginx            # установленные пакеты
rpm -ql nginx                   # файлы пакета
```

Репозитории — файлы `.repo` в `/etc/yum.repos.d/`. Важный дополнительный репозиторий для RHEL-совместимых систем — **EPEL**.

## Другие способы установки

- **snap** и **flatpak** — пакеты со всеми зависимостями внутри, изолированные от системы. Удобны на десктопе.
- **Бинарник** с сайта или GitHub Releases — положить в `/usr/local/bin` и выставить права `755`.
- **Сборка из исходников** — `./configure && make && sudo make install`. На серверах так делают редко: такие программы не обновляются менеджером пакетов.

## Менеджеры пакетов языков

Приложения ставят свои библиотеки не через apt, а через менеджер пакетов своего языка. Это пригодится в главной практике по Linux, когда вы будете запускать приложение без Docker.

### Python: pip и venv

```bash
sudo apt install python3-venv python3-pip
python3 -m venv .venv           # создать виртуальное окружение в каталоге проекта
source .venv/bin/activate       # активировать (в приглашении появится (.venv))
pip install -r requirements.txt # поставить зависимости проекта
pip install flask==3.0.3        # конкретная версия
pip freeze > requirements.txt   # зафиксировать версии
deactivate
```

- **venv** изолирует библиотеки проекта: у двух приложений могут быть разные версии одной библиотеки, и они не мешают друг другу и системному Python.
- В современных Debian и Ubuntu `pip install` в системный Python запрещён ошибкой `externally-managed-environment`. Это защита системных пакетов — используйте venv.
- Каталог `.venv` не коммитят в Git.

### Node.js: npm

```bash
npm install          # поставить зависимости из package.json в node_modules/
npm ci               # чистая установка строго по package-lock.json — для CI и серверов
npm run build        # выполнить скрипт из раздела scripts в package.json
npm start
```

`package.json` описывает зависимости, `package-lock.json` фиксирует точные версии. Каталог `node_modules` не коммитят.

### Java: Maven

```bash
sudo apt install openjdk-21-jdk maven
mvn package          # скомпилировать, прогнать тесты и собрать target/app-1.0.jar
mvn clean package -DskipTests
java -jar target/app-1.0.jar
```

Проект описывается в `pom.xml`. Зависимости скачиваются в локальный кэш `~/.m2/repository`.

> [!tip] Версии языков
> Если нужна версия Python или Node.js, которой нет в репозитории дистрибутива, используют менеджеры версий: `pyenv`, `nvm` — или официальные репозитории проекта.

## Лаборатория

Пакеты ставятся из интернета — задачи с установкой могут занять полминуты.

### Поставить пакет и найти его файлы

Установите утилиту `ncdu` (анализ занятого места на диске) из репозитория Ubuntu. Затем узнайте **через менеджер пакетов**, куда установлен её исполняемый файл, и запишите этот путь в `~/ncdu-path.txt`.

```bash setup
DEBIAN_FRONTEND=noninteractive apt-get purge -y -q ncdu >/dev/null 2>&1; true
rm -f /home/student/ncdu-path.txt
```

```bash check
dpkg-query -W -f='${Status}' ncdu 2>/dev/null | grep -q 'install ok installed' || fail "Пакет ncdu не установлен"
[ -f /home/student/ncdu-path.txt ] || fail "Нет ~/ncdu-path.txt"
want=$(dpkg -L ncdu | grep -E '/bin/ncdu$' | head -1)
got=$(tr -d '[:space:]' < /home/student/ncdu-path.txt)
[ "$got" = "$want" ] || fail "В ~/ncdu-path.txt «$got» — это не путь к исполняемому файлу ncdu"
ok "ncdu $(dpkg-query -W -f='${Version}' ncdu) → $want"
```

```text hint
1. Обновить списки пакетов и установить пакет (нужны права администратора).
2. У низкоуровневого менеджера пакетов есть ключ «показать список файлов пакета». Среди них найдите исполняемый файл — он лежит в каталоге bin.
```

```bash solution
sudo apt-get update -q
sudo apt-get install -y -q ncdu
dpkg -L ncdu | grep '/bin/ncdu$' > ~/ncdu-path.txt
```

```text review
Эталон: `sudo apt update && sudo apt install ncdu` → `dpkg -L ncdu | grep bin`.

- `apt update` обновляет **списки** пакетов, `apt upgrade` — сами пакеты. Перед установкой на свежем сервере всегда `update`.
- `dpkg -L пакет` — файлы пакета; обратная задача `dpkg -S /путь` — какому пакету принадлежит файл; `apt show пакет` — описание и зависимости; `apt policy пакет` — какая версия и из какого репозитория.
- `command -v ncdu` или `which ncdu` тоже покажут путь, но только если файл в PATH. `dpkg -L` знает все файлы: конфиги, man-страницы, systemd-юниты.
```

```text notes
snap\s+install => ncdu ставился через snap. Задача была про репозиторий Ubuntu и apt: у snap-пакетов другие пути и обновления.
```

### Удалить программу вместе с настройками

На сервере стоит FTP-сервер `vsftpd`, он больше не нужен. Удалите пакет **полностью — вместе с его конфигурационными файлами**, чтобы в системе не осталось следов.

```bash setup
DEBIAN_FRONTEND=noninteractive apt-get install -y -q vsftpd >/dev/null 2>&1
dpkg-query -W -f='${Status}' vsftpd | grep -q 'install ok installed'
```

```bash check
st=$(dpkg-query -W -f='${db:Status-Abbrev}' vsftpd 2>/dev/null | tr -d ' ')
[ "$st" = ii ] && fail "Пакет vsftpd всё ещё установлен"
[ "$st" = rc ] && fail "Пакет удалён, но его конфигурационные файлы остались (статус rc в dpkg -l)"
[ -e /etc/vsftpd.conf ] && fail "Остался /etc/vsftpd.conf"
ok "vsftpd удалён полностью"
```

```text hint
У менеджера пакетов две команды удаления: одна оставляет конфигурационные файлы (на случай переустановки), другая убирает и их. Нужна вторая.
```

```bash solution
sudo apt-get purge -y -q vsftpd
```

```text review
Эталон: `sudo apt purge vsftpd`.

- `apt remove` удаляет программу, но оставляет конфиги в `/etc` — в `dpkg -l` пакет получает статус `rc` (removed, config-files). При повторной установке старые настройки вернутся.
- `apt purge` убирает и конфиги. Уже удалённый пакет можно «дочистить» той же командой.
- Найти все такие хвосты: `dpkg -l | grep '^rc'`. Неиспользуемые зависимости — `apt autoremove`.
- Данные программы (базы, загруженные файлы) пакетный менеджер не трогает ни при `remove`, ни при `purge` — их удаляют вручную.
```

```text notes
rm\s+[^\n]*/etc/vsftpd => Конфиг удалялся руками через rm — dpkg об этом не знает. Правильно — apt purge: менеджер пакетов уберёт всё, что ставил.
```

### Какому пакету принадлежит файл

На сервере есть утилита `/usr/bin/dig`, но её пакет называется не `dig`. Узнайте через менеджер пакетов, какой пакет установил этот файл, и запишите **имя пакета** в `~/dig-package.txt`.

```bash setup
rm -f /home/student/dig-package.txt
```

```bash check
[ -f /home/student/dig-package.txt ] || fail "Нет ~/dig-package.txt"
want=$(dpkg -S /usr/bin/dig | cut -d: -f1)
got=$(tr -d '[:space:]' < /home/student/dig-package.txt)
[ "$got" = "$want" ] || fail "В файле «$got» — это не пакет, которому принадлежит /usr/bin/dig"
ok "/usr/bin/dig → пакет $want"
```

```text hint
У низкоуровневого менеджера пакетов есть ключ «поиск»: по пути к файлу он показывает, какой установленный пакет его содержит. Ответ — часть строки до двоеточия.
```

```bash solution
dpkg -S /usr/bin/dig | cut -d: -f1 > ~/dig-package.txt
```

```text review
Эталон: `dpkg -S /usr/bin/dig` → `bind9-dnsutils`.

- Нужно, когда на сервере «откуда-то» есть программа и непонятно, как её обновить или удалить.
- Для **неустановленных** пакетов — `apt-file search bin/dig` (пакет `apt-file`, сначала `apt-file update`). В Fedora/RHEL: `dnf provides */dig`.
- Если `dpkg -S` ничего не нашёл — файл поставили мимо менеджера пакетов (скрипт, `make install`, скачанный бинарник). Такие программы сами не обновятся.
```

### Изолированное окружение Python

В `~/flaskapp` лежит маленькое веб-приложение на Flask. Подготовьте для него виртуальное окружение `~/flaskapp/.venv`, установите туда `flask` и сохраните зависимости с **точными версиями** в `~/flaskapp/requirements.txt`. В системный Python пакет ставить нельзя.

```bash setup
rm -rf /home/student/flaskapp
mkdir -p /home/student/flaskapp
cat > /home/student/flaskapp/app.py <<'EOF'
from flask import Flask
app = Flask(__name__)

@app.get("/")
def index():
    return "ok"
EOF
chown -R student:student /home/student/flaskapp
```

```bash check
d=/home/student/flaskapp
[ -x $d/.venv/bin/python ] || fail "Нет виртуального окружения ~/flaskapp/.venv"
v=$($d/.venv/bin/python -c 'import flask, importlib.metadata as m; print(m.version("flask"))' 2>/dev/null) || fail "В окружении .venv нет flask"
python3 -c 'import flask' 2>/dev/null && fail "flask установлен в системный Python — так ломают пакеты системы"
[ -f $d/requirements.txt ] || fail "Нет ~/flaskapp/requirements.txt"
grep -qiE "^flask==$v\$" $d/requirements.txt || fail "В requirements.txt нет строки flask==$v (точной версии, которая установлена)"
ok "flask $v в .venv; зависимостей в requirements.txt: $(grep -c '==' $d/requirements.txt)"
```

```text hint
1. Создать окружение модулем venv в каталоге проекта.
2. Установить пакет менеджером пакетов **из этого окружения** (не системным).
3. Выгрузить список установленных пакетов с версиями в файл зависимостей.
```

```bash solution
cd ~/flaskapp
python3 -m venv .venv
.venv/bin/pip install -q flask
.venv/bin/pip freeze > requirements.txt
```

```text review
Эталон: `python3 -m venv .venv` → `.venv/bin/pip install flask` → `pip freeze > requirements.txt`.

- В Ubuntu 24.04 системный pip отказывается ставить пакеты (`externally-managed-environment`, PEP 668) — и правильно: пакеты Python, от которых зависят утилиты системы, нельзя перетирать. Обходить через `--break-system-packages` не надо — для этого и есть venv.
- `source .venv/bin/activate` подменяет `python` и `pip` на версии из окружения до `deactivate`; вызов `.venv/bin/pip` работает и без активации (так пишут в Dockerfile и systemd-юнитах).
- Восстановить окружение на другой машине: `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt`. Сам `.venv` в Git не коммитят — он в `.gitignore`.
- `pip freeze` фиксирует и транзитивные зависимости (Werkzeug, Jinja2…) — сборка повторяема.
```

```text notes
break-system-packages => Использовался --break-system-packages — так можно сломать системные утилиты на Python. Для приложений — виртуальное окружение.
sudo\s+pip => pip запускался через sudo — пакеты ставятся системно, мимо venv.
```

## Тест

### Что делает команда apt update?
- [ ] Обновляет все установленные пакеты
- [x] Обновляет списки доступных пакетов из репозиториев, ничего не устанавливая
- [ ] Обновляет ядро
- [ ] Удаляет старые пакеты
> Обновляет пакеты `apt upgrade`. Перед установкой на свежем сервере всегда сначала `apt update`.

### Чем apt purge отличается от apt remove?
- [ ] Ничем
- [x] purge удаляет пакет вместе с его конфигурационными файлами, remove оставляет конфиги
- [ ] remove удаляет и зависимости
- [ ] purge только помечает пакет на удаление
> Ненужные больше зависимости удаляет `apt autoremove`.

### Почему dpkg -i package.deb может завершиться ошибкой, а apt install — нет?
- [ ] dpkg работает только с rpm
- [x] dpkg ставит один файл и не скачивает зависимости; apt сам разрешает и ставит зависимости из репозиториев
- [ ] dpkg требует интернета
- [ ] apt не проверяет подписи
> Недостающие зависимости после dpkg можно доставить через `apt -f install`.

### Каким менеджером пакетов ставят программы в Rocky Linux?
= dnf
= yum
> yum — старое имя; в современных версиях это ссылка на dnf.

### Как узнать, какому пакету принадлежит файл /usr/sbin/nginx в Ubuntu?
- [ ] apt show /usr/sbin/nginx
- [x] dpkg -S /usr/sbin/nginx
- [ ] which -p nginx
- [ ] dpkg -L /usr/sbin/nginx
> `dpkg -L пакет` — наоборот, список файлов пакета. В RHEL-семействе — `rpm -qf` или `dnf provides`.

### Зачем при подключении стороннего репозитория добавляют его GPG-ключ?
- [ ] Чтобы ускорить скачивание
- [x] Чтобы менеджер пакетов мог проверить подпись и не установить подменённый пакет
- [ ] Для шифрования трафика
- [ ] Чтобы обойти лицензию
> Без доверенного ключа apt откажется работать с репозиторием.

### Зачем в Python использовать виртуальное окружение venv?
- [ ] Чтобы Python работал быстрее
- [x] Чтобы изолировать зависимости проекта от системного Python и других проектов
- [ ] Чтобы запускать Python без интерпретатора
- [ ] Это обязательное требование pip для любых пакетов
> У разных приложений могут быть несовместимые версии одной и той же библиотеки.

### Ubuntu на pip install requests отвечает ошибкой externally-managed-environment. Что правильно сделать?
- [ ] Удалить системный Python
- [x] Создать виртуальное окружение (python3 -m venv .venv), активировать его и ставить пакеты туда
- [ ] Выполнить pip install от root
- [ ] Удалить файл /etc/apt/sources.list
> Ошибка защищает системные пакеты, на которых работает сам дистрибутив.

### Как сохранить точные версии установленных Python-пакетов в файл?
= pip freeze > requirements.txt
> Восстановить окружение: `pip install -r requirements.txt`.

### Чем npm ci отличается от npm install?
- [ ] npm ci устанавливает пакеты глобально
- [x] npm ci делает чистую установку строго по package-lock.json, не меняя его, — подходит для CI и серверов
- [ ] npm ci только проверяет зависимости
- [ ] Ничем
> Так на каждой сборке получается одинаковый набор версий.

### Какая команда Maven собирает Java-проект в jar-файл?
- [ ] mvn run
- [x] mvn package
- [ ] mvn build-jar
- [ ] mvn install-jar
> Результат появляется в каталоге `target/`.

### Какие каталоги с зависимостями обычно не коммитят в Git?
- [x] .venv
- [x] node_modules
- [ ] src
- [ ] Файлы requirements.txt и package-lock.json
> Коммитят описание зависимостей (`requirements.txt`, `package-lock.json`, `pom.xml`), а не сами библиотеки.

### Куда принято класть вручную скачанный бинарник, чтобы он запускался по имени у всех пользователей?
- [ ] /tmp
- [ ] /etc
- [x] /usr/local/bin
- [ ] /var/log
> `/usr/local` — для программ, установленных не менеджером пакетов. Этот каталог уже есть в PATH.
