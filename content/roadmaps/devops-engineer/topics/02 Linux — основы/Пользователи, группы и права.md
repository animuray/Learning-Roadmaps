# Пользователи, группы и права

Linux — многопользовательская система. Каждый процесс работает от имени какого-то пользователя, у каждого файла есть владелец и группа. Права определяют, кто что может делать с файлом. Половина проблем вида «сервис не запускается» на самом деле — проблемы с правами.

## Пользователи и группы

- У каждого пользователя есть **UID**, у группы — **GID**. Система работает с числами, а имена нужны людям.
- **root** (UID 0) может всё; проверки прав на него почти не действуют.
- **Системные пользователи** (`www-data`, `postgres`, `nginx`) нужны службам: если взломают сервис, злоумышленник получит только права этого пользователя.

| Файл | Что хранит |
| --- | --- |
| `/etc/passwd` | Пользователи: имя, UID, GID, домашний каталог, оболочка |
| `/etc/shadow` | Хеши паролей (читает только root) |
| `/etc/group` | Группы и их участники |

```bash
whoami                       # кто я
id                           # мой UID, GID и группы
id alice
sudo useradd -m -s /bin/bash alice   # создать пользователя с домашним каталогом
sudo adduser alice           # интерактивный вариант в Debian/Ubuntu
sudo passwd alice            # задать пароль
sudo usermod -aG docker alice   # добавить в группу (-a обязателен, иначе другие группы пропадут!)
sudo groupadd devops
sudo userdel -r alice        # удалить вместе с домашним каталогом
```

Новая группа применяется к новым сеансам: нужно перелогиниться (или `newgrp docker`).

## Права rwx

```
-rwxr-x--- 1 alice devops 2048 Jun 1 10:00 deploy.sh
 └┬┘└┬┘└┬┘   владелец группа
  u  g  o
```

Три тройки прав: **u** — владелец, **g** — группа, **o** — все остальные.

| Право | Для файла | Для каталога |
| --- | --- | --- |
| `r` (4) | Читать содержимое | Видеть список файлов (`ls`) |
| `w` (2) | Изменять содержимое | Создавать, удалять и переименовывать файлы внутри |
| `x` (1) | Запускать как программу | Входить в каталог (`cd`) и обращаться к файлам внутри |

> [!important] Удаление файла
> Возможность удалить файл зависит от прав на **каталог** (w + x), а не на сам файл.

## chmod — изменить права

Числовая запись — сумма r=4, w=2, x=1 для каждой тройки:

| Права | Число | Типичное применение |
| --- | --- | --- |
| `rwxr-xr-x` | 755 | Каталоги, исполняемые файлы и скрипты |
| `rw-r--r--` | 644 | Обычные файлы, конфиги |
| `rw-------` | 600 | Приватные ключи, файлы с паролями |
| `rwx------` | 700 | `~/.ssh`, личные каталоги |

```bash
chmod 644 nginx.conf
chmod 755 deploy.sh
chmod u+x script.sh        # добавить владельцу право запуска
chmod g-w,o-r secret.txt   # убрать права группе и остальным
chmod -R 750 /opt/app      # рекурсивно
```

> [!question] Частый вопрос на собеседовании: почему каталогу 755, а файлу 644?
> Каталогу нужен `x`, иначе в него нельзя войти и обратиться к файлам. Обычному файлу `x` не нужен — его не запускают как программу.

## chown — владелец и группа

```bash
sudo chown alice file.txt
sudo chown alice:devops file.txt
sudo chown -R www-data:www-data /var/www/site
sudo chgrp devops file.txt
```

Менять владельца файла может только root.

## sudo и su

- `sudo команда` — выполнить команду от root (или другого пользователя: `sudo -u postgres psql`). Запрашивает **ваш** пароль, а все действия пишутся в журнал.
- Кому что разрешено, задаётся в `/etc/sudoers` и `/etc/sudoers.d/`. Правьте только через `visudo`: он проверяет синтаксис, и вы не потеряете sudo из-за опечатки.
- В Ubuntu право на sudo дают через группу `sudo`, в RHEL-семействе — через `wheel`.
- `sudo -i` — интерактивная оболочка root. `su - user` — переключиться на пользователя по **его** паролю.

## umask — права по умолчанию

Новый файл получает права `666` минус umask, каталог — `777` минус umask:

```bash
umask        # обычно 0022
# файл: 666 - 022 = 644, каталог: 777 - 022 = 755
umask 077    # новые файлы будут доступны только владельцу
```

## Специальные биты

| Бит | Как выглядит | Смысл |
| --- | --- | --- |
| SUID (4000) | `rwsr-xr-x` | Программа выполняется с правами **владельца файла**. Пример: `/usr/bin/passwd` меняет `/etc/shadow` |
| SGID (2000) | `rwxr-sr-x` | На каталоге: новые файлы получают группу каталога — удобно для общих папок |
| Sticky (1000) | `rwxrwxrwt` | На каталоге: удалить файл может только его владелец. Так устроен `/tmp` (1777) |

Тонкую настройку для отдельных пользователей дают **ACL**: `setfacl`, `getfacl`.

## Лаборатория

### Пользователь и группа

Создайте группу `devops` и пользователя `deploy`:

- с домашним каталогом `/home/deploy`;
- с оболочкой `/bin/bash`;
- состоящего в группе `devops`.

```bash setup
userdel -r deploy 2>/dev/null; groupdel devops 2>/dev/null; true
```

```bash check
getent group devops >/dev/null || fail "Группы devops нет"
id deploy >/dev/null 2>&1 || fail "Пользователя deploy нет"
[ -d /home/deploy ] || fail "У deploy нет домашнего каталога /home/deploy"
shell=$(getent passwd deploy | cut -d: -f7)
[ "$shell" = /bin/bash ] || fail "Оболочка deploy — «$shell», а нужна /bin/bash"
id -nG deploy | tr ' ' '\n' | grep -qx devops || fail "deploy не в группе devops: $(id deploy)"
ok "$(id deploy)"
```

```text hint
1. Создать группу devops.
2. Создать пользователя deploy: сразу с домашним каталогом, оболочкой bash и дополнительной группой devops.
Всё это делает одна команда создания пользователя с нужными ключами — они перечислены в конспекте. Не забудьте права администратора.
```

```bash solution
sudo groupadd devops
sudo useradd -m -s /bin/bash -G devops deploy
```

```text review
Эталон: `groupadd devops`, затем `useradd -m -s /bin/bash -G devops deploy` — всё в одной команде, без последующих правок.

- `-m` создаёт домашний каталог и копирует в него файлы из `/etc/skel`. Без `-m` пользователь создастся, но без дома — частая причина странных ошибок у служб.
- `-s /bin/bash` — без него в Ubuntu будет `/bin/sh`, у человека не будет истории и автодополнения.
- `adduser` в Debian/Ubuntu — интерактивная обёртка, она всё это делает сама и спрашивает пароль. В скриптах и Ansible используют `useradd`: он не задаёт вопросов.
- Добавить **существующего** пользователя в группу — только `usermod -aG группа user`. Без `-a` пользователь потеряет все остальные дополнительные группы.
- Членство в группе применяется при следующем входе: уже открытая сессия его не увидит (`newgrp` или перелогиниться).
```

```text notes
usermod\s+(?![^\n]*-a)[^\n]*-G => usermod -G без -a заменяет ВСЕ дополнительные группы пользователя на указанные. Добавлять в группу нужно через usermod -aG — иначе можно случайно убрать человека, например, из sudo.
useradd\s+(?![^\n]*(-m\b|--create-home))[^\n]*deploy => Пользователь создавался без -m: домашний каталог не появится сам. Его пришлось создавать вручную — с -m это делается сразу, вместе с файлами из /etc/skel.
```

### Секретный конфиг

В `/opt/app/secret.env` лежат пароли приложения. Сейчас его может прочитать любой пользователь системы. Сделайте так, чтобы:

- владельцем файла был пользователь `app`, группой — `app`;
- читать и менять файл мог **только владелец**.

```bash setup
id app >/dev/null 2>&1 || useradd -r -s /usr/sbin/nologin app
mkdir -p /opt/app
printf 'DB_PASSWORD=s3cr3t\nAPI_KEY=abc123\n' > /opt/app/secret.env
chown root:root /opt/app/secret.env
chmod 644 /opt/app/secret.env
```

```bash check
f=/opt/app/secret.env
[ -f "$f" ] || fail "Файла $f нет — его удалили?"
owner=$(stat -c '%U:%G' "$f"); mode=$(stat -c '%a' "$f")
[ "$owner" = app:app ] || fail "Владелец $owner, а нужен app:app"
[ "$mode" = 600 ] || fail "Права $mode ($(stat -c '%A' "$f")), а нужно, чтобы читать и писать мог только владелец"
grep -q DB_PASSWORD "$f" || fail "Из файла пропало содержимое"
ok "$(ls -l "$f")"
```

```text hint
1. Сменить владельца и группу файла на app — одной командой, через двоеточие.
2. Оставить права только владельцу: чтение и запись. Посчитайте цифру: r = 4, w = 2, x = 1; группе и остальным — ноль.
```

```bash solution
sudo chown app:app /opt/app/secret.env
sudo chmod 600 /opt/app/secret.env
```

```text review
Эталон: `chown app:app` и `chmod 600`.

- `600` = `rw-------`: файл с секретами не должен быть исполняемым, а группе и остальным он не нужен вовсе.
- Иногда ставят `640` и группу, в которой состоит служба (например, `root:app`, `640`): так файл может поменять только root, а приложение — только прочитать. Это даже строже, но требует понимать, под кем работает служба.
- `chmod u=rw,go=` — та же настройка в символьной записи; в скриптах привычнее цифры.
- Секреты в файле — нормальная практика, но рядом с ним не должно быть копий вроде `secret.env.bak` с правами 644.
```

```text notes
chmod\s+(-R\s+)?0?777 => 777 даёт всем пользователям системы право читать и менять файл. Это никогда не бывает правильным ответом — права нужно сужать, а не расширять.
chmod\s+-R => chmod -R здесь не нужен: он меняет права у всего дерева файлов, и одной ошибкой в пути можно испортить права системного каталога.
```

### Общий каталог команды

Команде `devops` нужен общий каталог `/opt/shared`:

- владелец `root`, группа `devops`;
- члены группы могут создавать и читать файлы, остальные — не могут даже зайти;
- новые файлы внутри автоматически получают группу `devops` (а не основную группу автора).

Пользователь `deploy` из группы `devops` уже создан.

```bash setup
groupadd -f devops
id deploy >/dev/null 2>&1 || useradd -m -s /bin/bash deploy
usermod -aG devops deploy
rm -rf /opt/shared
```

```bash check
d=/opt/shared
[ -d "$d" ] || fail "Каталога $d нет"
[ "$(stat -c '%U:%G' "$d")" = root:devops ] || fail "Владелец $(stat -c '%U:%G' "$d"), а нужен root:devops"
mode=$(stat -c '%a' "$d")
case "$mode" in
  2770) ;;
  770) fail "Права 770: новые файлы в каталоге получат группу своего автора, а не devops" ;;
  *) fail "Права $mode ($(stat -c '%A' "$d")) не подходят под условие" ;;
esac
su -s /bin/sh deploy -c "touch $d/.lab-probe" 2>/dev/null || fail "deploy не может создать файл в $d"
g=$(stat -c '%G' "$d/.lab-probe"); rm -f "$d/.lab-probe"
[ "$g" = devops ] || fail "Новый файл получил группу $g, а не devops"
ok "$(ls -ld "$d")"
```

```text hint
1. Создать каталог от имени администратора.
2. Сменить группу каталога на devops.
3. Права: полный доступ владельцу и группе, ноль остальным — и ещё специальный бит (SGID), который заставляет новые файлы наследовать группу каталога. Специальные биты пишутся четвёртой цифрой спереди.
```

```bash solution
sudo mkdir /opt/shared
sudo chgrp devops /opt/shared
sudo chmod 2770 /opt/shared
```

```text review
Эталон: `chgrp devops` и `chmod 2770`.

- `2` спереди — бит SGID. На каталоге он означает «новые файлы получают группу каталога». Без него файл, созданный deploy, получит группу deploy, и коллеги его не смогут прочитать.
- То же самое символьно: `chmod g+s /opt/shared`.
- Чтобы новые файлы ещё и создавались с правами на запись для группы, пользователям нужна `umask 002`, или на каталог ставят ACL по умолчанию: `setfacl -d -m g::rwx /opt/shared`.
- Для каталогов вроде `/tmp`, куда пишут все, используют другой бит — sticky (`1777`): удалять файл может только его владелец.
```

```text notes
chmod\s+(-R\s+)?0?2?777 => 777 открывает каталог всем пользователям системы — ровно то, чего команда хотела избежать.
chown\s+[^\s]*devops:devops => Владельцем указан devops — но это группа, а не пользователь. Владельцем общего каталога оставляют root, а доступ даёт группа.
```

### Права sudo на одну команду

Разрешите пользователю `deploy` выполнять **только** `systemctl restart cron` от root **без пароля**. Остальные команды через sudo ему по-прежнему недоступны.

Правило положите в отдельный файл `/etc/sudoers.d/deploy`.

```bash setup
groupadd -f devops
id deploy >/dev/null 2>&1 || useradd -m -s /bin/bash deploy
gpasswd -d deploy sudo >/dev/null 2>&1; true
rm -f /etc/sudoers.d/deploy
```

```bash check
f=/etc/sudoers.d/deploy
[ -f "$f" ] || fail "Файла $f нет"
visudo -cf "$f" >/dev/null 2>&1 || fail "В $f синтаксическая ошибка. С такой ошибкой sudo может перестать работать у всех"
visudo -c >/dev/null 2>&1 || fail "В настройках sudo есть синтаксическая ошибка"
mode=$(stat -c '%a' "$f")
[ "$mode" = 440 ] || [ "$mode" = 640 ] || [ "$mode" = 400 ] || [ "$mode" = 600 ] || fail "Права на $f — $mode: файл sudoers доступен на запись не только root"
rules=$(sudo -l -U deploy 2>/dev/null)
echo "$rules" | grep -Eq '\(ALL( : ALL)?\)[[:space:]]+(NOPASSWD: )?ALL$' && fail "deploy получил полный доступ (ALL). Нужна только одна команда"
echo "$rules" | grep -q 'NOPASSWD: /usr/bin/systemctl restart cron' || fail "deploy не может перезапустить cron через sudo без пароля. Сейчас deploy разрешено:
$rules"
ok "deploy может: $(echo "$rules" | grep NOPASSWD | sed 's/^ *//')"
```

```text hint
1. Правило sudo в отдельном файле каталога /etc/sudoers.d: «кто — на каких машинах — от чьего имени — без пароля — какая команда».
2. Команда пишется полным путём (узнайте его через which).
3. Создавать и проверять такой файл нужно специальным редактором sudo — он не даст сохранить ошибку. Права на файл — только чтение для владельца и группы.
```

```bash solution
echo 'deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart cron' | sudo tee /etc/sudoers.d/deploy >/dev/null
sudo chmod 440 /etc/sudoers.d/deploy
sudo visudo -cf /etc/sudoers.d/deploy
```

```text review
Эталон: строка `deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart cron` в `/etc/sudoers.d/deploy` с правами 440.

- Руками файл правят через `sudo visudo -f /etc/sudoers.d/deploy`: visudo проверяет синтаксис перед сохранением. Ошибка в обычном редакторе может сломать sudo целиком — и починить его будет нечем, кроме входа под root или загрузки в recovery.
- В скриптах и Ansible файл пишут через `tee`, а затем обязательно проверяют `visudo -cf` (в Ansible — параметр `validate: visudo -cf %s`).
- Полный путь к команде обязателен: иначе можно подложить свой `systemctl` в PATH.
- Аргументы ограничивают права: правило разрешает именно `restart cron`, а не `systemctl` целиком. `systemctl *` открыл бы и `systemctl edit`, через который получают root.
```

```text notes
(nano|vim?|vi)\s+/etc/sudoers => Файлы sudoers правят через visudo: обычный редактор сохранит файл с ошибкой, и sudo перестанет работать у всех пользователей.
sudo\s+echo[^|]*>\s*/etc/sudoers => sudo echo ... > файл не сработает: перенаправление делает ваша оболочка без прав root. Для записи в системный файл используют echo ... | sudo tee файл.
NOPASSWD:\s*ALL => NOPASSWD: ALL — это полный root без пароля. Давайте ровно те команды, которые нужны.
```

### Файлы с битом SUID

Найдите во всей системе обычные файлы с битом SUID и сохраните список (полные пути, по одному на строку) в `~/suid.txt`. Сообщений об ошибках доступа в файле быть не должно.

```bash setup
rm -f /home/student/suid.txt
```

```bash check
f=/home/student/suid.txt
[ -s "$f" ] || fail "Файл ~/suid.txt пуст или не создан"
grep -qi 'denied\|отказано' "$f" && fail "В файл попали сообщения об ошибках доступа"
grep -qx '/usr/bin/passwd' "$f" || fail "В списке нет /usr/bin/passwd — а у него точно есть SUID"
grep -qx '/usr/bin/sudo' "$f" || fail "В списке нет /usr/bin/sudo"
while read -r p; do
  [ -u "$p" ] || fail "У $p нет бита SUID — в списке лишние файлы"
done < "$f"
ok "найдено файлов: $(wc -l < "$f")"
```

```text hint
1. Искать по всей системе, начиная с корня, только обычные файлы.
2. Условие — установленный бит SUID (его числовое значение 4000).
3. Ошибки «доступ запрещён» идут в поток ошибок — отправьте его в никуда, а найденное — в файл.
```

```bash solution
find / -perm -4000 -type f 2>/dev/null > ~/suid.txt
```

```text review
Эталон: `find / -perm -4000 -type f 2>/dev/null > ~/suid.txt`.

- `-perm -4000` — «бит SUID установлен» (минус значит «как минимум эти биты»). Без минуса нашлись бы файлы с правами ровно 4000.
- `2>/dev/null` убирает ошибки доступа к чужим каталогам, `>` пишет только найденное.
- Зачем это на практике: SUID-файлы выполняются с правами владельца, обычно root. Неожиданный SUID-файл (например, копия bash) — классический бэкдор, поэтому список сверяют при аудите.
- Можно было запустить через `sudo` — ошибок доступа не будет вовсе, а результат точнее: обычный пользователь не видит часть каталогов.
```

## Тест

### Какие права в числовом виде соответствуют rwxr-xr-x?
= 755
> rwx = 4+2+1 = 7, r-x = 4+1 = 5.

### Какие права обычно выставляют для конфигурационного файла, который все могут читать, а менять — только владелец?
- [ ] 777
- [ ] 755
- [x] 644
- [ ] 600
> 6 = rw- для владельца, 4 = r-- для группы и остальных.

### Почему каталогу обычно нужны права 755, а файлу — 644?
- [ ] Так требует ядро для всех файлов
- [x] Для каталога x означает право войти в него и обращаться к файлам внутри; обычному файлу x не нужен
- [ ] 644 для каталога запрещён
- [ ] Чтобы файлы занимали меньше места
> Без x на каталоге не сработают ни `cd`, ни чтение файлов внутри, даже если у них права 644.

### Что даёт право w на каталог?
- [ ] Право изменять содержимое файлов внутри
- [x] Право создавать, удалять и переименовывать файлы в каталоге (вместе с x)
- [ ] Право видеть список файлов
- [ ] Право запускать файлы из каталога
> Поэтому файл можно удалить даже без прав на сам файл, если есть w и x на каталог.

### Какие права нужны приватному SSH-ключу?
- [ ] 644
- [ ] 755
- [x] 600
- [ ] 777
> Если права шире, ssh откажется использовать ключ с ошибкой «UNPROTECTED PRIVATE KEY FILE».

### Как сделать пользователя alice и группу www-data владельцами каталога /var/www/site со всем содержимым?
= sudo chown -R alice:www-data /var/www/site
= chown -R alice:www-data /var/www/site
> `-R` — рекурсивно, формат `пользователь:группа`.

### Что произойдёт, если выполнить usermod -G docker alice без -a?
- [ ] alice будет добавлена в группу docker в дополнение к остальным
- [x] alice окажется только в группе docker, а из остальных дополнительных групп (например, sudo) будет удалена
- [ ] Команда завершится ошибкой
- [ ] Будет создана новая группа docker
> Классическая ошибка, после которой пользователь теряет sudo. Всегда пишите `-aG`.

### Пользователя добавили в группу docker, но docker по-прежнему пишет permission denied. Почему?
- [ ] Нужно переустановить Docker
- [x] Членство в новой группе применяется к новым сеансам: нужно перелогиниться
- [ ] Группы в Linux работают только для root
- [ ] Нужно выставить права 777 на /var/run/docker.sock
> Можно проверить командой `id`: группы текущего сеанса ещё старые.

### Чем лучше править /etc/sudoers?
- [ ] nano /etc/sudoers
- [x] visudo
- [ ] echo >> /etc/sudoers
- [ ] chmod 777 /etc/sudoers
> visudo проверяет синтаксис перед сохранением. С ошибкой в sudoers можно остаться без sudo вообще.

### umask равен 022. Какие права получит новый файл?
- [ ] 755
- [x] 644
- [ ] 666
- [ ] 600
> Для файла базовые права 666: 666 − 022 = 644. Каталог получит 777 − 022 = 755.

### Зачем на каталоге /tmp установлен sticky bit (права 1777)?
- [ ] Чтобы файлы в /tmp не удалялись при перезагрузке
- [x] Чтобы каждый мог создавать файлы, но удалять только свои
- [ ] Чтобы файлы запускались с правами root
- [ ] Чтобы /tmp был доступен только root
> Без sticky bit любой пользователь мог бы удалить чужие временные файлы.

### Что делает бит SUID на исполняемом файле?
- [ ] Запрещает его удаление
- [x] Программа выполняется с правами владельца файла, а не запустившего её пользователя
- [ ] Делает файл скрытым
- [ ] Включает логирование запусков
> Так `passwd` обычного пользователя может записать новый хеш в `/etc/shadow`. Лишние SUID-файлы — риск безопасности.

### В каком файле хранятся хеши паролей пользователей?

- [x] /etc/shadow
- [ ] /etc/group
- [ ] /etc/sudoers
> `/etc/passwd` читают все, поэтому хеши вынесены в `/etc/shadow`, доступный только root.
