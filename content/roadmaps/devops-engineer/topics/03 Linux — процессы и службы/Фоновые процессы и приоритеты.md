# Фоновые процессы и приоритеты

Долгая команда — бэкап, сборка, миграция базы — не должна держать терминал занятым. Ещё важнее, чтобы она не умерла, если оборвётся SSH-соединение.

## Передний план и фон

```bash
./backup.sh &          # запустить в фоне; оболочка выведет [1] 12345
jobs                   # задания текущей оболочки
fg %1                  # вернуть задание 1 на передний план
# Ctrl+Z               # приостановить текущую команду (состояние T)
bg %1                  # продолжить её в фоне
kill %1                # отправить сигнал заданию по номеру
```

`jobs`, `fg` и `bg` работают только с заданиями **текущей** оболочки.

## Почему фоновый процесс умирает после выхода из SSH

Когда терминал закрывается, оболочка получает **SIGHUP** и рассылает его своим заданиям. По умолчанию SIGHUP завершает процесс. Поэтому `./long-task.sh &` умрёт вместе с SSH-сессией.

Решения:

```bash
nohup ./long-task.sh > task.log 2>&1 &   # игнорировать SIGHUP, вывод — в файл
./long-task.sh &                         # уже запущено без nohup...
disown                                   # ...убрать задание из списка оболочки
setsid ./long-task.sh                    # запустить в новой сессии без терминала
```

- **nohup** запускает команду с игнорированием SIGHUP. Если вывод не перенаправлен, он попадёт в `nohup.out`.
- **disown** «отвязывает» уже запущенное задание: оболочка не отправит ему SIGHUP.

## screen и tmux — сессии, которые живут без вас

Терминальные мультиплексоры держат сессию на сервере. Вы отключаетесь, команда продолжает работать, а потом вы подключаетесь обратно и видите всё как было. Это стандартный инструмент для долгих ручных работ на сервере.

**tmux** (префикс — Ctrl+B):

```bash
tmux new -s migrate      # новая сессия с именем
# Ctrl+B, затем d        # отключиться (detach), сессия продолжает работать
tmux ls                  # список сессий
tmux attach -t migrate   # подключиться снова
# Ctrl+B, затем %        # разделить окно по вертикали
# Ctrl+B, затем "        # по горизонтали
# Ctrl+B, затем стрелки  # переход между панелями
# Ctrl+B, затем c / n    # новое окно / следующее окно
tmux kill-session -t migrate
```

**screen** (префикс — Ctrl+A): `screen -S name`, отключиться — Ctrl+A затем d, вернуться — `screen -r name`, список — `screen -ls`. screen есть на старых серверах, tmux — современнее и удобнее.

> [!important] Для постоянных служб — systemd
> nohup и tmux подходят для разовых задач. Приложение, которое должно работать постоянно, оформляют как службу systemd: с автозапуском, перезапуском при падении и логами в journald.

## Приоритеты: nice и renice

Планировщик раздаёт процессорное время с учётом **niceness** — «вежливости» процесса:

- от **−20** (самый высокий приоритет) до **19** (самый низкий), по умолчанию **0**;
- чем выше nice, тем охотнее процесс уступает CPU другим;
- повышать nice (понижать приоритет) может любой пользователь своим процессам, а понижать nice (то есть поднимать приоритет) — только root.

```bash
nice -n 10 tar czf backup.tar.gz /data     # запустить с пониженным приоритетом
nice -n 19 ./heavy-report.sh               # минимальный приоритет
renice -n 5 -p 1234                        # изменить у работающего процесса
sudo renice -n -5 -p 1234                  # повысить приоритет — только root
ps -o pid,ni,pri,cmd -p 1234               # посмотреть nice
```

В `top` и `htop` колонка **NI** — nice, **PR** — итоговый приоритет в планировщике.

Приоритет ввода-вывода задаёт **ionice**: `ionice -c3 rsync ...` — диск только когда он никому больше не нужен. Удобно для бэкапов на рабочем сервере.

## Практика

- [ ] Запустить `sleep 300 &`, посмотреть `jobs`, вернуть на передний план, приостановить через Ctrl+Z и продолжить через `bg`
- [ ] Запустить `sleep 600 &`, закрыть SSH-сессию, зайти снова и проверить, жив ли процесс. Повторить с `nohup` и с `disown`
- [ ] Запустить долгую команду в tmux, отключиться, переподключиться по SSH и вернуться в сессию
- [ ] Разделить окно tmux на две панели: в одной `htop`, в другой `tail -f` лога
- [ ] Запустить две нагрузки на CPU (`yes > /dev/null`) с разным nice и сравнить их %CPU в `top`

### Долгая задача в tmux

Скрипт `~/long-backup.sh` работает несколько часов. Если запустить его в обычном SSH-сеансе, он умрёт при обрыве связи. Запустите его внутри **сессии tmux с именем `backup`** — так, чтобы можно было отключиться и потом вернуться к нему.

```bash setup
su - student -c 'tmux kill-server' 2>/dev/null
pkill -u student -f long-backup.sh 2>/dev/null
cat > /home/student/long-backup.sh <<'EOF'
#!/bin/bash
# «Долгое резервное копирование»
for i in $(seq 1 100000); do echo "копирую блок $i"; sleep 2; done
EOF
chmod 755 /home/student/long-backup.sh
chown student:student /home/student/long-backup.sh
true
```

```bash check
su - student -c 'tmux has-session -t backup' 2>/dev/null || fail "Сессии tmux с именем backup нет"
pid=$(pgrep -u student -f long-backup.sh | head -1)
[ -n "$pid" ] || fail "Скрипт long-backup.sh не запущен"
p=$pid; inside=no
while [ "$p" -gt 1 ] 2>/dev/null; do
  [ "$(ps -o comm= -p "$p")" = "tmux: server" ] && { inside=yes; break; }
  p=$(ps -o ppid= -p "$p" | tr -d ' ')
done
[ $inside = yes ] || fail "long-backup.sh работает, но не внутри tmux — при обрыве SSH он завершится"
ok "long-backup.sh (PID $pid) работает в tmux-сессии backup"
```

```text hint
1. Создать новую сессию tmux с заданным именем. Можно сразу указать команду, которую в ней выполнить, или запустить скрипт уже внутри.
2. Отключиться от сессии, не закрывая её, — сочетание префикса tmux и одной клавиши.
3. Посмотреть список сессий и вернуться в нужную по имени.
```

```bash solution
tmux new-session -d -s backup ~/long-backup.sh
tmux ls
```

```text review
Эталон: `tmux new -s backup` (и в ней `./long-backup.sh`) → `Ctrl+B D` (отключиться) → `tmux attach -t backup` (вернуться).

- Почему умирает обычный запуск: при закрытии терминала оболочка рассылает SIGHUP своим заданиям. tmux держит свой сервер и псевдотерминалы независимо от SSH.
- Шпаргалка (префикс Ctrl+B): `d` — отключиться, `c` — новое окно, `%` и `"` — разделить панель, стрелки — перейти между панелями, `[` — прокрутка истории.
- Альтернативы: `nohup cmd &` (вывод в nohup.out), `setsid`, `disown`. Для того, что должно работать постоянно, — systemd-юнит, а не tmux.
- `screen` — старший брат tmux, встречается на старых серверах: `screen -S backup`, `Ctrl+A D`, `screen -r backup`.
```

```text notes
nohup|disown|setsid => Скрипт запускался через nohup/disown/setsid — он тоже переживёт выход, но вернуться к его выводу и управлять им нельзя. Для этого и нужен tmux.
```

### Понизить приоритет на ходу

Процесс `video-encoder` пользователя `student` мешает остальным: перекодирование не срочное. **Не перезапуская** его, понизьте ему приоритет до значения nice `15`.

```bash setup
lab_unit lab-encoder
cat > /opt/lab/video-encoder <<'EOF'
#!/bin/bash
while true; do sleep 1; done
EOF
chmod 755 /opt/lab/video-encoder
systemd-run -q --unit=lab-encoder -p User=student /opt/lab/video-encoder
sleep 0.5
systemctl show -p MainPID --value lab-encoder > /var/lib/lab/encoder-pid
```

```bash check
pid=$(cat /var/lib/lab/encoder-pid)
[ -d /proc/$pid ] || fail "Процесс video-encoder (PID $pid) больше не работает — его перезапустили или остановили"
ni=$(ps -o ni= -p $pid | tr -d ' ')
[ "$ni" = 15 ] || fail "У video-encoder nice = $ni"
ok "video-encoder (PID $pid): nice $ni"
```

```text hint
1. Найти PID процесса.
2. Есть команда, которая меняет приоритет уже работающего процесса. Понизить приоритет своему процессу можно без sudo, повысить — только администратору.
```

```bash solution
renice -n 15 -p "$(pgrep -f /opt/lab/video-encoder)"
ps -o pid,ni,args -p "$(pgrep -f /opt/lab/video-encoder)"
```

```text review
Эталон: `renice -n 15 -p <PID>`.

- nice — от −20 (самый высокий приоритет) до 19 (самый низкий), по умолчанию 0. Чем больше nice, тем «вежливее» процесс уступает процессор.
- Запуск сразу с низким приоритетом: `nice -n 15 ./encode.sh`. В systemd-юните — `Nice=15`, а для диска — `IOSchedulingClass=idle` (или `ionice -c3`).
- Обычный пользователь может только **понижать** приоритет своих процессов; вернуть назад — уже нужен root.
- nice влияет, только когда процессору не хватает на всех. Жёсткий лимит («не больше 20% CPU») — это cgroups: `CPUQuota=20%`.
```

### Ночная задача с низким приоритетом

Запустите скрипт `~/reindex.sh` **в фоне** с приоритетом nice `10` так, чтобы он не зависел от вашего терминала (пережил выход из SSH), а его вывод сохранялся в `~/reindex.log`.

```bash setup
pkill -u student -f reindex.sh 2>/dev/null
rm -f /home/student/reindex.log /home/student/nohup.out
cat > /home/student/reindex.sh <<'EOF'
#!/bin/bash
for i in $(seq 1 100000); do echo "индексирую документ $i"; sleep 3; done
EOF
chmod 755 /home/student/reindex.sh
chown student:student /home/student/reindex.sh
true
```

```bash check
pid=$(pgrep -u student -f reindex.sh | head -1)
[ -n "$pid" ] || fail "reindex.sh не запущен"
ni=$(ps -o ni= -p $pid | tr -d ' ')
[ "$ni" = 10 ] || fail "У reindex.sh nice = $ni"
ign=$(awk '/^SigIgn/ {print $2}' /proc/$pid/status)
tty=$(ps -o tty= -p $pid | tr -d ' ')
[ $(( 0x$ign & 1 )) = 1 ] || [ "$tty" = "?" ] || fail "reindex.sh привязан к терминалу $tty и не защищён от сигнала разрыва связи"
sleep 3.5
[ -s /home/student/reindex.log ] || fail "~/reindex.log пуст или не создан — вывод идёт не туда"
ok "reindex.sh (PID $pid): nice $ni, вывод в ~/reindex.log"
```

```text hint
1. Комбинация трёх вещей в одной строке: команда «не обращать внимания на разрыв связи», команда «запустить с другим приоритетом» и сам скрипт.
2. Вывод перенаправить в файл, а всю строку отправить в фон знаком в конце.
```

```bash solution
nohup nice -n 10 ~/reindex.sh > ~/reindex.log 2>&1 &
sleep 1
ps -o pid,ni,stat,args -p "$(pgrep -f reindex.sh)"
```

```text review
Эталон: `nohup nice -n 10 ~/reindex.sh > ~/reindex.log 2>&1 &`.

- `nohup` ставит игнорирование SIGHUP — сигнала, который получают задания при закрытии терминала. Без перенаправления вывод уходит в `nohup.out`.
- Порядок важен: `nohup nice ...` — nohup запускает nice, тот — скрипт; оба свойства наследуются.
- `jobs`, `fg`, `bg`, `Ctrl+Z` работают только в той оболочке, где задание запущено. После выхода из SSH процесс ищут уже через `pgrep`.
- Для регулярных ночных задач — cron или systemd-таймер с `Nice=10`, а не ручной запуск.
```

## Тест

### Как запустить команду в фоне?
- [ ] bg ./script.sh
- [x] ./script.sh &
- [ ] background ./script.sh
- [ ] ./script.sh --bg
> Оболочка выведет номер задания и PID.

### Как вернуть фоновое задание номер 1 на передний план?
= fg %1
= fg 1
> Список заданий — `jobs`.

### Что делает Ctrl+Z, а затем команда bg?
- [ ] Завершает процесс и запускает заново в фоне
- [x] Приостанавливает текущую команду, а затем продолжает её выполнение в фоне
- [ ] Отправляет процессу SIGKILL
- [ ] Отключает терминал
> Ctrl+Z отправляет SIGTSTP, bg — SIGCONT.

### Почему процесс, запущенный через &, может завершиться после выхода из SSH?
- [ ] Фоновые процессы живут не дольше 10 минут
- [x] При закрытии терминала оболочка рассылает заданиям SIGHUP, который по умолчанию завершает процесс
- [ ] SSH удаляет все процессы пользователя
- [ ] Из-за нехватки памяти
> nohup, disown, setsid, tmux и screen защищают от этого.

### Что делает nohup?
- [ ] Повышает приоритет процесса
- [x] Запускает команду с игнорированием SIGHUP; вывод по умолчанию идёт в nohup.out
- [ ] Запускает процесс от root
- [ ] Ставит процесс на паузу
> Обычно его комбинируют с перенаправлением вывода и `&`.

### Вы уже запустили долгую команду через & и забыли nohup. Как не дать ей умереть при выходе из SSH?
- [ ] Перезапустить её
- [x] Выполнить disown, чтобы оболочка не отправила ей SIGHUP
- [ ] Выполнить bg
- [ ] Выполнить renice
> disown убирает задание из списка оболочки.

### Как отключиться от сессии tmux, оставив её работать?
- [ ] Ctrl+C
- [ ] exit
- [x] Ctrl+B, затем d
- [ ] Ctrl+D
> Вернуться — `tmux attach -t имя` (или `tmux a`).

### В каком диапазоне лежит значение nice?
- [ ] от 0 до 100
- [x] от −20 до 19
- [ ] от 1 до 10
- [ ] от −100 до 100
> По умолчанию 0. −20 — самый высокий приоритет, 19 — самый низкий.

### Какой процесс получит больше процессорного времени при прочих равных?
- [x] С nice −5
- [ ] С nice 10
- [ ] С nice 19
- [ ] Nice не влияет на распределение CPU
> Меньше nice — выше приоритет, процесс «менее вежливый».

### Может ли обычный пользователь выполнить renice -n -10 для своего процесса?
- [ ] Да, это его процесс
- [x] Нет, понижать nice (повышать приоритет) может только root
- [ ] Да, но только для фоновых процессов
- [ ] Нет, renice работает только для служб
> Повышать nice своим процессам (понижать им приоритет) можно без root.

### Как запустить бэкап с минимальной нагрузкой на CPU и диск для остальных процессов?
- [x] nice -n 19 ionice -c3 ./backup.sh
- [ ] sudo renice -20 ./backup.sh
- [ ] nohup ./backup.sh
- [ ] ./backup.sh &
> nice влияет на CPU, ionice -c3 (idle) — на диск.

### Приложение должно работать постоянно и подниматься после перезагрузки. Как его правильно запустить?
- [ ] nohup app &
- [ ] В сессии tmux
- [x] Оформить как службу systemd с автозапуском и Restart=
- [ ] Через screen -dm
> nohup и tmux — для разовых ручных задач, а не для продакшена.

### Какая колонка в top показывает значение nice процесса?
= NI
> PR — итоговый приоритет в планировщике.
