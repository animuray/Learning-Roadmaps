# Сломанный сервер — процессы и службы

«Служба не работает» — самая частая жалоба на сервере. Причина почти всегда находится за три команды, если идти по порядку и читать вывод.

## Алгоритм «служба не работает»

1. `systemctl status имя` — состояние, код выхода (`status=203/EXEC`, `status=1/FAILURE`), последние строки журнала, PID.
2. `journalctl -u имя -n 50 --no-pager` — что программа сказала перед смертью. `-b` — с текущей загрузки, `-f` — следить.
3. `systemctl cat имя` — **итоговый** юнит со всеми drop-in: что именно запускается, от кого, с каким окружением.
4. Ресурсы: порт (`ss -ltnp`), права на файлы (`namei -l`), место (`df -h`), память (OOM в `journalctl -k`).
5. Починить → `systemctl daemon-reload` (если менялся юнит) → `systemctl restart` → снова `status`. Если служба упёрлась в лимит перезапусков — `systemctl reset-failed`.

## Коды выхода systemd

| Код в status | Значит | Где искать |
| --- | --- | --- |
| `203/EXEC` | не удалось запустить файл из `ExecStart` | путь, право x, shebang |
| `217/USER` | пользователя из `User=` нет | `id пользователь` |
| `200/CHDIR` | нет `WorkingDirectory` | путь каталога |
| `226/NAMESPACE` | не создать изоляцию (`ReadWritePaths` на несуществующий путь и т.п.) | директивы `Protect*`, пути |
| `1/FAILURE` | программа сама завершилась с ошибкой | журнал службы |
| `start-limit-hit` | слишком частые падения | причина в журнале + `reset-failed` |

### Служба не поднялась после обновления

После выкладки новой версии служба **`lab-api`** не запускается. Файлы приложения перекладывать нельзя — новая версия лежит там, куда её положил деплой. Служба должна работать и запускаться при загрузке.

```bash setup
lab_unit lab-api
rm -rf /opt/api /etc/systemd/system/lab-api.service /etc/systemd/system/lab-api.service.d
mkdir -p /opt/api/releases/2.4.1
cat > /opt/api/releases/2.4.1/api-server <<'EOF'
#!/usr/bin/env python3
from http.server import BaseHTTPRequestHandler, HTTPServer
class H(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200); self.end_headers(); self.wfile.write(b"api 2.4.1\n")
HTTPServer(("127.0.0.1", 8093), H).serve_forever()
EOF
chmod 755 /opt/api/releases/2.4.1/api-server
ln -sfn /opt/api/releases/2.4.1 /opt/api/current
cat > /etc/systemd/system/lab-api.service <<'EOF'
[Unit]
Description=API server

[Service]
ExecStart=/opt/api/bin/api-server
Restart=on-failure

[Install]
WantedBy=multi-user.target
EOF
systemctl daemon-reload
systemctl enable lab-api >/dev/null 2>&1
systemctl start lab-api >/dev/null 2>&1; true
```

```bash check
[ -x /opt/api/releases/2.4.1/api-server ] && [ "$(readlink /opt/api/current)" = /opt/api/releases/2.4.1 ] || fail "Файлы приложения перемещены"
[ "$(systemctl is-active lab-api)" = active ] || fail "Служба lab-api не работает ($(systemctl show -p Result --value lab-api))"
[ "$(systemctl is-enabled lab-api)" = enabled ] || fail "Служба не запустится при загрузке"
r=$(curl -s --max-time 3 127.0.0.1:8093)
[ "$r" = "api 2.4.1" ] || fail "Служба активна, но не отвечает на 127.0.0.1:8093"
ok "lab-api работает: $r"
```

```text hint
1. Статус службы: код и состояние при последнем запуске. Есть таблица кодов в конспекте.
2. Итоговый unit-файл: что именно запускается. Существует ли этот путь?
3. Найти, где теперь лежит программа, исправить юнит (лучше через drop-in), перечитать конфигурацию systemd и перезапустить.
```

```bash solution
systemctl status lab-api --no-pager | head -6
systemctl cat lab-api
ls -l /opt/api/
sudo mkdir -p /etc/systemd/system/lab-api.service.d
printf '[Service]\nExecStart=\nExecStart=/opt/api/current/api-server\n' | sudo tee /etc/systemd/system/lab-api.service.d/path.conf >/dev/null
sudo systemctl daemon-reload
sudo systemctl restart lab-api
systemctl is-active lab-api
```

```text review
Причина: `ExecStart=/opt/api/bin/api-server` — такого файла нет: деплой кладёт релизы в `releases/<версия>` и переключает ссылку `current`. `status` показывал `status=203/EXEC`.

- Ссылка `current` на релиз — классическая схема (Capistrano, Ansible): переключение версии и откат — смена ссылки и `restart`. В юните всегда путь через `current`.
- В drop-in для замены `ExecStart` сначала пустая строка `ExecStart=` — иначе для `Type=simple` будет ошибка «несколько ExecStart».
- После правки юнита без `daemon-reload` systemd продолжит запускать старый вариант и честно предупредит в `status`: «unit file changed on disk».
```

### Чужой процесс на порту

Служба **`lab-web2`** (веб-сервер на `127.0.0.1:8091`) не может стартовать и перезапускается по кругу. Сделайте так, чтобы она работала и порт `8091` был **её**.

```bash setup
lab_unit lab-web2; lab_unit lab-squat2
mkdir -p /srv/web2 && echo "web2 ok" > /srv/web2/index.html
cat > /etc/systemd/system/lab-web2.service <<'EOF'
[Unit]
Description=Web2

[Service]
ExecStart=/usr/bin/python3 -m http.server 8091 --bind 127.0.0.1 --directory /srv/web2
Restart=always
RestartSec=3
EOF
systemctl daemon-reload
systemd-run -q --unit=lab-squat2 -p User=guest python3 -m http.server 8091 --bind 127.0.0.1 --directory /tmp 2>/dev/null \
  || { id guest >/dev/null 2>&1 || useradd -m guest; systemd-run -q --unit=lab-squat2 -p User=guest python3 -m http.server 8091 --bind 127.0.0.1 --directory /tmp; }
sleep 1
systemctl start lab-web2 >/dev/null 2>&1; true
```

```bash check
[ "$(systemctl is-active lab-web2)" = active ] || fail "Служба lab-web2 не работает"
pid=$(systemctl show -p MainPID --value lab-web2)
owner=$(ss -ltnpH 'sport = :8091' | grep -oE 'pid=[0-9]+' | head -1 | cut -d= -f2)
[ "$owner" = "$pid" ] || fail "Порт 8091 слушает не lab-web2 (PID $owner, а у службы $pid)"
[ "$(curl -s --max-time 3 127.0.0.1:8091/)" = "web2 ok" ] || fail "На 8091 отвечает не lab-web2"
ok "порт 8091 принадлежит lab-web2 (PID $pid)"
```

```text hint
1. В журнале службы видна причина падения при старте.
2. Найти, какой процесс держит порт, и кто его запустил (он может быть оформлен как временная служба).
3. Остановить его, затем убедиться, что служба поднялась (она перезапускается сама) или перезапустить её.
```

```bash solution
journalctl -u lab-web2 -n 5 --no-pager
sudo ss -ltnp 'sport = :8091'
pid=$(sudo ss -ltnpH 'sport = :8091' | grep -oE 'pid=[0-9]+' | head -1 | cut -d= -f2)
systemctl status "$pid" --no-pager | head -3
sudo systemctl stop lab-squat2
sudo systemctl restart lab-web2
sleep 1
curl -s 127.0.0.1:8091/
```

```text review
Причина: порт 8091 занял посторонний процесс (временная служба `lab-squat2` от пользователя guest). lab-web2 падала с «Address already in use» и перезапускалась по кругу.

- `ss -ltnp` — кто слушает порт (с `sudo` — и чужие процессы). `systemctl status <PID>` показывает, к какой службе (cgroup) принадлежит процесс: убьёте процесс, принадлежащий службе с `Restart=always`, — он вернётся.
- Правильно останавливать службу (`systemctl stop`), а не убивать процесс: иначе её перезапустит systemd.
- Профилактика: фиксировать порты в документации/конфиге, для своих приложений — сокет-активация systemd или явный `After=`/`Conflicts=`.
```

```text notes
kill\s+-9 => Процесс убивали SIGKILL — если он принадлежит службе с Restart, он вернётся. Найдите и остановите его службу.
```

## Тест

### systemctl status показывает «status=203/EXEC». Что это значит?
- [ ] Программа завершилась с ошибкой 203
- [x] systemd не смог запустить файл из ExecStart: нет файла, нет права x или неверный shebang
- [ ] Не хватает памяти
- [ ] Служба остановлена вручную
> 203/EXEC — ошибка самого запуска, до выполнения программы.

### Какой командой посмотреть итоговый unit-файл службы со всеми drop-in?
= systemctl cat
= systemctl cat lab-api
> `systemctl cat` показывает основной файл и все дополнения в порядке применения.

### Вы поправили unit-файл и сделали restart, но запускается старая версия. Что забыли?
- [ ] enable
- [x] systemctl daemon-reload
- [ ] reset-failed
- [ ] Перезагрузить сервер
> systemd читает unit-файлы в память; после правки — `daemon-reload`.

### Как в drop-in заменить ExecStart службы типа simple?
- [ ] Просто написать новую строку ExecStart=
- [x] Сначала пустая строка ExecStart=, затем новая ExecStart=...
- [ ] Удалить основной unit-файл
- [ ] Это невозможно
> Пустое значение сбрасывает список команд; без него будет ошибка «more than one ExecStart».

### Служба падает с «Address already in use». С чего начать?
- [ ] Перезагрузить сервер
- [x] Найти процесс, который слушает порт: ss -ltnp
- [ ] Сменить порт службы на случайный
- [ ] kill -9 всех процессов python
> Сначала узнать, кто занял порт и почему, — может быть, это вторая копия той же службы.

### Вы убили процесс на порту, а через пару секунд он снова там. Почему?
- [ ] Это вирус
- [x] Процесс принадлежит службе с Restart=always — systemd его перезапустил
- [ ] Порт закреплён ядром
- [ ] kill не работает от sudo
> Нужно остановить саму службу (`systemctl stop`), найти её можно через `systemctl status <PID>`.

### Как узнать, какой службе systemd принадлежит процесс с PID 4321?
= systemctl status 4321
> systemctl status принимает PID и показывает юнит и его cgroup.

### Служба упала 5 раз подряд, и теперь systemctl start сразу отказывает. Что сделать после исправления причины?
- [ ] Переустановить systemd
- [x] systemctl reset-failed имя, затем start
- [ ] Удалить unit-файл и создать заново
- [ ] daemon-reload
> Сработал StartLimitBurst; `reset-failed` сбрасывает счётчик неудач.

### Где искать, что программа написала перед падением?
= journalctl -u
= journalctl -u имя
> Вывод службы (stdout и stderr) попадает в журнал: `journalctl -u имя -n 50`.

### Деплой кладёт версии в /opt/app/releases/<версия> и переключает ссылку /opt/app/current. Что писать в ExecStart?
- [ ] Путь к конкретной версии
- [x] Путь через /opt/app/current
- [ ] Относительный путь
- [ ] Ничего — systemd найдёт сам
> Переключение и откат версии — смена ссылки и restart, юнит не меняется.

### Код 217/USER в status службы означает:
- [ ] Служба запущена не от root
- [x] Пользователя из User= не существует
- [ ] У пользователя нет пароля
- [ ] Пользователь не в группе sudo
> systemd не смог переключиться на указанного пользователя.

### Как следить за журналом службы в реальном времени?
- [ ] journalctl -u имя -n
- [x] journalctl -u имя -f
- [ ] tail -f /var/log/syslog — единственный способ
- [ ] systemctl watch имя
> `-f` (follow) — как `tail -f` для журнала.
