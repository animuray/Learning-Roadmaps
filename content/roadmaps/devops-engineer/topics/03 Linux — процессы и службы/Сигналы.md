# Сигналы

**Сигнал** — асинхронное уведомление, которое ядро доставляет процессу: «завершись», «перечитай конфиг», «тебя прервали с клавиатуры», «у тебя завершился ребёнок». Сигналы отправляют ядро, другие процессы (`kill`) и терминал (Ctrl+C).

В Linux 64 сигнала: стандартные с номерами 1–31 и сигналы реального времени 34–64. Знать нужно десяток. Список: `kill -l`.

## Главные сигналы

| № | Сигнал | Откуда берётся | Действие по умолчанию / применение |
| --- | --- | --- | --- |
| 1 | **SIGHUP** | Закрыли терминал (hang up) | Завершение. Демоны по договорённости **перечитывают конфиг** |
| 2 | **SIGINT** | Ctrl+C | Прерывание |
| 3 | SIGQUIT | Ctrl+\ | Завершение с core dump |
| 9 | **SIGKILL** | `kill -9` | Немедленное уничтожение. **Нельзя перехватить** |
| 10 | **SIGUSR1** | Пользовательский | Смысл задаёт программа: nginx переоткрывает лог-файлы |
| 12 | **SIGUSR2** | Пользовательский | Смысл задаёт программа |
| 15 | **SIGTERM** | `kill` по умолчанию | Вежливая просьба завершиться |
| 17 | SIGCHLD | Ядро | Дочерний процесс завершился или остановился |
| 18 | SIGCONT | `kill -CONT`, `fg`, `bg` | Продолжить остановленный процесс |
| 19 | SIGSTOP | `kill -STOP` | Остановить. **Нельзя перехватить** |
| 20 | SIGTSTP | Ctrl+Z | Остановить (можно перехватить) |

Номера приведены для x86 и ARM — самых распространённых архитектур. В скриптах надёжнее писать имена: `kill -TERM`, `kill -HUP`.

## Как процесс реагирует

Для каждого сигнала процесс может:

1. выполнить **действие по умолчанию** — завершиться, остановиться или проигнорировать;
2. **проигнорировать** сигнал;
3. **перехватить** его своим обработчиком: например, корректно завершиться или перечитать конфиг.

**SIGKILL** и **SIGSTOP** нельзя ни перехватить, ни проигнорировать — их обрабатывает ядро.

## Сигналы в жизни DevOps

- **Перезагрузка конфига без остановки:** `systemctl reload nginx` и `nginx -s reload` отправляют мастер-процессу nginx SIGHUP. Он перечитывает конфиг и плавно заменяет рабочие процессы, не обрывая соединения.
- **Ротация логов:** после переименования лог-файла nginx получает SIGUSR1 и открывает новый файл (так настроен `postrotate` в logrotate).
- **Корректная остановка:** systemd, `docker stop` и Kubernetes отправляют **SIGTERM** и ждут: Docker по умолчанию 10 секунд, Kubernetes — `terminationGracePeriodSeconds`, по умолчанию 30. Потом приходит **SIGKILL**. Приложение должно ловить SIGTERM: перестать принимать новые запросы, доработать текущие и выйти.
- **SIGHUP при закрытии терминала** завершает запущенные из него процессы. Как этого избежать, разберём в теме «Фоновые процессы».

## trap — обработка сигналов в bash

```bash
#!/usr/bin/env bash
TMP=$(mktemp)

cleanup() {
  echo "Убираю за собой"
  rm -f "$TMP"
}
trap cleanup EXIT              # выполнится при любом выходе из скрипта
trap 'echo "Ctrl+C пойман"; exit 130' INT
trap 'echo "Получен SIGTERM"; exit 143' TERM
trap '' HUP                    # игнорировать SIGHUP

echo "PID $$, работаю..."
sleep 1000
```

- `EXIT` — псевдосигнал bash: срабатывает при любом выходе из скрипта. Идеален для удаления временных файлов и снятия блокировок.
- Код возврата процесса, убитого сигналом, равен **128 + номер сигнала**: 130 — SIGINT, 137 — SIGKILL, 143 — SIGTERM. Код **137** вы будете часто видеть в Docker и Kubernetes: это SIGKILL, нередко от OOM Killer.

## Отправка сигналов

```bash
kill -HUP $(pidof -s nginx)    # то же, что nginx -s reload (pidof -s вернёт один PID)
kill -USR1 1234
pkill -TERM -f myapp
systemctl kill -s HUP myapp    # всем процессам службы
```

lab_unit() { systemctl stop "$1" 2>/dev/null; systemctl reset-failed "$1" 2>/dev/null; true; }

### Применить конфиг без перезапуска

Служба `lab-greeter` при старте читает `/etc/greeter.conf` и пишет в журнал приветствие. Поменяйте в конфиге приветствие на `greeting=Добрый день` и сделайте так, чтобы **работающий** процесс применил новый конфиг. Перезапускать службу нельзя — у неё долгий прогрев. Программа умеет перечитывать конфиг по стандартному сигналу.

```bash setup
lab_unit lab-greeter
cat > /opt/lab/greeter <<'EOF'
#!/bin/bash
# Читает конфиг при старте и по SIGHUP; каждые 2 секунды пишет текущее приветствие в журнал.
load() { greeting=$(sed -n 's/^greeting=//p' /etc/greeter.conf); echo "config loaded: $greeting"; }
trap load HUP
load
while true; do echo "current: $greeting"; sleep 2 & wait $!; done
EOF
chmod 755 /opt/lab/greeter
echo 'greeting=Привет' > /etc/greeter.conf
systemd-run -q --unit=lab-greeter /opt/lab/greeter
sleep 1
systemctl show -p MainPID --value lab-greeter > /var/lib/lab/greeter-pid
```

```bash check
pid=$(cat /var/lib/lab/greeter-pid)
[ "$(systemctl show -p MainPID --value lab-greeter)" = "$pid" ] || fail "У службы другой PID — её перезапустили или остановили"
grep -qx 'greeting=Добрый день' /etc/greeter.conf || fail "В /etc/greeter.conf нет строки greeting=Добрый день"
journalctl -u lab-greeter --no-pager -o cat | grep -q "config loaded: Добрый день" || fail "Процесс ещё не перечитал конфиг: в журнале службы нет «config loaded: Добрый день»"
ok "PID $pid тот же; $(journalctl -u lab-greeter --no-pager -o cat | grep 'config loaded' | tail -1)"
```

```text hint
1. Исправить конфиг (файл принадлежит root).
2. Узнать главный PID службы.
3. Отправить процессу сигнал, который по традиции означает «перечитай настройки» (его исходное значение — «терминал отключился»). Systemd умеет отправить сигнал процессам службы и сам.
4. Посмотреть журнал службы.
```

```bash solution
echo 'greeting=Добрый день' | sudo tee /etc/greeter.conf >/dev/null
sudo systemctl kill -s HUP lab-greeter
sleep 1
journalctl -u lab-greeter -n 3 --no-pager -o cat
```

```text review
Эталон: правка конфига → `sudo kill -HUP <PID>` или `sudo systemctl kill -s HUP lab-greeter`.

- SIGHUP («hang up») исторически — разрыв терминала; у демонов без терминала его договорились использовать как «перечитай конфигурацию». Так работают nginx, sshd, rsyslog, haproxy, PostgreSQL.
- Именно это делает `systemctl reload` — для служб, где в юните описан `ExecReload=/bin/kill -HUP $MAINPID`.
- Перед reload проверяйте конфиг: `nginx -t`, `sshd -t`. Сломанный конфиг при reload обычно игнорируется со строчкой в логе, при restart — служба не поднимется.
- Не всякая программа понимает HUP: если обработчика нет, действие по умолчанию — **завершение** процесса. Смотрите документацию.
```

```text notes
systemctl\s+restart\s+lab-greeter => Служба перезапускалась — по условию так нельзя. Перечитать конфиг без перезапуска — сигнал HUP.
```

### Скрипт, который убирает за собой

Напишите скрипт `~/worker.sh`, который:

1. при старте создаёт lock-файл `/tmp/worker.lock` (с любым содержимым, например своим PID);
2. работает бесконечно (например, `sleep` в цикле);
3. при получении **SIGTERM** удаляет `/tmp/worker.lock` и завершается с кодом 0.

```bash setup
rm -f /home/student/worker.sh /tmp/worker.lock
```

```bash check
s=/home/student/worker.sh
[ -f $s ] || fail "Нет ~/worker.sh"
[ -x $s ] || fail "~/worker.sh нельзя запустить: нет права на выполнение"
rm -f /tmp/worker.lock
su - student -c "setsid $s </dev/null >/dev/null 2>&1 & echo \$! > /tmp/lab-worker.pid"
sleep 1.5
pid=$(cat /tmp/lab-worker.pid); rm -f /tmp/lab-worker.pid
kill -0 $pid 2>/dev/null || fail "Скрипт завершился сам, не дожидаясь сигнала"
[ -f /tmp/worker.lock ] || { kill -9 $pid; fail "После запуска нет /tmp/worker.lock"; }
kill -TERM $pid
for i in $(seq 25); do kill -0 $pid 2>/dev/null || break; sleep 0.2; done
if kill -0 $pid 2>/dev/null; then kill -9 $pid; pkill -KILL -P $pid 2>/dev/null; fail "Через 5 секунд после SIGTERM скрипт всё ещё работает"; fi
[ -f /tmp/worker.lock ] && { rm -f /tmp/worker.lock; fail "Скрипт завершился, но /tmp/worker.lock остался"; }
ok "lock создаётся при старте и удаляется по SIGTERM"
```

```text hint
1. В начале скрипта — интерпретатор в первой строке и создание lock-файла.
2. Встроенная команда оболочки позволяет назначить действие на сигнал: удалить файл и выйти с нулевым кодом. Её ставят до основной работы.
3. Бесконечный цикл. Учтите: пока выполняется внешняя команда (sleep), оболочка ждёт её и обрабатывает сигнал только после её завершения — короткий sleep или ожидание фонового sleep решают это.
```

```bash solution
cat > ~/worker.sh <<'EOF'
#!/bin/bash
lock=/tmp/worker.lock
echo $$ > "$lock"
trap 'rm -f "$lock"; exit 0' TERM INT
while true; do
    sleep 1 & wait $!
done
EOF
chmod +x ~/worker.sh
```

```text review
Эталон — `trap 'rm -f "$lock"; exit 0' TERM INT` до основного цикла.

- `trap` ставят **до** работы: сигнал может прийти в любой момент.
- Пока bash ждёт внешнюю команду (`sleep 60`), обработчик выполнится только после её завершения. Приём `sleep 1 & wait $!` делает реакцию мгновенной: `wait` прерывается сигналом.
- `trap ... EXIT` срабатывает при любом выходе (кроме SIGKILL) — удобно для временных файлов: `tmp=$(mktemp); trap 'rm -f "$tmp"' EXIT`.
- Именно так должно вести себя приложение в контейнере: Docker и Kubernetes шлют SIGTERM и ждут (10 и 30 секунд по умолчанию), потом SIGKILL. Скрипт без обработчика в роли PID 1 вообще игнорирует SIGTERM — контейнер останавливается долго.
```

- [ ] Для переключения пользователей

- [ ] Приложение вернуло ошибку 137

- [ ] Не найден образ
- [ ] Нет прав на запуск
> Код процесса, убитого сигналом, равен 128 + номер сигнала. 143 — SIGTERM, 130 — SIGINT.

### Как в bash-скрипте удалить временный файл при любом выходе из скрипта?
- [ ] trap 'rm -f "$TMP"' KILL
- [x] trap 'rm -f "$TMP"' EXIT
- [ ] on exit rm -f "$TMP"
- [ ] signal EXIT rm -f "$TMP"
> EXIT — псевдосигнал bash. На KILL поставить обработчик невозможно.

### Что делают docker stop и Kubernetes при остановке контейнера?
- [ ] Сразу отправляют SIGKILL
- [x] Отправляют SIGTERM, ждут таймаут (10 и 30 секунд по умолчанию) и затем отправляют SIGKILL
- [ ] Отправляют SIGHUP
- [ ] Ставят процесс на паузу
> Приложение должно обрабатывать SIGTERM, иначе его каждый раз будут убивать жёстко.

- [ ] Отправляет SIGHUP себе
- [x] Заставляет скрипт игнорировать SIGHUP
- [ ] Восстанавливает обработчик по умолчанию
- [ ] Выводит список сигналов
> Пустая команда — игнорировать. Вернуть поведение по умолчанию: `trap - HUP`.
