# Резюме и портфолио DevOps-инженера

Резюме читают 20–40 секунд: сначала рекрутер (совпадают ли ключевые слова и опыт), потом инженер (что вы реально делали). Задача резюме — получить приглашение на собеседование, а портфолио — дать инженеру повод задать вопросы именно о вашей работе.

## Структура резюме

1. **Заголовок:** желаемая должность — «DevOps-инженер» (или «Junior DevOps / SRE»), город, формат работы, контакты (телеграм, почта, GitHub).
2. **О себе** — 2–3 строки: кто вы, что умеете, что ищете. Без «стрессоустойчив и коммуникабелен».
3. **Навыки** — сгруппированные списки, только то, о чём готовы говорить на собеседовании:
   - Linux (Ubuntu, systemd, диагностика), сети (TCP/IP, DNS, nginx);
   - контейнеры (Docker, Compose), оркестрация (Kubernetes, Helm);
   - CI/CD (GitLab CI, GitHub Actions), IaC (Terraform, Ansible);
   - мониторинг и логи (Prometheus, Grafana, Loki), базы (PostgreSQL, Redis);
   - скрипты (Bash, Python), Git.
4. **Опыт** — по местам работы, свежее сверху; если коммерческого опыта DevOps нет — **проекты** (см. ниже) и смежный опыт (админ, разработчик, тестировщик, поддержка).
5. **Образование и курсы** — кратко.

Объём — **1–2 страницы**. PDF и профиль на hh.ru/Хабр Карьере с тем же текстом.

## Формулировки: действие → инструмент → результат

| Плохо | Хорошо |
| --- | --- |
| Работал с Docker | Упаковал приложение (React + FastAPI + PostgreSQL) в Docker Compose; образ бэкенда уменьшен с 1,1 ГБ до 140 МБ multi-stage сборкой |
| Настраивал CI/CD | Настроил GitLab CI: линтер, тесты, сборка образа, деплой по SSH на staging и prod с ручным подтверждением; время от коммита до staging — 6 минут |
| Знаю Kubernetes | Развернул приложение в k3s через Helm-чарт с values для dev и prod, пробы, HPA, Ingress с TLS; деплой через Argo CD из Git |
| Мониторинг | Поднял Prometheus, Grafana и Alertmanager; дашборд по 4 золотым сигналам, алерты в Telegram с runbook |

- Глагол в прошедшем времени («настроил», «автоматизировал», «сократил»), конкретный инструмент и **число**: время, размер, количество серверов, процент.
- Учебный проект — честно называйте учебным/пет-проектом. Ложь всплывает на первом же уточняющем вопросе.

## Ключевые слова

Рекрутер и поиск hh.ru ищут по словам из вакансии. Прочитайте 10–20 вакансий джуна/мидла, выпишите повторяющиеся требования и убедитесь, что **те, что у вас есть**, написаны в резюме так же, как в вакансии (`Kubernetes`, а не только `k8s`; `CI/CD`, `GitLab CI`).

## Портфолио на GitHub

Лучшее портфолио после этого роадмапа — **сквозной проект**: одно приложение, которое прошло весь путь.

```
my-shop/                     # или несколько репозиториев с понятными именами
├── README.md                # схема, стек, как запустить, что сделано
├── app/                     # фронтенд, бэкенд
├── docker/                  # Dockerfile, compose.yaml
├── .gitlab-ci.yml           # или .github/workflows/
├── ansible/                 # настройка серверов
├── terraform/               # инфраструктура в облаке
├── k8s/ или helm/           # манифесты, чарт
├── monitoring/              # Prometheus, Grafana, алерты
└── docs/
    ├── architecture.png
    └── incidents.md         # разборы поломок: симптом → диагностика → причина → решение
```

README — это витрина: за минуту должно быть понятно, **что** сделано и **как** проверить.

- схема (картинка) и стек;
- запуск в одну-две команды (`docker compose up -d`, `make deploy`);
- что автоматизировано и почему так (компромиссы);
- скриншоты дашбордов и пайплайна;
- раздел «Что бы я улучшил» — показывает зрелость лучше, чем идеальный проект.

Чего избегать: десятки форков и пустых репозиториев, секреты в истории (проверьте `gitleaks`), один гигантский коммит «initial», код без README.

## Профиль и активность

- GitHub-профиль с README: кто вы и ссылки на 2–3 главных проекта (закрепить — Pin).
- Конспект в Git, который вы ведёте с первой темы роадмапа, — тоже портфолио: регулярные коммиты показывают системность.
- Статья на Хабре или в блоге о решённой проблеме («Как я уменьшил образ в 8 раз», «Разбор: почему падал под») — сильный сигнал для джуна.

## Отклик

- Короткое сопроводительное письмо под **конкретную** вакансию: 3–5 предложений, почему вы и что из требований уже делали (со ссылкой на проект).
- Откликайтесь регулярно и много: 5–10 откликов в день — нормальная воронка для джуна; ведите таблицу (компания, дата, этап, обратная связь).
- Отказ без объяснений — норма рынка; просите обратную связь после технического собеседования, она ценнее всего.

## Практика

- [ ] Выписать требования из 15 вакансий и составить свою таблицу «требование → где я это делал»
- [ ] Написать резюме по структуре выше; каждую строку опыта — через действие, инструмент и число
- [ ] Оформить README сквозного проекта: схема, стек, запуск, разборы инцидентов
- [ ] Проверить репозитории на секреты (`gitleaks detect`) и закрепить 2–3 главных проекта в профиле
- [ ] Дать резюме на ревью знакомому инженеру или в профильном чате и учесть замечания

## Тест

### Сколько времени рекрутер обычно тратит на первый просмотр резюме?
- [ ] 5–10 минут
- [x] Около полуминуты
- [ ] Час
- [ ] Читает всё дважды
> Поэтому главное — в заголовке, навыках и первых строках опыта.

### Какая формулировка опыта сильнее?
- [ ] «Работал с Docker и CI/CD»
- [x] «Настроил GitLab CI со сборкой образа и деплоем на staging; время от коммита до staging — 6 минут»
- [ ] «Знаю Docker, GitLab, Kubernetes»
- [ ] «Ответственный, обучаемый»
> Действие, инструмент и измеримый результат.

### Что делать, если коммерческого опыта DevOps нет?
- [ ] Придумать опыт
- [x] Описать сквозной учебный проект и смежный опыт (админ, разработчик, поддержка), честно указав, что проект учебный
- [ ] Не указывать проекты
- [ ] Перечислить все пройденные курсы
> Проекты дают инженеру повод для вопросов; ложь всплывает на собеседовании.

### Зачем сверять резюме с текстами вакансий?
- [ ] Чтобы скопировать вакансию в резюме
- [x] Поиск и рекрутеры ищут по ключевым словам — ваши реальные навыки должны быть названы так же, как в вакансиях
- [ ] Это требование hh.ru
- [ ] Чтобы указать все технологии из вакансий
> Указывайте только то, о чём готовы говорить.

### Какой объём резюме оптимален для джуна или мидла?
- [ ] 5 страниц
- [x] 1–2 страницы
- [ ] Полстраницы без опыта
- [ ] Чем больше, тем лучше
> Лишнее отвлекает от главного.

### Что важнее всего в README проекта-портфолио?
- [ ] Список всех технологий мира
- [x] Схема, стек, запуск в пару команд и что сделано — понятно за минуту
- [ ] Лицензия
- [ ] Эмодзи
> README — витрина проекта для занятого инженера.

### Почему в портфолио полезен раздел с разборами инцидентов?
- [ ] Он увеличивает число строк
- [x] Показывает умение диагностировать: симптом → команды → причина → решение — то, что спрашивают на собеседованиях
- [ ] Так требуют работодатели
- [ ] Чтобы скрыть ошибки
> Траблшутинг — ядро работы DevOps и любимая тема собеседований.

### Что нужно проверить в репозиториях перед отправкой ссылок работодателю?
- [ ] Число звёзд
- [x] Что в истории нет секретов (токены, пароли, ключи) — например, gitleaks
- [ ] Цвет аватарки
- [ ] Что все коммиты сделаны ночью
> Секрет в истории публичного репозитория — минус и реальная уязвимость.

### Как писать навыки в резюме?
- [ ] Одной строкой через запятую всё подряд
- [x] Группами (Linux, контейнеры, CI/CD, IaC, мониторинг…) и только то, о чём готовы говорить
- [ ] Только с процентами владения
- [ ] Не писать вовсе
> Группы читаются быстро; каждое слово может стать вопросом.

### Каким должно быть сопроводительное письмо?
- [ ] Шаблонным для всех вакансий
- [x] Коротким и под конкретную вакансию: почему вы и что из требований уже делали, со ссылкой на проект
- [ ] Длиной в страницу
- [ ] Его не читают, можно не писать
> 3–5 предложений, показывающих, что вы прочитали вакансию.

### Что показывает раздел «Что бы я улучшил» в README?
- [ ] Что проект плохой
- [x] Понимание компромиссов и направлений развития — признак инженерной зрелости
- [ ] Что автор не закончил работу
- [ ] Ничего
> Идеальных проектов нет; важно понимать ограничения своего решения.

### Что делать после отказа на техническом этапе?
- [ ] Ничего
- [x] Попросить обратную связь и закрыть пробелы, которые она показала
- [ ] Перестать откликаться
- [ ] Спорить с интервьюером
> Обратная связь после технического собеседования — самый ценный материал для подготовки.
