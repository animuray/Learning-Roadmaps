# Роли

Когда плейбук разрастается до сотен строк, его делят на **роли** — самостоятельные переиспользуемые модули с понятным интерфейсом: «роль nginx», «роль postgresql», «роль node_exporter». Одна роль подключается в разные плейбуки и проекты.

## Структура роли

```
roles/
└── nginx/
    ├── tasks/
    │   └── main.yml        # задачи роли (точка входа)
    ├── handlers/
    │   └── main.yml        # handlers роли
    ├── templates/
    │   └── site.conf.j2    # шаблоны для модуля template
    ├── files/
    │   └── index.html      # файлы для copy
    ├── defaults/
    │   └── main.yml        # переменные по умолчанию — низший приоритет
    ├── vars/
    │   └── main.yml        # внутренние переменные роли — высокий приоритет
    ├── meta/
    │   └── main.yml        # метаданные и зависимости
    └── README.md
```

```bash
ansible-galaxy role init roles/nginx        # создать скелет
```

- В каждом каталоге Ansible автоматически ищет `main.yml`.
- В задачах роли пути пишут **относительно роли**: `src: site.conf.j2` (без `templates/`).
- Пустые каталоги можно удалить.

## defaults и vars

`roles/nginx/defaults/main.yml` — **интерфейс роли**, всё, что можно настроить:

```yaml
nginx_worker_processes: auto
nginx_server_name: _
nginx_listen_port: 80
nginx_upstreams: []
```

`roles/nginx/vars/main.yml` — константы, которые пользователь роли менять не должен:

```yaml
nginx_conf_dir: /etc/nginx/conf.d
```

Переменные роли принято **префиксовать именем роли** (`nginx_...`) — чтобы не столкнуться с переменными других ролей.

## Подключение ролей

```yaml
- name: Веб-серверы
  hosts: web
  become: true
  roles:
    - common
    - role: nginx
      vars:
        nginx_server_name: app.example.com
        nginx_listen_port: 8080
    - role: node_exporter
      tags: [monitoring]
```

Внутри задач:

```yaml
- name: Статическое подключение
  ansible.builtin.import_role:
    name: nginx

- name: Динамическое подключение по условию
  ansible.builtin.include_role:
    name: postgresql
  when: install_db | bool
```

| | `import_role` / `roles:` | `include_role` |
| --- | --- | --- |
| Когда обрабатывается | При разборе плейбука (статически) | Во время выполнения (динамически) |
| `--list-tasks`, `--tags` | Видны задачи роли | Задачи видны, только когда include выполнится |
| `loop` | Нельзя | Можно |

Порядок выполнения плея: `pre_tasks` → handlers → `roles` → `tasks` → handlers → `post_tasks` → handlers.

## Зависимости

`roles/app/meta/main.yml`:

```yaml
dependencies:
  - role: common
  - role: docker
```

Зависимости выполняются **перед** ролью и по умолчанию один раз за плей.

## Ansible Galaxy и коллекции

**Galaxy** — каталог ролей и коллекций сообщества (например, популярные роли geerlingguy). `requirements.yml`:

```yaml
roles:
  - name: geerlingguy.docker
    version: 7.4.1
  - name: company.base
    src: https://gitlab.example.com/ansible/role-base.git
    scm: git
    version: v2.0.0

collections:
  - name: community.docker
    version: ">=3.10.0"
  - name: ansible.posix
```

```bash
ansible-galaxy install -r requirements.yml
ansible-galaxy role list
ansible-galaxy collection list
```

- **Фиксируйте версии** — чужая роль может измениться.
- Читайте код ролей из Galaxy перед использованием: они выполняются с правами root на ваших серверах.
- **Коллекция** — формат распространения, который объединяет модули, плагины и роли (`community.docker`, `ansible.posix`).

## Типовая структура проекта

```
ansible/
├── ansible.cfg
├── requirements.yml
├── inventories/
│   ├── prod/
│   │   ├── hosts.yml
│   │   └── group_vars/
│   └── stage/
├── roles/
│   ├── common/
│   ├── docker/
│   ├── nginx/
│   └── app/
├── site.yml
├── web.yml
└── db.yml
```

`site.yml` импортирует остальные: `- ansible.builtin.import_playbook: web.yml`.

## Качество ролей

- **ansible-lint** — проверка на типичные ошибки и стиль (FQCN, `name` у задач, `mode` у файлов, неидемпотентные команды).
- **Molecule** — тестирование роли: поднять контейнер или ВМ, применить роль, **запустить второй раз и проверить идемпотентность**, выполнить проверки (verify), удалить окружение.
- Каждая роль — с README: что делает, переменные, пример.

## Лаборатория

«Серверы» — контейнеры `lab-web1`, `lab-web2`, `lab-db1`; проект `~/ansible-lab` с `ansible.cfg` и `inventory.ini` (группы `web` и `db`) готов.

```bash lib
# «Серверы» для Ansible — контейнеры lab-web1, lab-web2, lab-db1 (Python, sudo, sshd); подключение — community.docker.docker
lab_host_image() {
  docker image inspect lab-ansible-host:2 >/dev/null 2>&1 && return
  docker image inspect python:3.12-slim >/dev/null 2>&1 || docker pull -q python:3.12-slim >/dev/null
  docker build -q -t lab-ansible-host:2 - >/dev/null <<'EOF'
FROM python:3.12-slim
RUN apt-get update -q && apt-get install -y -q --no-install-recommends sudo openssh-server \
 && mkdir -p /run/sshd && rm -rf /var/lib/apt/lists/*
CMD ["sleep", "infinity"]
EOF
}
lab_hosts() { lab_host_image; for h in ${*:-lab-web1 lab-web2 lab-db1}; do docker rm -f $h >/dev/null 2>&1; docker run -d --name $h --hostname $h lab-ansible-host:2 >/dev/null; done; }
# lab_inv каталог — ansible.cfg и inventory.ini: web = lab-web1, lab-web2; db = lab-db1
lab_inv() {
  mkdir -p "$1"
  printf '[defaults]\ninventory = inventory.ini\ninterpreter_python = /usr/local/bin/python3\n' > "$1/ansible.cfg"
  printf '[web]\nlab-web1\nlab-web2\n\n[db]\nlab-db1\n\n[all:vars]\nansible_connection=community.docker.docker\n' > "$1/inventory.ini"
}
lab_own() { chown -R student:student "$1"; }
# lab_play каталог аргументы — ansible-playbook от имени ученика, вывод — в /tmp/lab-ans.log
lab_play() { su - student -c "cd $1 && ANSIBLE_NOCOLOR=1 ansible-playbook $2" > /tmp/lab-ans.log 2>&1; }
# сумма changed по всем хостам из итогов последнего прогона
lab_changed() { grep -E '^lab-[a-z0-9]+ +:' /tmp/lab-ans.log | grep -oE 'changed=[0-9]+' | cut -d= -f2 | awk '{s += $1} END {print s + 0}'; }
lab_anslog() { grep -E 'fatal|ERROR|FAILED|error' /tmp/lab-ans.log | head -2 | tr '\n' ' ' | cut -c1-300; }
```

```bash setup
lab_hosts
rm -rf /home/student/ansible-lab
lab_inv /home/student/ansible-lab
lab_own /home/student/ansible-lab
```

### Своя роль

Создайте в проекте роль **`motd`** (`~/ansible-lab/roles/motd`) со стандартной структурой:

- `defaults/main.yml` — переменная `motd_text` со значением **`Добро пожаловать`**;
- `templates/motd.j2` — шаблон `/etc/motd`: первая строка — `motd_text`, вторая — `Хост: <имя хоста из inventory>`;
- `tasks/main.yml` — задача, которая рендерит шаблон в `/etc/motd`.

Подключите роль в плейбуке `~/ansible-lab/roles.yml` для **всех** хостов, а для группы **`db`** переопределите текст на **`База данных: только для DBA`** — через `group_vars`, не трогая роль.

```bash check
d=/home/student/ansible-lab
for f in tasks/main.yml defaults/main.yml templates/motd.j2; do [ -f $d/roles/motd/$f ] || fail "В роли нет roles/motd/$f"; done
grep -q 'motd_text' $d/roles/motd/defaults/main.yml || fail "motd_text не задан в defaults роли"
grep -rq 'Только для DBA\|только для DBA' $d/roles && fail "Текст для db вписан в роль — его нужно переопределять снаружи"
[ -f $d/roles.yml ] || fail "Нет ~/ansible-lab/roles.yml"
lab_play $d roles.yml || fail "Плейбук падает: $(lab_anslog)"
for p in "lab-web1:Добро пожаловать" "lab-web2:Добро пожаловать" "lab-db1:База данных: только для DBA"; do
  h=${p%%:*}; t=${p#*:}
  got=$(docker exec $h cat /etc/motd 2>/dev/null | sed '/^[[:space:]]*$/d')
  [ "$got" = "$(printf '%s\nХост: %s' "$t" "$h")" ] || fail "/etc/motd на $h: «$(echo "$got" | tr '\n' '|')»"
done
lab_play $d roles.yml || fail "Повторный прогон падает"
[ "$(lab_changed)" = 0 ] || fail "Повторный прогон что-то меняет: changed=$(lab_changed)"
ok "роль motd работает, для db текст переопределён"
```

```text hint
1. Скелет роли создаёт утилита ansible-galaxy — подкоманда инициализации роли с путём.
2. В шаблоне — переменная текста и имя хоста из inventory (специальная переменная).
3. В плейбуке роли подключаются списком в разделе roles. Ansible ищет роли в каталоге roles рядом с плейбуком.
4. Значения из defaults роли — самые слабые: их перекрывает любая переменная группы.
```

```bash solution
cd ~/ansible-lab
ansible-galaxy role init roles/motd >/dev/null
echo 'motd_text: Добро пожаловать' > roles/motd/defaults/main.yml
printf '{{ motd_text }}\nХост: {{ inventory_hostname }}\n' > roles/motd/templates/motd.j2
cat > roles/motd/tasks/main.yml <<'EOF'
- name: Приветствие при входе
  ansible.builtin.template:
    src: motd.j2
    dest: /etc/motd
    mode: "0644"
EOF
mkdir -p group_vars
echo 'motd_text: "База данных: только для DBA"' > group_vars/db.yml
cat > roles.yml <<'EOF'
- name: Общие настройки
  hosts: all
  become: true
  roles:
    - motd
EOF
ansible-playbook roles.yml
```

```text review
Эталон — в «Решении».

- Структура роли: `tasks/` (что делать), `handlers/`, `templates/`, `files/`, `defaults/` (настраиваемые значения — **самый слабый** приоритет), `vars/` (внутренние константы — сильный приоритет, не для переопределения), `meta/` (зависимости, совместимость).
- Роль — переиспользуемый модуль: одни и те же `nginx`, `common`, `users` подключаются в разные проекты, а отличия задаются переменными снаружи.
- Значения для пользователя роли кладут в `defaults` и описывают в README роли. Переопределять — через group_vars/host_vars, не правя роль.
- Готовые роли — Ansible Galaxy (`ansible-galaxy install -r requirements.yml` с фиксированными версиями); тестировать свои — Molecule.
```

```text notes
\bvars/main\.yml => Значение по умолчанию положено в vars/ роли — у vars высокий приоритет, его не перекрыть через group_vars. Настраиваемые значения — в defaults/.
```

### Зависимость ролей

В `~/ansible-lab/roles` есть роль **`common`** — она создаёт пользователя `deploy`. Создайте роль **`app`**, которая создаёт каталог **`/opt/app`** с владельцем `deploy`, и объявите, что `app` **зависит** от `common` — так, чтобы плейбук `~/ansible-lab/app-role.yml` с одной лишь ролью `app` (для группы `web`) сам выполнял и `common`.

```bash setup
mkdir -p /home/student/ansible-lab/roles/common/tasks
cat > /home/student/ansible-lab/roles/common/tasks/main.yml <<'EOF'
- name: Пользователь deploy
  ansible.builtin.user:
    name: deploy
    shell: /bin/bash
EOF
cat > /home/student/ansible-lab/app-role.yml <<'EOF'
- name: Приложение
  hosts: web
  become: true
  roles:
    - app
EOF
rm -rf /home/student/ansible-lab/roles/app
lab_own /home/student/ansible-lab
```

```bash check
d=/home/student/ansible-lab
[ -f $d/roles/app/tasks/main.yml ] || fail "Нет роли app (roles/app/tasks/main.yml)"
[ -f $d/roles/app/meta/main.yml ] || fail "У роли app нет meta/main.yml"
python3 -c 'import yaml,sys; m=yaml.safe_load(open(sys.argv[1])) or {}; deps=[d if isinstance(d,str) else d.get("role", d.get("name")) for d in m.get("dependencies", [])]; sys.exit(0 if "common" in deps else 1)' $d/roles/app/meta/main.yml || fail "В meta/main.yml роли app нет зависимости от common"
grep -q 'common' $d/app-role.yml && fail "Роль common подключена в плейбуке вручную — она должна подтягиваться зависимостью"
lab_play $d app-role.yml || fail "Плейбук падает: $(lab_anslog)"
for h in lab-web1 lab-web2; do
  docker exec $h id deploy >/dev/null 2>&1 || fail "На $h нет deploy — роль common не выполнилась"
  [ "$(docker exec $h stat -c %U /opt/app 2>/dev/null)" = deploy ] || fail "На $h нет /opt/app с владельцем deploy"
done
ok "app подтянула common через meta/dependencies"
```

```text hint
1. Создать скелет роли app и задачу создания каталога.
2. Зависимости роли объявляются в её метаданных — списком ролей, которые выполнятся раньше неё.
3. Плейбук не трогать: в нём только роль app.
```

```bash solution
cd ~/ansible-lab
ansible-galaxy role init roles/app >/dev/null
cat > roles/app/tasks/main.yml <<'EOF'
- name: Каталог приложения
  ansible.builtin.file:
    path: /opt/app
    state: directory
    owner: deploy
    group: deploy
    mode: "0755"
EOF
cat > roles/app/meta/main.yml <<'EOF'
galaxy_info:
  author: student
  description: Приложение
  min_ansible_version: "2.14"
dependencies:
  - role: common
EOF
ansible-playbook app-role.yml
```

```text review
Эталон: `roles/app/meta/main.yml` → `dependencies: - role: common`.

- Зависимости выполняются **до** роли и один раз за плей (даже если на них ссылаются несколько ролей), если не задано `allow_duplicates`.
- Можно передать параметры: `- role: common` + `vars: {deploy_shell: /bin/zsh}`.
- Не увлекайтесь: глубокие цепочки зависимостей трудно отлаживать. Часто проще явный список ролей в плейбуке (`roles: [common, docker, app]`) — порядок виден сразу.
- `include_role`/`import_role` в задачах — подключить роль условно или в середине списка задач.
```

## Тест

### Где роль ищет задачи по умолчанию?
= tasks/main.yml
= roles/имя/tasks/main.yml
> Аналогично handlers/main.yml, defaults/main.yml и т. д.

### Чем defaults/main.yml отличается от vars/main.yml в роли?
- [x] defaults — значения по умолчанию с самым низким приоритетом, их легко переопределить
- [x] vars — внутренние переменные роли с высоким приоритетом, их сложно переопределить
- [ ] defaults выполняются раньше задач
- [ ] Это одно и то же
> Настраиваемые параметры роли кладут в defaults.

### Какая команда создаёт скелет новой роли?
- [ ] ansible-playbook --init-role nginx
- [x] ansible-galaxy role init nginx
- [ ] ansible-role create nginx
- [ ] ansible-doc role nginx
> В старых инструкциях встречается ansible-galaxy init.

### Как в задаче роли указать шаблон templates/site.conf.j2 этой роли?
- [ ] src: roles/nginx/templates/site.conf.j2 — всегда полный путь
- [x] src: site.conf.j2 — Ansible сам ищет в каталоге templates роли
- [ ] src: ../templates/site.conf.j2
- [ ] Шаблоны в роли не поддерживаются
> То же для files/ и модуля copy.

### Чем import_role отличается от include_role?
- [x] import_role подключает роль статически при разборе плейбука
- [x] include_role подключает роль динамически во время выполнения и поддерживает loop
- [ ] include_role работает быстрее
- [ ] import_role нельзя использовать с when
> С include_role задачи роли не видны в --list-tasks до выполнения.

### Где описываются зависимости роли от других ролей?
- [ ] tasks/main.yml
- [x] meta/main.yml в ключе dependencies
- [ ] defaults/main.yml
- [ ] requirements.txt
> Зависимости выполняются до самой роли.

### Как установить роли и коллекции, перечисленные в requirements.yml?
= ansible-galaxy install -r requirements.yml
> Фиксируйте версии в requirements.yml.

### Зачем к переменным роли добавляют префикс с её именем, например nginx_listen_port?
- [ ] Так требует Ansible
- [x] Чтобы избежать конфликтов с одноимёнными переменными других ролей и плейбуков
- [ ] Чтобы переменная зашифровалась
- [ ] Чтобы повысить приоритет
> Все переменные в плее живут в общем пространстве имён.

### Что проверяет Molecule при тестировании роли?
- [x] Что роль применяется в чистом окружении (контейнере или ВМ)
- [x] Что повторный запуск ничего не меняет (идемпотентность)
- [x] Что проверки verify проходят
- [ ] Скорость интернета
> Обычно вместе с ansible-lint в CI.

### Почему роль из Galaxy стоит прочитать перед использованием?
- [ ] Иначе она не установится
- [x] Она будет выполняться с правами root на ваших серверах; качество и безопасность ролей сообщества разные
- [ ] Роли из Galaxy зашифрованы
- [ ] Это требование лицензии
> И фиксируйте версию, чтобы обновление не пришло внезапно.

### В каком порядке выполняются части плея?
- [ ] tasks → roles → pre_tasks
- [x] pre_tasks → roles → tasks → post_tasks (с выполнением уведомлённых handlers после каждой части)
- [ ] roles → post_tasks → tasks
- [ ] Порядок случайный
> Роли, указанные в roles, выполняются раньше обычных tasks.

### Чем коллекция отличается от роли?
- [ ] Это синонимы
- [x] Коллекция — формат распространения, который может включать модули, плагины и роли, а роль — набор задач, handlers, шаблонов и переменных
- [ ] Коллекции работают только в Windows
- [ ] Роль может содержать коллекции, но не наоборот
> Пример коллекции — community.docker с модулями для Docker.
