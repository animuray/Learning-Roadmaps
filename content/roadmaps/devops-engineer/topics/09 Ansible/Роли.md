# Роли

Когда плейбук разрастается до сотен строк, его делят на **роли** — самостоятельные переиспользуемые модули с понятным интерфейсом: «роль nginx», «роль postgresql», «роль node_exporter». Одна роль подключается в разные плейбуки и проекты.

## Структура роли

```
roles/
└── nginx/
    ├── tasks/
    │   └── main.yml        # задачи роли (точка входа)
    ├── handlers/
    │   └── main.yml        # handlers роли
    ├── templates/
    │   └── site.conf.j2    # шаблоны для модуля template
    ├── files/
    │   └── index.html      # файлы для copy
    ├── defaults/
    │   └── main.yml        # переменные по умолчанию — низший приоритет
    ├── vars/
    │   └── main.yml        # внутренние переменные роли — высокий приоритет
    ├── meta/
    │   └── main.yml        # метаданные и зависимости
    └── README.md
```

```bash
ansible-galaxy role init roles/nginx        # создать скелет
```

- В каждом каталоге Ansible автоматически ищет `main.yml`.
- В задачах роли пути пишут **относительно роли**: `src: site.conf.j2` (без `templates/`).
- Пустые каталоги можно удалить.

## defaults и vars

`roles/nginx/defaults/main.yml` — **интерфейс роли**, всё, что можно настроить:

```yaml
nginx_worker_processes: auto
nginx_server_name: _
nginx_listen_port: 80
nginx_upstreams: []
```

`roles/nginx/vars/main.yml` — константы, которые пользователь роли менять не должен:

```yaml
nginx_conf_dir: /etc/nginx/conf.d
```

Переменные роли принято **префиксовать именем роли** (`nginx_...`) — чтобы не столкнуться с переменными других ролей.

## Подключение ролей

```yaml
- name: Веб-серверы
  hosts: web
  become: true
  roles:
    - common
    - role: nginx
      vars:
        nginx_server_name: app.example.com
        nginx_listen_port: 8080
    - role: node_exporter
      tags: [monitoring]
```

Внутри задач:

```yaml
- name: Статическое подключение
  ansible.builtin.import_role:
    name: nginx

- name: Динамическое подключение по условию
  ansible.builtin.include_role:
    name: postgresql
  when: install_db | bool
```

| | `import_role` / `roles:` | `include_role` |
| --- | --- | --- |
| Когда обрабатывается | При разборе плейбука (статически) | Во время выполнения (динамически) |
| `--list-tasks`, `--tags` | Видны задачи роли | Задачи видны, только когда include выполнится |
| `loop` | Нельзя | Можно |

Порядок выполнения плея: `pre_tasks` → handlers → `roles` → `tasks` → handlers → `post_tasks` → handlers.

## Зависимости

`roles/app/meta/main.yml`:

```yaml
dependencies:
  - role: common
  - role: docker
```

Зависимости выполняются **перед** ролью и по умолчанию один раз за плей.

## Ansible Galaxy и коллекции

**Galaxy** — каталог ролей и коллекций сообщества (например, популярные роли geerlingguy). `requirements.yml`:

```yaml
roles:
  - name: geerlingguy.docker
    version: 7.4.1
  - name: company.base
    src: https://gitlab.example.com/ansible/role-base.git
    scm: git
    version: v2.0.0

collections:
  - name: community.docker
    version: ">=3.10.0"
  - name: ansible.posix
```

```bash
ansible-galaxy install -r requirements.yml
ansible-galaxy role list
ansible-galaxy collection list
```

- **Фиксируйте версии** — чужая роль может измениться.
- Читайте код ролей из Galaxy перед использованием: они выполняются с правами root на ваших серверах.
- **Коллекция** — формат распространения, который объединяет модули, плагины и роли (`community.docker`, `ansible.posix`).

## Типовая структура проекта

```
ansible/
├── ansible.cfg
├── requirements.yml
├── inventories/
│   ├── prod/
│   │   ├── hosts.yml
│   │   └── group_vars/
│   └── stage/
├── roles/
│   ├── common/
│   ├── docker/
│   ├── nginx/
│   └── app/
├── site.yml
├── web.yml
└── db.yml
```

`site.yml` импортирует остальные: `- ansible.builtin.import_playbook: web.yml`.

## Качество ролей

- **ansible-lint** — проверка на типичные ошибки и стиль (FQCN, `name` у задач, `mode` у файлов, неидемпотентные команды).
- **Molecule** — тестирование роли: поднять контейнер или ВМ, применить роль, **запустить второй раз и проверить идемпотентность**, выполнить проверки (verify), удалить окружение.
- Каждая роль — с README: что делает, переменные, пример.

## Тест

### Где роль ищет задачи по умолчанию?
= tasks/main.yml
= roles/имя/tasks/main.yml
> Аналогично handlers/main.yml, defaults/main.yml и т. д.

### Чем defaults/main.yml отличается от vars/main.yml в роли?
- [x] defaults — значения по умолчанию с самым низким приоритетом, их легко переопределить
- [x] vars — внутренние переменные роли с высоким приоритетом, их сложно переопределить
- [ ] defaults выполняются раньше задач
- [ ] Это одно и то же
> Настраиваемые параметры роли кладут в defaults.

### Какая команда создаёт скелет новой роли?
- [ ] ansible-playbook --init-role nginx
- [x] ansible-galaxy role init nginx
- [ ] ansible-role create nginx
- [ ] ansible-doc role nginx
> В старых инструкциях встречается ansible-galaxy init.

### Как в задаче роли указать шаблон templates/site.conf.j2 этой роли?
- [ ] src: roles/nginx/templates/site.conf.j2 — всегда полный путь
- [x] src: site.conf.j2 — Ansible сам ищет в каталоге templates роли
- [ ] src: ../templates/site.conf.j2
- [ ] Шаблоны в роли не поддерживаются
> То же для files/ и модуля copy.

### Чем import_role отличается от include_role?
- [x] import_role подключает роль статически при разборе плейбука
- [x] include_role подключает роль динамически во время выполнения и поддерживает loop
- [ ] include_role работает быстрее
- [ ] import_role нельзя использовать с when
> С include_role задачи роли не видны в --list-tasks до выполнения.

### Где описываются зависимости роли от других ролей?
- [ ] tasks/main.yml
- [x] meta/main.yml в ключе dependencies
- [ ] defaults/main.yml
- [ ] requirements.txt
> Зависимости выполняются до самой роли.

### Как установить роли и коллекции, перечисленные в requirements.yml?
= ansible-galaxy install -r requirements.yml
> Фиксируйте версии в requirements.yml.

### Зачем к переменным роли добавляют префикс с её именем, например nginx_listen_port?
- [ ] Так требует Ansible
- [x] Чтобы избежать конфликтов с одноимёнными переменными других ролей и плейбуков
- [ ] Чтобы переменная зашифровалась
- [ ] Чтобы повысить приоритет
> Все переменные в плее живут в общем пространстве имён.

### Что проверяет Molecule при тестировании роли?
- [x] Что роль применяется в чистом окружении (контейнере или ВМ)
- [x] Что повторный запуск ничего не меняет (идемпотентность)
- [x] Что проверки verify проходят
- [ ] Скорость интернета
> Обычно вместе с ansible-lint в CI.

### Почему роль из Galaxy стоит прочитать перед использованием?
- [ ] Иначе она не установится
- [x] Она будет выполняться с правами root на ваших серверах; качество и безопасность ролей сообщества разные
- [ ] Роли из Galaxy зашифрованы
- [ ] Это требование лицензии
> И фиксируйте версию, чтобы обновление не пришло внезапно.

### В каком порядке выполняются части плея?
- [ ] tasks → roles → pre_tasks
- [x] pre_tasks → roles → tasks → post_tasks (с выполнением уведомлённых handlers после каждой части)
- [ ] roles → post_tasks → tasks
- [ ] Порядок случайный
> Роли, указанные в roles, выполняются раньше обычных tasks.

### Чем коллекция отличается от роли?
- [ ] Это синонимы
- [x] Коллекция — формат распространения, который может включать модули, плагины и роли, а роль — набор задач, handlers, шаблонов и переменных
- [ ] Коллекции работают только в Windows
- [ ] Роль может содержать коллекции, но не наоборот
> Пример коллекции — community.docker с модулями для Docker.
