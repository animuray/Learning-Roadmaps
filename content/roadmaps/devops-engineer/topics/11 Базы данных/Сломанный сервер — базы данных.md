# Сломанный сервер — базы данных

PostgreSQL очень подробно объясняет, почему не работает, — но в разных местах: при старте — в журнале кластера, при подключении — клиенту и в журнал, при запросе — клиенту. Главное — знать, куда смотреть, и не «чинить» правами суперпользователя и `trust`.

## Где искать

| Симптом | Куда смотреть |
| --- | --- |
| Кластер не стартует | `/var/log/postgresql/postgresql-16-<кластер>.log`, `journalctl -u postgresql@16-<кластер>` |
| `pg_lsclusters` — `down` | там же; частые причины — ошибка в конфиге, права на каталог данных, занят порт, нет места |
| `connection refused` | кластер не запущен или слушает другой адрес/порт (`listen_addresses`, `port`) |
| `no pg_hba.conf entry for host …` | нет подходящей строки в `pg_hba.conf` (тип, база, пользователь, адрес) |
| `password authentication failed` | неверный пароль или у роли нет пароля |
| `permission denied for table …` | у роли нет `GRANT` на таблицу (или на схему) |

## Полезные команды

```bash
pg_lsclusters                                   # кластеры, порты, статус
sudo -u postgres psql -p 5434 -c 'SHOW config_file'
sudo -u postgres psql -p 5434 -c 'SELECT * FROM pg_hba_file_rules'   # как сервер прочитал pg_hba
sudo -u postgres psql -p 5434 -c 'SELECT pg_reload_conf()'           # перечитать pg_hba и конфиг
\dp orders                                      # в psql: права на таблицу
```

- `pg_hba.conf` читается **сверху вниз**, срабатывает первая подходящая строка. После правки — `reload`, не `restart`.
- Каталог данных должен быть `0700` (или `0750`) и принадлежать `postgres` — иначе сервер откажется стартовать.
- Параметры с единицами: `256MB`, `4GB`, `30s`. Опечатка в единице — сервер не стартует.

## Лаборатория

```bash lib
# PostgreSQL 16 на стенде: кластер 16/main, порт 5432. Администратор — системный пользователь postgres.
lab_psql() { sudo -u postgres psql -qXtA "$@"; }
# lab_shopdb — учебная база shop: customers, orders (крупная), audit_log (самая крупная), settings
lab_shopdb() {
  lab_psql -c "DROP DATABASE IF EXISTS shop WITH (FORCE)" -c "CREATE DATABASE shop" >/dev/null
  lab_psql -d shop >/dev/null <<'EOF'
CREATE TABLE customers (id serial PRIMARY KEY, name text, city text);
CREATE TABLE orders (id serial PRIMARY KEY, customer_id int REFERENCES customers, total numeric, status text, created_at timestamptz DEFAULT now());
CREATE TABLE audit_log (id bigserial PRIMARY KEY, event text, payload text, at timestamptz DEFAULT now());
CREATE TABLE settings (key text PRIMARY KEY, value text);
INSERT INTO customers (name, city) SELECT 'customer ' || g, (ARRAY['Москва','Казань','Пермь'])[1 + g % 3] FROM generate_series(1, 2000) g;
INSERT INTO orders (customer_id, total, status) SELECT 1 + g % 2000, (g % 500) * 10, (ARRAY['new','paid','shipped'])[1 + g % 3] FROM generate_series(1, 30000) g;
INSERT INTO audit_log (event, payload) SELECT 'event ' || g, repeat(md5(g::text), 8) FROM generate_series(1, 60000) g;
INSERT INTO settings VALUES ('currency', 'RUB'), ('vat', '20');
EOF
}
# lab_bs_cluster имя порт — чистый кластер PostgreSQL 16 (старые кластеры задач удаляются)
lab_bs_cluster() {
  for c in bs bs2; do pg_dropcluster --stop 16 $c >/dev/null 2>&1; done
  rm -rf /var/lib/postgresql/16/bs /var/lib/postgresql/16/bs2 /etc/postgresql/16/bs /etc/postgresql/16/bs2
  pg_createcluster 16 "$1" -p "$2" >/dev/null 2>&1
  systemctl daemon-reload
  systemctl start "postgresql@16-$1"
}
```

### Кластер не стартует

На сервере есть кластер PostgreSQL **`16/bs`** (порт `5434`) с базой отчётов. Вчера администратор «настроил производительность» (подняли `shared_buffers` до 256 МБ) и «поправил права для бэкапов». После перезагрузки кластер не поднимается.

Почините так, чтобы кластер работал как служба systemd, `shared_buffers` был **256MB**, а данные остались на месте.

```bash setup
lab_bs_cluster bs 5434
sudo -u postgres psql -qX -p 5434 -c "CREATE TABLE reports AS SELECT g AS id, 'report ' || g AS title FROM generate_series(1, 1234) g" >/dev/null
systemctl stop postgresql@16-bs
printf 'shared_buffers = 256MBB\nwork_mem = 8MB\n' > /etc/postgresql/16/bs/conf.d/tuning.conf
chmod 755 /var/lib/postgresql/16/bs
systemctl start postgresql@16-bs >/dev/null 2>&1; true
```

```bash check
[ -d /var/lib/postgresql/16/bs ] || fail "Кластера 16/bs нет — нажмите «Начать задачу» заново"
[ "$(systemctl is-active postgresql@16-bs)" = active ] || fail "Служба postgresql@16-bs не работает"
pg_lsclusters -h | awk '$2 == "bs" {print $4}' | grep -q online || fail "Кластер 16/bs не в состоянии online"
q() { sudo -u postgres psql -qXtA -p 5434 -c "$1" 2>/dev/null; }
[ "$(q 'SHOW shared_buffers')" = 256MB ] || fail "shared_buffers = $(q 'SHOW shared_buffers')"
[ "$(q 'SELECT count(*) FROM reports')" = 1234 ] || fail "В таблице reports не 1234 строки"
m=$(stat -c %a /var/lib/postgresql/16/bs); [ "$m" = 700 ] || [ "$m" = 750 ] || fail "Права на каталог данных: $m"
[ "$(stat -c %U /var/lib/postgresql/16/bs)" = postgres ] || fail "Каталог данных принадлежит не postgres"
ok "кластер 16/bs работает, shared_buffers=256MB, данные на месте"
```

```text hint
1. Узнать состояние кластеров и прочитать журнал именно этого кластера: последние строки при попытке старта.
2. Исправлять по одной причине и пробовать запустить снова — следующая причина появится в журнале.
3. Сервер строго проверяет единицы измерения в параметрах и права на каталог данных: доступ к нему должен быть только у владельца (и, возможно, его группы).
```

```bash solution
pg_lsclusters
sudo systemctl start postgresql@16-bs || true
sudo tail -n 4 /var/log/postgresql/postgresql-16-bs.log
sudo grep -rn shared_buffers /etc/postgresql/16/bs/
sudo sed -i 's/256MBB/256MB/' /etc/postgresql/16/bs/conf.d/tuning.conf
sudo systemctl start postgresql@16-bs || true
sudo tail -n 3 /var/log/postgresql/postgresql-16-bs.log
sudo chmod 700 /var/lib/postgresql/16/bs
sudo systemctl start postgresql@16-bs
pg_lsclusters
sudo -u postgres psql -p 5434 -c 'SHOW shared_buffers'
```

```text review
Две поломки, вторая видна только после первой:

1. `shared_buffers = 256MBB` — неверная единица: `invalid value for parameter "shared_buffers"`. Сервер не стартует при любой ошибке в конфиге.
2. `chmod 755` на каталог данных — `data directory ... has invalid permissions`. PostgreSQL требует `0700` (или `0750` для групповых бэкапов), чтобы другие пользователи не читали файлы базы.

- Перед перезапуском проверяйте конфиг: `sudo -u postgres /usr/lib/postgresql/16/bin/postgres -D /var/lib/postgresql/16/bs -c config_file=/etc/postgresql/16/bs/postgresql.conf -C shared_buffers` выведет значение или ошибку, не запуская сервер. Большинство параметров можно применить через `pg_reload_conf()` и сразу увидеть ошибку в `pg_settings`/`pg_file_settings`.
- `SELECT * FROM pg_file_settings WHERE error IS NOT NULL` — ошибки в конфигурационных файлах на работающем сервере.
- Права «для бэкапов» правильно давать через группу и `0750` (`initdb --allow-group-access`) или делать бэкапы от `postgres` (`pg_basebackup`, `pg_dump`).
- `shared_buffers` требует перезапуска — его меняют в окно обслуживания, а не «на ходу».
```

```text notes
chmod\s+[^\n]*(777|-R) => Права меняли широко или рекурсивно — достаточно права на сам каталог данных.
```

### Приложение не может подключиться

На кластере **`16/bs2`** (порт `5435`) база `shopdb` с таблицей `orders`. Приложение подключается так:

```
postgresql://app:App-pass-2026@127.0.0.1:5435/shopdb
```

и выполняет `SELECT count(*) FROM orders` — сейчас безуспешно. Почините так, чтобы запрос приложения проходил. Безопасность не ослаблять: вход только с паролем, роль `app` — не суперпользователь, к базе не подключиться с других адресов.

```bash setup
lab_bs_cluster bs2 5435
p() { sudo -u postgres psql -qX -p 5435 "$@" >/dev/null; }
p -c "CREATE ROLE app LOGIN PASSWORD 'App-pass-2026'" -c "CREATE DATABASE shopdb"
p -d shopdb -c "CREATE TABLE orders AS SELECT g AS id, g * 10 AS total FROM generate_series(1, 500) g"
cat > /etc/postgresql/16/bs2/pg_hba.conf <<'EOF'
# TYPE  DATABASE        USER            ADDRESS                 METHOD
local   all             postgres                                peer
local   all             all                                     peer
host    shop            app             127.0.0.1/32            scram-sha-256
EOF
p -c "SELECT pg_reload_conf()"
```

```bash check
[ -d /var/lib/postgresql/16/bs2 ] || fail "Кластера 16/bs2 нет — нажмите «Начать задачу» заново"
[ "$(systemctl is-active postgresql@16-bs2)" = active ] || fail "Служба postgresql@16-bs2 не работает"
out=$(PGPASSWORD=App-pass-2026 psql -XtA -h 127.0.0.1 -p 5435 -U app -d shopdb -c 'SELECT count(*) FROM orders' 2>&1)
[ "$out" = 500 ] || fail "Запрос приложения не проходит: $(echo "$out" | head -1 | cut -c1-200)"
PGPASSWORD=wrong psql -XtA -h 127.0.0.1 -p 5435 -U app -d shopdb -c 'SELECT 1' >/dev/null 2>&1 && fail "Роль app входит с неверным паролем"
q() { sudo -u postgres psql -qXtA -p 5435 -c "$1" 2>/dev/null; }
[ "$(q "SELECT rolsuper FROM pg_roles WHERE rolname = 'app'")" = f ] || fail "Роль app — суперпользователь"
q "SELECT count(*) FROM pg_hba_file_rules WHERE type LIKE 'host%' AND (auth_method = 'trust' OR address IN ('0.0.0.0', '::') OR address = 'all' OR netmask IN ('0.0.0.0', '::'))" | grep -qx 0 \
  || fail "В pg_hba.conf есть сетевые строки без пароля или для любых адресов"
[ "$(q 'SHOW listen_addresses')" = localhost ] || fail "listen_addresses изменён: $(q 'SHOW listen_addresses')"
ok "приложение читает orders (500 строк) по паролю с 127.0.0.1"
```

```text hint
1. Повторить подключение приложения самому и прочитать ошибку сервера дословно.
2. Сравнить строку разрешений для приложения (тип, база, пользователь, адрес) с тем, куда оно подключается; после правки попросить сервер перечитать настройки.
3. Если вход прошёл, а запрос нет — выдать роли приложения минимальное право на чтение этой таблицы от имени владельца.
```

```bash solution
PGPASSWORD=App-pass-2026 psql -h 127.0.0.1 -p 5435 -U app -d shopdb -c 'SELECT count(*) FROM orders' || true
sudo grep -vE '^\s*(#|$)' /etc/postgresql/16/bs2/pg_hba.conf
sudo sed -i 's/^host    shop            app/host    shopdb          app/' /etc/postgresql/16/bs2/pg_hba.conf
sudo -u postgres psql -p 5435 -c 'SELECT pg_reload_conf()'
PGPASSWORD=App-pass-2026 psql -h 127.0.0.1 -p 5435 -U app -d shopdb -c 'SELECT count(*) FROM orders' || true
sudo -u postgres psql -p 5435 -d shopdb -c 'GRANT SELECT ON orders TO app'
PGPASSWORD=App-pass-2026 psql -h 127.0.0.1 -p 5435 -U app -d shopdb -c 'SELECT count(*) FROM orders'
```

```text review
Две поломки на разных уровнях:

1. **Аутентификация:** в `pg_hba.conf` строка для `app` разрешала базу `shop`, а приложение ходит в `shopdb` — `no pg_hba.conf entry for host "127.0.0.1", user "app", database "shopdb"`.
2. **Авторизация:** вход прошёл, но у `app` нет права на таблицу — `permission denied for table orders`. Таблицу создал `postgres`, и права на неё по умолчанию есть только у владельца.

- `pg_hba.conf` перечитывается по `pg_reload_conf()` (или `systemctl reload`), перезапуск не нужен. `SELECT * FROM pg_hba_file_rules` покажет, как сервер понял файл, и ошибки в нём.
- `trust`, `0.0.0.0/0` и `ALTER ROLE app SUPERUSER` «чинят» обе ошибки сразу — и открывают базу. Минимально необходимые права: нужная база, нужный адрес, `GRANT SELECT` на нужные таблицы.
- Чтобы права на новые таблицы выдавались автоматически: `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO app` (от имени роли, которая создаёт таблицы). Удобнее выдавать права групповой роли (`app_read`) и включать в неё пользователей.
```

```text notes
\btrust\b => В pg_hba.conf пробовали trust — так база пускает без пароля.
SUPERUSER => Роли выдавали SUPERUSER — приложению это никогда не нужно.
GRANT\s+ALL => Выдавали GRANT ALL — приложению для чтения хватает SELECT.
```

## Тест

### Кластер PostgreSQL не стартует. Где искать причину в Ubuntu?
- [ ] В ~/.psql_history
- [x] В /var/log/postgresql/postgresql-16-<кластер>.log и journalctl -u postgresql@16-<кластер>
- [ ] В /etc/hosts
- [ ] В pg_hba.conf
> Ошибки старта сервер пишет в свой журнал; systemctl status показывает только, что pg_ctl не смог запустить сервер.

### В журнале «invalid value for parameter "shared_buffers": "256MBB"». Что сделать?
- [ ] Увеличить память сервера
- [x] Исправить единицу измерения в конфиге (256MB) и запустить снова
- [ ] Переустановить PostgreSQL
- [ ] Удалить каталог данных
> Любая ошибка в конфиге не даёт серверу стартовать.

### Сервер пишет «data directory has invalid permissions». Какие права нужны?
- [ ] 755
- [ ] 777
- [x] 700 (или 750 при групповом доступе), владелец postgres
- [ ] 644
> PostgreSQL не стартует, если файлы базы могут читать посторонние.

### Клиент получает «no pg_hba.conf entry for host "10.0.0.5", user "app", database "shop"». Что это значит?
- [ ] Неверный пароль
- [x] В pg_hba.conf нет строки, подходящей под тип подключения, базу, пользователя и адрес
- [ ] База не существует
- [ ] Сервер не запущен
> Проверьте все четыре поля строки и порядок строк.

### Как применить изменения pg_hba.conf без перезапуска сервера?
= SELECT pg_reload_conf()
= pg_reload_conf
= systemctl reload postgresql
> pg_hba.conf перечитывается по сигналу reload.

### Как посмотреть, как сервер прочитал pg_hba.conf, включая ошибки в строках?
= pg_hba_file_rules
= SELECT * FROM pg_hba_file_rules
> Представление показывает итоговые правила и поле error.

### Вход прошёл, но «permission denied for table orders». Правильное решение?
- [ ] Сделать app суперпользователем
- [ ] Сменить метод в pg_hba на trust
- [x] Выдать роли app GRANT SELECT ON orders (минимально нужное право)
- [ ] Пересоздать таблицу от имени app
> Это авторизация, а не аутентификация: роль вошла, но прав на таблицу нет.

### Чем опасна строка `host all all 0.0.0.0/0 trust` в pg_hba.conf?
- [ ] Ничем, если включён файрвол
- [x] Любой, кто достучится до порта, войдёт под любой ролью без пароля
- [ ] Она замедляет подключения
- [ ] Она работает только для localhost
> trust — вход без проверки пароля; для сети недопустим.

### Строки в pg_hba.conf проверяются:
- [ ] Все, и выбирается самая строгая
- [x] Сверху вниз; применяется первая подходящая
- [ ] Снизу вверх
- [ ] В случайном порядке
> Поэтому более конкретные правила ставят выше общих.

### Клиент получает «connection refused» на 127.0.0.1:5435. Что проверить первым?
- [ ] pg_hba.conf
- [x] Запущен ли кластер и на каком порту и адресе он слушает (pg_lsclusters, ss -ltn)
- [ ] Пароль роли
- [ ] Права на таблицу
> Отказ в соединении — до PostgreSQL дело не дошло.

### Какой параметр требует перезапуска сервера, а не reload?
- [ ] work_mem
- [x] shared_buffers
- [ ] log_min_duration_statement
- [ ] pg_hba.conf
> Общая память выделяется при старте; `pg_settings.context = postmaster` — только перезапуск.

### Как сделать, чтобы роль app автоматически получала SELECT на новые таблицы в схеме public?
- [ ] GRANT SELECT ON ALL TABLES — действует и на будущие
- [x] ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO app
- [ ] Сделать app владельцем базы
- [ ] Это невозможно
> `GRANT ... ON ALL TABLES` касается только существующих таблиц; для будущих — default privileges.
