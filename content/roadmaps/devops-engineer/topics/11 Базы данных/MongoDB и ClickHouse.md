# MongoDB и ClickHouse

Реляционная база (PostgreSQL) — правильный выбор по умолчанию. Но DevOps-инженеру часто достаются и другие системы. Две самые частые — **MongoDB** и **ClickHouse**. Цель темы — понимать, что это, зачем и что с ними делать в эксплуатации.

## OLTP и OLAP

| | OLTP | OLAP |
| --- | --- | --- |
| Задача | Транзакции приложения: заказ, платёж, профиль | Аналитика: отчёты, агрегаты по миллиардам строк |
| Запросы | Много коротких, читают/пишут несколько строк | Мало тяжёлых, читают много строк, но немного колонок |
| Хранение | Построчное | **Колоночное** |
| Примеры | PostgreSQL, MySQL, MongoDB | ClickHouse, BigQuery, Snowflake |

## MongoDB — документная база

Данные — **документы** (похожи на JSON, хранятся в двоичном BSON) в **коллекциях** (аналог таблиц). Схема гибкая: документы одной коллекции могут отличаться.

```javascript
db.users.insertOne({ email: "a@example.com", name: "Аня", tags: ["vip"], address: { city: "Москва" } })
db.users.find({ "address.city": "Москва" }, { email: 1 })
db.users.updateOne({ email: "a@example.com" }, { $set: { name: "Анна" } })
db.users.createIndex({ email: 1 }, { unique: true })
db.orders.aggregate([{ $group: { _id: "$status", total: { $sum: "$amount" } } }])
```

Подходит: каталоги с разнородными атрибутами, контент, события, прототипы — когда данные естественно ложатся в «документ» и не нужны сложные JOIN.

### Эксплуатация

- Порт **27017**, клиент **mongosh**.
- **Replica set** — основа продакшена: один **primary** принимает запись, **secondary** реплицируют, при отказе primary узлы **выбирают** новый автоматически. Минимум 3 узла (или 2 + arbiter, который голосует, но не хранит данные).
- **Sharding** — горизонтальное разбиение данных по ключу шардирования между несколькими replica set; маршрутизатор `mongos`, config servers.
- Бэкап: `mongodump`/`mongorestore` (логический), снапшоты томов, Percona Backup for MongoDB, managed (Atlas).
- Безопасность: **включить аутентификацию** (`security.authorization: enabled`), `bindIp` на внутренний адрес — открытые MongoDB без пароля десятилетиями становятся жертвами «ransom»-атак.
- Лицензия Community Server — SSPL (не OSI); существуют совместимые альтернативы (например, FerretDB поверх PostgreSQL).

## ClickHouse — колоночная база для аналитики и логов

Каждая колонка хранится отдельно и сильно сжимается. Запрос `SELECT count() ... WHERE status = 500 GROUP BY toStartOfHour(ts)` читает только две колонки из ста — поэтому агрегаты по миллиардам строк считаются за секунды.

```sql
CREATE TABLE logs
(
    ts        DateTime,
    service   LowCardinality(String),
    level     LowCardinality(String),
    status    UInt16,
    message   String
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(ts)
ORDER BY (service, ts)
TTL ts + INTERVAL 30 DAY;

INSERT INTO logs VALUES (now(), 'api', 'error', 500, 'db timeout');

SELECT service, count() AS errors
FROM logs
WHERE level = 'error' AND ts > now() - INTERVAL 1 HOUR
GROUP BY service
ORDER BY errors DESC;
```

Ключевые идеи:

- **MergeTree** — основной движок: данные пишутся «кусками» (parts), которые фоново сливаются.
- **ORDER BY** — ключ сортировки и разреженный первичный индекс: фильтры по его префиксу (`service`, `ts`) читают мало данных.
- **PARTITION BY** — например, по месяцу: старые партиции удаляются мгновенно; **TTL** — автоматическое удаление старых данных.
- Вставлять **пачками** (тысячи строк за раз), а не по одной строке — иначе слишком много мелких частей. Для потока — буферизация, асинхронные вставки или Kafka-движок.
- Обновления и удаления — тяжёлые фоновые «мутации»; ClickHouse не для OLTP.
- Порты: **8123** (HTTP), **9000** (нативный протокол); репликация — ReplicatedMergeTree + ClickHouse Keeper.

Где встретите: хранилища логов и трассировок (SigNoz, Uptrace, собственные пайплайны), продуктовая аналитика, метрики. Появился в Яндексе для Яндекс.Метрики.

## Что выбрать

- Транзакции, связи, целостность → **PostgreSQL**.
- Гибкие документы без сложных JOIN, команда уже на MongoDB → **MongoDB**.
- Аналитика, логи, события в огромных объёмах → **ClickHouse**.
- Кэш, сессии, счётчики → **Redis/Valkey**.
- Полнотекстовый поиск → OpenSearch/Elasticsearch (тема в разделе логирования).

## Тест

### Чем OLTP-нагрузка отличается от OLAP?
- [x] OLTP — много коротких транзакций, затрагивающих несколько строк
- [x] OLAP — тяжёлые аналитические запросы по большому числу строк и немногим колонкам
- [ ] OLAP — это кэш
- [ ] OLTP работает только в облаке
> PostgreSQL — OLTP, ClickHouse — OLAP.

### Как MongoDB хранит данные?
- [ ] В таблицах со строгой схемой
- [x] В виде документов (BSON, похожих на JSON) в коллекциях с гибкой схемой
- [ ] В колонках
- [ ] Только в памяти
> Коллекция — аналог таблицы.

### Что такое replica set в MongoDB?
- [ ] Набор шардов
- [x] Группа узлов с одинаковыми данными: primary принимает запись, secondary реплицируют, при отказе primary выбирается новый
- [ ] Резервная копия
- [ ] Индекс
> Основа любого продакшен-развёртывания MongoDB.

### Зачем в replica set MongoDB может быть arbiter?
- [ ] Хранить дополнительную копию данных
- [x] Участвовать в выборах primary без хранения данных, чтобы было нечётное число голосов
- [ ] Шифровать трафик
- [ ] Принимать запись
> Он не даёт избыточности данных.

### Какая главная ошибка безопасности приводит к массовым взломам MongoDB?
- [ ] Использование индексов
- [x] Запуск без аутентификации с доступом из интернета
- [ ] Включённый replica set
- [ ] Использование mongosh
> Включайте authorization и ограничивайте bindIp.

### Почему ClickHouse быстро считает агрегаты по миллиардам строк?
- [x] Данные хранятся по колонкам, и запрос читает только нужные колонки
- [x] Колонки хорошо сжимаются, а выполнение запросов векторизовано
- [ ] Все данные всегда в оперативной памяти
- [ ] Он не использует диск
> Цена — неудобные обновления отдельных строк.

### Какой основной движок таблиц в ClickHouse?
= MergeTree
> Для репликации — ReplicatedMergeTree.

### Что даёт TTL в таблице ClickHouse?
- [ ] Ускоряет вставку
- [x] Автоматически удаляет (или перемещает) данные старше заданного срока
- [ ] Шифрует колонки
- [ ] Ограничивает число запросов
> Удобно для логов с хранением 30 дней.

### Как правильно вставлять данные в ClickHouse?
- [ ] По одной строке на каждый запрос
- [x] Пачками по тысячи строк (или через буферизацию и асинхронные вставки)
- [ ] Только через UPDATE
- [ ] Только через mongosh
> Иначе образуется слишком много мелких частей, и сервер не успевает их сливать.

### Для каких задач ClickHouse подходит плохо?
- [ ] Хранение логов
- [ ] Аналитика событий
- [x] OLTP с частыми обновлениями отдельных строк и транзакциями
- [ ] Агрегаты по большим объёмам
> Для этого — PostgreSQL.

### Что выбрать для хранения заказов с транзакциями и связями между таблицами?
= PostgreSQL
> Реляционная база — разумный выбор по умолчанию для данных приложения.

### Чем mongodump отличается от снапшота тома MongoDB?
- [x] mongodump — логический бэкап документов, удобен для небольших баз и переноса
- [x] Снапшот тома — физическая копия файлов, быстрее для больших баз, но требует согласованности (например, при остановленной записи или с journal)
- [ ] mongodump копирует файлы WiredTiger
- [ ] Разницы нет
> Для крупных инсталляций используют специализированные инструменты бэкапа.
