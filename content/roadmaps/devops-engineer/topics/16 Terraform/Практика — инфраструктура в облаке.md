# Практика — инфраструктура в облаке

Цель: вся инфраструктура вашего проекта создаётся одной командой из Git и так же удаляется. Новое окружение — это новый tfvars, а не день кликов в консоли.

## Целевая архитектура

```
 Облачная сеть shop-<env>
 ├── public-d 10.X.0.0/24 ──── bastion (SSH только с вашего IP)
 │                          └─ web-1, web-2 (публичный IP или балансировщик, 80/443)
 ├── private-d 10.X.1.0/24 ─── app / db (без публичных IP, выход в интернет через NAT-шлюз)
 └── NAT-шлюз + таблица маршрутов для private

 Группы безопасности: bastion-sg, web-sg (443/80 от всех, 22 от bastion-sg), db-sg (5432 от web-sg)
 Бакет backups-<env> (версионирование, жизненный цикл 30 дней)
 Бакет tfstate (создаётся отдельной bootstrap-конфигурацией)
```

## Структура репозитория

```
infra/
├── bootstrap/                 — бакет для state, сервисные аккаунты (локальный state, один раз)
├── modules/
│   ├── network/               — сеть, подсети, NAT, маршруты, группы безопасности
│   ├── vm/                    — ВМ с cloud-init и метками
│   └── bucket/                — бакет с версионированием и lifecycle
├── envs/
│   ├── dev/                   — backend key dev/..., terraform.tfvars
│   └── prod/
├── ansible/                   — настройка ВМ (inventory из outputs Terraform)
└── .gitlab-ci.yml
```

## Фрагменты

Группа безопасности базы, разрешающая доступ только от веб-группы:

```hcl
resource "yandex_vpc_security_group" "db" {
  name       = "${var.env}-db-sg"
  network_id = yandex_vpc_network.this.id

  ingress {
    protocol          = "TCP"
    port              = 5432
    security_group_id = yandex_vpc_security_group.web.id
  }

  egress {
    protocol       = "ANY"
    v4_cidr_blocks = ["0.0.0.0/0"]
  }
}
```

NAT-шлюз для приватной подсети:

```hcl
resource "yandex_vpc_gateway" "nat" {
  name = "${var.env}-nat"
  shared_egress_gateway {}
}

resource "yandex_vpc_route_table" "private" {
  name       = "${var.env}-private-rt"
  network_id = yandex_vpc_network.this.id

  static_route {
    destination_prefix = "0.0.0.0/0"
    gateway_id         = yandex_vpc_gateway.nat.id
  }
}

resource "yandex_vpc_subnet" "private" {
  name           = "${var.env}-private-d"
  zone           = "ru-central1-d"
  network_id     = yandex_vpc_network.this.id
  v4_cidr_blocks = [var.private_cidr]
  route_table_id = yandex_vpc_route_table.private.id
}
```

Бакет для бэкапов (классическая схема со статическим ключом сервисного аккаунта):

```hcl
resource "yandex_iam_service_account" "storage" {
  name = "${var.env}-storage-sa"
}

resource "yandex_resourcemanager_folder_iam_member" "storage_editor" {
  folder_id = var.folder_id
  role      = "storage.editor"
  member    = "serviceAccount:${yandex_iam_service_account.storage.id}"
}

resource "yandex_iam_service_account_static_access_key" "storage" {
  service_account_id = yandex_iam_service_account.storage.id
}

resource "yandex_storage_bucket" "backups" {
  bucket     = "shop-${var.env}-backups-${var.suffix}"
  access_key = yandex_iam_service_account_static_access_key.storage.access_key
  secret_key = yandex_iam_service_account_static_access_key.storage.secret_key

  versioning {
    enabled = true
  }

  lifecycle_rule {
    id      = "expire-old"
    enabled = true
    expiration {
      days = 30
    }
  }

  lifecycle {
    prevent_destroy = true
  }
}
```

Секретный ключ попадёт в state — ещё одна причина держать state в закрытом бакете. Синтаксис ресурсов меняется между версиями провайдера — сверяйтесь с документацией провайдера своей версии.

Связка с Ansible — генерировать inventory из outputs:

```hcl
resource "local_file" "inventory" {
  filename = "${path.module}/../../ansible/inventory-${var.env}.ini"
  content  = templatefile("${path.module}/inventory.tftpl", {
    bastion = module.bastion.public_ip
    web     = [for m in module.web : m.private_ip]
  })
}
```

## Порядок работы

1. **bootstrap**: бакет для state (закрытый, версионирование), сервисный аккаунт Terraform для каждого окружения с ролями только на свой каталог.
2. **modules**: network → vm → bucket; у каждого README, переменные с описаниями.
3. **envs/dev**: backend в Object Storage, вызовы модулей, `terraform.tfvars`; `init`, `plan`, `apply`.
4. Проверка: SSH на бастион только с вашего IP, на веб — только через бастион, база недоступна извне, приватная ВМ выходит в интернет через NAT.
5. **Ansible**: настройка ВМ по сгенерированному inventory (тема Ansible).
6. **envs/prod**: те же модули, другие tfvars и CIDR, отдельный каталог и сервисный аккаунт.
7. **CI**: fmt, validate, tflint, Checkov и plan в MR; apply dev после merge; apply prod вручную.
8. **Учения**: удалить dev целиком через `destroy` и пересоздать одной командой — засечь время.

## Лаборатория

Вместо облака — Docker, но структура проекта та же, что для настоящей инфраструктуры: сеть, хранилище, база, приложение, переменные и секреты.

```bash lib
# Terraform 1.x на стенде; провайдеры скачиваются из registry.terraform.io (кэш — ~/.terraform.d/plugin-cache).
# Инфраструктура в задачах — файлы (hashicorp/local) и контейнеры Docker (kreuzwerker/docker).
lab_tf() { su - student -c "cd $1 && terraform $2" > /tmp/lab-tf.log 2>&1; }
# план без изменений: 0 — ничего не меняется, 2 — есть изменения, 1 — ошибка
lab_tfclean() { su - student -c "cd $1 && terraform plan -detailed-exitcode -input=false -lock=false" > /tmp/lab-tf.log 2>&1; echo $?; }
lab_tflog() { sed 's/\x1b\[[0-9;]*m//g' /tmp/lab-tf.log | grep -E 'Error|will be|must be|#' | head -3 | tr '\n' ' ' | cut -c1-250; }
lab_tfdir() { rm -rf "$1"; mkdir -p "$1"; chown -R student:student "$(dirname "$1")"; }
lab_drm() { docker rm -f "$@" >/dev/null 2>&1; true; }
# образ есть локально или скачивается (если ученик почистил образы через prune)
lab_img() { for i in "$@"; do docker image inspect "$i" >/dev/null 2>&1 || docker pull -q "$i" >/dev/null; done; }
# lab_wait_http URL [строка] — дождаться ответа
lab_wait_http() { for i in $(seq 60); do curl -s --max-time 1 "$1" 2>/dev/null | grep -q "${2:-.}" && return 0; sleep 0.25; done; return 1; }
```

### Стек приложения кодом

В `~/tf/stack` опишите и примените инфраструктуру:

1. сеть Docker **`stack-net`**;
2. том **`stack-pgdata`**;
3. контейнер **`stack-db`** (`postgres:16-alpine`) в сети `stack-net`, данные — на томе `stack-pgdata` (`/var/lib/postgresql/data`), пароль — из переменной **`db_password`**, помеченной **`sensitive`**;
4. контейнер **`stack-app`** (`hashicorp/http-echo:1.0` с аргументом `-text=stack ok`) в той же сети, порт **8195** → 5678;
5. output **`app_url`** = `http://localhost:8195`.

Значение `db_password` (`Db-Pa55-2026`) задайте в файле **`terraform.tfvars`**, который **не должен попасть в Git** (в каталоге уже есть репозиторий). Переменная `db_password` не должна иметь значения по умолчанию.

```bash check
docker inspect -f '{{range .Mounts}}{{.Name}}:{{.Destination}} {{end}}' stack-db | grep -q 'stack-pgdata:/var/lib/postgresql/data' || fail "Данные stack-db не на томе stack-pgdata"

[ "$(lab_tfclean $d)" = 0 ] || fail "terraform plan находит изменения: $(lab_tflog)"

```

```text hint
1. Ресурсы провайдера Docker: сеть, том, образ, контейнер. У контейнера — блоки сетей, томов и портов, переменные окружения списком строк.
2. Переменная пароля: тип, пометка «чувствительная», без значения по умолчанию. Значение — в файле .tfvars рядом (Terraform подхватывает terraform.tfvars сам).
3. Файл .gitignore: значения переменных, state и каталог провайдеров.
```

```bash solution
cd ~/tf/stack
cat > main.tf <<'EOF'
terraform {
  required_providers {
    docker = { source = "kreuzwerker/docker", version = "~> 3.0" }
  }
}

provider "docker" {}

variable "db_password" {
  type      = string
  sensitive = true
}

resource "docker_network" "net" { name = "stack-net" }
resource "docker_volume" "pgdata" { name = "stack-pgdata" }

resource "docker_image" "postgres" {
  name         = "postgres:16-alpine"
  keep_locally = true
}
resource "docker_image" "echo" {
  name         = "hashicorp/http-echo:1.0"
  keep_locally = true
}

resource "docker_container" "db" {
  name  = "stack-db"
  image = docker_image.postgres.image_id
  env   = ["POSTGRES_PASSWORD=${var.db_password}"]
  networks_advanced { name = docker_network.net.name }
  volumes {
    volume_name    = docker_volume.pgdata.name
    container_path = "/var/lib/postgresql/data"
  }
}

resource "docker_container" "app" {
  name    = "stack-app"
  image   = docker_image.echo.image_id
  command = ["-text=stack ok"]
  networks_advanced { name = docker_network.net.name }
  ports {
    internal = 5678
    external = 8195
  }
}

output "app_url" { value = "http://localhost:8195" }
EOF
echo 'db_password = "Db-Pa55-2026"' > terraform.tfvars
printf '.terraform/\n*.tfstate\n*.tfstate.*\n*.tfvars\n' > .gitignore
terraform init -input=false
terraform apply -auto-approve
terraform output
```

```text review
Эталон — в «Решении».

- `sensitive = true` скрывает значение в выводе `plan`/`apply`, но **не в state**: там пароль открытым текстом. Поэтому state — в защищённом backend, а `*.tfstate` — в `.gitignore`.
- Значения переменных: `terraform.tfvars` (вне Git), переменные окружения `TF_VAR_db_password` (так в CI), `-var-file=prod.tfvars`. Ещё лучше — брать секреты из Vault (провайдер `vault`) или Secret Manager облака.
- Структура реального проекта: `versions.tf` (провайдеры), `variables.tf`, `main.tf`/по файлу на подсистему, `outputs.tf`, модули, отдельные каталоги или workspaces на окружения, backend с блокировкой, `terraform fmt`/`validate`/`plan` в CI на каждый merge request и `apply` — только из пайплайна.
```

## Тест

### Почему бакет для state создают отдельной bootstrap-конфигурацией?
- [ ] Так быстрее
- [x] Конфигурация не может хранить свой state в бакете, который сама же создаёт: бакет должен существовать до terraform init
- [ ] Terraform не умеет создавать бакеты
- [ ] Это требование Ansible
> Bootstrap обычно применяется один раз с локальным state.

### Как дать приватным ВМ без публичных IP выход в интернет в Yandex Cloud через Terraform?
- [ ] Открыть группу безопасности для 0.0.0.0/0
- [x] Создать NAT-шлюз, таблицу маршрутов с маршрутом 0.0.0.0/0 через него и привязать таблицу к приватной подсети
- [ ] Выдать всем ВМ nat = true
- [ ] Это невозможно
> Входящие подключения из интернета к таким ВМ при этом невозможны.

### Как в группе безопасности базы разрешить доступ только с веб-серверов?
- [ ] Правило ingress с v4_cidr_blocks = ["0.0.0.0/0"]
- [x] Правило ingress на порт 5432 с security_group_id группы веб-серверов
- [ ] Отключить группу безопасности
- [ ] Выдать базе публичный IP
> Ссылка на группу не требует перечислять IP-адреса.

### Почему секретный ключ, созданный ресурсом yandex_iam_service_account_static_access_key, — повод особенно защищать state?
- [ ] Ключ не попадает в state
- [x] Значение ключа сохраняется в state открытым текстом, и любой с доступом к state получит его
- [ ] Ключ шифруется Terraform автоматически
- [ ] Ключ виден только в консоли
> State хранят в закрытом бакете с минимальным доступом.

### Как передать адреса созданных ВМ в Ansible?
- [ ] Вписать вручную после каждого apply
- [x] Сгенерировать inventory из outputs Terraform, например через templatefile и local_file
- [ ] Ansible сам найдёт ВМ в облаке без настроек
- [ ] Через terraform destroy
> Ещё вариант — динамический inventory по меткам облака.

### Что должно отличаться у envs/dev и envs/prod?
- [x] Значения в tfvars и CIDR сетей
- [x] Ключ state в backend и каталог облака
- [x] Сервисный аккаунт Terraform с правами только на своё окружение
- [ ] Код модулей
> Модули общие, чтобы staging и dev проверяли то же, что уйдёт в prod.

### Зачем пересоздавать dev целиком через destroy и apply?
- [ ] Чтобы сэкономить на хранении кода
- [x] Чтобы убедиться, что вся инфраструктура действительно описана в коде и воспроизводится одной командой
- [ ] Это обязательно каждый день
- [ ] Чтобы обновить Terraform
> Если что-то пришлось доделать руками — это пробел в коде.

### Какой инструмент проверяет Terraform-код на проблемы безопасности, например открытые порты?
= Checkov
= checkov
> Также подходят Trivy и tflint с наборами правил.

### Что делает lifecycle prevent_destroy у бакета с бэкапами?
- [ ] Ускоряет создание
- [x] Не даёт Terraform удалить бакет: план с его удалением завершится ошибкой
- [ ] Шифрует бакет
- [ ] Удаляет старые объекты
> Удаление старых объектов настраивается правилами жизненного цикла бакета.

### Кто должен иметь доступ на apply в prod?
- [ ] Любой разработчик со своего ноутбука
- [x] Только CI из защищённой ветки с ручным подтверждением, используя сервисный аккаунт prod
- [ ] Все сервисные аккаунты dev
- [ ] Никто, prod меняют вручную в консоли
> Изменения проходят ревью в MR вместе с планом.

### Где описана настройка программ внутри ВМ в этой схеме?
- [ ] В Terraform-ресурсах для каждого пакета
- [x] В cloud-init для первичной настройки и в Ansible для полной конфигурации
- [ ] Только вручную по SSH
- [ ] В state
> Terraform создаёт инфраструктуру, Ansible её настраивает.

### Зачем ограничивать SSH на бастион только своим IP?
- [ ] Это ускоряет SSH
- [x] Чтобы уменьшить поверхность атаки: открытый всем SSH постоянно сканируют и перебирают
- [ ] Иначе ВМ не создастся
- [ ] Так требует Terraform
> Остальные ВМ доступны по SSH только из бастиона.
