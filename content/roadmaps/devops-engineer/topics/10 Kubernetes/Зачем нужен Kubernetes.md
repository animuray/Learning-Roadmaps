# Зачем нужен Kubernetes

Docker Compose отлично управляет контейнерами на **одном** сервере. Но в продакшене серверов десятки, а требования такие:

- сервер упал — контейнеры должны **сами** переехать на другие;
- нагрузка выросла — запустить ещё 10 копий и распределить трафик;
- обновить приложение **без простоя** и быстро откатить, если что-то пошло не так;
- раскладывать контейнеры по серверам так, чтобы хватало CPU и памяти;
- находить сервисы друг друга по имени, хотя IP постоянно меняются;
- раздавать конфиги и секреты, подключать диски.

Делать это скриптами — бесконечная работа. **Оркестратор контейнеров** берёт её на себя. Стандарт индустрии — **Kubernetes** (K8s): открытый проект, вышедший из внутренней системы Google Borg, сейчас — под крылом CNCF. Альтернативы (Docker Swarm, Nomad) встречаются редко.

## Что даёт Kubernetes

| Возможность | Как это выглядит |
| --- | --- |
| Самовосстановление | Упал контейнер — перезапуск; умер сервер — поды пересоздаются на других нодах |
| Масштабирование | `replicas: 5` или автоматически по нагрузке (HPA) |
| Выкатка без простоя | Rolling update, откат одной командой |
| Service discovery и балансировка | Service с постоянным DNS-именем и балансировкой между подами |
| Планирование | Scheduler сам выбирает ноду по ресурсам и правилам |
| Конфигурация и секреты | ConfigMap и Secret, монтируемые в поды |
| Хранилище | Тома из облака или СХД подключаются автоматически |
| Расширяемость | Свои ресурсы (CRD) и операторы, огромная экосистема |

## Декларативный подход и желаемое состояние

Вы не говорите «запусти три контейнера на сервере 2». Вы описываете в YAML **желаемое состояние** и отдаёте его в API:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.27
```

Дальше работают **контроллеры** — программы, которые бесконечно выполняют **цикл согласования** (reconciliation loop):

```
  ┌──────────────► наблюдать фактическое состояние ──┐
  │                                                   ▼
  │                       сравнить с желаемым (spec)
  │                                                   │
  └──── привести к желаемому (создать / удалить) ◄────┘
```

Удалили под руками — контроллер увидит, что подов 2 вместо 3, и создаст новый. Поменяли образ в манифесте — контроллер постепенно заменит поды. Это и есть суть Kubernetes: **вы описываете «что», система сама делает «как» и постоянно поддерживает это состояние.**

Отсюда правило: **источник истины — манифесты в Git**, а не команды, выполненные руками в кластере (на этом построен GitOps).

## Объекты Kubernetes

У каждого объекта:

- `apiVersion` и `kind` — тип;
- `metadata` — имя, namespace, **labels** (метки для выбора), annotations;
- `spec` — желаемое состояние (пишете вы);
- `status` — фактическое состояние (пишет Kubernetes).

**Labels и selectors** — главный способ связи объектов: Deployment управляет подами с `app: web`, Service отправляет трафик подам с `app: web`.

**Namespace** — логическое разделение кластера: `dev`, `prod`, `monitoring`, `team-a`. Имена уникальны внутри namespace; к namespace привязываются квоты, права (RBAC) и сетевые политики. Системные компоненты живут в `kube-system`.

## Когда Kubernetes не нужен

Kubernetes сложен: нужно понимать сеть, хранилище, безопасность, обновлять сам кластер. Для одного-двух сервисов на одном сервере честнее Docker Compose или PaaS. Kubernetes окупается, когда сервисов много, нужна отказоустойчивость, автомасштабирование и единая платформа для команд. Managed-кластеры в облаке снимают часть сложности.
