# Практика — приложение в кластере

Цель — руками, без Helm, пройти весь путь приложения в Kubernetes и **увидеть своими глазами** поведение, о котором спрашивают на собеседованиях. Используйте приложение из практики Docker (образ уже лежит в реестре) или любое простое веб-приложение с эндпоинтами `/health` и `/ready`.

## Часть 1. Кластер и namespace

```bash
kind create cluster --name lab --config kind-3nodes.yaml
kubectl create namespace app
kubectl config set-context --current --namespace=app
```

Если образ в приватном реестре — `kubectl create secret docker-registry regcred ...` и `imagePullSecrets` в поде (или `kind load docker-image`).

## Часть 2. Deployment + Service + ConfigMap

Создайте каталог `k8s/` с манифестами:

- `configmap.yaml` — `APP_MODE`, `LOG_LEVEL`;
- `secret.yaml` — пароль базы (в Git — только пример без настоящего значения);
- `deployment.yaml` — 3 реплики, requests/limits, `envFrom` из ConfigMap и Secret, readiness и liveness, `maxSurge: 1, maxUnavailable: 0`;
- `service.yaml` — ClusterIP на порт приложения.

```bash
kubectl apply -f k8s/
kubectl get deploy,rs,pods,svc -o wide
kubectl port-forward svc/web 8080:80
```

## Часть 3. Обновление, откат, масштабирование

```bash
while true; do curl -s -o /dev/null -w "%{http_code}\n" localhost:8080/; sleep 0.2; done
```

В соседнем терминале:

1. Обновите образ на новую версию — `kubectl set image` или новый тег в манифесте + `apply`. Следите за `kubectl get pods -w` и за кодами ответов: при правильной readiness **ошибок быть не должно**.
2. Выкатите **несуществующий тег** — выкатка зависнет, старые поды продолжат обслуживать трафик. `kubectl rollout status` сообщит об ошибке.
3. Откатитесь: `kubectl rollout undo deploy/web`, посмотрите `rollout history`.
4. Масштабируйте до **5**, затем обратно до **1** и посмотрите, какие поды удаляются.

## Часть 4. Эксперименты с пробами

Сделайте в приложении возможность «ломать» эндпоинты (например, переменная окружения или ручка `/break-ready`):

| Эксперимент | Что должно произойти | Чем проверить |
| --- | --- | --- |
| Сломать **readiness** у одного пода | Под **исчезает из EndpointSlice**, трафик на него не идёт, **но под не перезапускается** (RESTARTS не растёт) | `kubectl get endpointslices`, `kubectl get pods` |
| Сломать **liveness** | Контейнер **перезапускается**, RESTARTS растёт, в `describe` — событие `Liveness probe failed` | `kubectl describe pod` |
| Убрать readiness совсем и обновить образ | Во время выкатки появятся ошибки — трафик идёт в неготовые поды | цикл `curl` |
| Медленный старт без startupProbe | CrashLoopBackOff — liveness убивает приложение до окончания старта | `kubectl get pods` |

## Часть 5. Полный стек

```
 Ingress (app.local)
   ├── /      → Service frontend → Deployment frontend (nginx со статикой)
   └── /api   → Service backend  → Deployment backend (3 реплики, HPA)
                                       └── PostgreSQL
```

- **Frontend** — nginx со статикой (multi-stage образ из практики Docker).
- **Backend** — ваше API, конфигурация через ConfigMap/Secret, адрес базы — DNS-имя.
- **PostgreSQL** — два варианта:
  - в кластере: StatefulSet + headless Service + PVC (или оператор CloudNativePG);
  - вне кластера: база на ВМ или managed, а в кластере — Service без селектора или `ExternalName`. В проде часто выбирают именно этот вариант.
- **Миграции** — Job перед выкаткой backend.
- **Ingress** — контроллер Traefik (или Gateway API) с маршрутами по путям.
- **HPA** для backend, **PDB** с `minAvailable: 2`.
- **NetworkPolicy**: frontend → backend, backend → postgres, DNS; всё остальное запрещено.

Проверьте: удалите под backend — сервис работает; удалите под postgres — после пересоздания данные на месте; выполните `kubectl drain` ноды — PDB не даёт уронить сервис.

## Тест

### Вы сломали readiness-пробу у одного пода. Что произойдёт?
- [ ] Под будет перезапущен
- [x] Под будет исключён из EndpointSlice сервиса и перестанет получать трафик, но перезапускаться не будет
- [ ] Deployment удалит под
- [ ] Ничего
> Когда проба снова пройдёт, под вернётся в балансировку.

### Вы сломали liveness-пробу. Что произойдёт?
- [ ] Под исчезнет из Service без перезапуска
- [x] kubelet перезапустит контейнер, счётчик RESTARTS вырастет, в событиях появится Liveness probe failed
- [ ] Под переедет на другую ноду
- [ ] Ничего
> При постоянных провалах под уйдёт в CrashLoopBackOff.

### Как убедиться, что обновление действительно проходит без простоя?
- [ ] Посмотреть kubectl get deploy один раз
- [x] Во время выкатки непрерывно отправлять запросы к сервису и следить, чтобы не было ошибок
- [ ] Проверить логи etcd
- [ ] Посмотреть kubectl version
> Без readiness ошибки во время выкатки почти неизбежны.

### Вы выкатили несуществующий тег образа при maxUnavailable: 0. Что будет с сервисом?
- [ ] Сервис упадёт
- [x] Новые поды застрянут в ImagePullBackOff, а старые продолжат обслуживать трафик; выкатка не завершится
- [ ] Kubernetes сам откатится
- [ ] Удалятся все поды
> Откат — kubectl rollout undo или исправление тега.

### Где лучше держать PostgreSQL для продакшен-приложения в Kubernetes?
- [x] Вне кластера — managed-база или отдельные ВМ — часто проще в эксплуатации
- [x] В кластере — через StatefulSet с PVC или, лучше, через оператор вроде CloudNativePG
- [ ] В Deployment с emptyDir
- [ ] В ConfigMap
> Выбор зависит от команды и требований, но emptyDir потеряет данные.

### Как обратиться из кластера к базе, которая работает вне кластера, по внутреннему имени?
- [ ] Через NodePort
- [x] Через Service типа ExternalName или Service без селектора с EndpointSlice на IP базы
- [ ] Через Ingress
- [ ] Это невозможно
> Приложение использует стабильное имя, а адрес базы меняется в одном месте.

### Зачем запускать миграции отдельным Job перед выкаткой backend?
- [ ] Так быстрее
- [x] Чтобы миграции выполнились один раз до старта новой версии, а не параллельно в каждой реплике
- [ ] Job не нужен, миграции делает Service
- [ ] Чтобы не нужен был Secret
> Альтернатива — Helm-хук pre-upgrade.

### Какие объекты обеспечат доступность backend при выводе ноды на обслуживание?
- [x] Несколько реплик, разнесённых по нодам
- [x] PodDisruptionBudget, который не даёт выселить слишком много реплик сразу
- [ ] Один под с большим лимитом памяти
- [ ] ConfigMap
> drain учитывает PDB.

### Какой набор NetworkPolicy соответствует принципу наименьших привилегий для этого стека?
- [ ] Разрешить всё всем
- [x] Запретить всё по умолчанию и разрешить frontend → backend, backend → postgres и DNS
- [ ] Запретить только трафик к frontend
- [ ] NetworkPolicy не нужны внутри одного namespace
> Не забудьте про Ingress-контроллер → frontend и backend.

### Где должны храниться манифесты после окончания практики?
- [ ] Только в кластере
- [x] В Git-репозитории — это источник истины, из которого кластер можно воспроизвести
- [ ] В etcd
- [ ] На рабочем столе
> Дальше их удобно превратить в Helm-чарт.

### Что произойдёт, когда вы уменьшите Deployment с 5 до 1 реплики?
- [ ] Удаляются случайные ноды
- [x] ReplicaSet удаляет лишние поды, оставляя один; сервис продолжает работать через оставшийся под
- [ ] Удаляются все поды и создаётся новый
- [ ] Deployment выдаёт ошибку
> Порядок удаления учитывает, например, неготовые поды и поды на перегруженных нодах.
