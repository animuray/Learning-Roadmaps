# Ресурсы и пробы

## requests и limits

```yaml
resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: "1"
    memory: 512Mi
```

| | **requests** | **limits** |
| --- | --- | --- |
| Что это | Гарантированный минимум | Максимум |
| Кто использует | **Scheduler**: ставит под только на ноду, где свободно ≥ requests | **kubelet/ядро (cgroups)**: не даёт превысить |
| CPU сверх | Можно использовать свободный CPU ноды | **Троттлинг** — процесс замедляется, но живёт |
| Память сверх | — | **OOMKilled** — контейнер убит (код 137) и перезапущен |

Единицы: CPU — ядра (`1`, `0.5` = `500m` милиядер); память — `Mi`, `Gi` (двоичные), `M`, `G` (десятичные).

Практические правила:

- **Всегда задавайте requests** — без них scheduler «не видит» нагрузку, ноды переполняются, HPA по CPU не работает.
- **Лимит памяти** — почти всегда; значение — по реальному потреблению с запасом. Часто requests = limits для памяти.
- **Лимит CPU** — спорный: троттлинг увеличивает задержки даже при свободных ядрах. Многие команды не ставят CPU limits для latency-чувствительных сервисов, ограничиваясь requests.
- Приложение должно знать о лимитах: JVM (`-XX:MaxRAMPercentage`), Node.js (`--max-old-space-size`), число воркеров gunicorn.

## Классы QoS

Kubernetes присваивает поду класс по его ресурсам:

| Класс | Условие | При нехватке памяти на ноде |
| --- | --- | --- |
| **Guaranteed** | У всех контейнеров requests = limits по CPU и памяти | Вытесняется последним |
| **Burstable** | Есть requests, но не равны limits | В середине |
| **BestEffort** | Нет ни requests, ни limits | Вытесняется **первым** |

Когда на ноде заканчивается память или диск, kubelet **вытесняет** (evicts) поды — статус `Evicted`. Для критичных сервисов — Guaranteed и PriorityClass.

## LimitRange и ResourceQuota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a
  namespace: team-a
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    limits.memory: 40Gi
    pods: "50"
    persistentvolumeclaims: "10"
---
apiVersion: v1
kind: LimitRange
metadata:
  name: defaults
  namespace: team-a
spec:
  limits:
    - type: Container
      default:
        memory: 512Mi
      defaultRequest:
        cpu: 100m
        memory: 256Mi
      max:
        memory: 2Gi
```

- **ResourceQuota** — лимит на весь namespace (сумма ресурсов, число объектов). С квотой поды **без** requests/limits не создадутся.
- **LimitRange** — значения по умолчанию и границы для каждого контейнера namespace.

## Пробы

kubelet периодически проверяет контейнер:

| Проба | Вопрос | Если провалилась |
| --- | --- | --- |
| **startupProbe** | Приложение уже запустилось? | Пока не прошла, liveness и readiness **не выполняются**; провал после всех попыток — перезапуск контейнера |
| **livenessProbe** | Процесс жив, не завис? | **Перезапуск контейнера** |
| **readinessProbe** | Готов принимать трафик прямо сейчас? | Под **исключается из Service** (EndpointSlice), но **не перезапускается** |

```yaml
containers:
  - name: api
    image: registry.example.com/api:1.4.2
    ports:
      - containerPort: 8000
    startupProbe:
      httpGet:
        path: /healthz
        port: 8000
      periodSeconds: 5
      failureThreshold: 30
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8000
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3
    readinessProbe:
      httpGet:
        path: /ready
        port: 8000
      periodSeconds: 5
      failureThreshold: 2
```

Способы проверки: `httpGet` (код 200–399), `tcpSocket` (порт открыт), `exec` (команда с кодом 0), `grpc`.

Параметры: `initialDelaySeconds`, `periodSeconds` (по умолчанию 10), `timeoutSeconds` (1), `failureThreshold` (3), `successThreshold` (1; для liveness и startup — только 1).

startupProbe выше даёт приложению до 30 × 5 = **150 секунд** на старт, при этом liveness после старта реагирует быстро.

### Типичные ошибки

- **Liveness проверяет зависимости** (базу, Redis, внешний API). База упала — все поды начинают перезапускаться по кругу, нагрузка растёт, восстановление дольше. Liveness проверяет **только сам процесс**. Зависимости — в readiness (и то осторожно).
- **Нет readiness** — трафик идёт в под до того, как приложение прогрелось; ошибки при каждом деплое.
- **Слишком жёсткие таймауты** — под под нагрузкой отвечает 2 секунды, liveness с `timeoutSeconds: 1` убивает его — нагрузка перекидывается на остальные, и они тоже падают.
- **Медленный старт без startupProbe** — liveness убивает приложение, которое не успело запуститься, — бесконечный CrashLoopBackOff.
- **Тяжёлый эндпоинт проверки** — проба нагружает приложение и базу.

### Пробы и ресурсы для API

В namespace **`lab-probes`** работает Deployment **`api`** (`hashicorp/http-echo:1.0`, порт 5678, без проб и ресурсов). Добавьте ему:

- **readinessProbe** и **livenessProbe** — HTTP GET на `/` порт 5678; liveness — с начальной задержкой 5 секунд;
- **requests**: 25m CPU, 32Mi памяти; **limits**: 64Mi памяти.

Deployment должен раскатиться, все поды — Ready.

```bash setup
lab_kns lab-probes
kubectl -n lab-probes create deployment api --image=hashicorp/http-echo:1.0 --replicas=2 --port=5678 -- /http-echo "-text=ok" >/dev/null
kubectl -n lab-probes rollout status deploy/api --timeout=90s >/dev/null
```

```bash check
c=$(lab_kj -n lab-probes get deploy api | jq '.spec.template.spec.containers[0]') || fail "Deployment api нет"
[ "$(echo "$c" | jq -r '.readinessProbe.httpGet.port')" = 5678 ] || fail "Нет readinessProbe с HTTP GET на 5678"
[ "$(echo "$c" | jq -r '.livenessProbe.httpGet.port')" = 5678 ] || fail "Нет livenessProbe с HTTP GET на 5678"
[ "$(echo "$c" | jq -r '.livenessProbe.initialDelaySeconds')" = 5 ] || fail "У livenessProbe начальная задержка не 5 секунд"
r=$(echo "$c" | jq -c .resources)
[ "$(echo "$r" | jq -r .requests.cpu)" = 25m ] && [ "$(echo "$r" | jq -r .requests.memory)" = 32Mi ] && [ "$(echo "$r" | jq -r .limits.memory)" = 64Mi ] || fail "Ресурсы не те: $r"
kubectl -n lab-probes rollout status deploy/api --timeout=60s >/dev/null 2>&1 || fail "Deployment не раскатился"
[ "$(lab_kj -n lab-probes get deploy api | jq -r .status.readyReplicas)" = 2 ] || fail "Не все поды Ready"
ok "пробы и ресурсы заданы, 2/2 Ready, QoS: $(kubectl -n lab-probes get pods -l app=api -o jsonpath='{.items[0].status.qosClass}')"
```

```text hint
1. Пробы и ресурсы — поля контейнера в шаблоне пода. Удобно поправить манифест (получить его можно выводом объекта в YAML) или отредактировать Deployment прямо в кластере.
2. У пробы — тип проверки (HTTP GET с путём и портом) и тайминги.
3. После изменения шаблона Deployment сам перекатит поды.
```

```bash solution
kubectl -n lab-probes patch deployment api --type=json -p '[
  {"op": "add", "path": "/spec/template/spec/containers/0/readinessProbe", "value": {"httpGet": {"path": "/", "port": 5678}, "periodSeconds": 5}},
  {"op": "add", "path": "/spec/template/spec/containers/0/livenessProbe", "value": {"httpGet": {"path": "/", "port": 5678}, "initialDelaySeconds": 5, "periodSeconds": 10}},
  {"op": "add", "path": "/spec/template/spec/containers/0/resources", "value": {"requests": {"cpu": "25m", "memory": "32Mi"}, "limits": {"memory": "64Mi"}}}
]'
kubectl -n lab-probes rollout status deploy/api
```

```text review
Эталон: `readinessProbe` + `livenessProbe` (HTTP GET) и `resources` в контейнере.

- **readiness** — готов ли под принимать трафик: не Ready → под убирают из endpoints сервиса, но не перезапускают. **liveness** — жив ли процесс: провал → перезапуск контейнера. **startup** — для медленно стартующих приложений: пока не прошла, liveness не проверяется.
- Liveness не должна проверять зависимости (базу): упала база — перезапуск всех подов ничего не исправит, только добавит нагрузки.
- `requests` = `limits` для всех ресурсов → класс QoS **Guaranteed** (выселяется последним), только requests → **Burstable**, ничего → **BestEffort** (выселяется первым при нехватке памяти на узле).
- В работе проще редактировать манифест в Git, а `kubectl patch`/`edit` — для экспериментов.
```

### Почему перезапускается под

В namespace **`lab-probes`** под **`cruncher`** постоянно перезапускается. Выясните **причину последнего завершения** контейнера (поле `reason` в его состоянии) и запишите её в `~/reason.txt`, а **код выхода** — в `~/exitcode.txt`.

```bash setup
lab_kns lab-probes
rm -f /home/student/reason.txt /home/student/exitcode.txt
cat <<'EOF' | kubectl apply -f - >/dev/null
apiVersion: v1
kind: Pod
metadata:
  name: cruncher
  namespace: lab-probes
spec:
  containers:
    - name: cruncher
      image: python:3.12-slim
      command: ["python3", "-c", "import time; time.sleep(2); a = b'x' * 300_000_000; time.sleep(60)"]
      resources:
        limits:
          memory: 64Mi
EOF
for i in $(seq 60); do [ -n "$(kubectl -n lab-probes get pod cruncher -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}' 2>/dev/null)" ] && break; sleep 1; done
```

```bash check
reason=$(kubectl -n lab-probes get pod cruncher -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}')
code=$(kubectl -n lab-probes get pod cruncher -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}')
[ -f /home/student/reason.txt ] && [ -f /home/student/exitcode.txt ] || fail "Нет ~/reason.txt или ~/exitcode.txt"
[ "$(tr -d '[:space:]' < /home/student/reason.txt)" = "$reason" ] || fail "В ~/reason.txt «$(tr -d '[:space:]' < /home/student/reason.txt)» — это не причина последнего завершения"
[ "$(tr -d '[:space:]' < /home/student/exitcode.txt)" = "$code" ] || fail "В ~/exitcode.txt неверный код выхода"
ok "cruncher: $reason, код $code — превышен лимит памяти"
```

```text hint
1. В списке подов видно число перезапусков и состояние. Подробное описание пода показывает текущее и **предыдущее** состояние контейнера: причину и код завершения.
2. Логи упавшего контейнера смотрят с ключом «предыдущий» — но при этой причине лог часто пуст.
```

```bash solution
kubectl -n lab-probes get pod cruncher
kubectl -n lab-probes describe pod cruncher | grep -A4 'Last State'
kubectl -n lab-probes get pod cruncher -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}' > ~/reason.txt
kubectl -n lab-probes get pod cruncher -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}' > ~/exitcode.txt
```

```text review
Эталон: `kubectl describe pod cruncher` → `Last State: Terminated, Reason: OOMKilled, Exit Code: 137`.

- **OOMKilled** + 137 (128 + SIGKILL) — контейнер превысил `limits.memory`, его убило ядро. В логах приложения ничего нет — оно не успело.
- Состояние `CrashLoopBackOff` — не причина, а следствие: Kubernetes перезапускает упавший контейнер с растущей паузой (10 с, 20 с … до 5 минут). Причину смотрят в `Last State` и `kubectl logs --previous`.
- Что делать: поднять лимит по реальному потреблению (`kubectl top pod`, метрики `container_memory_working_set_bytes`), найти утечку, для JVM — `-XX:MaxRAMPercentage`.
- Другие частые причины: `Error` (код ≠ 0 — смотреть логи), `Completed` у долгоживущего контейнера (процесс просто завершился), провал liveness (в событиях `Liveness probe failed`).
```
