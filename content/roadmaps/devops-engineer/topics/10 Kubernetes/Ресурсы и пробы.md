# Ресурсы и пробы

## requests и limits

```yaml
resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: "1"
    memory: 512Mi
```

| | **requests** | **limits** |
| --- | --- | --- |
| Что это | Гарантированный минимум | Максимум |
| Кто использует | **Scheduler**: ставит под только на ноду, где свободно ≥ requests | **kubelet/ядро (cgroups)**: не даёт превысить |
| CPU сверх | Можно использовать свободный CPU ноды | **Троттлинг** — процесс замедляется, но живёт |
| Память сверх | — | **OOMKilled** — контейнер убит (код 137) и перезапущен |

Единицы: CPU — ядра (`1`, `0.5` = `500m` милиядер); память — `Mi`, `Gi` (двоичные), `M`, `G` (десятичные).

Практические правила:

- **Всегда задавайте requests** — без них scheduler «не видит» нагрузку, ноды переполняются, HPA по CPU не работает.
- **Лимит памяти** — почти всегда; значение — по реальному потреблению с запасом. Часто requests = limits для памяти.
- **Лимит CPU** — спорный: троттлинг увеличивает задержки даже при свободных ядрах. Многие команды не ставят CPU limits для latency-чувствительных сервисов, ограничиваясь requests.
- Приложение должно знать о лимитах: JVM (`-XX:MaxRAMPercentage`), Node.js (`--max-old-space-size`), число воркеров gunicorn.

## Классы QoS

Kubernetes присваивает поду класс по его ресурсам:

| Класс | Условие | При нехватке памяти на ноде |
| --- | --- | --- |
| **Guaranteed** | У всех контейнеров requests = limits по CPU и памяти | Вытесняется последним |
| **Burstable** | Есть requests, но не равны limits | В середине |
| **BestEffort** | Нет ни requests, ни limits | Вытесняется **первым** |

Когда на ноде заканчивается память или диск, kubelet **вытесняет** (evicts) поды — статус `Evicted`. Для критичных сервисов — Guaranteed и PriorityClass.

## LimitRange и ResourceQuota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a
  namespace: team-a
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    limits.memory: 40Gi
    pods: "50"
    persistentvolumeclaims: "10"
---
apiVersion: v1
kind: LimitRange
metadata:
  name: defaults
  namespace: team-a
spec:
  limits:
    - type: Container
      default:
        memory: 512Mi
      defaultRequest:
        cpu: 100m
        memory: 256Mi
      max:
        memory: 2Gi
```

- **ResourceQuota** — лимит на весь namespace (сумма ресурсов, число объектов). С квотой поды **без** requests/limits не создадутся.
- **LimitRange** — значения по умолчанию и границы для каждого контейнера namespace.

## Пробы

kubelet периодически проверяет контейнер:

| Проба | Вопрос | Если провалилась |
| --- | --- | --- |
| **startupProbe** | Приложение уже запустилось? | Пока не прошла, liveness и readiness **не выполняются**; провал после всех попыток — перезапуск контейнера |
| **livenessProbe** | Процесс жив, не завис? | **Перезапуск контейнера** |
| **readinessProbe** | Готов принимать трафик прямо сейчас? | Под **исключается из Service** (EndpointSlice), но **не перезапускается** |

```yaml
containers:
  - name: api
    image: registry.example.com/api:1.4.2
    ports:
      - containerPort: 8000
    startupProbe:
      httpGet:
        path: /healthz
        port: 8000
      periodSeconds: 5
      failureThreshold: 30
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8000
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3
    readinessProbe:
      httpGet:
        path: /ready
        port: 8000
      periodSeconds: 5
      failureThreshold: 2
```

Способы проверки: `httpGet` (код 200–399), `tcpSocket` (порт открыт), `exec` (команда с кодом 0), `grpc`.

Параметры: `initialDelaySeconds`, `periodSeconds` (по умолчанию 10), `timeoutSeconds` (1), `failureThreshold` (3), `successThreshold` (1; для liveness и startup — только 1).

startupProbe выше даёт приложению до 30 × 5 = **150 секунд** на старт, при этом liveness после старта реагирует быстро.

### Типичные ошибки

- **Liveness проверяет зависимости** (базу, Redis, внешний API). База упала — все поды начинают перезапускаться по кругу, нагрузка растёт, восстановление дольше. Liveness проверяет **только сам процесс**. Зависимости — в readiness (и то осторожно).
- **Нет readiness** — трафик идёт в под до того, как приложение прогрелось; ошибки при каждом деплое.
- **Слишком жёсткие таймауты** — под под нагрузкой отвечает 2 секунды, liveness с `timeoutSeconds: 1` убивает его — нагрузка перекидывается на остальные, и они тоже падают.
- **Медленный старт без startupProbe** — liveness убивает приложение, которое не успело запуститься, — бесконечный CrashLoopBackOff.
- **Тяжёлый эндпоинт проверки** — проба нагружает приложение и базу.

## Практика

- [ ] Задать поду requests и limits, посмотреть его класс QoS в `kubectl get pod -o jsonpath='{.status.qosClass}'`
- [ ] Запустить под с потреблением памяти выше лимита (`polinux/stress`) и увидеть OOMKilled и код 137
- [ ] Запустить под с requests больше, чем есть на нодах, и разобрать `Pending` с сообщением `Insufficient cpu`
- [ ] Посмотреть распределённые ресурсы ноды: `kubectl describe node` (Allocated resources) и `kubectl top`
- [ ] Сломать readiness (вернуть 500 с /ready) и убедиться, что под пропал из EndpointSlice, но не перезапускается
- [ ] Сломать liveness и убедиться, что контейнер перезапускается (растёт RESTARTS)
- [ ] Сделать приложение с долгим стартом и подобрать startupProbe так, чтобы оно не уходило в CrashLoopBackOff
- [ ] Создать namespace с ResourceQuota и LimitRange и проверить, что под без ресурсов получает значения по умолчанию
