# CI и CD

Раньше выпуск релиза выглядел так: месяц разработки в отдельных ветках, неделя «интеграционного ада» со слиянием и починкой, ночной ручной деплой по инструкции из вики. **CI/CD** превращает это в конвейер: каждое изменение автоматически собирается, проверяется и доставляется.

## Continuous Integration — непрерывная интеграция

Разработчики **часто** (минимум раз в день) вливают изменения в основную ветку, и **каждое** изменение автоматически:

1. собирается;
2. проверяется линтерами и тестами;
3. даёт быструю обратную связь — сломал → узнал через минуты, а не через неделю.

Принципы CI:

- один общий репозиторий и основная ветка;
- автоматическая сборка одной командой;
- самотестирующаяся сборка — тесты часть пайплайна;
- маленькие и частые коммиты;
- **сломанная сборка — приоритет номер один**, её чинят сразу;
- сборка быстрая (ориентир — до 10 минут);
- результат виден всем.

## Continuous Delivery — непрерывная поставка

Продолжение CI: каждое изменение, прошедшее проверки, автоматически доходит до состояния **«готово к релизу»** — собран артефакт (образ), развёрнут на тестовые окружения, прошёл тесты. **Выкатка в прод — по кнопке** (решение человека: бизнес, время, согласование).

## Continuous Deployment — непрерывное развёртывание

Ещё шаг дальше: каждое изменение, прошедшее **все** проверки, уходит в прод **автоматически**, без ручного шага. Требует очень хороших автотестов, мониторинга, feature flags и быстрого отката.

```
         Continuous Integration          Continuous Delivery        Continuous Deployment
код ─► сборка ─► тесты ─► артефакт ─► деплой на stage ─► [кнопка] ─► прод
                                                       └─ авто ───► прод
```

| | CI | Continuous Delivery | Continuous Deployment |
| --- | --- | --- | --- |
| Сборка и тесты на каждый коммит | Да | Да | Да |
| Автоматический деплой на тестовые окружения | Нет/по желанию | Да | Да |
| Деплой в прод | Вручную, отдельно | По кнопке | Автоматически |

## Зачем это бизнесу

- **Маленькие изменения** — проще найти ошибку и откатить.
- **Быстрее time-to-market** — фича в проде через часы, а не месяцы.
- **Меньше ручного труда и человеческих ошибок** — деплой одинаковый каждый раз.
- **Прозрачность** — история: какой коммит, когда и куда выкачен.

Метрики DORA для оценки процесса: частота деплоев, время от коммита до прода (lead time), доля неудачных изменений, время восстановления.

## Стратегии ветвления

- **GitFlow** — ветки `main`, `develop`, `feature/*`, `release/*`, `hotfix/*`. Подходит для продуктов с явными версиями, но длинные ветки противоречат идее частой интеграции.
- **GitHub Flow / GitLab Flow** — короткие feature-ветки и merge request в `main`; GitLab Flow добавляет ветки или правила для окружений.
- **Trunk-based development** — все коммитят в `main` (или очень короткие ветки), незаконченные фичи прячутся за feature flags. Ближе всего к «настоящему» CI.

## Инструменты

- **GitLab CI** — встроен в GitLab, YAML-конфиг в репозитории. Популярен в России.
- **Jenkins** — старейший, гибкий, тысячи плагинов, часто в банках и крупных компаниях с легаси.
- **GitHub Actions**, TeamCity, CircleCI, Bitbucket Pipelines, Tekton.
- В CD интегрируются Docker (образ — артефакт), реестры, Ansible, Helm, Terraform, Argo CD (GitOps).

## Роль DevOps-инженера

Не «нажимать кнопку деплоя», а **построить и поддерживать конвейер**: шаблоны пайплайнов, раннеры, кэш, секреты, окружения, безопасность (сканирование), скорость и надёжность сборок — чтобы разработчики сами безопасно доставляли код.

## Тест

### Что такое Continuous Integration?
- [ ] Автоматический деплой в прод
- [x] Практика частого слияния изменений в основную ветку с автоматической сборкой и тестами на каждое изменение
- [ ] Ручное тестирование перед релизом
- [ ] Хранение кода в Git
> Цель — быстро находить ошибки интеграции.

### Чем Continuous Delivery отличается от Continuous Deployment?
- [ ] Это одно и то же
- [x] При Continuous Delivery релиз в прод выполняется по решению человека (кнопкой), при Continuous Deployment — автоматически после прохождения всех проверок
- [ ] Continuous Deployment не использует тесты
- [ ] Continuous Delivery не собирает артефакты
> В обоих случаях код всегда в состоянии «готово к релизу».

### Что должна делать команда, если сборка в основной ветке сломана?
- [ ] Продолжать коммитить, починят потом
- [x] Починить её в первую очередь — сломанный main блокирует всех
- [ ] Отключить тесты
- [ ] Удалить ветку
> Это один из ключевых принципов CI.

### Почему маленькие и частые изменения лучше больших редких?
- [x] Проще найти причину ошибки и откатить изменение
- [x] Меньше конфликтов при слиянии
- [ ] Так меньше нагрузка на Git
- [ ] Большие изменения нельзя протестировать
> Большие релизы — большой риск.

### Что требуется для Continuous Deployment в первую очередь?
- [x] Надёжные автоматические тесты
- [x] Мониторинг и быстрый откат
- [ ] Ручное согласование каждого релиза
- [ ] Ночные окна обслуживания
> Без хороших тестов автоматический прод — лотерея.

### Какая стратегия ветвления ближе всего к идее непрерывной интеграции?
- [ ] GitFlow с долгоживущими ветками
- [x] Trunk-based development с короткими ветками и feature flags
- [ ] Ветка на каждого разработчика на месяц
- [ ] Без веток и без Git
> Чем дольше живёт ветка, тем больнее её вливать.

### Какие метрики DORA оценивают процесс доставки?
- [x] Частота деплоев
- [x] Время от коммита до прода (lead time)
- [x] Доля неудачных изменений и время восстановления
- [ ] Число строк кода
> Четыре ключевые метрики DORA.

### Какой инструмент CI/CD встроен прямо в GitLab?
= GitLab CI
= gitlab ci/cd
> Конфигурация — `.gitlab-ci.yml` в корне репозитория.

### Где чаще встречается Jenkins?
- [ ] Только в стартапах
- [x] В крупных компаниях и банках с давно настроенной инфраструктурой и легаси-проектами
- [ ] Только в облаках
- [ ] Только на Windows
> Jenkins гибок за счёт плагинов, но требует больше поддержки.

### Что является артефактом в типичном пайплайне контейнерного приложения?
- [ ] Исходный код
- [x] Docker-образ, выгруженный в реестр
- [ ] Логи сборки
- [ ] Merge request
> Один и тот же образ продвигается по окружениям.

### Какова главная задача DevOps-инженера в CI/CD?
- [ ] Вручную деплоить каждый релиз
- [x] Построить и поддерживать надёжный и быстрый конвейер, через который разработчики сами безопасно доставляют код
- [ ] Писать бизнес-логику приложения
- [ ] Тестировать приложение вручную
> Шаблоны, раннеры, секреты, окружения, скорость сборок.

### Что даёт бизнесу CI/CD?
- [x] Более быстрый выпуск фич
- [x] Меньше ошибок из-за ручных действий
- [ ] Отказ от тестирования
- [ ] Гарантию отсутствия багов
> Ошибки всё равно будут, но их проще находить и откатывать.
