# CI-CD на собеседовании

## Главные вопросы

**Как бы ты построил идеальный пайплайн?**
На MR: линтеры, юнит-тесты, сборка образа, сканирование — параллельно (`needs`), с кэшем, 5–10 минут. Merge в main: образ с тегом SHA в реестр, автодеплой на staging, smoke-тесты. Прод: тот же образ, ручное подтверждение или тег релиза, защищённое окружение, rolling/canary, проверка health и метрик, быстрый откат на прошлый тег. Секреты — Vault или masked + protected переменные. Общие шаблоны через `include`. Уведомления. Всё в Git.

**CI, Continuous Delivery, Continuous Deployment?**
CI — частое слияние + автосборка и тесты на каждое изменение. Delivery — каждое изменение автоматически доходит до готовности к релизу, прод — по кнопке. Deployment — в прод автоматически, без ручного шага.

**extends и include?**
`include` подключает YAML из других файлов, проектов, URL, шаблонов. `extends` наследует конфигурацию скрытой задачи (словари сливаются, списки заменяются). Вместе: шаблоны в отдельном репозитории + `extends` в проектах. YAML-якоря — только в пределах файла.

**Кэш и артефакты?**
Кэш — ускорение (зависимости), на раннере, между пайплайнами, без гарантий. Артефакты — результат задачи, в GitLab, передаются следующим этапам, гарантированы.

**Как хранить секреты?**
Не в репозитории. CI/CD Variables: masked (не видно в логах), protected (только защищённые ветки), file (ключи), environment scope. Лучше — внешнее хранилище (Vault) с короткоживущими токенами (OIDC, `id_tokens`).

**Executors?**
shell — на хосте, без изоляции; docker — контейнер на задачу; kubernetes — под на задачу; autoscaler — облачные ВМ по требованию.

**Как собирать Docker-образы в CI?**
dind (privileged), проброс docker.sock (опасно), Kaniko/Buildah (без привилегий). Кэш слоёв через реестр.

**Как ускорить пайплайн?**
`needs` вместо этапов, параллельные задачи и `parallel: matrix`, кэш зависимостей и слоёв Docker, `rules: changes` (не запускать лишнее), `interruptible`, лёгкие образы, свои раннеры поближе к реестру.

**Стратегии деплоя?**
Recreate, rolling, blue-green, canary, feature flags. Откат — деплой предыдущего неизменяемого тега.

**Push или GitOps?**
Push — CI сам деплоит (нужны креды прода в CI). GitOps — CI обновляет тег в Git, Argo CD/Flux в кластере сам синхронизирует.

**Jenkins: из чего состоит?**
Controller + agents (executors, labels), Jenkinsfile (declarative: pipeline, agent, stages, steps, post), credentials, плагины, shared libraries.

## Разбор упавших пайплайнов

| Симптом | Причина и решение |
| --- | --- |
| Задача в `pending` | Нет подходящего раннера: tags, раннер не назначен, protected-раннер для незащищённой ветки |
| `command not found` | В образе задачи нет утилиты — другой образ или установка в `before_script`; на shell-раннере не установлено на хосте |
| Секрет пустой | Переменная Protected, а ветка не защищена; не тот environment scope |
| `Cannot connect to the Docker daemon` | Нет `services: docker:dind`, не включён privileged, неверный `DOCKER_HOST`/TLS |
| `Host key verification failed` | Нет `known_hosts` для сервера деплоя |
| Задача не появилась в пайплайне | `rules` не совпали, `workflow:rules` отфильтровал, `changes` не сработал |
| Пайплайн медленный | Нет кэша, всё последовательно, тяжёлые образы, каждый раз качаются зависимости |
| Двойные пайплайны | Пайплайн и для ветки, и для MR — настроить `workflow:rules` |
| `toomanyrequests` от Docker Hub | Лимит анонимных pull — зеркало, авторизация, свой реестр |

## Тест

### Чем Continuous Delivery отличается от Continuous Deployment?
- [ ] Ничем
- [x] При Delivery выкатка в прод выполняется по решению человека, при Deployment — автоматически после прохождения всех проверок
- [ ] Delivery не использует автотесты
- [ ] Deployment не использует CI
> В обоих случаях каждое изменение доводится до готовности к релизу.

### Чем extends отличается от include?
- [x] include подключает YAML-конфигурацию из других файлов или проектов
- [x] extends наследует настройки другой (обычно скрытой) задачи
- [ ] Это синонимы
- [ ] extends работает только с удалёнными файлами
> Их используют вместе: шаблон подключается include и применяется extends.

### Что верно про кэш и артефакты в GitLab CI?
- [x] Кэш — оптимизация для зависимостей, может отсутствовать
- [x] Артефакты гарантированно передаются задачам следующих этапов пайплайна
- [ ] Артефакты переиспользуются между разными пайплайнами вместо кэша
- [ ] Кэш хранится в Git
> Задача должна работать и без кэша.

### Какие способы реально ускоряют пайплайн?
- [x] needs вместо ожидания целых этапов
- [x] Кэш зависимостей и слоёв Docker
- [x] rules: changes, чтобы не запускать задачи для неизменённых частей
- [ ] Отключение всех тестов
> Ещё — параллельность, лёгкие образы, interruptible.

### Секретная переменная пустая в задаче feature-ветки, хотя в main она есть. Почему?
- [ ] Ошибка GitLab
- [x] Переменная отмечена Protected и доступна только в защищённых ветках и тегах
- [ ] Переменная Masked
- [ ] Нужно перезапустить раннер
> Это защита: код из произвольной ветки не получает секреты прода.

### Задача падает с Cannot connect to the Docker daemon. Что проверить?
- [x] Подключён ли services: docker:dind
- [x] Включён ли privileged-режим у docker executor раннера
- [x] Правильность DOCKER_HOST и настроек TLS
- [ ] Наличие файла README
> Альтернатива — собирать образы через Kaniko без демона.

### Чем опасен shell executor для общих раннеров?
- [ ] Он медленный
- [x] Задачи выполняются прямо на хосте без изоляции: любой проект может повлиять на систему и другие задачи
- [ ] Он не поддерживает переменные
- [ ] Он не умеет запускать скрипты
> Для общих раннеров используют docker или kubernetes executor.

### Как правильно откатить неудачный релиз?
- [ ] Чинить прямо на сервере
- [x] Задеплоить предыдущий неизменяемый тег образа (например, Re-deploy в Environments)
- [ ] Пересобрать образ latest
- [ ] Удалить коммит из истории
> Поэтому теги образов — SHA коммита или версия.

### Почему в прод выкатывают тот же образ, что прошёл staging?
- [ ] Чтобы сэкономить место
- [x] Пересобранный образ — новый, непроверенный артефакт: могли измениться зависимости или базовый образ
- [ ] Так требует Kubernetes
- [ ] Прод не умеет скачивать образы
> Build once, deploy many.

### Чем GitOps отличается от push-деплоя из CI?
- [ ] GitOps не использует Git
- [x] В GitOps агент в кластере сам приводит состояние к описанию в Git, а CI лишь обновляет описание; при push CI сам подключается к целевой системе
- [ ] Push-деплой всегда безопаснее
- [ ] GitOps работает только с Jenkins
> Примеры GitOps-инструментов — Argo CD и Flux.

### Задача не появилась в пайплайне. Возможные причины?
- [x] Ни одно правило rules не совпало
- [x] workflow:rules не создал пайплайн для этого события
- [x] Условие changes не сработало для изменённых файлов
- [ ] У задачи слишком длинный script
> Если задача не попала в пайплайн, у неё нет и статуса.

### Как избежать двух одновременных пайплайнов для ветки и для её merge request?
- [ ] Удалить ветку
- [x] Настроить workflow:rules, чтобы создавался либо пайплайн MR, либо пайплайн ветки
- [ ] Отключить merge request
- [ ] Использовать only: branches
> Это частая проблема при переходе на rules.

### Как безопаснее всего собирать Docker-образы на общих раннерах?
- [ ] Пробросить /var/run/docker.sock
- [x] Использовать сборщики без привилегий и без демона — Kaniko, Buildah или BuildKit rootless
- [ ] Запускать раннер от root на хосте с shell executor
- [ ] Собирать образы на проде
> dind требует privileged-режим, а проброс сокета даёт root на хосте.

### Где в Jenkins задают действия, которые выполняются после пайплайна при любом исходе?
- [ ] В блоке environment
- [x] В блоке post с секцией always
- [ ] В блоке parameters
- [ ] В блоке options
> Для успеха и падения — секции success и failure.
