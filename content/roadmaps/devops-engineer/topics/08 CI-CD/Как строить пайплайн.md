# Как строить пайплайн

**Пайплайн** — автоматизированная цепочка шагов от коммита до работающего в проде кода. Ранние стадии быстрые и ловят большинство проблем, поздние — медленнее и проверяют глубже.

## Типичные стадии

```
 lint ─► build ─► test ─► security ─► push ─► deploy dev ─► deploy stage ─► [approve] ─► deploy prod ─► smoke/verify
```

| Стадия | Что делаем | Примеры |
| --- | --- | --- |
| **Lint / проверка** | Стиль кода, синтаксис конфигов, Dockerfile | flake8, ruff, eslint, hadolint, yamllint, `terraform validate` |
| **Build** | Сборка артефакта | `docker build`, `npm run build`, `go build` |
| **Test** | Юнит- и интеграционные тесты | pytest, jest, `go test`, тесты с базой в services |
| **Security** | Уязвимости и секреты | trivy (образ), SAST, поиск секретов (gitleaks), проверка зависимостей |
| **Push / publish** | Артефакт в реестр | `docker push` с тегом SHA, публикация пакета |
| **Deploy** | Выкатка на окружение | SSH + `docker compose`, Ansible, `helm upgrade`, коммит в GitOps-репозиторий |
| **Verify** | Smoke-тесты после деплоя | `curl /health`, e2e, проверка метрик |

## Принципы хорошего пайплайна

1. **Fail fast** — быстрые проверки первыми: линтер за 20 секунд лучше, чем ждать 10 минут сборки ради опечатки.
2. **Собрать один раз — продвигать везде** (build once, deploy many). Тот же образ с тем же digest едет в dev, stage и prod. Окружения различаются только конфигурацией. Пересобирать для прода — значит выкатывать непроверенное.
3. **Неизменяемые артефакты** — тег = SHA коммита или версия, не `latest`.
4. **Воспроизводимость** — сборка в контейнере с фиксированными версиями, пайплайн как код в репозитории.
5. **Параллельность и кэш** — независимые задачи параллельно (`needs`), кэш зависимостей, кэш слоёв Docker.
6. **Секреты не в коде** — переменные CI/CD (masked, protected), Vault; секреты прода доступны только защищённым веткам.
7. **Окружения и контроль** — dev автоматически, stage по merge в main, prod вручную или с согласованием; защищённые окружения.
8. **Откат за минуты** — деплой предыдущего тега, а не «чиним в проде».
9. **Наблюдаемость** — уведомления о падениях, видно, какая версия где развёрнута.
10. **Быстрота** — ориентир 10–15 минут до результата; медленные тесты — отдельно (по расписанию, перед релизом).

## Артефакты

**Артефакт** — результат одной задачи, нужный следующим: собранный бинарник, отчёт тестов, план Terraform, архив статики. В GitLab — `artifacts:`; для образов артефактом служит реестр.

Не путать с **кэшем**: кэш — ускорение (зависимости), может отсутствовать; артефакт — гарантированный результат, без которого следующий шаг не выполнится.

## Окружения

| Окружение | Когда деплоится | Зачем |
| --- | --- | --- |
| **dev** / review | На каждый push в ветку или MR | Проверить фичу, показать |
| **staging** | После merge в main | Копия прода: финальные проверки |
| **prod** | Вручную, по тегу или после согласования | Пользователи |

Динамические review-окружения: отдельный стенд на каждый merge request (`review/$CI_COMMIT_REF_SLUG`), удаляется после мержа.

## Стратегии деплоя

- **Recreate** — остановить старое, запустить новое. Есть простой.
- **Rolling update** — заменять экземпляры по одному. По умолчанию в Kubernetes.
- **Blue-green** — два одинаковых окружения, переключение трафика целиком. Мгновенный откат.
- **Canary** — новая версия получает небольшой процент трафика, затем больше.
- **Feature flags** — код выкачен, но фича включается флагом.

## Push и pull (GitOps)

- **Push-модель:** пайплайн сам ходит в целевую систему (SSH на сервер, `kubectl apply`, `helm upgrade`). Просто, но CI нужны креды от прода.
- **Pull-модель / GitOps:** желаемое состояние описано в Git-репозитории (манифесты, values с тегом образа). Агент в кластере (**Argo CD**, Flux) сам подтягивает изменения и приводит кластер к описанию. CI только собирает образ и коммитит новый тег. Git — единый источник истины, история и откат — через Git.

## Идеальный пайплайн — как ответить на собеседовании

> Каждый merge request: линтеры, юнит-тесты, сборка образа, сканирование — параллельно, с кэшем, за 5–10 минут. Merge в main: образ с тегом SHA в реестр, автоматический деплой на staging, smoke-тесты. Прод: тот же образ, ручное подтверждение или по тегу релиза, защищённое окружение, rolling или canary, автоматическая проверка health и метрик, откат на предыдущий тег. Секреты в Vault или защищённых переменных, общие шаблоны через include, уведомления о падениях, всё описано кодом в Git.

## Практика

- [ ] Нарисовать пайплайн для своего приложения из практики Docker: стадии, задачи, что параллельно, где ручной шаг
- [ ] Определить, какие проверки можно запускать до сборки образа (fail fast)
- [ ] Расписать, какие секреты нужны каждой стадии и кто должен иметь к ним доступ
- [ ] Описать план отката: что именно делается, если после деплоя в прод выросло число ошибок
- [ ] Сформулировать вслух ответ «как бы ты построил идеальный пайплайн» за 2 минуты

## Тест

### Что означает принцип fail fast в пайплайне?
- [ ] Пайплайн должен падать как можно чаще
- [x] Быстрые проверки (линтеры, юнит-тесты) выполняются первыми, чтобы ошибка обнаруживалась как можно раньше
- [ ] Тесты запускаются после деплоя
- [ ] Не нужно запускать тесты
> Минута на линтер экономит десятки минут пустой сборки.

### Почему образ собирают один раз и продвигают по окружениям, а не пересобирают для прода?
- [ ] Так экономится место в реестре
- [x] Пересобранный образ — это новый непроверенный артефакт: могли измениться зависимости или базовый образ
- [ ] Прод не умеет собирать образы
- [ ] Так требует Docker
> В проде должен оказаться ровно тот образ, который прошёл тесты на stage.

### Чем артефакт отличается от кэша в CI?
- [x] Артефакт — гарантированный результат задачи для следующих шагов, кэш — ускорение, которое может отсутствовать
- [ ] Ничем
- [ ] Кэш передаётся между стадиями, артефакт — нет
- [ ] Артефакты хранятся только на раннере
> Зависимости — в кэш, собранный результат — в артефакты.

### Какие задачи обычно относятся к стадии security?
- [x] Сканирование образа на уязвимости (например, trivy)
- [x] Поиск секретов в коде
- [x] Проверка уязвимых зависимостей
- [ ] Сборка Docker-образа
> Это часть подхода DevSecOps.

### Чем стратегия blue-green отличается от rolling update?
- [ ] Ничем
- [x] Blue-green держит два полных окружения и переключает трафик целиком, rolling update заменяет экземпляры постепенно
- [ ] Rolling update требует двух кластеров
- [ ] Blue-green всегда с простоем
> Blue-green даёт мгновенный откат переключением обратно.

### Что такое canary-деплой?
- [ ] Деплой ночью
- [x] Новая версия сначала получает небольшую долю трафика, и её долю увеличивают, если метрики в норме
- [ ] Деплой без тестов
- [ ] Деплой на одну машину разработчика
> Ошибка затронет малую часть пользователей.

### Чем GitOps (pull-модель) отличается от push-модели деплоя?
- [ ] В GitOps деплой выполняет разработчик руками
- [x] В GitOps агент в кластере сам синхронизирует состояние с Git-репозиторием, а CI только обновляет описание; в push-модели пайплайн сам подключается к целевой системе
- [ ] GitOps не использует Git
- [ ] Push-модель безопаснее, потому что CI не нужны креды
> Примеры GitOps-агентов — Argo CD и Flux.

### Как правильно тегировать образ, который едет в прод?
- [ ] latest
- [x] SHA коммита или номер версии — неизменяемый тег
- [ ] Имя ветки
- [ ] Дата без времени
> Так видно, что развёрнуто, и откат — это деплой предыдущего тега.

### Как обычно организуют доставку по окружениям?
- [x] dev — автоматически на push или merge request
- [x] staging — автоматически после merge в main
- [x] prod — вручную, по тегу релиза или после согласования
- [ ] prod — на каждый push в любую ветку
> Это классическая схема Continuous Delivery.

### Где должны храниться секреты, нужные пайплайну?
- [ ] В .gitlab-ci.yml
- [ ] В Dockerfile
- [x] В переменных CI/CD с маскированием и защитой или во внешнем хранилище секретов (например, Vault)
- [ ] В README
> Секреты прода — только для защищённых веток и окружений.

### Что такое review-окружение?
- [ ] Окружение для code review без деплоя
- [x] Временный стенд, который поднимается для конкретного merge request и удаляется после мержа
- [ ] Прод для тестировщиков
- [ ] Окружение только для документации
> Удобно показать фичу до слияния.

### Какое действие правильное, если после деплоя в прод выросло число ошибок?
- [ ] Чинить прямо на сервере
- [x] Быстро откатиться на предыдущую версию (предыдущий тег), а затем разбираться
- [ ] Ждать, пока само пройдёт
- [ ] Удалить мониторинг
> Сначала восстановление сервиса, потом поиск причины.
