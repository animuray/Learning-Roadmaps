# Практика — окружения и шаблоны

Продолжение прошлой практики. Задача из роадмапа: **dev** — по пушу в ветку, **staging** — по мержу в main, **prod** — вручную; артефакты; секреты в настройках CI/CD; кэш зависимостей; общий шаблон CI для нескольких проектов через `include`.

## Часть 1. Окружения

| Окружение | Когда | Сервер | Правило |
| --- | --- | --- | --- |
| `dev` | push в любую ветку, кроме main | dev-сервер | автоматически |
| `staging` | merge в main | staging-сервер | автоматически |
| `production` | после staging | prod-сервер | `when: manual` |

Один и тот же образ `:SHA` едет на staging и prod — пересобирать нельзя.

Секреты — с **environment scope**: переменная `DEPLOY_HOST` создаётся трижды со scope `dev`, `staging`, `production` и разными значениями. Задача с `environment: name: staging` получит значение для staging. Секреты прода — ещё и Protected.

## Часть 2. Репозиторий шаблонов

Создаём проект `devops/ci-templates`:

```
ci-templates/
├── templates/
│   ├── python-lint.yml
│   ├── docker-build.yml
│   └── deploy-ssh.yml
└── README.md
```

`templates/docker-build.yml`:

```yaml
.docker-build:
  stage: build
  image: docker:27
  services: [docker:27-dind]
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
    IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
  before_script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login "$CI_REGISTRY" -u "$CI_REGISTRY_USER" --password-stdin
  script:
    - docker build -t "$IMAGE" .
    - docker push "$IMAGE"
```

`templates/deploy-ssh.yml`:

```yaml
.deploy-ssh:
  stage: deploy
  image: alpine:3.20
  resource_group: $CI_ENVIRONMENT_NAME
  before_script:
    - apk add --no-cache openssh-client curl
    - eval $(ssh-agent -s)
    - chmod 400 "$SSH_PRIVATE_KEY" && ssh-add "$SSH_PRIVATE_KEY"
    - mkdir -p ~/.ssh && cp "$SSH_KNOWN_HOSTS" ~/.ssh/known_hosts
  script:
    - ssh "$DEPLOY_HOST" "cd /opt/app && APP_IMAGE=$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA docker compose up -d app"
    - curl --fail --retry 10 --retry-all-errors "$CI_ENVIRONMENT_URL/health"
```

Выпускаем версию шаблонов: тег `v1.0.0`.

## Часть 3. Пайплайн проекта — 40 строк вместо 150

```yaml
include:
  - project: devops/ci-templates
    ref: v1.0.0
    file:
      - templates/python-lint.yml
      - templates/docker-build.yml
      - templates/deploy-ssh.yml

stages: [lint, build, deploy]

variables:
  PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip"

lint:
  extends: .python-lint
  cache:
    key:
      files: [requirements.txt]
    paths: [.cache/pip]

build:
  extends: .docker-build

deploy-dev:
  extends: .deploy-ssh
  environment:
    name: dev
    url: https://dev.app.example.com
  rules:
    - if: $CI_COMMIT_BRANCH && $CI_COMMIT_BRANCH != $CI_DEFAULT_BRANCH

deploy-staging:
  extends: .deploy-ssh
  environment:
    name: staging
    url: https://staging.app.example.com
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

deploy-prod:
  extends: .deploy-ssh
  needs: [deploy-staging]
  environment:
    name: production
    url: https://app.example.com
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: manual
```

Второй проект подключает те же шаблоны — и получает такой же проверенный пайплайн. Исправление в шаблоне — новая версия `v1.1.0`, проекты переходят на неё осознанно.

## Часть 4. Артефакты

Добавьте задачу, которая сохраняет отчёт тестов (`reports: junit`) и `coverage.xml` с `expire_in: 1 week`, а в деплое — файл `deploy-info.txt` с версией, временем и окружением (`artifacts: when: always`).

## Что проверить

- push в feature-ветку → lint, build, deploy-dev;
- merge в main → lint, build, deploy-staging, кнопка deploy-prod;
- у deploy-prod значения переменных из scope `production`;
- в Environments видна история каждого окружения;
- время lint с тёплым кэшем заметно меньше, чем с холодным.

## Лаборатория

```bash lib
# Пайплайны GitLab CI выполняются локально утилитой gitlab-ci-local (shell executor — задачи идут прямо на стенде)
# lab_ci_repo каталог — новый репозиторий ученика с одним коммитом (файлы кладёт вызывающий до коммита)
lab_ci_repo() { rm -rf "$1"; mkdir -p "$1"; }
lab_ci_commit() { chown -R student:student "$1"; su - student -c "cd $1 && git init -q -b main 2>/dev/null; git add -A && git commit -qm 'Initial commit'"; }
# lab_ci_run каталог [ключи] — пайплайн от имени ученика; вывод — в /tmp/lab-ci.log, код возврата — код пайплайна
lab_ci_run() { su - student -c "cd $1 && timeout 300 gitlab-ci-local $2" > /tmp/lab-ci.log 2>&1; }
# lab_ci_preview каталог — итоговый YAML после include, extends и default (JSON)
lab_ci_preview() { su - student -c "cd $1 && gitlab-ci-local --preview" 2>/dev/null | sed -n '/^---$/,$p' | python3 -c 'import sys,yaml,json; print(json.dumps(yaml.safe_load(sys.stdin)))'; }
# lab_ci_jobs каталог [ветка] — список задач (JSON); с веткой — во временной копии репозитория на этой ветке
lab_ci_jobs() {
  if [ -n "$2" ]; then
    rm -rf /tmp/lab-ci-branch; su - student -c "git clone -q $1 /tmp/lab-ci-branch && cd /tmp/lab-ci-branch && cp $1/.gitlab-ci*.yml . 2>/dev/null; [ -d $1/ci ] && mkdir -p ci && cp -r $1/ci/. ci/; git switch -qc $2 && gitlab-ci-local --list-json" 2>/dev/null
  else
    su - student -c "cd $1 && gitlab-ci-local --list-json" 2>/dev/null
  fi
}
lab_ci_log() { sed 's/\x1b\[[0-9;]*m//g' /tmp/lab-ci.log | grep -vE '^\s*$' | tail -n "${1:-4}" | tr '\n' ' ' | cut -c1-300; }
lab_drm() { docker rm -f "$@" >/dev/null 2>&1; true; }
# образ есть локально или скачивается (если ученик почистил образы через prune)
lab_img() { for i in "$@"; do docker image inspect "$i" >/dev/null 2>&1 || docker pull -q "$i" >/dev/null; done; }
# lab_wait_http URL [строка] — дождаться ответа
lab_wait_http() { for i in $(seq 60); do curl -s --max-time 1 "$1" 2>/dev/null | grep -q "${2:-.}" && return 0; sleep 0.25; done; return 1; }
```

### Три окружения на общих шаблонах

В `~/ci-envs` нужно построить деплой в три окружения с **общим шаблоном в отдельном файле**:

1. Создайте `ci/templates.yml` со скрытой задачей **`.deploy`**: этап `deploy`, скрипт `echo "deploy to $ENV_NAME"`.
2. Подключите этот файл в `.gitlab-ci.yml` через **`include`** и опишите три задачи, наследующие `.deploy` через `extends`, — у каждой своё **окружение** (`environment`) и своя `ENV_NAME`:
   - **`deploy-dev`** — окружение `dev`, автоматически, **во всех ветках, кроме `main`**;
   - **`deploy-staging`** — окружение `staging`, автоматически, **только в `main`**;
   - **`deploy-production`** — окружение `production`, **вручную**, только в `main` и **только после** `deploy-staging` (`needs`).

```bash setup
su - student -c 'git config --global user.name >/dev/null || git config --global user.name Student; git config --global user.email >/dev/null || git config --global user.email student@stand.local'
d=/home/student/ci-envs
lab_ci_repo $d
printf 'stages: [deploy]\n' > $d/.gitlab-ci.yml
printf '.gitlab-ci-local/\n' > $d/.gitignore
lab_ci_commit $d
```

```bash check
d=/home/student/ci-envs
[ -f $d/ci/templates.yml ] || fail "Нет ~/ci-envs/ci/templates.yml"
grep -qE '^\.deploy:' $d/ci/templates.yml || fail "В ci/templates.yml нет скрытой задачи .deploy"
grep -qE '^\.deploy:' $d/.gitlab-ci.yml && fail "Шаблон .deploy описан в .gitlab-ci.yml, а должен — в ci/templates.yml"
grep -q 'templates.yml' $d/.gitlab-ci.yml || fail ".gitlab-ci.yml не подключает ci/templates.yml"
p=$(lab_ci_preview $d); [ -n "$p" ] && [ "$p" != null ] || fail "gitlab-ci-local не может разобрать .gitlab-ci.yml"
for pair in deploy-dev:dev deploy-staging:staging deploy-production:production; do
  j=${pair%%:*}; e=${pair#*:}
  echo "$p" | jq -e --arg j $j '.[$j]' >/dev/null || fail "Нет задачи $j"
  [ "$(echo "$p" | jq -r --arg j $j '.[$j].environment | if type == "object" then .name else . end')" = "$e" ] || fail "У $j окружение не $e"
  echo "$p" | jq -r --arg j $j '.[$j].script | join(" ")' | grep -q 'ENV_NAME' || fail "$j не берёт скрипт из шаблона .deploy"
  [ "$(echo "$p" | jq -r --arg j $j '.[$j].variables.ENV_NAME')" = "$e" ] || fail "У $j ENV_NAME не $e"
done
echo "$p" | jq -e '."deploy-production".needs | map(if type == "string" then . else .job end) | index("deploy-staging")' >/dev/null || fail "deploy-production не ждёт deploy-staging"
w() { echo "$1" | jq -r --arg n "$2" '[.[] | select(.name == $n) | .when][0] // "нет"'; }
m=$(lab_ci_jobs $d)
[ "$(w "$m" deploy-staging)" = on_success ] || fail "В main deploy-staging: $(w "$m" deploy-staging)"
[ "$(w "$m" deploy-production)" = manual ] || fail "В main deploy-production: $(w "$m" deploy-production)"
x=$(w "$m" deploy-dev); [ "$x" = нет ] || [ "$x" = never ] || fail "В main есть deploy-dev ($x)"
f=$(lab_ci_jobs $d feature/cart)
[ "$(w "$f" deploy-dev)" = on_success ] || fail "В ветке feature/cart deploy-dev: $(w "$f" deploy-dev)"
for j in deploy-staging deploy-production; do x=$(w "$f" $j); [ "$x" = нет ] || [ "$x" = never ] || fail "В ветке feature/cart есть $j ($x)"; done
lab_ci_run $d || fail "Пайплайн в main не проходит: $(lab_ci_log)"
ok "dev — ветки, staging — main автоматически, production — main вручную после staging"
```

```text hint
1. Шаблон в отдельном файле — обычный YAML со скрытой задачей. Подключение — раздел include с локальным путём.
2. Каждая задача: наследование от шаблона, окружение с именем, переменная с именем окружения и правила.
3. «Все ветки, кроме main» — условие «не равно» на переменную текущей ветки. Ручной запуск — в правиле. Зависимость — параметр needs.
4. Проверить список задач в main и в другой ветке.
```

```bash solution
cd ~/ci-envs
mkdir -p ci
cat > ci/templates.yml <<'EOF'
.deploy:
  stage: deploy
  script:
    - echo "deploy to $ENV_NAME"
EOF
cat > .gitlab-ci.yml <<'EOF'
include:
  - local: ci/templates.yml

stages: [deploy]

deploy-dev:
  extends: .deploy
  variables:
    ENV_NAME: dev
  environment:
    name: dev
  rules:
    - if: $CI_COMMIT_BRANCH != "main"

deploy-staging:
  extends: .deploy
  variables:
    ENV_NAME: staging
  environment:
    name: staging
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

deploy-production:
  extends: .deploy
  variables:
    ENV_NAME: production
  environment:
    name: production
  needs: [deploy-staging]
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual
EOF
gitlab-ci-local --list
```

```text review
Эталон — в «Решении».

- `environment` — GitLab ведёт историю деплоев по окружениям (Operate → Environments), показывает, какой коммит где, и даёт **Re-deploy** для отката. Окружение `production` защищают (Protected environments) — запускать могут только избранные.
- Шаблоны в отдельном проекте подключают так: `include: - project: 'devops/ci-templates', ref: v1.0.0, file: 'deploy.yml'`. Фиксировать `ref` на теге обязательно — иначе правка шаблона сломает пайплайны всех проектов сразу.
- Переменные с **environment scope** (`DEPLOY_HOST` для dev, staging, production) — одна задача-шаблон, разные адреса.
- Классическая схема: dev — на каждый push в ветку, staging — после слияния в main, prod — вручную после проверки staging. С ростом уверенности prod становится автоматическим (continuous deployment).
```

## Тест

### Какое правило запустит деплой на dev для пуша в любую ветку, кроме основной?
- [ ] if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
- [x] if: $CI_COMMIT_BRANCH && $CI_COMMIT_BRANCH != $CI_DEFAULT_BRANCH
- [ ] if: $CI_COMMIT_TAG
- [ ] when: manual
> Проверка `$CI_COMMIT_BRANCH` отсекает пайплайны тегов и MR, где переменной нет.

### Как сделать разные значения DEPLOY_HOST для dev, staging и production?
- [ ] Три разных имени переменной в .gitlab-ci.yml
- [x] Создать переменную с одним именем трижды с разным environment scope; задача получит значение своего окружения
- [ ] Хранить хосты в README
- [ ] Использовать одну переменную для всех окружений
> Задача должна иметь ключ environment с нужным именем.

### Почему образ для прода не пересобирают, а берут тот же :SHA, что был на staging?
- [ ] Пересборка запрещена GitLab
- [x] Чтобы в прод попал ровно тот артефакт, который проверили на staging
- [ ] Так меньше места в реестре
- [ ] Prod-раннер не умеет собирать
> Build once, deploy many.

### Что даёт вынос шаблонов в отдельный репозиторий ci-templates?
- [x] Один проверенный пайплайн для многих проектов
- [x] Исправление делается в одном месте и распространяется выпуском новой версии
- [ ] Пайплайны перестают зависеть от GitLab Runner
- [ ] Не нужны переменные CI/CD
> Проекты подключают шаблоны через include: project.

### Зачем в include указан ref: v1.0.0, а не main?
- [ ] Так быстрее
- [x] Чтобы изменение шаблонов не сломало сразу все проекты: переход на новую версию — осознанный
- [ ] Ветку main нельзя подключить
- [ ] Это требование extends
> Это версионирование инфраструктурного кода.

### Как задача deploy-dev получает настройки из шаблона .deploy-ssh?
- [ ] Через якорь `*deploy-ssh`
- [x] Через extends: .deploy-ssh после подключения файла шаблона через include
- [ ] Через needs
- [ ] Через trigger
> Якоря между файлами не работают, extends — работает.

### Что гарантирует resource_group: $CI_ENVIRONMENT_NAME в шаблоне деплоя?
- [ ] Деплой на все окружения сразу
- [x] В одно и то же окружение не пойдут два деплоя одновременно, а в разные окружения — могут
- [ ] Задача выполнится вручную
- [ ] Переменные будут защищены
> Группа ресурсов — по имени окружения.

### Почему deploy-prod имеет needs: [deploy-staging]?
- [ ] Чтобы прод деплоился раньше staging
- [x] Чтобы кнопка деплоя в прод стала доступна только после успешного деплоя на staging
- [ ] Чтобы скачать кэш staging
- [ ] needs обязателен для when: manual
> Сначала проверка на staging, потом прод.

### Какой ключ кэша лучше выбрать для зависимостей pip?
- [ ] Случайный
- [x] По файлу зависимостей (key: files: [requirements.txt]) — кэш обновится, только когда изменятся зависимости
- [ ] По номеру пайплайна
- [ ] Без ключа кэш работает лучше всего
> Имя ветки тоже возможный ключ, но по lock-файлу точнее.

### Где пользователь увидит, какая версия сейчас развёрнута на staging и production?
- [ ] В README
- [x] В разделе Operate → Environments: история деплоев каждого окружения
- [ ] В Container Registry
- [ ] В логах раннера
> Там же кнопки повторного деплоя и отката.

### Как задача deploy узнаёт URL окружения внутри скрипта?
- [ ] Никак
- [x] Через переменную CI_ENVIRONMENT_URL, заданную ключом environment: url
- [ ] Через CI_COMMIT_SHA
- [ ] Через docker inspect
> Аналогично CI_ENVIRONMENT_NAME содержит имя окружения.
