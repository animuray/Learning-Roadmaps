# Сломанный сервер — очереди

Брокер почти никогда не «падает» — он делает ровно то, что настроено. Поэтому сообщения не теряются «сами»: их отбрасывает маршрутизация, удаляет TTL или лимит очереди, а обработчики простаивают из-за того, как распределены партиции.

## RabbitMQ: «сообщения пропадают»

1. **Дошло ли до обменника?** Публикация в несуществующий обменник — ошибка канала. Обменник есть, а подходящей привязки нет — сообщение **молча отбрасывается** (если у издателя нет `mandatory`).
2. **Привязки:** `rabbitmqctl list_bindings -p vhost` — ключ привязки должен совпадать с routing key (для `direct`) или подходить под шаблон (для `topic`).
3. **Очередь:** `rabbitmqctl list_queues -p vhost name messages consumers` — сколько лежит и кто читает.
4. **Политики:** `rabbitmqctl list_policies -p vhost` — `message-ttl`, `max-length`, `expires` применяются ко всем очередям по шаблону имени, даже если в самой очереди ничего такого не объявлено.
5. Страховка: **alternate exchange** для немаршрутизируемых сообщений и **dead letter exchange** для просроченных и отклонённых.

## Kafka: «обработчики простаивают»

- Одна партиция читается **одним** потребителем группы. Партиций меньше, чем потребителей, — лишние простаивают.
- Потребители с **разными** `group.id` — разные группы: каждая читает все сообщения. Опечатка в имени группы = двойная обработка.
- `kafka-consumer-groups.sh --describe --group G --members` — участники группы и сколько партиций у каждого; без `--members` — отставание (`LAG`) по партициям.
- Число партиций можно только **увеличить** (`kafka-topics.sh --alter --partitions N`), и при этом меняется соответствие «ключ → партиция».

### Сообщения не доходят до биллинга

В виртуальном хосте **`shopbs`** магазин публикует события в обменник `orders` скриптом `~/bin/publish-order.sh` (с ключом маршрутизации `order.created`). Биллинг читает очередь **`billing`**, но говорит, что сообщений там не бывает. Обработчик биллинга сейчас остановлен — сообщения должны копиться в очереди.

Почините так, чтобы каждое сообщение скрипта попадало в `billing` и оставалось там, пока его не заберут. Скрипт издателя не меняйте — тем же ключом пользуются и другие сервисы. Веб-интерфейс: `http://localhost:15672` (`admin` / `admin`).

```bash setup
lab_rabbit
rabbitmqctl -q delete_vhost shopbs >/dev/null 2>&1
rabbitmqctl -q add_vhost shopbs >/dev/null
rabbitmqctl -q set_permissions -p shopbs admin '.*' '.*' '.*' >/dev/null
lab_ra -V shopbs declare exchange name=orders type=direct durable=true >/dev/null
lab_ra -V shopbs declare queue name=billing durable=true >/dev/null
lab_ra -V shopbs declare binding source=orders destination=billing routing_key=orders.created >/dev/null
rabbitmqctl -q set_policy -p shopbs cleanup '.*' '{"message-ttl": 1000}' --apply-to queues >/dev/null
mkdir -p /home/student/bin
cat > /home/student/bin/publish-order.sh <<'EOF'
#!/bin/sh
rabbitmqadmin -u admin -p admin -V shopbs publish exchange=orders routing_key=order.created payload="{\"order\": $(date +%s%N)}" </dev/null
EOF
chmod +x /home/student/bin/publish-order.sh
chown -R student:student /home/student/bin
```

```bash check
rabbitmqctl -q list_vhosts | grep -qx shopbs || fail "Виртуального хоста shopbs нет — нажмите «Начать задачу» заново"
s=/home/student/bin/publish-order.sh
grep -q 'exchange=orders routing_key=order.created' $s || fail "Скрипт издателя изменён"
rabbitmqctl -q list_queues -p shopbs name durable | grep -qE '^billing\s+true' || fail "Нет устойчивой (durable) очереди billing"
rabbitmqctl -q purge_queue -p shopbs billing >/dev/null 2>&1
for i in 1 2 3; do su - student -c "$s" </dev/null >/dev/null 2>&1; done
sleep 2.5
n=$(rabbitmqctl -q list_queues -p shopbs name messages | awk '$1 == "billing" {print $2}')
[ "${n:-0}" = 3 ] || fail "Опубликовано 3 сообщения, через 2 секунды в очереди billing: ${n:-0}"
rabbitmqctl -q purge_queue -p shopbs billing >/dev/null 2>&1
ok "3 сообщения из 3 дошли до billing и остались в очереди"
```

2. Когда сообщение начало появляться в очереди, понаблюдать, что с ним происходит через пару секунд.

```bash solution
~/bin/publish-order.sh
sudo rabbitmqctl list_queues -p shopbs name messages
sudo rabbitmqctl list_bindings -p shopbs
rabbitmqadmin -u admin -p admin -V shopbs declare binding source=orders destination=billing routing_key=order.created
rabbitmqadmin -u admin -p admin -V shopbs delete binding source=orders destination_type=queue destination=billing properties_key=orders.created
~/bin/publish-order.sh; sudo rabbitmqctl list_queues -p shopbs name messages; sleep 2; sudo rabbitmqctl list_queues -p shopbs name messages
sudo rabbitmqctl list_policies -p shopbs
sudo rabbitmqctl clear_policy -p shopbs cleanup
~/bin/publish-order.sh; sleep 2; sudo rabbitmqctl list_queues -p shopbs name messages
```

```text review
Две поломки:

1. Привязка `orders → billing` с ключом `orders.created`, а издатель шлёт `order.created`. Для `direct`-обменника ключи должны совпасть **точно** — иначе сообщение молча отбрасывается.
2. Политика `cleanup` с шаблоном `.*` и `message-ttl: 1000` — все очереди vhost'а получили TTL в 1 секунду. Сообщение доходило и через секунду исчезало. В объявлении очереди ничего такого нет — видно только в `list_policies` и в свойствах очереди (`Policy: cleanup`).

- Чтобы немаршрутизируемые сообщения не пропадали молча — **alternate exchange** у обменника и флаг `mandatory` у издателя (брокер вернёт сообщение).
- Чтобы просроченные не пропадали — **dead letter exchange** (`x-dead-letter-exchange`), туда же уходят отклонённые.
- Политики с широким шаблоном `.*` опасны: применяются и к очередям, созданным позже. Давайте им узкий шаблон (`^tmp\.`) и приоритет.
```

```text notes
delete_vhost|delete\s+queue => Пересоздавали vhost или очередь — на живом брокере так теряются накопленные сообщения. Достаточно исправить привязку и политику.
```

### Обработчики простаивают и дублируют работу

Топик Kafka **`events`** обрабатывают три обработчика (службы `lab-kc@1`, `lab-kc@2`, `lab-kc@3`), все должны работать в группе **`workers`** и делить работу между собой. Сейчас один обработчик загружен, второй простаивает, а часть событий обрабатывается дважды.

Почините так, чтобы все три обработчика были в группе `workers` и **каждому** досталась своя часть топика. Настройки обработчиков — в `/etc/lab-kafka/`. Утилиты Kafka — в контейнере `kafka`: `docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 ...`.

```bash setup
lab_kafka
for i in 1 2 3; do systemctl stop lab-kc@$i 2>/dev/null; systemctl reset-failed lab-kc@$i 2>/dev/null; done
docker rm -f lab-kc-1 lab-kc-2 lab-kc-3 >/dev/null 2>&1
lab_kt --delete --topic events >/dev/null; sleep 2
for g in workers worker; do lab_kg --delete --group $g >/dev/null; done
lab_kt --create --topic events --partitions 1 --replication-factor 1 >/dev/null
mkdir -p /etc/lab-kafka
echo 'GROUP=workers' > /etc/lab-kafka/consumer-1.env
echo 'GROUP=workers' > /etc/lab-kafka/consumer-2.env
echo 'GROUP=worker' > /etc/lab-kafka/consumer-3.env
cat > /etc/systemd/system/lab-kc@.service <<'EOF'
[Unit]
Description=events worker %i
[Service]
EnvironmentFile=/etc/lab-kafka/consumer-%i.env
ExecStartPre=-/usr/bin/docker rm -f lab-kc-%i
ExecStart=/usr/bin/docker run --rm --name lab-kc-%i --network container:kafka -e KAFKA_HEAP_OPTS=-Xmx96m apache/kafka:3.8.1 /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic events --group ${GROUP} --consumer-property client.id=worker-%i --consumer-property metadata.max.age.ms=3000
ExecStop=/usr/bin/docker stop -t 15 lab-kc-%i
Restart=on-failure
EOF
systemctl daemon-reload
for i in 1 2 3; do systemctl start lab-kc@$i; done
for t in $(seq 60); do [ "$(lab_kg --describe --group workers --members | grep -c 'worker-')" -ge 2 ] && break; sleep 1; done
```

```bash check
lab_kt --describe --topic events | grep -q PartitionCount || fail "Топика events нет — нажмите «Начать задачу» заново"
for i in 1 2 3; do [ "$(systemctl is-active lab-kc@$i)" = active ] || fail "Обработчик lab-kc@$i не работает"; done
end=$(( $(date +%s) + 25 ))
while :; do
  m=$(lab_kg --describe --group workers --members | awk '$4 ~ /^worker-/ {print $4, $NF}')
  [ "$(echo "$m" | grep -c 'worker-')" = 3 ] && ! echo "$m" | awk '$2 == 0' | grep -q . && break
  [ "$(date +%s)" -lt $end ] || break
  sleep 1
done
for i in 1 2 3; do echo "$m" | grep -q "^worker-$i " || fail "Обработчика worker-$i нет в группе workers"; done
idle=$(echo "$m" | awk '$2 == 0 {print $1}' | tr '\n' ' ')
[ -z "$idle" ] || fail "В группе workers без партиций (простаивают): $idle"
lab_kg --describe --group worker --members | grep -q 'worker-' && fail "В группе worker остались потребители — они читают все события повторно"
ok "три обработчика в группе workers, у каждого есть партиции: $(echo $m)"
```

2. Сравнить имя группы в настройках каждого обработчика; после правки перезапустить этот обработчик.
3. Посчитать, сколько частей у топика и сколько обработчиков в группе. Частей должно быть не меньше, чем обработчиков, — их число можно увеличить.

```bash solution
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --list
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group workers --members
grep . /etc/lab-kafka/*.env
echo 'GROUP=workers' | sudo tee /etc/lab-kafka/consumer-3.env
sudo systemctl restart lab-kc@3
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic events
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic events --partitions 3
sleep 20
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group workers --members
```

```text review
Две поломки:

1. У третьего обработчика `GROUP=worker` вместо `workers` — он оказался в **своей** группе и читал весь топик сам: каждое событие обрабатывалось дважды.
2. У топика `events` одна партиция. В группе партиция достаётся одному участнику — второй (а после исправления и третий) простаивал.

- Число партиций — потолок параллелизма группы. Закладывайте запас заранее: увеличить можно, уменьшить нельзя, а при увеличении события с одним ключом начнут попадать в другую партицию (порядок по ключу нарушится на стыке).
- `--describe --members` показывает распределение, `--describe` без него — `LAG` по партициям: растущее отставание — первый сигнал, что обработчиков не хватает.
- Обработка должна быть идемпотентной (повтор события не ломает данные): при перебалансировке и сбоях Kafka гарантирует «хотя бы один раз», а не «ровно один».
```

- [ ] Нет потребителей
> Обменник принял сообщение; привязки с подходящим ключом не нашлось.

### В direct-обменнике привязка с ключом orders.created, издатель шлёт order.created. Что будет?
- [ ] Сообщение дойдёт — ключи похожи
- [x] Сообщение не попадёт в очередь: для direct ключи должны совпасть точно
- [ ] Сообщение попадёт во все очереди
- [ ] Издатель получит ошибку

### Сообщения появляются в очереди и через секунду исчезают, потребителей нет. Что проверить?
- [ ] Права пользователя
- [x] TTL сообщений: аргументы очереди и политики (rabbitmqctl list_policies)
- [ ] Версию Erlang
- [ ] Размер диска
> Политика применяется по шаблону имени и не видна в объявлении очереди.

### Куда настроить отправку просроченных и отклонённых сообщений, чтобы они не терялись?
- [ ] В alternate exchange
- [x] В dead letter exchange (x-dead-letter-exchange)
- [ ] В default exchange
- [ ] В отдельный vhost
> DLX получает сообщения, у которых истёк TTL, превышен лимит или которые отклонены.

### Для чего alternate exchange?
- [ ] Для резервного брокера
- [x] Принимает сообщения, которые основной обменник не смог маршрутизировать
- [ ] Для балансировки потребителей
- [ ] Для шифрования
> Немаршрутизируемые сообщения уходят туда вместо отбрасывания.

### В топике 1 партиция, в группе 3 потребителя. Сколько из них получают сообщения?
- [ ] Все три по очереди
- [x] Один; двое простаивают
- [ ] Ни одного
- [ ] Двое
> Партиция внутри группы закрепляется за одним участником.

### Два обработчика случайно запущены с разными group.id. Что произойдёт?
- [ ] Они поделят партиции
- [x] Каждый прочитает все сообщения — события обработаются дважды
- [ ] Второй не запустится
- [ ] Kafka объединит группы
> Каждая группа читает топик независимо со своими оффсетами.

### Какой командой посмотреть участников группы и распределение партиций?
= kafka-consumer-groups.sh --describe --group workers --members
= kafka-consumer-groups --describe --members
> С --members — участники и число партиций у каждого; без него — оффсеты и LAG.

### Можно ли уменьшить число партиций топика?
- [ ] Да, командой --alter
- [x] Нет, только увеличить; для уменьшения создают новый топик и переливают данные
- [ ] Да, после остановки брокера
- [ ] Да, если топик пуст
> Kafka поддерживает только увеличение числа партиций.

### Что меняется при увеличении числа партиций у топика с ключами?
- [ ] Ничего
- [x] Соответствие «ключ → партиция»: новые события с тем же ключом могут попасть в другую партицию
- [ ] Удаляются старые сообщения
- [ ] Меняются оффсеты потребителей
> Партиция выбирается по хешу ключа по модулю числа партиций.

### Растёт LAG группы потребителей. Что это значит?
- [ ] Брокер перегружен
- [x] Потребители не успевают: в партициях копятся непрочитанные сообщения
- [ ] Сообщения теряются
- [ ] Отключена репликация
> LAG — разница между последним оффсетом партиции и оффсетом, до которого дочитала группа.

### Почему обработку сообщений из Kafka делают идемпотентной?
- [ ] Так быстрее
- [x] При сбоях и перебалансировке сообщение может быть доставлено повторно
- [ ] Kafka требует этого при создании топика
- [ ] Чтобы не нужны были партиции
> Гарантия по умолчанию — «хотя бы один раз».
