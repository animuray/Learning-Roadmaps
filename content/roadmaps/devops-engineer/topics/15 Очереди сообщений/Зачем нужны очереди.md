# Зачем нужны очереди

## Синхронно и асинхронно

**Синхронно**: сервис заказов вызывает по HTTP сервис оплаты, потом склад, потом уведомления — и ждёт каждого. Если уведомления тормозят или лежат, тормозит и падает оформление заказа.

**Асинхронно**: сервис заказов кладёт событие «заказ создан» в **брокер сообщений** и сразу отвечает пользователю. Склад, уведомления, аналитика читают событие сами, когда смогут.

```
 Синхронно:   orders ──HTTP──► payments ──HTTP──► stock ──HTTP──► notify      (цепочка: падает одно — падает всё)

 Асинхронно:  orders ──► [ брокер: событие order.created ] ──► stock
                                                          ├──► notify
                                                          └──► analytics
```

## Что дают очереди

- **Развязка (decoupling)**: отправителю не нужно знать, кто и сколько получателей; новый потребитель подключается без изменения отправителя.
- **Буфер нагрузки**: всплеск в 10 000 заказов в минуту ложится в очередь, а обработчики разбирают её в своём темпе — без падения.
- **Устойчивость к сбоям**: потребитель упал — сообщения ждут в брокере и будут обработаны после перезапуска.
- **Масштабирование**: больше обработчиков — быстрее разбирается очередь (конкурирующие потребители).
- **Фоновые задачи**: отправка писем, генерация отчётов, обработка видео — не в HTTP-запросе пользователя.
- **Повторы**: временная ошибка → сообщение вернётся и будет обработано позже.

Цена: усложнение системы (ещё один критичный компонент), **итоговая согласованность** (eventual consistency — склад узнает о заказе через мгновение, а не сразу), сложнее отладка и трассировка.

## Модели доставки

| Модель | Как | Пример |
| --- | --- | --- |
| **Point-to-point (очередь задач)** | Каждое сообщение обрабатывает **один** из потребителей | Очередь «отправить письмо» с 5 воркерами |
| **Publish-subscribe** | Каждое сообщение получает **каждый** подписчик (или каждая группа) | Событие «заказ создан» → склад, уведомления, аналитика |

Классический брокер (RabbitMQ) удаляет сообщение после подтверждения обработки. Лог-брокер (Kafka) **хранит** сообщения заданное время, а потребители сами помнят позицию и могут перечитать историю.

## Гарантии доставки

| Гарантия | Смысл | Риск |
| --- | --- | --- |
| **At-most-once** (не более раза) | Отправили и забыли, подтверждение до обработки | Сообщения могут **теряться** |
| **At-least-once** (хотя бы раз) | Подтверждение после обработки, при сбое — повтор | Возможны **дубли** |
| **Exactly-once** (ровно раз) | Ни потерь, ни дублей | Сложно и дорого; в полном смысле — только в пределах одной системы (транзакции Kafka) |

На практике выбирают **at-least-once** + **идемпотентную** обработку: повторная обработка того же сообщения не меняет результат. Приёмы: уникальный `message_id`/ключ идемпотентности и таблица обработанных сообщений, `INSERT ... ON CONFLICT DO NOTHING`, операции «установить значение» вместо «прибавить».

## Порядок, ошибки, отставание

- **Порядок** гарантируется только в пределах одной очереди или **партиции** Kafka. Нужен порядок событий одного заказа — отправляйте их с одним ключом (в одну партицию).
- **Ядовитые сообщения** (poison messages) — те, что всегда вызывают ошибку. Без ограничения повторов они блокируют очередь. Решение — счётчик попыток и **dead letter queue (DLQ)**: после N неудач сообщение уходит в отдельную очередь для разбора человеком.
- **Повторы с задержкой** (retry с backoff) — не долбить упавший внешний сервис каждую миллисекунду.
- **Отставание потребителей** (consumer lag) — сколько сообщений ждёт обработки. Растёт — потребители не справляются: масштабировать, искать медленную обработку.

## Что мониторить

- Длина очереди / **consumer lag** и время ожидания сообщений.
- Скорость публикации и обработки (msg/s).
- Ошибки, повторы, размер DLQ.
- Состояние брокера: узлы кластера, диск (брокеры хранят данные на диске!), память, соединения, репликация.
- Алерты: lag растёт N минут, DLQ не пустая, узел брокера недоступен, диск брокера заполняется.

## Какие бывают брокеры

| Брокер | Модель | Для чего |
| --- | --- | --- |
| **Apache Kafka** | Распределённый журнал (лог) с партициями | Потоки событий, большой объём, хранение и повторное чтение, аналитика, логи, CDC |
| **RabbitMQ** | Классический брокер с exchange и очередями (AMQP), плюс streams | Очереди задач, гибкая маршрутизация, RPC, микросервисы |
| **NATS** | Лёгкий pub/sub, JetStream для хранения | Быстрый обмен между сервисами, IoT, edge |
| **Redis/Valkey** (lists, streams) | Простые очереди в памяти | Небольшие фоновые задачи (Celery, Sidekiq) |
| **Облачные** | Managed Kafka, Yandex Message Queue (совместима с SQS), AWS SQS/SNS | Без администрирования брокера |

Раньше советовали коротко «RabbitMQ — для очередей, Kafka — для потоков». Сейчас границы сближаются: в RabbitMQ есть streams с повторным чтением, в Kafka появились share groups (очереди), — но сильные стороны остались прежними.

## Тест

### Чем асинхронное взаимодействие через брокер лучше синхронной цепочки HTTP-вызовов?
- [x] Отправитель не ждёт обработки и не падает, если получатель временно недоступен
- [x] Брокер сглаживает всплески нагрузки, а получатели разбирают сообщения в своём темпе
- [x] Новых получателей можно подключать без изменения отправителя
- [ ] Данные становятся мгновенно согласованными во всех сервисах
> Цена — итоговая (eventual) согласованность и усложнение системы.

### Чем модель point-to-point отличается от publish-subscribe?
- [x] В point-to-point каждое сообщение обрабатывает один из конкурирующих потребителей
- [x] В publish-subscribe каждое сообщение получает каждый подписчик
- [ ] Это одно и то же
- [ ] Point-to-point работает только в Kafka
> Очередь задач — point-to-point, рассылка событий — pub/sub.

### Какая гарантия доставки чаще всего используется на практике?
= at-least-once
> Вместе с идемпотентной обработкой, чтобы дубли не вредили.

### Чем грозит гарантия at-least-once?
- [ ] Потерей сообщений
- [x] Повторной доставкой — одно сообщение может быть обработано дважды
- [ ] Остановкой брокера
- [ ] Нарушением шифрования
> Поэтому обработчик должен быть идемпотентным.

### Что значит идемпотентная обработка сообщения?
- [ ] Сообщение обрабатывается очень быстро
- [x] Повторная обработка того же сообщения не меняет результат — например, благодаря уникальному message_id
- [ ] Сообщение нельзя прочитать дважды
- [ ] Обработка без базы данных
> Пример: INSERT ... ON CONFLICT DO NOTHING по ключу сообщения.

### Где гарантируется порядок сообщений?
- [ ] Во всём брокере
- [x] Только в пределах одной очереди или одной партиции
- [ ] Только между разными топиками
- [ ] Порядок не гарантируется никогда
> События одного заказа отправляют с одним ключом, чтобы они попали в одну партицию.

### Для чего нужна dead letter queue?
- [ ] Для удаления всех сообщений
- [x] Чтобы сообщения, которые раз за разом не удаётся обработать, уходили в отдельную очередь для разбора и не блокировали основную
- [ ] Для хранения логов брокера
- [ ] Для шифрования сообщений
> Обычно после ограниченного числа попыток.

### Что показывает consumer lag?
- [ ] Задержку сети
- [x] Сколько сообщений ожидает обработки потребителями
- [ ] Число брокеров
- [ ] Размер сообщения
> Постоянный рост lag означает, что потребители не справляются.

### Что стоит мониторить у брокера сообщений?
- [x] Длину очереди или consumer lag
- [x] Размер dead letter queue и число ошибок обработки
- [x] Диск, память и состояние узлов кластера
- [ ] Число строк в README
> Брокеры хранят данные на диске, его заполнение — частая авария.

### Чем Kafka принципиально отличается от классического брокера вроде RabbitMQ?
- [ ] Kafka не умеет хранить сообщения
- [x] Kafka хранит сообщения в журнале заданное время, а потребители сами отслеживают позицию и могут перечитать историю; классическая очередь удаляет сообщение после подтверждения
- [ ] RabbitMQ не поддерживает несколько потребителей
- [ ] Kafka работает только в облаке
> В RabbitMQ для повторного чтения есть отдельный тип — streams.

### Какой минус появляется при переходе на асинхронное взаимодействие?
- [ ] Сервисы становятся быстрее
- [x] Итоговая согласованность и сложность: ещё один критичный компонент, сложнее отладка и трассировка запросов
- [ ] Нельзя масштабировать обработчики
- [ ] Сообщения нельзя отправлять в JSON
> Поэтому важны мониторинг, трейсинг и идемпотентность.

### Какая гарантия доставки допускает потерю сообщений, но исключает дубли?
= at-most-once
> Подтверждение отправляется до обработки, и при сбое сообщение пропадает.
