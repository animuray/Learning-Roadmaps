# Практика — сеть для своего приложения

Цель блока — уметь диагностировать сетевые проблемы и настроить базовую инфраструктуру. Продолжаем работать со своим приложением из практики Linux (фронтенд + бэкенд + PostgreSQL).

## Целевая схема

```
Интернет
   │  80/443 (открыты в файрволе)
   ▼
nginx ──── /        → статика фронтенда (/var/www/app/dist)
   │
   └────── /api/    → 127.0.0.1:8000 (бэкенд, наружу закрыт)
                          │
                          ▼
                    127.0.0.1:5432 (PostgreSQL, наружу закрыт)

SSH 22: только по ключу, без root, под защитой fail2ban
```

Снаружи открыты только **22, 80 и 443**. Бэкенд и база слушают только `127.0.0.1` или внутреннюю сеть.

## Шаг 1. Столкнуться с проблемами и решить их

Если вы делали практику Linux, проблемы уже есть: «бэкенд не видит базу», «сайт не открывается», «порт закрыт». Для каждой пройдите алгоритм из темы «Сетевая диагностика в Linux» и запишите в README:

1. Симптом (текст ошибки).
2. Какие команды выполнили и что увидели.
3. Причина.
4. Исправление.

## Шаг 2. Команды диагностики — до автоматизма

```bash
ip a                     # свои адреса
ping 10.0.0.7            # жив ли узел
sudo ss -tulpn           # какие порты открыты и кто их занимает
nc -zv 127.0.0.1 5432    # доступен ли порт
curl -v http://127.0.0.1:8000/health
```

## Шаг 3. Nginx как reverse proxy

1. Установить nginx.
2. Собрать фронтенд и положить в `/var/www/app/dist`.
3. Написать конфиг: `location /` со статикой и `try_files`, `location /api/` с `proxy_pass` и заголовками `X-Forwarded-*` (пример — в теме «Nginx»).
4. Проверить `nginx -t` и применить через **`nginx -s reload`**, а не restart.
5. Перевести бэкенд на прослушивание `127.0.0.1:8000`: теперь к нему можно попасть только через nginx.

## Шаг 4. SSH

1. Ключ: `ssh-keygen`, `ssh-copy-id`.
2. Отключить вход по паролю.
3. Отключить вход под root.

Подробно — в теме «Первичная настройка сервера». Проверяйте со второй сессии.

## Шаг 5. Файрвол

```bash
sudo ufw default deny incoming
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'      # 80 и 443
sudo ufw enable
sudo ufw status verbose
```

Проверьте с **другой** машины: `nc -zv сервер 80` — открыт, `nc -zv сервер 8000` и `nc -zv сервер 5432` — недоступны.

## Шаг 6. fail2ban

```bash
sudo apt install fail2ban
# jail.local с [sshd] enabled = true (пример — в теме «Файрвол и fail2ban»)
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd
```

## Шаг 7 (если есть домен). HTTPS

```bash
sudo certbot --nginx -d app.example.com
sudo certbot renew --dry-run
```

## Проверка результата

- `curl -I http://сервер/` → 200 (или 301 на HTTPS);
- `curl http://сервер/api/items` → данные из базы через nginx;
- снаружи порты 8000 и 5432 недоступны;
- `ssh root@сервер` и вход по паролю не работают;
- в `fail2ban-client status sshd` видны заблокированные адреса (через сутки они почти наверняка появятся сами).

## Лаборатория

```bash lib
# «Машины» задачи — network namespace lab-*, «кабели» — пары veth. Всё лабораторное начинается с lab.
lab_net_reset() {
  for u in $(systemctl list-units --all --plain --no-legend 'lab-net-*' | awk '{print $1}'); do
    systemctl stop "$u" 2>/dev/null; systemctl reset-failed "$u" 2>/dev/null
  done
  for ns in $(ip netns list | awk '$1 ~ /^lab-/ {print $1}'); do
    ip netns pids "$ns" | xargs -r kill -9 2>/dev/null; ip netns del "$ns"
  done
  for l in $(ip -o link show | awk -F': ' '{print $2}' | cut -d@ -f1 | grep '^lab'); do ip link del "$l" 2>/dev/null; done
  rm -rf /etc/netns/lab-*
  true
}
# lab_ns имя — пустая «машина» lab-имя с поднятым loopback
lab_ns() { ip netns add "lab-$1"; ip -n "lab-$1" link set lo up; }
# lab_link ns1 if1 addr1 ns2 if2 addr2 — кабель между двумя машинами; ns «-» — сам стенд, addr «-» — без адреса
lab_link() {
  local t1=labt$RANDOM t2=labu$RANDOM
  ip link add "$t1" type veth peer name "$t2"
  _lab_end "$1" "$t1" "$2" "$3"; _lab_end "$4" "$t2" "$5" "$6"
}
_lab_end() {
  if [ "$1" = - ]; then
    ip link set "$2" name "$3"; ip link set "$3" up; [ "$4" = - ] || ip addr add "$4" dev "$3"
  else
    ip link set "$2" netns "lab-$1"; ip -n "lab-$1" link set "$2" name "$3"; ip -n "lab-$1" link set "$3" up
    [ "$4" = - ] || ip -n "lab-$1" addr add "$4" dev "$3"
  fi
}
# lab_bg имя ns команда... — фоновый процесс внутри машины (служба lab-net-имя)
lab_bg() { local u=$1 ns=$2; shift 2; systemd-run -q --unit="lab-net-$u" ip netns exec "lab-$ns" "$@"; }
# lab_wait_port ns адрес порт — дождаться, пока сервис начнёт слушать
lab_wait_port() { for i in $(seq 40); do ip netns exec "lab-$1" ss -ltnH "src $2 and sport = :$3" | grep -q . && return 0; sleep 0.25; done; return 1; }
# tcp_ok ns хост порт — 0, если соединение установилось; ns «-» — со стенда
tcp_ok() {
  if [ "$1" = - ]; then timeout 3 bash -c "</dev/tcp/$2/$3" 2>/dev/null
  else ip netns exec "lab-$1" timeout 3 bash -c "</dev/tcp/$2/$3" 2>/dev/null; fi
}
```

### Приложение за nginx

Сервер приложения **`lab-srv`** (`10.84.0.2`) подключён к стенду (`10.84.0.1`), стенд здесь — «интернет». На сервере уже работают:

- бэкенд — служба **`lab-net-srv-api`**, порт `8000`, адрес прослушивания задаётся в `/etc/lab-srv/api.env`; отдаёт `/api/items`;
- база — служба **`lab-net-srv-db`**, порт `5432`;
- SSH — порт `22`;
- nginx — служба **`lab-net-srv-nginx`** с конфигом `/etc/lab-srv/nginx.conf`, сейчас отдаёт только статику фронтенда.

Доведите сервер до целевой схемы из конспекта:

- со стенда `http://10.84.0.2/` открывает фронтенд, а `http://10.84.0.2/api/items` — данные бэкенда **через nginx**;
- со стенда порты `8000` и `5432` недоступны, `22` — доступен;
- бэкенд и база продолжают работать на самом сервере.

Команды на сервере: `sudo ip netns exec lab-srv ...`. Проверить конфиг nginx: `sudo nginx -t -c /etc/lab-srv/nginx.conf`.

```bash setup
lab_net_reset
lab_ns srv
lab_link - labsrv0 10.84.0.1/24 srv eth0 10.84.0.2/24
mkdir -p /etc/lab-srv /opt/lab-srv /var/www/lab-srv /var/log/lab-srv
echo '<h1>lab-srv front</h1>' > /var/www/lab-srv/index.html
cat > /opt/lab-srv/api.py <<'EOF'
import json, os
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
class H(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path.rstrip("/") in ("/api/items", "/items"):
            body = json.dumps({"items": ["кофе", "чай"], "via": self.headers.get("X-Forwarded-For", "")}).encode()
            self.send_response(200); self.send_header("Content-Type", "application/json")
        else:
            body = b'{"error": "not found"}'; self.send_response(404)
        self.end_headers(); self.wfile.write(body)
    def log_message(self, *a): pass
ThreadingHTTPServer((os.environ.get("BIND", "0.0.0.0"), 8000), H).serve_forever()
EOF
cat > /opt/lab-srv/listen.py <<'EOF'
import socket, sys, threading
def serve(host, port):
    s = socket.socket(); s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    s.bind((host, port)); s.listen(50)
    while True:
        c, _ = s.accept(); c.close()
for spec in sys.argv[1:]:
    h, p = spec.rsplit(":", 1)
    threading.Thread(target=serve, args=(h, int(p)), daemon=True).start()
threading.Event().wait()
EOF
echo 'BIND=0.0.0.0' > /etc/lab-srv/api.env
echo 'LISTEN=0.0.0.0:5432' > /etc/lab-srv/db.env
cat > /etc/lab-srv/nginx.conf <<'EOF'
worker_processes 1;
pid /run/lab-srv-nginx.pid;
error_log /var/log/lab-srv/error.log;
events {}
http {
    include /etc/nginx/mime.types;
    access_log /var/log/lab-srv/access.log;
    server {
        listen 80;
        root /var/www/lab-srv;
        location / {
            try_files $uri /index.html;
        }
    }
}
EOF
cat > /etc/systemd/system/lab-net-srv-api.service <<'EOF'
[Unit]
Description=lab-srv backend
[Service]
EnvironmentFile=/etc/lab-srv/api.env
ExecStart=/usr/bin/ip netns exec lab-srv /usr/bin/python3 /opt/lab-srv/api.py
Restart=on-failure
EOF
cat > /etc/systemd/system/lab-net-srv-db.service <<'EOF'
[Unit]
Description=lab-srv database
[Service]
EnvironmentFile=/etc/lab-srv/db.env
ExecStart=/usr/bin/ip netns exec lab-srv /usr/bin/python3 /opt/lab-srv/listen.py ${LISTEN}
Restart=on-failure
EOF
cat > /etc/systemd/system/lab-net-srv-ssh.service <<'EOF'
[Unit]
Description=lab-srv ssh
[Service]
ExecStart=/usr/bin/ip netns exec lab-srv /usr/bin/python3 /opt/lab-srv/listen.py 0.0.0.0:22
EOF
cat > /etc/systemd/system/lab-net-srv-nginx.service <<'EOF'
[Unit]
Description=lab-srv nginx
[Service]
ExecStartPre=/usr/sbin/nginx -t -q -c /etc/lab-srv/nginx.conf
ExecStart=/usr/bin/ip netns exec lab-srv /usr/sbin/nginx -c /etc/lab-srv/nginx.conf -g 'daemon off;'
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
EOF
systemctl daemon-reload
systemctl start lab-net-srv-api lab-net-srv-db lab-net-srv-ssh lab-net-srv-nginx
lab_wait_port srv 0.0.0.0 80
lab_wait_port srv 0.0.0.0 8000
```

```text hint
1. Посмотреть со стенда, какие порты сервера открыты сейчас, а на самом сервере — какие службы слушают какие адреса.
2. В конфиг nginx добавить отдельный блок для пути API, который передаёт запросы бэкенду на локальный адрес; проверить конфиг и перечитать его без перезапуска.
3. Бэкенд и базу перевести на прослушивание только локального адреса (через их файлы настроек) и перезапустить службы. Либо закрыть эти порты файрволом сервера — но так, чтобы SSH и веб остались доступны.
```

```bash solution
nc -zv -w2 10.84.0.2 8000 || true
sudo ip netns exec lab-srv ss -ltnp
sudo sed -i 's|^        location / {|        location /api/ {\n            proxy_pass http://127.0.0.1:8000;\n            proxy_set_header Host $host;\n            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;\n        }\n        location / {|' /etc/lab-srv/nginx.conf
sudo nginx -t -c /etc/lab-srv/nginx.conf
sudo systemctl reload lab-net-srv-nginx
echo 'BIND=127.0.0.1' | sudo tee /etc/lab-srv/api.env
echo 'LISTEN=127.0.0.1:5432' | sudo tee /etc/lab-srv/db.env
sudo systemctl restart lab-net-srv-api lab-net-srv-db
sleep 1
curl -s http://10.84.0.2/api/items; echo
nc -zv -w2 10.84.0.2 8000 || true
```

```text review
Эталон — в «Решении»: `location /api/` с `proxy_pass http://127.0.0.1:8000`, бэкенд и база слушают только `127.0.0.1`.

- Привязка к `127.0.0.1` — первая линия защиты: порт снаружи даже не существует (`Connection refused`). Файрвол — вторая: защищает от случайного `0.0.0.0` в будущем. На настоящем сервере делают обе.
- `proxy_pass http://127.0.0.1:8000;` без завершающего `/` передаёт путь как есть (`/api/items`); с `/` на конце nginx отрезает префикс `location` (`/items`). Это частая причина 404 после переноса за прокси.
- `X-Forwarded-For` и `Host` — чтобы бэкенд знал настоящий адрес клиента и имя сайта; без них в журналах бэкенда только `127.0.0.1`.
- `nginx -t` перед `reload`: ошибка в конфиге не уронит работающий сервер — reload просто не применится.
- Если база должна быть доступна с другого сервера (отдельная машина под PostgreSQL), её слушают на внутреннем адресе, а не на `0.0.0.0`, и закрывают файрволом всё, кроме адреса бэкенда.
```

```text notes
systemctl\s+restart\s+[^\n]*nginx => nginx перезапускали целиком — для нового конфига достаточно reload: он не рвёт текущие соединения.
```
