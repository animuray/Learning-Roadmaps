# Практика — сеть для своего приложения

Цель блока — уметь диагностировать сетевые проблемы и настроить базовую инфраструктуру. Продолжаем работать со своим приложением из практики Linux (фронтенд + бэкенд + PostgreSQL).

## Целевая схема

```
Интернет
   │  80/443 (открыты в файрволе)
   ▼
nginx ──── /        → статика фронтенда (/var/www/app/dist)
   │
   └────── /api/    → 127.0.0.1:8000 (бэкенд, наружу закрыт)
                          │
                          ▼
                    127.0.0.1:5432 (PostgreSQL, наружу закрыт)

SSH 22: только по ключу, без root, под защитой fail2ban
```

Снаружи открыты только **22, 80 и 443**. Бэкенд и база слушают только `127.0.0.1` или внутреннюю сеть.

## Шаг 1. Столкнуться с проблемами и решить их

Если вы делали практику Linux, проблемы уже есть: «бэкенд не видит базу», «сайт не открывается», «порт закрыт». Для каждой пройдите алгоритм из темы «Сетевая диагностика в Linux» и запишите в README:

1. Симптом (текст ошибки).
2. Какие команды выполнили и что увидели.
3. Причина.
4. Исправление.

## Шаг 2. Команды диагностики — до автоматизма

```bash
ip a                     # свои адреса
ping 10.0.0.7            # жив ли узел
sudo ss -tulpn           # какие порты открыты и кто их занимает
nc -zv 127.0.0.1 5432    # доступен ли порт
curl -v http://127.0.0.1:8000/health
```

## Шаг 3. Nginx как reverse proxy

1. Установить nginx.
2. Собрать фронтенд и положить в `/var/www/app/dist`.
3. Написать конфиг: `location /` со статикой и `try_files`, `location /api/` с `proxy_pass` и заголовками `X-Forwarded-*` (пример — в теме «Nginx»).
4. Проверить `nginx -t` и применить через **`nginx -s reload`**, а не restart.
5. Перевести бэкенд на прослушивание `127.0.0.1:8000`: теперь к нему можно попасть только через nginx.

## Шаг 4. SSH

1. Ключ: `ssh-keygen`, `ssh-copy-id`.
2. Отключить вход по паролю.
3. Отключить вход под root.

Подробно — в теме «Первичная настройка сервера». Проверяйте со второй сессии.

## Шаг 5. Файрвол

```bash
sudo ufw default deny incoming
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'      # 80 и 443
sudo ufw enable
sudo ufw status verbose
```

Проверьте с **другой** машины: `nc -zv сервер 80` — открыт, `nc -zv сервер 8000` и `nc -zv сервер 5432` — недоступны.

## Шаг 6. fail2ban

```bash
sudo apt install fail2ban
# jail.local с [sshd] enabled = true (пример — в теме «Файрвол и fail2ban»)
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd
```

## Шаг 7 (если есть домен). HTTPS

```bash
sudo certbot --nginx -d app.example.com
sudo certbot renew --dry-run
```

## Проверка результата

- `curl -I http://сервер/` → 200 (или 301 на HTTPS);
- `curl http://сервер/api/items` → данные из базы через nginx;
- снаружи порты 8000 и 5432 недоступны;
- `ssh root@сервер` и вход по паролю не работают;
- в `fail2ban-client status sshd` видны заблокированные адреса (через сутки они почти наверняка появятся сами).

## Тест

### Какие порты должны быть открыты снаружи у сервера с nginx и приложением в этой практике?
- [x] 22 (SSH)
- [x] 80 и 443 (nginx)
- [ ] 8000 (бэкенд)
- [ ] 5432 (PostgreSQL)
> Бэкенд и база доступны только локально, через nginx и приложение.

### Зачем переводить бэкенд на прослушивание 127.0.0.1:8000, если перед ним стоит nginx?
- [ ] Чтобы ускорить бэкенд
- [x] Чтобы к бэкенду нельзя было обратиться напрямую в обход nginx (а значит, в обход TLS, лимитов и логов)
- [ ] Иначе nginx не запустится
- [ ] Это требование PostgreSQL
> Защита в глубину: даже если файрвол настроен неверно, порт не виден снаружи.

### Как применить изменения конфига nginx без обрыва соединений?
= sudo nginx -s reload
= nginx -s reload
= sudo systemctl reload nginx
= systemctl reload nginx
> Перед этим — `nginx -t`.

### Сайт возвращает 502 после настройки nginx. С чего начать?
- [ ] Переустановить nginx
- [x] Проверить, запущен ли бэкенд и на каком адресе и порту он слушает (ss -tulpn), и прочитать /var/log/nginx/error.log
- [ ] Открыть порт 8000 в файрволе
- [ ] Отключить ufw
> 502 — nginx не смог получить ответ от бэкенда.

### Как проверить с другой машины, что порт PostgreSQL закрыт снаружи?
- [ ] ping сервер
- [x] nc -zv сервер 5432 — ожидаем таймаут или отказ
- [ ] dig сервер
- [ ] curl -I сервер
> Сканирование своих серверов через nmap тоже подойдёт.

### Что сделать до команды ufw enable на удалённом сервере?
- [ ] Отключить SSH
- [x] Разрешить SSH (ufw allow OpenSSH)
- [ ] Удалить nginx
- [ ] Перезагрузить сервер
> Иначе соединение оборвётся, и доступ придётся восстанавливать через консоль.

### Бэкенд не видит базу. Какие проверки разумны?
- [x] Запущен ли PostgreSQL: systemctl status postgresql
- [x] Слушает ли он нужный адрес и порт: ss -tlnp | grep 5432
- [x] Правильная ли строка подключения DATABASE_URL и правило в pg_hba.conf
- [ ] Перезагрузить сервер без диагностики
> Диагностика по шагам быстрее и надёжнее перезагрузки наугад.

### Зачем вести в README раздел с решёнными сетевыми проблемами?
- [ ] Этого требует nginx
- [x] Это база знаний для себя и коллег и материал для рассказа о реальном опыте на собеседовании
- [ ] Без этого не работает fail2ban
- [ ] Чтобы GitHub показывал репозиторий выше в поиске
> «Расскажите о проблеме, которую вы решили» — частый вопрос на собеседовании.

### Какой профиль ufw открывает для nginx сразу порты 80 и 443?
= Nginx Full
> Профили — `sudo ufw app list`.

### Что делает fail2ban в этой схеме?
- [ ] Шифрует трафик nginx
- [x] Блокирует IP-адреса, с которых много раз неудачно пытались войти по SSH
- [ ] Открывает порты
- [ ] Обновляет сертификаты
> Можно добавить jail и для nginx — например, от перебора паролей к админке.

### Как убедиться, что автопродление сертификата Let's Encrypt работает?
= sudo certbot renew --dry-run
= certbot renew --dry-run
> Сертификат живёт 90 дней — продление должно работать без вашего участия.
