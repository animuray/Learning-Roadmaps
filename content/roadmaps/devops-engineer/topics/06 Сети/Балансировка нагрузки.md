# Балансировка нагрузки

**Балансировщик** распределяет запросы между несколькими копиями приложения. Это даёт:

- **масштабирование** — больше копий, больше запросов в секунду;
- **отказоустойчивость** — упавшая копия исключается, остальные продолжают работать;
- **обновления без простоя** — копии можно выводить из балансировки по одной.

## L4 и L7

| | L4 (транспортный) | L7 (прикладной) |
| --- | --- | --- |
| Что видит | IP и порты, TCP/UDP-соединения | HTTP: домен, путь, заголовки, cookies |
| Что умеет | Распределять соединения | Маршрутизировать по пути и домену, менять заголовки, терминировать TLS, кэшировать |
| Примеры | HAProxy в режиме tcp, IPVS, облачные сетевые балансировщики, Kubernetes Service | nginx, HAProxy в режиме http, Envoy, Traefik, Ingress-контроллеры |

## Алгоритмы

| Алгоритм | Как работает | Когда подходит |
| --- | --- | --- |
| **Round Robin** | По очереди | Одинаковые серверы, короткие запросы |
| **Weighted Round Robin** | По очереди с учётом весов | Серверы разной мощности |
| **Least Connections** | Тому, у кого меньше активных соединений | Запросы разной длительности, долгие соединения |
| **IP Hash / Source** | По хешу IP клиента — клиент всегда попадает на один сервер | Нужна привязка без cookies |
| **Hash по ключу** (URI, заголовок) | Один и тот же ключ → один сервер | Кэширующие бэкенды |
| Random (two choices) | Случайно из двух лучших | Большие кластеры |

## Проверки здоровья (health checks)

Балансировщик должен понимать, какие бэкенды живы:

- **пассивные** — после N ошибок подряд сервер временно исключается (`max_fails`, `fail_timeout` в nginx);
- **активные** — балансировщик сам регулярно опрашивает `/health` (HAProxy, nginx Plus, облачные балансировщики, Kubernetes readiness-пробы).

Эндпоинт `/health` в приложении должен проверять то, без чего приложение не может обслуживать запросы, — и при этом работать быстро.

## Липкие сессии (sticky sessions)

Если приложение хранит сессию в памяти конкретного сервера, пользователя нужно всегда отправлять на тот же сервер (IP Hash или cookie). Лучшее решение — сделать приложение **stateless**: хранить сессии в Redis или базе. Тогда любой запрос может обработать любой сервер.

## upstream в nginx

```nginx
upstream backend {
    least_conn;                                     # алгоритм (по умолчанию round robin)
    server 10.0.0.11:8000 weight=3;
    server 10.0.0.12:8000;
    server 10.0.0.13:8000 max_fails=3 fail_timeout=30s;
    server 10.0.0.14:8000 backup;                   # только если основные недоступны
    keepalive 32;                                   # держать соединения с бэкендами открытыми
}

server {
    listen 80;
    location /api/ {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";             # нужно для keepalive к upstream
        proxy_next_upstream error timeout http_502 http_503;
    }
}
```

## HAProxy

Специализированный балансировщик с богатыми проверками здоровья, статистикой и режимами L4 и L7.

```
# /etc/haproxy/haproxy.cfg (фрагмент)
frontend http_in
    bind *:80
    default_backend app

backend app
    balance roundrobin
    option httpchk GET /health
    server app1 10.0.0.11:8000 check
    server app2 10.0.0.12:8000 check

listen stats
    bind 127.0.0.1:8404
    stats enable
    stats uri /stats
```

```bash
haproxy -c -f /etc/haproxy/haproxy.cfg    # проверить конфиг
sudo systemctl reload haproxy
```

## Отказоустойчивость самого балансировщика

Один балансировщик — сам по себе единая точка отказа. Решения: два балансировщика с общим плавающим IP (**keepalived**, протокол VRRP), DNS с несколькими адресами или облачный managed-балансировщик.

## Где вы встретите балансировку

- nginx или HAProxy перед несколькими копиями приложения;
- облачный балансировщик перед группой ВМ;
- **Kubernetes Service** распределяет трафик между подами (L4), **Ingress** — по доменам и путям (L7);
- DNS round robin — несколько A-записей для одного имени (грубо и без проверок здоровья).

## Практика

- [ ] Запустить три копии бэкенда на портах 8001–8003 (например, `python3 -m http.server` в разных каталогах с разными index.html)
- [ ] Настроить upstream в nginx с round robin и убедиться через `curl` в цикле, что ответы чередуются
- [ ] Переключить на `least_conn` и `ip_hash` и сравнить поведение
- [ ] Остановить одну копию и проверить, что запросы продолжают обслуживаться
- [ ] Настроить то же в HAProxy с `option httpchk` и открыть страницу статистики

## Лаборатория

Три копии бэкенда работают на `127.0.0.1:8001`, `8002`, `8003` (службы `lab-lb1`…`lab-lb3`). Каждая отвечает строкой `backend N`.

```bash setup
cat > /opt/lab-lb-backend.py <<'EOF'
import sys
from http.server import BaseHTTPRequestHandler, HTTPServer
N = sys.argv[1]
class H(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200); self.end_headers(); self.wfile.write(f"backend {N}\n".encode())
    def log_message(self, *a): pass
HTTPServer(("127.0.0.1", 8000 + int(N)), H).serve_forever()
EOF
for n in 1 2 3; do
  systemctl stop lab-lb$n 2>/dev/null; systemctl reset-failed lab-lb$n 2>/dev/null
  systemd-run -q --unit=lab-lb$n python3 /opt/lab-lb-backend.py $n
done
rm -f /etc/nginx/sites-enabled/lb* /etc/nginx/sites-available/lb*
nginx -t -q && systemctl reload nginx
for n in 1 2 3; do for i in $(seq 40); do curl -s --max-time 1 http://127.0.0.1:800$n/ | grep -q "backend $n" && break; sleep 0.25; done; done
```

### Распределить запросы

Опубликуйте через nginx сайт **`lb.local`**, который распределяет запросы **по очереди** между всеми тремя копиями бэкенда.

```bash check
nginx -t >/dev/null 2>&1 || fail "nginx -t находит ошибку в конфигурации"
seen=$(for i in $(seq 30); do curl -s --max-time 3 -H 'Host: lb.local' http://127.0.0.1/; done | sort | uniq -c | tr -s ' ' | tr '\n' ';')
for n in 1 2 3; do echo "$seen" | grep -q "backend $n" || fail "За 30 запросов к lb.local ответили не все копии: $seen"; done
ok "ответы: $seen"
```

```text hint
1. Описать группу серверов-бэкендов отдельным блоком на уровне http (в файле сайта — вне блока server).
2. В сайте проксировать на эту группу по её имени.
3. По умолчанию nginx и так раздаёт запросы по очереди.
```

```bash solution
sudo tee /etc/nginx/sites-available/lb >/dev/null <<'EOF'
upstream app_backend {
    server 127.0.0.1:8001;
    server 127.0.0.1:8002;
    server 127.0.0.1:8003;
}

server {
    listen 80;
    server_name lb.local;
    location / {
        proxy_pass http://app_backend;
    }
}
EOF
sudo ln -sf /etc/nginx/sites-available/lb /etc/nginx/sites-enabled/lb
sudo nginx -t && sudo systemctl reload nginx
sleep 1
for i in 1 2 3 4 5 6; do curl -s -H 'Host: lb.local' http://127.0.0.1/; done
```

```text review
Эталон: `upstream app_backend { server ...:8001; server ...:8002; server ...:8003; }` + `proxy_pass http://app_backend;`.

- Алгоритмы: по умолчанию round robin; `least_conn` — тому, у кого меньше активных соединений (долгие запросы); `ip_hash`/`hash $cookie_...` — клиент всегда попадает на один бэкенд (сессии в памяти — лучше уносить в Redis).
- Пассивные проверки: после `max_fails` ошибок за `fail_timeout` сервер исключается на это время. Активные health-check — в nginx Plus, HAProxy (`option httpchk`), Traefik, облачных балансировщиках.
- У каждого рабочего процесса nginx свой счётчик очереди: при нескольких workers первые запросы каждого процесса уходят на первый сервер. Общее состояние (и счётчики ошибок) даёт `zone app_backend 64k;` в блоке upstream.
- `keepalive 32;` в upstream + `proxy_http_version 1.1; proxy_set_header Connection "";` — переиспользовать соединения к бэкендам.
```

### Веса и запасной сервер

Копия **2** работает на сервере вдвое мощнее — пусть получает **вдвое больше** запросов, чем копия 1. Копия **3** — **запасная**: запросы к ней идут, только когда 1 и 2 недоступны. Настройте так сайт **`lb.local`** (если его ещё нет — создайте).

```bash check
nginx -t >/dev/null 2>&1 || fail "nginx -t находит ошибку в конфигурации"
for n in 1 2 3; do systemctl is-active -q lab-lb$n || systemctl start lab-lb$n; done
sleep 0.5
out=$(for i in $(seq 30); do curl -s --max-time 3 -H 'Host: lb.local' http://127.0.0.1/; done)
c1=$(echo "$out" | grep -c 'backend 1'); c2=$(echo "$out" | grep -c 'backend 2'); c3=$(echo "$out" | grep -c 'backend 3')
[ "$c3" = 0 ] || fail "Запасная копия 3 получила $c3 из 30 запросов при живых основных"
[ $((c1 + c2)) = 30 ] || fail "Из 30 запросов основные копии ответили на $((c1 + c2)) — сайт lb.local не работает как нужно"
[ "$c2" -ge 17 ] && [ "$c2" -le 23 ] || fail "Копия 2 получила $c2 из 30 запросов, копия 1 — $c1: соотношение не 2:1"
systemctl stop lab-lb1 lab-lb2
r=$(for i in 1 2 3; do curl -s --max-time 3 -H 'Host: lb.local' http://127.0.0.1/; done | sort -u | tr '\n' ' ')
systemctl start lab-lb1 lab-lb2
echo "$r" | grep -q 'backend 3' || fail "При остановленных копиях 1 и 2 запасная не включилась (ответы: «$r»)"
ok "копия 1: $c1, копия 2: $c2, запасная: 0; при отказе основных отвечает запасная"
```

```text hint
У строк server в блоке upstream есть параметры: вес (чем больше, тем больше запросов) и пометка «резервный» — такой сервер получает запросы, только когда все основные недоступны.
```

```bash solution
sudo tee /etc/nginx/sites-available/lb >/dev/null <<'EOF'
upstream app_backend {
    server 127.0.0.1:8001 weight=1;
    server 127.0.0.1:8002 weight=2;
    server 127.0.0.1:8003 backup;
}

server {
    listen 80;
    server_name lb.local;
    location / {
        proxy_pass http://app_backend;
    }
}
EOF
sudo ln -sf /etc/nginx/sites-available/lb /etc/nginx/sites-enabled/lb
sudo nginx -t && sudo systemctl reload nginx
```

```text review
Эталон: `server ...:8002 weight=2;` и `server ...:8003 backup;`.

- `weight` пригождается при разных по мощности серверах и при плавной выкатке новой версии (canary: новой копии `weight=1` из 20).
- `backup` нельзя совмещать с `ip_hash`/`hash`. `down` — временно вывести сервер из ротации, не удаляя строку.
- Когда основная копия падает посреди запроса, nginx повторяет его на следующей (`proxy_next_upstream error timeout`) — для неидемпотентных POST это может привести к двойной обработке.
```

## Тест

### Зачем нужен балансировщик нагрузки?
- [x] Чтобы распределять запросы между несколькими копиями приложения и масштабироваться
- [x] Чтобы исключать упавшие копии и сохранять доступность
- [x] Чтобы обновлять копии по очереди без простоя
- [ ] Чтобы шифровать базу данных
> Масштабирование, отказоустойчивость, обновления без простоя.

### Чем L7-балансировщик отличается от L4?
- [ ] L7 работает только с UDP
- [x] L7 понимает HTTP и может маршрутизировать по домену, пути и заголовкам; L4 распределяет TCP/UDP-соединения по IP и порту
- [ ] L4 умеет терминировать TLS, а L7 нет
- [ ] Ничем
> Kubernetes Service — L4, Ingress — L7.

### Как работает алгоритм Round Robin?
- [ ] Отправляет запрос самому быстрому серверу
- [x] Отправляет запросы серверам по очереди
- [ ] Всегда отправляет клиента на один и тот же сервер
- [ ] Отправляет на сервер с наименьшим числом соединений
> Weighted Round Robin учитывает веса серверов.

### Какой алгоритм лучше подходит, если запросы сильно различаются по длительности?
- [ ] Round Robin
- [x] Least Connections
- [ ] IP Hash
- [ ] Random без условий
> Новые запросы уходят туда, где меньше активных соединений.

### Как в nginx объявить группу бэкендов для балансировки?
= upstream
> Затем на неё ссылаются: `proxy_pass http://backend;`

### Зачем нужны проверки здоровья (health checks)?
- [ ] Чтобы измерять скорость сети
- [x] Чтобы балансировщик знал, какие бэкенды живы, и не отправлял запросы на упавшие
- [ ] Чтобы обновлять сертификаты
- [ ] Чтобы собирать логи
> Активные проверки опрашивают /health, пассивные считают ошибки.

### Что такое sticky sessions и как обойтись без них?
- [ ] Это кэш балансировщика
- [x] Привязка клиента к одному серверу, когда сессия хранится в памяти сервера; без неё можно обойтись, если хранить сессии вне приложения (Redis, база)
- [ ] Это повторная отправка запросов
- [ ] Это способ шифрования cookies
> Stateless-приложение масштабируется проще.

### Что делает параметр backup у сервера в upstream nginx?
- [ ] Хранит резервную копию конфига
- [x] Сервер получает запросы, только когда основные серверы недоступны
- [ ] Удваивает вес сервера
- [ ] Включает проверку здоровья
> Удобно для запасного сервера или страницы обслуживания.

### Почему сам балансировщик может стать проблемой и как это решают?
- [ ] Он всегда медленнее бэкендов
- [x] Один балансировщик — единая точка отказа; ставят пару балансировщиков с плавающим IP (keepalived/VRRP) или используют облачный managed-балансировщик
- [ ] Балансировщик нельзя перезапустить
- [ ] Это не проблема
> Отказоустойчивость нужна на каждом уровне.

### Какой командой проверить конфиг HAProxy?
= haproxy -c -f /etc/haproxy/haproxy.cfg
> Как и у nginx: сначала проверка, потом reload.

### Какие недостатки у балансировки через DNS round robin (несколько A-записей)?
- [x] Нет проверок здоровья: клиент может получить адрес упавшего сервера
- [x] Изменения расходятся с задержкой из-за кэширования и TTL
- [ ] Она невозможна для HTTPS
- [ ] Она работает только в Kubernetes
> Поэтому DNS обычно используют для грубого распределения, а точную балансировку делают балансировщиком.

### Что делает директива proxy_next_upstream error timeout http_502 в nginx?
- [ ] Отключает балансировку
- [x] При ошибке, таймауте или ответе 502 от одного бэкенда повторяет запрос на следующем
- [ ] Перенаправляет клиента на другой домен
- [ ] Записывает ошибку в лог
> Осторожно с неидемпотентными запросами (POST): повтор может выполнить действие дважды.
