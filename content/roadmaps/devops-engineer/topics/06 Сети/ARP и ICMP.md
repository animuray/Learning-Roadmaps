# ARP и ICMP

Два «служебных» протокола, без которых сеть не работает. Через ARP узел узнаёт, кому физически отправить кадр. Через ICMP сеть сообщает об ошибках, и на нём работают `ping` и `traceroute`.

## ARP — от IP к MAC

Внутри локальной сети кадры Ethernet адресуются по **MAC-адресам** (48 бит, например `52:54:00:12:34:56`). Знать IP-адрес соседа недостаточно — нужен его MAC. Его находит **ARP** (Address Resolution Protocol):

1. Узел A хочет отправить пакет на `10.0.0.7` в своей подсети и смотрит в **ARP-кэш**.
2. Записи нет — A рассылает **широковещательный** запрос: «У кого 10.0.0.7? Ответь 10.0.0.5».
3. Узел с `10.0.0.7` отвечает **напрямую**: «10.0.0.7 — это 52:54:00:aa:bb:cc».
4. A сохраняет ответ в кэше и отправляет кадр.

Если адрес назначения в **другой** подсети, ARP ищет MAC не получателя, а **шлюза по умолчанию**: кадр уходит маршрутизатору, а тот пересылает пакет дальше. MAC-адреса имеют смысл только внутри одной локальной сети.

```bash
ip neigh                       # ARP-кэш (соседи): IP, MAC, состояние REACHABLE/STALE/FAILED
sudo ip neigh flush dev eth0   # очистить кэш на интерфейсе
arping -I eth0 10.0.0.7        # «пинг» на уровне ARP (пакет iputils-arping)
ip link                        # MAC-адреса своих интерфейсов
```

Типичная проблема — **конфликт IP**: два узла с одним адресом отвечают на ARP по очереди, и связь то есть, то нет. `arping -D` помогает это обнаружить.

## ICMP — служебные сообщения сети

**ICMP** (Internet Control Message Protocol) работает на сетевом уровне рядом с IP. У него нет портов: есть **типы** сообщений.

| Тип | Сообщение | Когда |
| --- | --- | --- |
| 8 / 0 | Echo Request / Echo Reply | `ping` |
| 3 | Destination Unreachable | Нет маршрута, хост или порт недоступен, нужна фрагментация |
| 11 | Time Exceeded | TTL пакета истёк — на этом основан `traceroute` |
| 5 | Redirect | Маршрутизатор подсказывает лучший шлюз |

> [!warning] Не запрещайте ICMP целиком
> Полная блокировка ICMP ломает диагностику и механизм Path MTU Discovery (сообщение «нужна фрагментация» — это ICMP). Можно ограничить частоту, но не выключать всё подряд.

## ping

```bash
ping -c 4 8.8.8.8          # 4 запроса
ping -c 4 example.com      # заодно проверяет DNS
ping -I eth1 10.0.0.1      # с определённого интерфейса
ping -s 1472 -M do 10.0.0.1  # проверка MTU: большой пакет без фрагментации
```

В выводе: **time** — время туда-обратно (RTT), **ttl** — оставшееся время жизни, **packet loss** — потери.

Что значит отсутствие ответа:

- узел выключен или недоступен;
- **или** ICMP заблокирован файрволом — при этом сервис может прекрасно работать. Поэтому «не пингуется» ≠ «не работает»: проверяйте нужный порт через `nc` или `curl`.

## traceroute и mtr

У каждого IP-пакета есть поле **TTL**: каждый маршрутизатор уменьшает его на 1, а когда оно доходит до 0, пакет отбрасывается и отправителю приходит ICMP **Time Exceeded**. `traceroute` отправляет пакеты с TTL = 1, 2, 3… и по ответам узнаёт каждый маршрутизатор на пути.

```bash
traceroute example.com          # по умолчанию UDP-пакеты (в Linux)
traceroute -I example.com       # через ICMP
sudo traceroute -T -p 443 example.com   # через TCP на порт 443 — проходит там, где ICMP и UDP режут
tracepath example.com           # без root, заодно определяет MTU
mtr example.com                 # traceroute + ping в реальном времени: потери и задержки на каждом хопе
mtr -rwc 100 example.com        # отчёт по 100 пакетам — удобно приложить к тикету провайдеру
```

Как читать:

- `* * *` на промежуточном хопе — маршрутизатор просто не отвечает на такие пакеты. Если дальше путь идёт нормально, это не проблема.
- Потери, которые начинаются на каком-то хопе и **сохраняются до конца** пути, — реальная проблема на этом участке.
- Рост задержки на одном хопе, который не сохраняется дальше, обычно означает, что маршрутизатор отвечает на ICMP с низким приоритетом.

## Практика

- [ ] Посмотреть ARP-кэш (`ip neigh`), очистить его и снова выполнить ping шлюза — запись появится
- [ ] Посмотреть ARP-запросы и ответы: `sudo tcpdump -i eth0 -n arp` во время ping соседнего хоста
- [ ] Выполнить `ping`, `traceroute` и `mtr` до `ya.ru` и `8.8.8.8` и разобрать вывод
- [ ] Найти хост, который не отвечает на ping, но открывает сайт (`curl -I`), и объяснить, почему так бывает
- [ ] Сравнить `traceroute` в режимах UDP, ICMP и TCP до одного и того же сайта
