# TCP и UDP

IP доставляет пакеты между **машинами**. Транспортный уровень доставляет данные между **программами** на этих машинах. Для этого есть порты и два главных протокола — TCP и UDP.

## Порты

Порт — число от 0 до 65535. Пара «IP + порт» называется **сокетом**, а соединение однозначно определяется четвёркой: IP и порт клиента, IP и порт сервера.

| Диапазон | Назначение |
| --- | --- |
| 0–1023 | Хорошо известные (well-known). Открыть на прослушивание может только root (или процесс с нужной capability) |
| 1024–49151 | Зарегистрированные |
| 49152–65535 | Эфемерные: их выдаёт ОС клиенту для исходящих соединений (в Linux диапазон задаётся `net.ipv4.ip_local_port_range`) |

Порты, которые нужно знать: 22 SSH, 53 DNS, 80 HTTP, 443 HTTPS, 25 SMTP, 123 NTP, 3306 MySQL, 5432 PostgreSQL, 6379 Redis, 27017 MongoDB, 9090 Prometheus, 3000 Grafana, 6443 Kubernetes API. Справочник — файл `/etc/services`.

## TCP

**TCP** — надёжная доставка потока байтов:

- устанавливает **соединение**;
- нумерует данные и требует **подтверждения** (ACK); потерянное **пересылает**;
- соблюдает **порядок**;
- управляет **потоком** (не забивает медленного получателя) и **перегрузкой** (не забивает сеть).

### Трёхстороннее рукопожатие (3-way handshake)

```
Клиент                      Сервер
  │ ── SYN (seq=x) ─────────► │   «хочу соединиться»
  │ ◄─ SYN-ACK (seq=y, ack=x+1)│   «согласен»
  │ ── ACK (ack=y+1) ───────► │   «поехали»
  │ ===== данные ===========  │
```

### Завершение

Каждая сторона закрывает своё направление: FIN → ACK, затем FIN → ACK с другой стороны. Сторона, закрывшая соединение первой, проводит какое-то время в состоянии **TIME-WAIT**: пакеты старого соединения не должны попасть в новое.

### Состояния, которые видны в ss

| Состояние | Значение |
| --- | --- |
| LISTEN | Сервер ждёт подключений |
| SYN-SENT / SYN-RECV | Рукопожатие в процессе |
| ESTABLISHED | Соединение установлено |
| TIME-WAIT | Соединение закрыто, ждём, пока «долетят» старые пакеты |
| CLOSE-WAIT | Удалённая сторона закрыла соединение, а **наше приложение ещё нет** — если таких много, это утечка соединений в коде |

```bash
ss -tan                                        # все TCP-соединения
ss -tan state established '( dport = :5432 )'  # установленные соединения к PostgreSQL
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c   # сколько в каждом состоянии
```

### RST

Пакет **RST** обрывает соединение. Если подключиться к порту, который никто не слушает, ответом будет RST — клиент увидит **Connection refused**. Если пакеты просто отбрасываются файрволом, клиент будет ждать и получит **таймаут**. Эта разница сильно помогает в диагностике.

## UDP

**UDP** — «отправил и забыл»:

- без соединения и без рукопожатия;
- без подтверждений, повторов и гарантии порядка;
- минимальный заголовок, минимальная задержка.

Надёжность, если нужна, обеспечивает само приложение.

## Сравнение

| | TCP | UDP |
| --- | --- | --- |
| Соединение | Есть (рукопожатие) | Нет |
| Надёжность | Подтверждения, повторы, порядок | Нет гарантий |
| Скорость и задержка | Выше накладные расходы | Минимальные |
| Где используется | HTTP/1.1 и HTTP/2, SSH, базы данных, почта | DNS (обычно), NTP, VoIP, видеозвонки, игры, DHCP, QUIC (HTTP/3) |

DNS использует UDP для обычных запросов и переходит на TCP для больших ответов и передачи зон. **HTTP/3** работает поверх **QUIC** — протокола на основе UDP, который сам реализует надёжность и шифрование.

## Проверка портов

```bash
nc -zv example.com 443          # TCP: открыт ли порт
nc -zuv 10.0.0.2 53             # UDP: проверка ненадёжна — ответа может не быть вовсе
sudo ss -tulpn                  # что слушает сервер
```

## Лаборатория

Сервер `lab-tsrv` (10.30.0.2) подключён к стенду кабелем: со стенда до него можно достучаться напрямую. Внутри сервера команды — через `sudo ip netns exec lab-tsrv ...`.

```bash setup
# «Машины» задачи — network namespace lab-*, «кабели» — пары veth. Всё лабораторное начинается с lab.
lab_net_reset() {
  for u in $(systemctl list-units --all --plain --no-legend 'lab-net-*' | awk '{print $1}'); do
    systemctl stop "$u" 2>/dev/null; systemctl reset-failed "$u" 2>/dev/null
  done
  for ns in $(ip netns list | awk '$1 ~ /^lab-/ {print $1}'); do
    ip netns pids "$ns" | xargs -r kill -9 2>/dev/null; ip netns del "$ns"
  done
  for l in $(ip -o link show | awk -F': ' '{print $2}' | cut -d@ -f1 | grep '^lab'); do ip link del "$l" 2>/dev/null; done
  rm -rf /etc/netns/lab-*
  true
}
# lab_ns имя — пустая «машина» lab-имя с поднятым loopback
lab_ns() { ip netns add "lab-$1"; ip -n "lab-$1" link set lo up; }
# lab_link ns1 if1 addr1 ns2 if2 addr2 — кабель между двумя машинами; ns «-» — сам стенд, addr «-» — без адреса
lab_link() {
  local t1=labt$RANDOM t2=labu$RANDOM
  ip link add "$t1" type veth peer name "$t2"
  _lab_end "$1" "$t1" "$2" "$3"; _lab_end "$4" "$t2" "$5" "$6"
}
_lab_end() {
  if [ "$1" = - ]; then
    ip link set "$2" name "$3"; ip link set "$3" up; [ "$4" = - ] || ip addr add "$4" dev "$3"
  else
    ip link set "$2" netns "lab-$1"; ip -n "lab-$1" link set "$2" name "$3"; ip -n "lab-$1" link set "$3" up
    [ "$4" = - ] || ip -n "lab-$1" addr add "$4" dev "$3"
  fi
}
# lab_bg имя ns команда... — фоновый процесс внутри машины (служба lab-net-имя)
lab_bg() { local u=$1 ns=$2; shift 2; systemd-run -q --unit="lab-net-$u" ip netns exec "lab-$ns" "$@"; }
# lab_wait_port ns адрес порт — дождаться, пока сервис начнёт слушать
lab_wait_port() { for i in $(seq 40); do ip netns exec "lab-$1" ss -ltnH "src $2 and sport = :$3" | grep -q . && return 0; sleep 0.25; done; return 1; }
lab_net_reset
lab_ns tsrv
lab_link - labtc0 10.30.0.1/24 tsrv eth0 10.30.0.2/24
cat > /opt/lab-listen.py <<'EOF'
import socket, sys, threading
def serve(port):
    s = socket.socket(); s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    s.bind(("0.0.0.0", port)); s.listen(50)
    while True:
        c, _ = s.accept(); c.close()
for p in sys.argv[1:]:
    threading.Thread(target=serve, args=(int(p),), daemon=True).start()
threading.Event().wait()
EOF
```

### Открыт, закрыт или фильтруется

Проверьте со стенда порты **22, 80, 5432, 6379** на `10.30.0.2` и запишите в `~/ports.txt` по строке на порт: `порт состояние`, где состояние — одно из:

- `open` — порт принимает соединения;
- `refused` — узел отвечает отказом (сервиса нет);
- `filtered` — ответа нет совсем (пакеты отбрасываются).

```bash setup
rm -f /home/student/ports.txt
lab_bg tcp-listen tsrv python3 /opt/lab-listen.py 22 80 6379
ip netns exec lab-tsrv nft -f - <<'EOF'
table inet filter {
  chain input { type filter hook input priority 0; policy accept; tcp dport 6379 drop; }
}
EOF
lab_wait_port tsrv 0.0.0.0 80
```

```bash check
f=/home/student/ports.txt
[ -f $f ] || fail "Нет ~/ports.txt"
for want in "22 open" "80 open" "5432 refused" "6379 filtered"; do
  p=${want%% *}
  got=$(awk -v p=$p '$1 == p {print $2}' $f | tr 'A-Z' 'a-z')
  [ "$got" = "${want#* }" ] || fail "Для порта $p указано «${got:-ничего}» — это не так"
done
ok "22 и 80 открыты, 5432 — отказ, 6379 — фильтруется"
```

```text hint
1. Утилита netcat умеет только проверить подключение (без отправки данных) и ограничить ожидание секундами.
2. Различайте исходы по сообщению и по времени: мгновенный отказ («Connection refused» — узел прислал сброс соединения) и долгое молчание до тайм-аута.
```

```bash solution
for p in 22 80 5432 6379; do
  out=$(nc -zv -w 2 10.30.0.2 $p 2>&1)
  case "$out" in
    *succeeded*) s=open ;;
    *refused*) s=refused ;;
    *) s=filtered ;;
  esac
  echo "$p $s"
done | tee ~/ports.txt
```

```text review
Эталон: `nc -zv -w 2 10.30.0.2 <порт>`.

- **open** — на SYN пришёл SYN-ACK. **refused** — пришёл RST: узел жив, но порт никто не слушает (сервис упал, слушает другой адрес). **filtered** — тишина до тайм-аута: пакеты режет файрвол (DROP), security group или их нет маршрута.
- Это сразу говорит, куда смотреть: refused → `ss -ltnp` на сервере; тайм-аут → файрволы и маршрутизация.
- `nmap -p 22,80,5432,6379 10.30.0.2` покажет то же самое таблицей. Сканировать чужие сети без разрешения нельзя.
- Без nc: `timeout 2 bash -c '</dev/tcp/10.30.0.2/80' && echo open`.
```

### Сообщение по UDP

На сервере `10.30.0.2` порт **5140/udp** принимает сообщения для журнала (как syslog). Отправьте ему со стенда одно сообщение — строку `hello-udp`.

```bash setup
rm -f /var/lib/lab/udp.log
touch /var/lib/lab/udp.log
lab_bg udp-recv tsrv socat -u UDP4-RECV:5140,bind=10.30.0.2 OPEN:/var/lib/lab/udp.log,append
sleep 0.5
```

```bash check
grep -q hello-udp /var/lib/lab/udp.log || fail "Сообщение hello-udp не дошло до сервера (принято: «$(head -c 60 /var/lib/lab/udp.log)»)"
ok "сервер получил: $(tr '\n' ' ' < /var/lib/lab/udp.log)"
```

```text hint
1. netcat умеет работать с UDP — для этого есть отдельный ключ. У UDP нет соединения: данные просто отправляются датаграммой.
2. Передать строку на вход netcat и ограничить ожидание, чтобы команда не висела.
3. Обратите внимание: сам netcat не узнает, дошло ли сообщение, — подтверждений у UDP нет.
```

```bash solution
echo hello-udp | nc -u -w1 10.30.0.2 5140
```

```text review
Эталон: `echo hello-udp | nc -u -w1 10.30.0.2 5140` (или `logger -n 10.30.0.2 -P 5140 -d hello-udp`).

- UDP без установки соединения и подтверждений: отправитель не знает, дошла ли датаграмма. Поэтому `nc -zu` про UDP-порт ничего надёжного не скажет: «open|filtered».
- На UDP работают DNS (53), DHCP, NTP, syslog (514), VXLAN в Kubernetes, QUIC (HTTP/3). Потери допустимы или повторяются самим приложением.
- Проверить, что сервер слушает UDP: `ss -lun`; увидеть датаграммы: `tcpdump -n udp port 5140`.
```

## Тест

### Какие флаги передаются при установке TCP-соединения?
- [ ] ACK, SYN, FIN
- [x] SYN, SYN-ACK, ACK
- [ ] SYN, FIN, RST
- [ ] HELLO, OK, ACK
> Трёхстороннее рукопожатие.

### Чем TCP отличается от UDP?
- [x] TCP устанавливает соединение, подтверждает доставку, пересылает потерянное и соблюдает порядок
- [x] UDP не устанавливает соединения и не гарантирует доставку, зато даёт минимальную задержку
- [ ] UDP всегда шифрует данные
- [ ] TCP работает только в локальной сети
> Выбор зависит от того, что важнее: надёжность или задержка.

### Какой протокол обычно использует DNS для запросов?
= UDP
> Большие ответы и передача зон идут по TCP.

### Какие сервисы обычно работают поверх UDP?
- [x] DNS
- [x] NTP
- [x] Голосовые и видеозвонки
- [ ] SSH
> SSH, HTTP/1.1, базы данных работают поверх TCP.

### Клиент получает Connection refused. Что это значит?
- [ ] Пакеты теряются по дороге
- [x] Хост доступен, но на этом порту никто не слушает: ответом пришёл RST
- [ ] Неверный DNS
- [ ] Истёк сертификат
> Если пакеты отбрасывает файрвол, будет не refused, а таймаут.

### Что означает большое число соединений в состоянии CLOSE-WAIT?
- [ ] Сервер под DDoS-атакой
- [x] Удалённая сторона закрыла соединения, а приложение не закрывает свои сокеты — утечка соединений в коде
- [ ] Это нормальное состояние активных соединений
- [ ] Медленный DNS
> TIME-WAIT — нормальное явление, а CLOSE-WAIT обычно указывает на баг в приложении.

### В каком состоянии находится сокет сервера, который ждёт подключений?
= LISTEN
> Слушающие сокеты показывает `ss -tln`.

### Какой порт по умолчанию у HTTPS?
= 443
> HTTP — 80, SSH — 22.

### Почему обычный пользователь не может запустить веб-сервер на порту 80?
- [ ] Порт 80 зарезервирован ядром
- [x] Порты ниже 1024 по умолчанию может открыть на прослушивание только root (или процесс с соответствующей capability)
- [ ] Порт 80 занят DNS
- [ ] Это запрещено файрволом
> Решения — reverse proxy на 80/443 и приложение на высоком порту, либо capability CAP_NET_BIND_SERVICE.

### Что такое эфемерный порт?
- [ ] Порт для широковещательных сообщений
- [x] Временный порт с большим номером, который ОС выдаёт клиенту для исходящего соединения
- [ ] Порт, который нельзя закрыть
- [ ] Порт на loopback-интерфейсе
> Поэтому в `ss` у клиентской стороны видны номера вроде 51514.

### Поверх какого транспортного протокола работает HTTP/3 (QUIC)?
- [ ] TCP
- [x] UDP
- [ ] ICMP
- [ ] SCTP
> QUIC сам реализует надёжность и шифрование поверх UDP.

### Какой командой посмотреть все TCP- и UDP-порты, которые слушает сервер, вместе с процессами?
= sudo ss -tulpn
= ss -tulpn
> Без sudo колонка процессов будет пустой для чужих процессов.
