# Сломанный сервер — сети

«Не подключается» — это десяток разных причин на разных уровнях. Угадывать бесполезно: идите снизу вверх и на каждом шаге получайте факт, а не ощущение.

## Алгоритм снизу вверх

1. **Адрес и линк:** `ip -br a` — интерфейс `UP`, адрес из нужной сети.
2. **Маршрут:** `ip route`, а точнее — `ip route get 10.0.5.7`: через какой интерфейс и шлюз уйдёт пакет.
3. **Сосед:** `ping` шлюза, `ip neigh` — `FAILED`/`INCOMPLETE` значит, что по этому адресу в сегменте никого нет.
4. **Путь:** `traceroute -n` / `mtr -n` — на каком хопе обрывается.
5. **Имя:** `getent hosts имя` (а не только `dig`: `getent` смотрит и в `/etc/hosts`, как приложение).
6. **Порт:** `nc -zv -w2 хост порт`. *Connection refused* — до хоста дошли, но порт никто не слушает (или REJECT). *Тайм-аут* — пакеты теряются: DROP в файрволе, нет маршрута, нет обратного маршрута.
7. **Сервер:** `ss -ltnp` (слушает ли и на каком адресе), `nft list ruleset` / `iptables -S`, журнал приложения.
8. **Пакеты:** `tcpdump -ni eth0 port 5432` на обеих сторонах — приходит ли запрос, уходит ли ответ.

## Частые поломки

| Симптом | Частая причина |
| --- | --- |
| Тайм-аут только к одному порту | DROP в файрволе на сервере |
| Тайм-аут ко всему в другой сети | неверный шлюз по умолчанию или нет обратного маршрута |
| `Connection refused` | сервис не запущен или слушает `127.0.0.1` |
| `Name or service not known` | DNS / `/etc/hosts` / `resolv.conf` |
| Подключается по IP, но не по имени | имя указывает на старый адрес |
| Пинг идёт, TCP нет | файрвол пропускает ICMP, но режет порт |

После переездов и смены адресов ломаются вещи, которые ссылались на старый адрес: записи в `hosts` и DNS, правила файрвола «пускать только с IP X», `pg_hba.conf`, списки доступа в облаке.

## Лаборатория

```bash lib
# «Машины» задачи — network namespace lab-*, «кабели» — пары veth. Всё лабораторное начинается с lab.
lab_net_reset() {
  for u in $(systemctl list-units --all --plain --no-legend 'lab-net-*' | awk '{print $1}'); do
    systemctl stop "$u" 2>/dev/null; systemctl reset-failed "$u" 2>/dev/null
  done
  for ns in $(ip netns list | awk '$1 ~ /^lab-/ {print $1}'); do
    ip netns pids "$ns" | xargs -r kill -9 2>/dev/null; ip netns del "$ns"
  done
  for l in $(ip -o link show | awk -F': ' '{print $2}' | cut -d@ -f1 | grep '^lab'); do ip link del "$l" 2>/dev/null; done
  rm -rf /etc/netns/lab-*
  true
}
# lab_ns имя — пустая «машина» lab-имя с поднятым loopback
lab_ns() { ip netns add "lab-$1"; ip -n "lab-$1" link set lo up; }
# lab_link ns1 if1 addr1 ns2 if2 addr2 — кабель между двумя машинами; ns «-» — сам стенд, addr «-» — без адреса
lab_link() {
  local t1=labt$RANDOM t2=labu$RANDOM
  ip link add "$t1" type veth peer name "$t2"
  _lab_end "$1" "$t1" "$2" "$3"; _lab_end "$4" "$t2" "$5" "$6"
}
_lab_end() {
  if [ "$1" = - ]; then
    ip link set "$2" name "$3"; ip link set "$3" up; [ "$4" = - ] || ip addr add "$4" dev "$3"
  else
    ip link set "$2" netns "lab-$1"; ip -n "lab-$1" link set "$2" name "$3"; ip -n "lab-$1" link set "$3" up
    [ "$4" = - ] || ip -n "lab-$1" addr add "$4" dev "$3"
  fi
}
# lab_bg имя ns команда... — фоновый процесс внутри машины (служба lab-net-имя)
lab_bg() { local u=$1 ns=$2; shift 2; systemd-run -q --unit="lab-net-$u" ip netns exec "lab-$ns" "$@"; }
# lab_wait_port ns адрес порт — дождаться, пока сервис начнёт слушать
lab_wait_port() { for i in $(seq 40); do ip netns exec "lab-$1" ss -ltnH "src $2 and sport = :$3" | grep -q . && return 0; sleep 0.25; done; return 1; }
lab_listener() {
cat > /opt/lab-listen.py <<'EOF'
import socket, sys, threading
def serve(host, port):
    s = socket.socket(); s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    s.bind((host, port)); s.listen(50)
    while True:
        c, _ = s.accept(); c.close()
host = sys.argv[1]
for p in sys.argv[2:]:
    threading.Thread(target=serve, args=(host, int(p)), daemon=True).start()
threading.Event().wait()
EOF
}
# tcp_ok ns хост порт — 0, если соединение установилось; ns «-» — со стенда
tcp_ok() {
  if [ "$1" = - ]; then timeout 3 bash -c "</dev/tcp/$2/$3" 2>/dev/null
  else ip netns exec "lab-$1" timeout 3 bash -c "</dev/tcp/$2/$3" 2>/dev/null; fi
}
```

### База после переезда

Бэкенд перенесли на новый сервер **`lab-app`**, и теперь он не может подключиться к базе по адресу **`db.internal:5432`**. Сервер базы — **`lab-db`**; к нему также подключена офисная сеть (стенд).

Почините так, чтобы с `lab-app` соединение с `db.internal:5432` устанавливалось, а база при этом оставалась закрытой для всех остальных. Команды на машинах: `sudo ip netns exec lab-app ...`, `sudo ip netns exec lab-db ...`.

```bash setup
lab_net_reset
lab_listener
lab_ns app; lab_ns db
lab_link app eth0 10.81.0.2/24 db eth0 10.81.0.3/24
lab_link - labdb0 10.81.1.1/24 db eth1 10.81.1.3/24
mkdir -p /etc/netns/lab-app
printf '127.0.0.1 localhost\n10.81.0.30 db.internal\n' > /etc/netns/lab-app/hosts
lab_bg db-listen db python3 /opt/lab-listen.py 0.0.0.0 22 5432 6379
ip netns exec lab-db nft -f - <<'EOF'
flush ruleset
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;
    ct state established,related accept
    iif "lo" accept
    tcp dport 22 accept
    ip saddr 10.81.0.100 tcp dport 5432 accept
  }
}
EOF
lab_wait_port db 0.0.0.0 5432
```

```bash check
ip netns list | grep -q '^lab-db' && ip netns list | grep -q '^lab-app' || fail "Машины задачи пропали — нажмите «Начать задачу» заново"
tcp_ok app db.internal 5432 || fail "С lab-app нет соединения с db.internal:5432"
[ "$(ip netns exec lab-app getent hosts db.internal | awk '{print $1}')" = 10.81.0.3 ] || fail "Соединение есть, но db.internal на lab-app указывает не на lab-db"
tcp_ok - 10.81.1.3 5432 && fail "Порт 5432 на lab-db открыт из офисной сети"
tcp_ok app 10.81.0.3 6379 && fail "С lab-app открылся порт 6379 на lab-db — файрвол базы пропускает лишнее"
tcp_ok - 10.81.1.3 22 || fail "SSH на lab-db из офисной сети недоступен"
ok "lab-app подключается к db.internal:5432, остальные порты базы закрыты"
```

```text hint
1. Пройти путь с lab-app по шагам: во что превращается имя базы, отвечает ли этот адрес, какой адрес на самом деле у сервера базы.
2. Когда имя исправлено, снова проверить порт: если соединение висит, а не отклоняется, смотреть правила файрвола на сервере базы — кого именно он пускает.
3. Исправить запись имени на новом сервере и разрешающее правило на сервере базы для нового адреса бэкенда, не открывая порт всем.
```

```bash solution
sudo ip netns exec lab-app getent hosts db.internal
sudo ip netns exec lab-db ip -br a
sudo sed -i 's/^10\.81\.0\.30 /10.81.0.3 /' /etc/netns/lab-app/hosts
sudo ip netns exec lab-app nc -zv -w2 db.internal 5432 || true
sudo ip netns exec lab-db nft -a list chain inet filter input
h=$(sudo ip netns exec lab-db nft -a list chain inet filter input | awk '/10.81.0.100/ {print $NF}')
sudo ip netns exec lab-db nft replace rule inet filter input handle "$h" ip saddr 10.81.0.2 tcp dport 5432 accept
sudo ip netns exec lab-app nc -zv -w2 db.internal 5432
```

```text review
Две поломки, обе — «осталось от старого адреса»:

1. В `/etc/hosts` нового сервера `db.internal` указывал на `10.81.0.30` — там никого нет (`ip neigh` показал бы `FAILED`).
2. Файрвол базы пускал на 5432 только старый адрес бэкенда `10.81.0.100`. Симптом — тайм-аут, а не отказ: пакет отбрасывается молча.

- `getent hosts` проверяет имя так же, как приложение (через `/etc/nsswitch.conf`: сначала `files`, потом `dns`). `dig` смотрит только в DNS и `/etc/hosts` не видит.
- Не открывайте 5432 «всем ради проверки»: правило по адресу источника — минимально необходимый доступ. В облаке то же делают группы безопасности.
- Такой же список адресов часто живёт ещё в `pg_hba.conf` — после переезда проверяйте и его.
- Профилактика: имена вместо адресов в конфигах, DNS вместо `/etc/hosts`, правила файрвола по подсетям/группам и чек-лист переезда.
```

```text notes
^(?!.*saddr).*dport\s+5432\s+accept => Порт 5432 открыли без ограничения по адресу источника — база доступна всем, кто дойдёт до неё по сети.
flush\s+ruleset => Правила базы сбрасывали целиком — на живом сервере это открывает или закрывает всё сразу. Точечно меняйте одно правило.
```

### Репозиторий недоступен

Сервер **`lab-srv2`** не может скачать пакеты с внутреннего репозитория `http://10.83.0.10/` — запрос висит. Репозиторий **`lab-repo`** стоит в соседней сети, между сетями — роутер **`lab-gw`** (в сети сервера его адрес `10.82.0.1`). Доступ есть ко всем трём машинам.

Почините так, чтобы с `lab-srv2` репозиторий отвечал. Подменять адреса на роутере (NAT) нельзя: репозиторий ведёт журнал по настоящим адресам клиентов.

```bash setup
lab_net_reset
lab_ns srv2; lab_ns gw; lab_ns repo
lab_link srv2 eth0 10.82.0.2/24 gw eth0 10.82.0.1/24
lab_link gw eth1 10.83.0.1/24 repo eth0 10.83.0.10/24
ip netns exec lab-gw sysctl -qw net.ipv4.ip_forward=1
ip -n lab-srv2 route add default via 10.82.0.254
mkdir -p /srv/lab-repo && echo "repo ok" > /srv/lab-repo/index.html
lab_bg repo repo python3 -m http.server 80 --bind 10.83.0.10 --directory /srv/lab-repo
lab_wait_port repo 10.83.0.10 80
```

```bash check
for n in srv2 gw repo; do ip netns list | grep -q "^lab-$n" || fail "Машины задачи пропали — нажмите «Начать задачу» заново"; done
ip -n lab-srv2 -br a show eth0 | grep -q '10\.82\.0\.2/24' || fail "У lab-srv2 изменился адрес"
ip netns exec lab-gw nft list ruleset 2>/dev/null | grep -qiE 'masquerade|snat' && fail "На lab-gw включена подмена адресов"
ip netns exec lab-gw iptables -t nat -S 2>/dev/null | grep -qiE 'MASQUERADE|SNAT' && fail "На lab-gw включена подмена адресов"
r=$(ip netns exec lab-srv2 curl -s --max-time 4 http://10.83.0.10/)
[ "$r" = "repo ok" ] || fail "С lab-srv2 репозиторий http://10.83.0.10/ не отвечает"
ip -n lab-repo route get 10.82.0.2 | grep -q 'via 10\.83\.0\.1' || fail "Ответ пришёл, но lab-repo отвечает в сеть сервера не через роутер"
ok "lab-srv2 получает ответ от репозитория через lab-gw"
```

```text hint
1. На сервере: куда, по мнению таблицы маршрутов, уйдёт пакет к репозиторию. Отвечает ли этот следующий узел.
2. Когда запрос стал уходить правильно, понять, где он теряется: дойти до роутера, до репозитория. Перехват пакетов на репозитории покажет, приходит ли запрос и уходит ли ответ.
3. Ответу тоже нужен маршрут: знает ли репозиторий, куда отправлять пакеты в сеть сервера.
```

```bash solution
sudo ip netns exec lab-srv2 ip route
sudo ip netns exec lab-srv2 ping -c1 -W1 10.82.0.254 || true
sudo ip netns exec lab-srv2 ip route replace default via 10.82.0.1
sudo ip netns exec lab-srv2 curl -s --max-time 3 http://10.83.0.10/ || true
sudo ip netns exec lab-repo ip route
sudo ip netns exec lab-repo ip route add default via 10.83.0.1
sudo ip netns exec lab-srv2 curl -s --max-time 3 http://10.83.0.10/
```

```text review
Две поломки на разных машинах:

1. На `lab-srv2` шлюз по умолчанию — `10.82.0.254`, а такого узла в сети нет: `ping` молчит, `ip neigh` — `FAILED`.
2. У `lab-repo` нет маршрута обратно в `10.82.0.0/24`: запрос доходил (видно в `tcpdump` на репозитории), а ответ уходить было некуда — классическая асимметрия. Снаружи это выглядит так же, как первая поломка: тайм-аут.

- `ip route get адрес` — самый быстрый ответ на вопрос «куда пойдёт пакет».
- Тайм-аут к целой сети — почти всегда маршрутизация (туда или обратно), а не файрвол на конкретном порту.
- NAT на роутере тоже «починил бы» связь, но спрятал бы настоящие адреса клиентов — поэтому по условию он запрещён. Это частый костыль, который потом мешает журналам, файрволам и `pg_hba.conf`.
- Сделано в рантайме; на настоящем сервере маршрут прописывают в netplan (`routes:`) или в конфиге NetworkManager, иначе он пропадёт после перезагрузки.
```

## Тест

### nc -zv db 5432 сразу отвечает «Connection refused». Что это значит?
- [ ] Пакеты отбрасывает файрвол
- [x] До хоста дошли, но на порту никто не слушает (или правило REJECT)
- [ ] Нет маршрута до хоста
- [ ] Не работает DNS
> Отказ — это ответ (TCP RST). Значит, сеть до хоста работает.

### Соединение с портом не отклоняется, а висит до тайм-аута. Самые вероятные причины?
- [ ] Сервис не запущен
- [x] DROP в файрволе, нет маршрута туда или нет обратного маршрута
- [ ] Сервис слушает 127.0.0.1
- [ ] Неверный пароль базы
> При тайм-ауте ответ не приходит совсем — пакет теряется по дороге или молча отбрасывается.

### Какая команда показывает, через какой интерфейс и шлюз уйдёт пакет к 10.0.5.7?
= ip route get 10.0.5.7
> `ip route get` применяет таблицу маршрутов к конкретному адресу.

### Приложение не находит хост db.internal, а dig db.internal отвечает правильно. Что проверить?
- [ ] Ничего — dig всегда прав
- [x] /etc/hosts и /etc/nsswitch.conf: приложение может брать имя из файла раньше DNS
- [ ] Перезапустить DNS-сервер
- [ ] MTU интерфейса
> Приложение резолвит через libc (`getent hosts`), а dig — только DNS.

### В ip neigh у адреса шлюза состояние FAILED. Что это значит?
- [ ] Шлюз отвечает, но медленно
- [x] На ARP-запрос никто не ответил — узла с таким адресом в сегменте нет или он недоступен
- [ ] Файрвол режет ICMP
- [ ] Шлюз перегружен
> ARP работает на L2; если адрес не разрешился в MAC, пакеты до шлюза не уходят.

### tcpdump на сервере показывает входящие SYN от клиента, но ответов SYN-ACK нет. Куда смотреть?
- [ ] На DNS клиента
- [x] Файрвол на сервере (DROP) или маршрут обратно к клиенту
- [ ] Сертификат TLS
- [ ] Нагрузку на CPU клиента
> Запрос дошёл — значит, проблема в обработке или в пути ответа.

### Бэкенд перенесли на новый IP, и база стала недоступна по тайм-ауту. Что вероятнее всего осталось от старого адреса?
- [ ] Версия PostgreSQL
- [x] Правило файрвола или pg_hba.conf, разрешающее только старый IP
- [ ] Таблица ARP на клиенте
- [ ] Часовой пояс
> Доступ «только с IP X» ломается при любом переезде; ищите старый адрес в конфигурации сервера.

### Сервис слушает 127.0.0.1:8000. Что получит клиент с другой машины при подключении к 8000?
- [ ] Тайм-аут
- [x] Connection refused
- [ ] Ответ сервиса
- [ ] Ошибку DNS
> На внешнем адресе порт никто не слушает, ядро отвечает RST.

### Как добавить шлюз по умолчанию 10.82.0.1, заменив текущий?
= ip route replace default via 10.82.0.1
> `replace` заменяет маршрут, если он есть, и создаёт, если нет.

### Почему NAT на роутере — плохой способ «починить» отсутствие обратного маршрута?
- [ ] NAT не работает в Linux
- [x] Сервер за роутером видит адрес роутера вместо клиентов: ломаются журналы, правила доступа по IP и аудит
- [ ] NAT замедляет сеть в 10 раз
- [ ] NAT запрещён стандартом
> Маршрутизация должна быть симметричной; NAT оправдан на границе с интернетом, а не между своими сетями.

### Пинг до сервера идёт, а TCP-порт 5432 висит. Что это говорит о проблеме?
- [ ] Сервер выключен
- [x] Сеть и маршрут в порядке; порт режется файрволом или сервис не отвечает на этом адресе
- [ ] Проблема в DNS
- [ ] Нужно перезагрузить роутер
> ICMP и TCP обрабатываются разными правилами; пинг проверяет только L3.

### Маршрут добавили командой ip route add — что будет после перезагрузки сервера?
- [ ] Маршрут сохранится
- [x] Маршрут пропадёт: нужно прописать его в netplan или конфиге NetworkManager
- [ ] Маршрут перенесётся в /etc/hosts
- [ ] Сервер не загрузится
> `ip` меняет состояние ядра в рантайме; постоянные настройки — в конфигурации сети.
