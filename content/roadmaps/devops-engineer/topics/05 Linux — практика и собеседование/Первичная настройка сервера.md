# Первичная настройка сервера

Новый сервер с белым IP-адресом начинают сканировать и перебирать пароли SSH уже через несколько минут после запуска. Поэтому у каждого сервера есть обязательный минимум настройки. Позже вы будете делать это плейбуком Ansible, но сначала нужно сделать всё руками и понять каждый шаг.

## Шаг 1. Обновить систему

```bash
sudo apt update && sudo apt upgrade -y          # Debian/Ubuntu
sudo dnf upgrade -y                             # RHEL-семейство
sudo apt install -y unattended-upgrades         # автоматические обновления безопасности (Ubuntu)
sudo dpkg-reconfigure -plow unattended-upgrades
```

Заодно задайте имя хоста и часовой пояс:

```bash
sudo hostnamectl set-hostname web1
sudo timedatectl set-timezone Europe/Moscow
timedatectl            # проверить, что синхронизация времени (NTP) включена
```

## Шаг 2. Пользователь с sudo

Работать под root постоянно нельзя: одна опечатка — и система уничтожена, а в журналах не видно, кто что сделал.

```bash
sudo adduser deploy                 # Debian/Ubuntu (интерактивно, с паролем)
sudo usermod -aG sudo deploy        # в RHEL-семействе — группа wheel
```

## Шаг 3. Вход по SSH-ключу

На **своём** компьютере:

```bash
ssh-keygen -t ed25519 -C "deploy@laptop"     # если ключа ещё нет
ssh-copy-id deploy@203.0.113.10
ssh deploy@203.0.113.10                      # должно пустить без пароля
```

## Шаг 4. Запретить вход по паролю и под root

Вместо правки основного файла создайте отдельный drop-in:

```bash
sudo tee /etc/ssh/sshd_config.d/00-hardening.conf <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
PubkeyAuthentication yes
EOF
sudo sshd -t                                        # проверить синтаксис
sudo sshd -T | grep -Ei 'passwordauth|permitroot'   # итоговые значения
sudo systemctl reload ssh                           # в RHEL: sshd
```

> [!important] Почему файл начинается с 00
> В sshd_config для каждого параметра действует **первое** найденное значение. Файлы из `sshd_config.d/` подключаются в алфавитном порядке в начале конфига. В облачных образах часто есть `50-cloud-init.conf` с `PasswordAuthentication yes`, и если назвать свой файл `99-…`, значение из cloud-init победит. Поэтому проверяйте итог через `sshd -T`.

> [!warning] Не закройте себе доступ
> Не выходите из текущей SSH-сессии. Откройте **второй терминал** и убедитесь, что вход по ключу работает, а по паролю и под root — нет. Только после этого закрывайте первую сессию.

Дополнительно можно ограничить, кто вообще может входить: `AllowUsers deploy` или `AllowGroups sshusers`.

## Шаг 5. Файрвол

Принцип: **запретить всё входящее**, открыть только нужное.

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH            # или: sudo ufw allow 22/tcp — ДО включения!
sudo ufw allow 80,443/tcp         # если это веб-сервер
sudo ufw enable
sudo ufw status verbose
sudo ufw allow from 10.0.0.0/24 to any port 5432 proto tcp   # доступ к БД только из внутренней сети
```

В RHEL-семействе вместо ufw используется **firewalld**: `firewall-cmd --permanent --add-service=ssh && firewall-cmd --reload`. Под капотом оба работают через netfilter (iptables/nftables) — подробнее в разделе «Сети».

В облаке есть ещё **группы безопасности** провайдера — файрвол перед сервером. Хорошая практика — закрывать порты и там, и на сервере.

## Шаг 6. Проверить результат

```bash
sudo ss -tulpn                  # какие порты слушаются и кем
sudo ufw status
sudo grep -i "Failed password" /var/log/auth.log | tail   # попытки подбора паролей
last -n 10                      # последние входы
```

## Лаборатория

### Администратор с sudo и ключом

На «новом сервере» (стенд, SSH на порту **2222**) нужен личный администратор вместо входа под root. Создайте пользователя **`admin`** с оболочкой bash и домашним каталогом, дайте ему права администратора через группу `sudo` и настройте вход **по вашему ключу** `~/.ssh/id_ed25519`: команда `ssh -p 2222 admin@localhost` должна пускать без пароля.

```bash setup
pkill -KILL -u admin 2>/dev/null; userdel -r admin 2>/dev/null; true
su - student -c '[ -f ~/.ssh/id_ed25519 ] || ssh-keygen -q -t ed25519 -N "" -f ~/.ssh/id_ed25519'
```

```bash check
id admin >/dev/null 2>&1 || fail "Пользователя admin нет"
[ "$(getent passwd admin | cut -d: -f7)" = /bin/bash ] || fail "Оболочка admin — $(getent passwd admin | cut -d: -f7)"
[ -d /home/admin ] || fail "У admin нет домашнего каталога"
id -nG admin | tr ' ' '\n' | grep -qx sudo || fail "admin не в группе sudo"
u=$(su - student -c "ssh -o BatchMode=yes -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -o ConnectTimeout=5 -p 2222 admin@localhost whoami" 2>/dev/null)
[ "$u" = admin ] || fail "Вход ssh -p 2222 admin@localhost по ключу не работает"
ok "admin: $(id admin)"
```

```text hint
1. Создать пользователя одной командой: с домашним каталогом, оболочкой и дополнительной группой администраторов.
2. Открытый ключ положить в файл авторизованных ключей нового пользователя; каталог и файл должны принадлежать ему и быть закрыты от других.
3. Проверить вход с указанием порта.
```

```bash solution
sudo useradd -m -s /bin/bash -G sudo admin
sudo install -d -m 700 -o admin -g admin /home/admin/.ssh
sudo install -m 600 -o admin -g admin ~/.ssh/id_ed25519.pub /home/admin/.ssh/authorized_keys
ssh -o StrictHostKeyChecking=accept-new -p 2222 admin@localhost 'id'
```

```text review
Эталон: `useradd -m -s /bin/bash -G sudo admin` → ключ в `/home/admin/.ssh/authorized_keys` (700/600, владелец admin).

- Под root на сервере не работают: любая опечатка — с полными правами, а в логах не видно, кто именно что сделал. У каждого администратора — свой пользователь, повышение — через `sudo`.
- В Debian/Ubuntu группа администраторов — `sudo`, в RHEL/Rocky — `wheel`.
- Пароль admin всё равно стоит задать (`passwd admin`): sudo спросит его. Либо выдать `NOPASSWD` точечно через `/etc/sudoers.d/` (см. тему про права).
- На облачной ВМ это обычно делает cloud-init; в команде — Ansible (`user` + `authorized_key`).
```

### Закрыть вход по паролю и под root

На сервере работает второй SSH-сервер (порт **2223**, служба `lab-sshd`, конфиг `/etc/ssh/sshd_lab.conf`) — с небезопасными настройками, как в некоторых образах облаков. Сделайте так, чтобы он:

- **не пускал root** ни с каким способом входа;
- **не принимал пароли** — только ключи.

Изменения должны действовать в **работающем** сервере. Учтите: итоговые настройки sshd могут собираться из нескольких файлов.

```bash setup
systemctl stop lab-sshd 2>/dev/null; true
mkdir -p /etc/ssh/lab_keys /etc/ssh/sshd_lab.d
rm -f /etc/ssh/sshd_lab.d/*
cat > /etc/ssh/sshd_lab.conf <<'EOF'
# Учебный SSH-сервер на порту 2223
Include /etc/ssh/sshd_lab.d/*.conf

Port 2223
PermitRootLogin yes
PasswordAuthentication yes
KbdInteractiveAuthentication no
UsePAM yes
AuthorizedKeysFile /etc/ssh/lab_keys/%u
PidFile /run/lab-sshd.pid
Subsystem sftp /usr/lib/openssh/sftp-server
EOF
# как в образах облаков: дополнение, которое снова включает пароли
printf 'PasswordAuthentication yes\n' > /etc/ssh/sshd_lab.d/50-cloud-init.conf
rm -f /var/lib/lab/rootkey /var/lib/lab/rootkey.pub
ssh-keygen -q -t ed25519 -N "" -f /var/lib/lab/rootkey
install -m 644 /var/lib/lab/rootkey.pub /etc/ssh/lab_keys/root
cat > /etc/systemd/system/lab-sshd.service <<'EOF'
[Unit]
Description=Lab SSH server (port 2223)
After=network.target

[Service]
ExecStartPre=/usr/sbin/sshd -t -f /etc/ssh/sshd_lab.conf
ExecStart=/usr/sbin/sshd -D -f /etc/ssh/sshd_lab.conf
ExecReload=/usr/sbin/sshd -t -f /etc/ssh/sshd_lab.conf
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
EOF
systemctl daemon-reload
systemctl start lab-sshd
for i in $(seq 20); do ss -ltnH 'sport = :2223' | grep -q . && break; sleep 0.25; done
```

```bash check
[ "$(systemctl is-active lab-sshd)" = active ] || fail "Служба lab-sshd не работает — проверьте конфиг (sshd -t -f /etc/ssh/sshd_lab.conf) и журнал службы"
eff=$(sshd -T -f /etc/ssh/sshd_lab.conf 2>/dev/null)
echo "$eff" | grep -qx 'permitrootlogin no' || fail "По итоговым настройкам root всё ещё может войти: $(echo "$eff" | grep '^permitrootlogin')"
echo "$eff" | grep -qx 'passwordauthentication no' || fail "По итоговым настройкам пароли всё ещё принимаются (проверьте все файлы, из которых собирается конфиг)"
ssh -o BatchMode=yes -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -o ConnectTimeout=5 -i /var/lib/lab/rootkey -p 2223 root@localhost true 2>/dev/null \
  && fail "Конфиг исправлен, но работающий сервер всё ещё пускает root по ключу — изменения не применены"
m=$(ssh -o BatchMode=yes -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -o ConnectTimeout=5 -o PubkeyAuthentication=no -p 2223 nobody@localhost true 2>&1 | grep -o 'Permission denied (.*)')
echo "$m" | grep -q password && fail "Работающий сервер всё ещё предлагает вход по паролю: $m"
ok "root не пускается, вход только по ключу ($m)"
```

```text hint
1. Посмотреть итоговые настройки этого сервера: у sshd есть ключ «вывести конфигурацию, как он её понял» и ключ «использовать этот файл конфигурации».
2. Для sshd действует **первое** найденное значение параметра — а дополнения подключаются в самом начале файла. Исправить нужно везде, где параметр задан.
3. Проверить синтаксис и применить без разрыва текущих соединений — перечитать конфигурацию службы.
```

```bash solution
sudo sshd -T -f /etc/ssh/sshd_lab.conf | grep -E '^(permitrootlogin|passwordauthentication)'
sudo sed -i 's/^PermitRootLogin .*/PermitRootLogin no/; s/^PasswordAuthentication .*/PasswordAuthentication no/' /etc/ssh/sshd_lab.conf
sudo sed -i 's/^PasswordAuthentication .*/PasswordAuthentication no/' /etc/ssh/sshd_lab.d/50-cloud-init.conf
sudo sshd -t -f /etc/ssh/sshd_lab.conf
sudo systemctl reload lab-sshd
sudo sshd -T -f /etc/ssh/sshd_lab.conf | grep -E '^(permitrootlogin|passwordauthentication)'
```

```text review
Эталон: `sshd -T` → исправить `PermitRootLogin no` и `PasswordAuthentication no` **во всех** местах (основной файл и `sshd_config.d/50-cloud-init.conf`) → `sshd -t` → `systemctl reload`.

- Ловушка из жизни: в облачных образах Ubuntu `/etc/ssh/sshd_config.d/50-cloud-init.conf` содержит `PasswordAuthentication yes`. Include стоит в начале основного файла, а sshd берёт **первое** значение — правка основного файла ничего не меняет. `sshd -T` показывает правду.
- `PermitRootLogin prohibit-password` — root только по ключу (по умолчанию), `no` — никак.
- Применять — `reload` (SIGHUP): текущие сессии не рвутся. И **не закрывайте** текущую сессию, пока не проверили вход в новой: ошибка в конфиге = потерянный сервер.
- Дальше: `AllowUsers admin deploy`, `MaxAuthTries 3`, fail2ban, нестандартный порт — по вкусу.
```

```text notes
systemctl\s+restart\s+lab-sshd => Сервер перезапускался — работает, но reload применяет настройки без разрыва уже открытых сессий.
```

### Автоматические обновления безопасности

Сервер должен сам ставить обновления безопасности. Установите пакет **unattended-upgrades** и включите **ежедневное** автоматическое обновление списков пакетов и установку обновлений.

```bash setup
DEBIAN_FRONTEND=noninteractive apt-get purge -y -q unattended-upgrades >/dev/null 2>&1
rm -f /etc/apt/apt.conf.d/20auto-upgrades /etc/apt/apt.conf.d/50unattended-upgrades
true
```

```bash check
dpkg-query -W -f='${Status}' unattended-upgrades 2>/dev/null | grep -q 'install ok installed' || fail "Пакет unattended-upgrades не установлен"
eval "$(apt-config shell L APT::Periodic::Update-Package-Lists U APT::Periodic::Unattended-Upgrade)"
[ "${L:-0}" = 1 ] || fail "Ежедневное обновление списков пакетов не включено (APT::Periodic::Update-Package-Lists = ${L:-не задано})"
[ "${U:-0}" = 1 ] || fail "Автоматическая установка обновлений не включена (APT::Periodic::Unattended-Upgrade = ${U:-не задано})"
ok "автообновления включены"
```

```text hint
1. Установить пакет.
2. Включить периодические задачи APT: два параметра со значением «каждый день». У пакета есть мастер настройки (через dpkg-reconfigure), либо параметры можно записать в файл в каталоге настроек APT.
3. Проверить итоговые значения настроек APT специальной утилитой.
```

```bash solution
sudo apt-get install -y -q unattended-upgrades
printf 'APT::Periodic::Update-Package-Lists "1";\nAPT::Periodic::Unattended-Upgrade "1";\n' | sudo tee /etc/apt/apt.conf.d/20auto-upgrades >/dev/null
apt-config dump | grep -E 'Periodic::(Update-Package-Lists|Unattended-Upgrade)'
```

```text review
Эталон: `apt install unattended-upgrades` → `/etc/apt/apt.conf.d/20auto-upgrades` с двумя параметрами `"1"` (то же делает `dpkg-reconfigure -plow unattended-upgrades`).

- Что именно ставить, задаёт `50unattended-upgrades`: по умолчанию только `-security`. Там же — автоперезагрузка (`Unattended-Upgrade::Automatic-Reboot`) и почта.
- Проверка без ожидания суток: `sudo unattended-upgrade --dry-run --debug`; журнал — `/var/log/unattended-upgrades/`.
- Нужна ли перезагрузка после обновления ядра или libc: файл `/var/run/reboot-required`.
- На проде автообновления ставят не везде: базы и кластеры обновляют по плану, с выводом узла из работы.
```
