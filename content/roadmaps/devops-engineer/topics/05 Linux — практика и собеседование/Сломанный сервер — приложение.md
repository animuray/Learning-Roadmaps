# Сломанный сервер — приложение

Итоговая практика блока Linux: сервер с nginx, бэкендом и SSH. Аварии здесь составные — нужно пройти цепочку целиком, а не чинить первое попавшееся.

## Путь запроса «сайт не открывается»

1. **DNS и сеть:** `dig сайт`, `curl -v http://сайт/` — до сервера доходим?
2. **nginx:** `curl -I -H 'Host: сайт' http://127.0.0.1/` с сервера; `nginx -t`; `/var/log/nginx/error.log`. 502 — nginx не достучался до бэкенда, 504 — бэкенд не ответил вовремя.
3. **Бэкенд:** `systemctl status`, `journalctl -u`, `ss -ltnp` — слушает ли он тот адрес и порт, что указан в `proxy_pass`.
4. **Зависимости бэкенда:** база, файлы конфигурации, переменные окружения, права.

## Путь SSH «не пускает по ключу»

1. Клиент: `ssh -v` — какой ключ предлагался и что ответил сервер.
2. Сервер: `journalctl -u ssh` — причина отказа («Authentication refused: bad ownership or modes», «user not allowed»).
3. Права: домашний каталог не доступен на запись группе/всем, `~/.ssh` — 700, `authorized_keys` — 600, владелец — сам пользователь (`StrictModes`).
4. Настройки: `sshd -T` — `AllowUsers`, `PubkeyAuthentication`, `AuthorizedKeysFile`.

## Лаборатория

### 502 на сайте

Сайт **`app.lab`** (nginx на этом сервере) отвечает **502 Bad Gateway**. Конфигурацию nginx менять не нужно — она правильная. Почините так, чтобы `curl -H 'Host: app.lab' http://127.0.0.1/` возвращал ответ приложения.

```bash setup
systemctl stop lab-backend 2>/dev/null; systemctl reset-failed lab-backend 2>/dev/null
rm -f /etc/backend.env /etc/backend/backend.env
mkdir -p /etc/backend
cat > /opt/lab-backend.py <<'EOF'
import os, sys
from http.server import BaseHTTPRequestHandler, HTTPServer
port = os.environ.get("BACKEND_PORT")
if not port:
    print("FATAL: BACKEND_PORT is not set (expected in /etc/backend.env)", file=sys.stderr); sys.exit(1)
class H(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200); self.end_headers(); self.wfile.write(b"backend ok\n")
HTTPServer(("127.0.0.1", int(port)), H).serve_forever()
EOF
echo "BACKEND_PORT=8098" > /etc/backend/backend.env
cat > /etc/systemd/system/lab-backend.service <<'EOF'
[Unit]
Description=Lab backend
[Service]
EnvironmentFile=-/etc/backend.env
ExecStart=/usr/bin/python3 /opt/lab-backend.py
Restart=on-failure
RestartSec=2
StartLimitBurst=3
[Install]
WantedBy=multi-user.target
EOF
systemctl daemon-reload
systemctl enable lab-backend >/dev/null 2>&1
systemctl start lab-backend >/dev/null 2>&1
rm -f /etc/nginx/sites-enabled/app-lab /etc/nginx/sites-available/app-lab
cat > /etc/nginx/sites-available/app-lab <<'EOF'
server {
    listen 80;
    server_name app.lab;
    location / { proxy_pass http://127.0.0.1:8098; }
}
EOF
ln -sf /etc/nginx/sites-available/app-lab /etc/nginx/sites-enabled/app-lab
nginx -t -q && systemctl reload nginx
md5sum /etc/nginx/sites-available/app-lab > /var/lib/lab/app-lab.md5
```

```bash check
md5sum -c --quiet /var/lib/lab/app-lab.md5 >/dev/null 2>&1 || fail "Конфигурация nginx для app.lab изменена — она была правильной"
[ "$(systemctl is-active lab-backend)" = active ] || fail "Бэкенд lab-backend не работает"
r=$(curl -s --max-time 3 -H 'Host: app.lab' http://127.0.0.1/)
[ "$r" = "backend ok" ] || fail "app.lab отвечает: «$(echo "$r" | head -1 | cut -c1-80)»"
ok "app.lab → backend ok"
```

```text hint
1. Что пишет nginx в журнал ошибок о 502: куда он пытался подключиться.
2. Работает ли то, что должно слушать этот адрес? Почему оно не запускается — в его журнале.
3. Сравнить, где программа ищет настройки, с тем, где они на самом деле лежат. Исправить, сбросить счётчик неудачных запусков и запустить.
```

```bash solution
sudo tail -n 2 /var/log/nginx/error.log
systemctl status lab-backend --no-pager | head -5
journalctl -u lab-backend -n 3 --no-pager -o cat
systemctl cat lab-backend | grep EnvironmentFile
ls /etc/backend/
sudo ln -s /etc/backend/backend.env /etc/backend.env
sudo systemctl reset-failed lab-backend
sudo systemctl start lab-backend
curl -s -H 'Host: app.lab' http://127.0.0.1/
```

```text review
Цепочка: nginx → 502 (connection refused к 127.0.0.1:8098) → бэкенд не запущен → в журнале «BACKEND_PORT is not set» → юнит читает `/etc/backend.env`, а файл лежит в `/etc/backend/backend.env`. Минус в `EnvironmentFile=-` разрешает отсутствие файла — служба стартует без переменной и падает.

- Починить можно по-разному: ссылка, перенос файла, правка `EnvironmentFile` в drop-in. Главное — найти, **где** ожидают настройки.
- После трёх быстрых падений служба упёрлась в `StartLimitBurst` — `reset-failed` перед `start`.
- `EnvironmentFile=-...` (с минусом) скрывает такие ошибки — для обязательной конфигурации минус не ставят.
```

### Администратор не может войти

Пользователь **`deploy`** вчера мог войти по ключу (`ssh -p 2222 deploy@localhost` с вашим ключом `~/.ssh/id_ed25519`), а сегодня сервер его не пускает. Ключ в его `authorized_keys` тот же. Восстановите вход по ключу. **Ослаблять проверки sshd нельзя** (например, выключать `StrictModes`).

```bash setup
su - student -c '[ -f ~/.ssh/id_ed25519 ] || ssh-keygen -q -t ed25519 -N "" -f ~/.ssh/id_ed25519'
id deploy >/dev/null 2>&1 || useradd -m -s /bin/bash deploy
install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
install -m 600 -o deploy -g deploy /home/student/.ssh/id_ed25519.pub /home/deploy/.ssh/authorized_keys
chmod 777 /home/deploy
rm -f /etc/ssh/sshd_config.d/99-lab-strict.conf
```

```bash check
sshd -T 2>/dev/null | grep -qx 'strictmodes yes' || fail "Проверки прав sshd (StrictModes) отключены"
u=$(su - student -c "ssh -o BatchMode=yes -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -o ConnectTimeout=5 -p 2222 deploy@localhost whoami" 2>/dev/null)
[ "$u" = deploy ] || fail "Вход deploy по ключу не работает"
m=$(stat -c %a /home/deploy); [ $(( 0$m & 022 )) = 0 ] || fail "Домашний каталог deploy доступен на запись группе или всем (права $m)"
ok "deploy входит по ключу; права /home/deploy — $m"
```

```text hint
1. Подробный вывод клиента ssh покажет, что сервер отверг ключ, но не скажет почему. Причину пишет сервер — в журнал службы ssh.
2. SSH проверяет права не только на ключи, но и на каталоги выше них.
3. Исправить права и попробовать войти снова.
```

```bash solution
ssh -o BatchMode=yes -p 2222 deploy@localhost true || true
sudo journalctl -u ssh -n 20 --no-pager | grep -i deploy | tail -2
ls -ld /home/deploy /home/deploy/.ssh /home/deploy/.ssh/authorized_keys
sudo chmod 755 /home/deploy
ssh -o StrictHostKeyChecking=accept-new -p 2222 deploy@localhost whoami
```

```text review
Причина: кто-то сделал `chmod 777 /home/deploy`. sshd в режиме `StrictModes` (по умолчанию) отказывается использовать `authorized_keys`, если домашний каталог или `.ssh` доступны на запись другим: в журнале — «Authentication refused: bad ownership or modes for directory /home/deploy».

- Клиент видит только «Permission denied (publickey)» — причину всегда ищут в журнале **сервера**.
- Правильные права: домашний каталог без записи для группы/всех (755 или 750), `~/.ssh` — 700, `authorized_keys` — 600, владелец — пользователь.
- Выключать `StrictModes no` — значит позволить любому, кто может писать в каталог, подложить свой ключ.
```

```text notes
StrictModes\s+no => StrictModes отключали — так в authorized_keys может подложить ключ любой, у кого есть запись в каталог.
chmod\s+[^\n]*777 => Права 777 на домашнем каталоге — как раз причина отказа sshd.
```

## Тест

### Сайт отдаёт 502 Bad Gateway. Что это значит?
- [ ] nginx не запущен
- [x] nginx работает, но не смог получить ответ от бэкенда (не подключился или соединение оборвалось)
- [ ] У сайта истёк сертификат
- [ ] Неверный DNS
> 502 генерирует сам прокси. При неработающем nginx был бы отказ соединения, а не 502.

### Где nginx пишет причину 502?
= /var/log/nginx/error.log
= error.log
> В error.log будет `connect() failed (111: Connection refused) while connecting to upstream` с адресом бэкенда.

### Чем 504 отличается от 502?
- [ ] Ничем
- [x] 504 — бэкенд не ответил за отведённое время; 502 — ответа не получилось вовсе
- [ ] 504 — ошибка DNS
- [ ] 504 — нет прав у nginx
> 504 Gateway Timeout — проблема скорости бэкенда, 502 — его недоступности или ошибки.

### Служба упала, в юните EnvironmentFile=-/etc/backend.env. Что значит минус?
- [ ] Файл читается в обратном порядке
- [x] Отсутствие файла не считается ошибкой — служба стартует без его переменных
- [ ] Переменные из файла удаляются
- [ ] Файл только для чтения
> Для обязательной конфигурации минус убирают: тогда ошибка будет видна сразу при старте.

### Клиент ssh пишет «Permission denied (publickey)». Где искать настоящую причину?
- [ ] В ~/.ssh/known_hosts клиента
- [x] В журнале sshd на сервере (journalctl -u ssh)
- [ ] В /etc/passwd клиента
- [ ] Её нигде нет
> Сервер не сообщает клиенту детали отказа — только пишет их в свой журнал.

### Почему sshd отвергает ключ при правах 777 на домашнем каталоге пользователя?
- [ ] Это ошибка sshd
- [x] StrictModes: если каталог доступен на запись другим, кто угодно мог подложить ключ — sshd не доверяет authorized_keys
- [ ] Ключ должен лежать в /root
- [ ] Права влияют только на скорость входа
> Защита от подмены `authorized_keys` через запись в каталог.

### Какие права нужны на ~/.ssh и authorized_keys?
- [ ] 777 и 666
- [x] 700 и 600, владелец — сам пользователь
- [ ] 755 и 644, владелец — root
- [ ] 750 и 640, владелец — sshd
> Закрыто от всех, кроме владельца.

### Какой ключ ssh покажет подробный ход подключения на стороне клиента?
= -v
= ssh -v
> `-v`, `-vv`, `-vvv` — всё более подробно: какие ключи предлагались, что ответил сервер.

### Служба трижды быстро упала и больше не запускается: «start request repeated too quickly». Что после исправления причины?
- [ ] Перезагрузить сервер
- [x] systemctl reset-failed имя и start
- [ ] Удалить юнит
- [ ] daemon-reload
> Сработал лимит перезапусков; reset-failed сбрасывает счётчик.

### Как с самого сервера проверить сайт на nginx, не трогая DNS?
- [ ] ping app.lab
- [x] curl -H 'Host: app.lab' http://127.0.0.1/
- [ ] nslookup app.lab
- [ ] systemctl status nginx
> Заголовок Host выбирает нужный server блок nginx.

### Какой командой посмотреть итоговые настройки sshd с учётом всех файлов?
= sshd -T
= sudo sshd -T
> `sshd -T` печатает конфигурацию так, как её понял сервер.

### Что проверить первым, если бэкенд «запущен», а nginx всё равно отдаёт 502?
- [ ] Версию nginx
- [x] Слушает ли бэкенд тот адрес и порт, что указан в proxy_pass (ss -ltnp)
- [ ] Свободное место
- [ ] Часовой пояс
> Частая причина — бэкенд слушает другой порт или только IPv6/другой адрес.
