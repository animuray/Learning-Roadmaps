# Загрузка Linux

«Расскажите, что происходит от включения сервера до приглашения входа» — классический вопрос на собеседовании. Знание этапов загрузки нужно и на практике: когда сервер не загружается, нужно понять, на каком этапе он сломался.

## Этапы загрузки

```
Питание → Прошивка (BIOS/UEFI) → Загрузчик (GRUB) → Ядро → initramfs → systemd (PID 1) → службы → вход
```

### 1. Прошивка: BIOS или UEFI

- Процессор запускает код прошивки материнской платы. Прошивка выполняет **POST** — самотестирование оборудования — и ищет загрузочное устройство по заданному порядку.
- **BIOS** (устаревший): читает первый сектор диска (**MBR**, 512 байт). В нём крошечный кусок загрузчика, который подгружает остальное. MBR поддерживает диски до 2 ТБ и до 4 основных разделов.
- **UEFI** (современный): понимает таблицу разделов **GPT** и файловую систему FAT. Он находит **EFI System Partition** (ESP, обычно `/boot/efi`) и запускает оттуда файл загрузчика, например `\EFI\ubuntu\shimx64.efi` или `grubx64.efi`. Загрузочные записи хранятся в NVRAM, их можно посмотреть через `efibootmgr -v`.
- **Secure Boot** (UEFI) проверяет цифровую подпись загрузчика и ядра. Дистрибутивы используют подписанный Microsoft промежуточный загрузчик **shim**.

### 2. Загрузчик GRUB

- Показывает меню: выбор ядра или ОС, дополнительные параметры.
- Читает свой конфиг `/boot/grub/grub.cfg`. Его **не правят вручную**: он генерируется из `/etc/default/grub` и скриптов в `/etc/grub.d/` командой `update-grub` (Debian/Ubuntu) или `grub2-mkconfig -o /boot/grub2/grub.cfg` (RHEL).
- Загружает в память **ядро** (`/boot/vmlinuz-...`) и **initramfs** (`/boot/initrd.img-...` или `initramfs-...img`) и передаёт ядру командную строку: `root=UUID=... ro quiet`.

### 3. Ядро

- Распаковывается, инициализирует процессор, память, планировщик и встроенные драйверы.
- Монтирует **initramfs** как временную корневую ФС и запускает его скрипт.
- Параметры, с которыми загружено ядро: `cat /proc/cmdline`.

### 4. initramfs

Маленькая файловая система в памяти, в которой есть всё, чтобы **добраться до настоящего корня**:

- модули драйверов дисков и контроллеров;
- сборка RAID (mdadm) и активация LVM;
- расшифровка дисков (LUKS) с запросом пароля;
- монтирование корневой ФС по `root=UUID=...` и переключение на неё (`switch_root`).

Пересобрать initramfs: `update-initramfs -u` (Debian/Ubuntu) или `dracut -f` (RHEL).

### 5. systemd — PID 1

- Ядро запускает `/sbin/init`, в современных системах это **systemd** с PID 1.
- systemd достигает цели по умолчанию (`systemctl get-default`): `multi-user.target` на серверах, `graphical.target` на десктопах.
- По дороге он монтирует файловые системы из `/etc/fstab`, поднимает сеть и **параллельно** запускает службы с учётом зависимостей.

### 6. Вход в систему

Запускаются `getty` на консолях (приглашение `login:`), `sshd` для удалённого входа и дисплейный менеджер на десктопе. Пользователь входит — запускается его оболочка.

## Диагностика

```bash
systemd-analyze                  # сколько длилась каждая стадия (firmware, loader, kernel, userspace)
systemd-analyze blame            # самые медленные юниты
systemd-analyze critical-chain   # цепочка, которая задержала загрузку
journalctl -b                    # логи текущей загрузки
journalctl -b -1 -p err          # ошибки предыдущей загрузки
dmesg -T | less                  # сообщения ядра
efibootmgr -v                    # загрузочные записи UEFI
```

## Если система не загружается

| Симптом | Этап | Что делать |
| --- | --- | --- |
| Нет загрузочного устройства, `grub rescue>` | Прошивка / загрузчик | Проверить порядок загрузки, восстановить GRUB с live-флешки (`grub-install`, `update-grub` через chroot) |
| Kernel panic: VFS unable to mount root fs | Ядро / initramfs | Не тот `root=` в параметрах, нет драйвера в initramfs — выбрать предыдущее ядро в GRUB, пересобрать initramfs |
| «You are in emergency mode» | systemd | Чаще всего ошибка в `/etc/fstab` или отсутствующий диск: войти, исправить fstab (`nofail`), `systemctl default` |
| Забыт пароль root | — | В меню GRUB нажать `e`, добавить к строке `linux` параметр `init=/bin/bash` или `systemd.unit=rescue.target`, затем `Ctrl+X` |
| Загрузка очень долгая | systemd | `systemd-analyze blame` — найти медленную службу |

В облаках вместо физической консоли используют **серийную консоль** провайдера, чтобы увидеть вывод загрузки и войти в rescue-режим.

## Практика

- [ ] Узнать, как загружается ваша машина: `ls /sys/firmware/efi` (есть каталог — UEFI), `efibootmgr -v`, `lsblk -f` (найти ESP)
- [ ] Посмотреть `/proc/cmdline`, `/etc/default/grub` и найти файлы ядра и initramfs в `/boot`
- [ ] Выполнить `systemd-analyze`, `blame` и `critical-chain` и найти самую медленную службу
- [ ] На тестовой ВМ прервать загрузку в GRUB, загрузиться в `rescue.target` и вернуться к обычной загрузке
- [ ] На тестовой ВМ специально испортить строку в `/etc/fstab`, перезагрузиться, попасть в emergency mode и починить

## Лаборатория

Стенд — Ubuntu в WSL: загрузчика GRUB здесь нет, но после ядра всё как на сервере — загрузку ведёт systemd.

### Что тормозит загрузку

Сервер долго загружается. Найдите юнит, который **дольше всех** инициализировался при последней загрузке, и запишите его имя (например, `something.service`) в `~/slowest.txt`.

```bash setup
rm -f /home/student/slowest.txt
```

```bash check
want=$(systemd-analyze blame --no-pager 2>/dev/null | head -1 | awk '{print $NF}')
[ -n "$want" ] || fail "systemd-analyze не отвечает"
[ -f /home/student/slowest.txt ] || fail "Нет ~/slowest.txt"
got=$(tr -d '[:space:]' < /home/student/slowest.txt)
[ "$got" = "$want" ] || fail "В ~/slowest.txt «$got» — это не самый долгий юнит загрузки"
ok "дольше всех: $(systemd-analyze blame --no-pager | head -1 | sed 's/^ *//')"
```

```text hint
У systemd есть утилита анализа загрузки: общее время, список юнитов по времени инициализации и цепочка, которая определила общее время. Нужен список — самый долгий в нём первый.
```

```bash solution
systemd-analyze
systemd-analyze blame --no-pager | head -5
systemd-analyze blame --no-pager | head -1 | awk '{print $NF}' > ~/slowest.txt
```

```text review
Эталон: `systemd-analyze blame | head`.

- `systemd-analyze` — сколько заняли прошивка, загрузчик, ядро и пространство пользователя. `blame` — время каждого юнита. `critical-chain` — цепочка, которая реально задержала загрузку: юниты стартуют параллельно, и самый долгий в blame не всегда виноват.
- Частые виновники на серверах: `systemd-networkd-wait-online` / `NetworkManager-wait-online` (ждёт сеть), cloud-init, монтирование отсутствующего диска из fstab без `nofail` (ждёт 90 секунд).
- Этапы загрузки для собеседования: UEFI/BIOS → загрузчик (GRUB) → ядро + initramfs → PID 1 (systemd) → `default.target`.
```

### Сервер без графики

На сервере по умолчанию выбрана цель загрузки с графическим окружением — серверу она не нужна. Сделайте так, чтобы система **по умолчанию** загружалась в многопользовательский режим без графики.

```bash setup
systemctl set-default graphical.target >/dev/null 2>&1
```

```bash check
d=$(systemctl get-default)
[ "$d" = multi-user.target ] || fail "Цель загрузки по умолчанию — $d"
ok "по умолчанию: $d"
```

```text hint
1. Посмотреть текущую цель загрузки по умолчанию — у systemctl есть пара команд «получить» и «установить» её.
2. Нужная цель — многопользовательский режим без графики.
```

```bash solution
systemctl get-default
sudo systemctl set-default multi-user.target
```

```text review
Эталон: `sudo systemctl set-default multi-user.target`.

- target — набор юнитов, «уровень» системы. `multi-user.target` — обычный сервер (сеть, службы, вход по SSH), `graphical.target` — плюс графика, `rescue.target` — минимум для починки от root, `emergency.target` — только корень в режиме чтения.
- `set-default` просто меняет ссылку `/etc/systemd/system/default.target`. Переключиться сейчас, без перезагрузки: `systemctl isolate multi-user.target`.
- Разовая загрузка в другой режим: в GRUB дописать к строке ядра `systemd.unit=rescue.target` (раньше — `single` или `1`).
- Старые runlevel: 3 ≈ multi-user, 5 ≈ graphical, 1 ≈ rescue.
```

```text notes
ln\s+-s[^\n]*default\.target => Ссылка default.target менялась вручную. Работает, но systemctl set-default делает то же самое без риска ошибиться в пути.
```

## Тест

### В каком порядке проходят этапы загрузки Linux?
- [ ] GRUB → BIOS/UEFI → systemd → ядро
- [x] BIOS/UEFI → GRUB → ядро → initramfs → systemd → службы и вход
- [ ] Ядро → GRUB → systemd → UEFI
- [ ] systemd → ядро → GRUB → BIOS
> Это и есть ответ на вопрос «что происходит от питания до приглашения входа».

### Чем UEFI отличается от BIOS при загрузке?
- [x] UEFI понимает GPT и файловую систему FAT и запускает файл загрузчика с раздела EFI (ESP)
- [x] UEFI поддерживает Secure Boot — проверку подписи загрузчика и ядра
- [ ] UEFI не нужен загрузчик
- [ ] UEFI работает только с дисками до 2 ТБ
> BIOS читает первый сектор диска (MBR), и у MBR есть ограничение в 2 ТБ.

### Какую задачу выполняет GRUB?
- [ ] Монтирует /home
- [x] Показывает меню выбора, загружает в память ядро и initramfs и передаёт ядру параметры
- [ ] Запускает службы
- [ ] Проверяет оборудование (POST)
> POST выполняет прошивка, а службы запускает systemd.

### Вы изменили /etc/default/grub в Ubuntu. Что нужно сделать, чтобы изменения применились?
= sudo update-grub
= update-grub
= sudo grub-mkconfig -o /boot/grub/grub.cfg
> grub.cfg генерируется — править его вручную нельзя. В RHEL — `grub2-mkconfig`.

### Зачем нужен initramfs?
- [ ] Это резервная копия ядра
- [x] Это временная корневая ФС в памяти с драйверами и утилитами, чтобы найти и смонтировать настоящий корень (диски, RAID, LVM, шифрование)
- [ ] Это конфигурация GRUB
- [ ] Это раздел подкачки
> Без нужного драйвера в initramfs ядро не сможет смонтировать корень.

### Какой процесс ядро запускает первым после монтирования настоящего корня?
- [ ] sshd
- [ ] GRUB
- [x] init — в современных системах systemd с PID 1
- [ ] bash
> Дальше systemd поднимает всё остальное.

### Где посмотреть параметры, с которыми загружено текущее ядро?
= cat /proc/cmdline
> Там, например, видно root=UUID=... корневой ФС.

### После перезагрузки система выдала «You are in emergency mode». Какая самая частая причина?
- [ ] Сломался процессор
- [x] Ошибка в /etc/fstab или недоступный диск, указанный в fstab без nofail
- [ ] Не хватает оперативной памяти
- [ ] Устарело ядро
> Войдите под root, исправьте fstab и продолжите загрузку через `systemctl default`.

### Как найти службу, которая сильнее всего замедляет загрузку?
- [ ] journalctl --slow
- [x] systemd-analyze blame
- [ ] top -b
- [ ] grub-analyze
> `critical-chain` покажет цепочку зависимостей, которая задержала загрузку.

### Что увидит администратор при ошибке Kernel panic — VFS: Unable to mount root fs?
- [ ] Это ошибка GRUB, нужно переустановить Windows
- [x] Ядро не смогло смонтировать корень: неверный root= в параметрах или нет нужного драйвера в initramfs
- [ ] Закончилось место на диске
- [ ] Ошибка в unit-файле службы
> Помогает загрузка предыдущего ядра из меню GRUB и пересборка initramfs.

### Как восстановить доступ к серверу с забытым паролем root, имея консоль?
- [ ] Это невозможно
- [x] В меню GRUB отредактировать параметры (e), загрузиться с init=/bin/bash или в rescue.target и сменить пароль через passwd
- [ ] Удалить /etc/passwd
- [ ] Переустановить ядро
> Поэтому физический доступ или доступ к консоли равен root-доступу. Защита — пароль на GRUB и шифрование диска.

### Как определить, загружена система через UEFI или через BIOS?
- [x] Проверить, существует ли каталог /sys/firmware/efi
- [ ] Посмотреть free -h
- [ ] Выполнить uname -a
- [ ] Посмотреть /etc/fstab
> Если каталог есть — загрузка через UEFI.

### Какой target systemd обычно используется по умолчанию на серверах без графики?
= multi-user.target
> На десктопах — graphical.target.
