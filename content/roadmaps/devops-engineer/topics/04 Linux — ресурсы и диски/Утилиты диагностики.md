# Утилиты диагностики

`top` даёт общую картину. Чтобы понять, **какой ресурс** упёрся в потолок — процессор, память, диск или сеть, — нужны специализированные утилиты. Большая часть из них входит в пакет **sysstat** (`apt install sysstat`).

## Первые 60 секунд

Команда инженеров по производительности Netflix предложила список команд, которые стоит выполнить в первую минуту на «тормозящем» сервере:

```bash
uptime                 # load average: растёт или падает?
dmesg -T | tail        # ошибки ядра: OOM, ошибки дисков, сети
vmstat 1               # общая картина: CPU, память, swap, диск, очередь
mpstat -P ALL 1        # загрузка каждого ядра: одно ядро на 100%?
pidstat 1              # какие процессы едят CPU (в динамике)
iostat -xz 1           # нагрузка на диски
free -m                # память
sar -n DEV 1           # трафик по сетевым интерфейсам
sar -n TCP,ETCP 1      # новые TCP-соединения и ретрансмиты
top                    # итоговая проверка
```

Число `1` — интервал в секундах. Первая строка вывода vmstat, iostat и sar обычно показывает средние значения с момента загрузки, смотрите на последующие.

## vmstat — общая картина

```
$ vmstat 1
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 3  0      0 312000  80000 9500000    0    0    12   480 1200 2400 35  6 54  5  0
```

| Колонка | Смысл |
| --- | --- |
| **r** | Процессы в очереди на CPU. Стабильно больше числа ядер — CPU не хватает |
| **b** | Процессы в непрерываемом ожидании (D) — обычно ждут диск |
| si / so | Swap in / out — активный свопинг |
| bi / bo | Блоки, прочитанные с диска / записанные на диск |
| in / cs | Прерывания / переключения контекста в секунду |
| us sy id wa st | Как в top |

## iostat — диски

```bash
iostat -xz 1
```

| Колонка | Смысл |
| --- | --- |
| r/s, w/s | Операций чтения и записи в секунду (IOPS) |
| rkB/s, wkB/s | Скорость чтения и записи |
| **r_await / w_await** | Среднее время операции в мс. Для SSD обычно единицы мс; десятки и сотни — диск перегружен |
| aqu-sz | Средняя длина очереди к устройству |
| **%util** | Доля времени, когда устройство было занято. Около 100% — диск насыщен (для SSD и RAID с параллельными операциями этот показатель условный) |

Какой процесс нагружает диск: `pidstat -d 1` или `sudo iotop`.

## pidstat — по процессам

```bash
pidstat 1          # CPU по процессам
pidstat -r 1       # память (minflt, majflt, RSS)
pidstat -d 1       # чтение и запись на диск
pidstat -p 1234 1  # один процесс
```

## sar — история

`sar` умеет не только показывать текущие значения, но и хранить историю: служба `sysstat` раз в 10 минут записывает статистику в `/var/log/sysstat/` (или `/var/log/sa/`).

```bash
sar -u            # CPU за сегодня
sar -r            # память
sar -d            # диски
sar -n DEV        # сеть
sar -u -f /var/log/sysstat/sa15   # за 15-е число месяца
```

Это спасает, когда проблема была ночью, а смотрите вы утром.

## Сеть: ss и iftop

```bash
ss -s                  # сводка: сколько соединений в каком состоянии
ss -tulpn              # слушающие TCP/UDP-порты и процессы
ss -tan state established | wc -l      # число установленных соединений
ss -tan | awk '{print $1}' | sort | uniq -c   # соединения по состояниям (много TIME-WAIT? CLOSE-WAIT?)
sudo iftop -i eth0     # трафик по соединениям в реальном времени
nload                  # общий трафик интерфейса
```

Подробно сетевая диагностика разбирается в разделе «Сети».

## perf и flame graphs

Когда понятно, что процессор занят, но непонятно чем внутри программы, помогает профилировщик **perf**:

```bash
sudo perf top                      # самые «горячие» функции в реальном времени
sudo perf record -g -p 1234 -- sleep 30   # записать профиль процесса за 30 секунд
sudo perf report                   # разобрать профиль
```

**Flame graph** (Brendan Gregg) — визуализация профиля: ширина «пламени» показывает, сколько времени процессор провёл в функции и её вызовах. Широкие плато — главные кандидаты на оптимизацию.

## Метод USE

Для каждого ресурса (CPU, память, диск, сеть) проверьте три вещи:

- **U**tilization — насколько ресурс загружен (%util, us+sy);
- **S**aturation — есть ли очередь (r в vmstat, aqu-sz, swap);
- **E**rrors — есть ли ошибки (dmesg, ошибки интерфейсов в `ip -s link`).

Этот подход вернётся в разделе «Мониторинг».

## Лаборатория

```bash setup
lab_unit() { systemctl stop "$1" 2>/dev/null; systemctl reset-failed "$1" 2>/dev/null; true; }
mkdir -p /opt/lab
```

### Кто пишет на диск

Диск сервера загружен записью, всё тормозит. На сервере несколько похожих агентов (`python3`), и один из них без конца пишет на диск. Найдите **PID процесса, который пишет на диск больше всех**, и запишите его в `~/io-pid.txt`.

```bash setup
for i in 1 2 3; do lab_unit lab-agent$i; done
cat > /opt/lab/agent <<'EOF'
#!/usr/bin/env python3
import os, sys, time
if sys.argv[1] == "writer":
    end = time.time() + 600
    buf = os.urandom(1024 * 1024)
    while time.time() < end:
        with open("/var/tmp/lab-agent.dat", "wb") as f:
            for _ in range(8):
                f.write(buf)
            f.flush(); os.fsync(f.fileno())
        time.sleep(0.2)
else:
    time.sleep(10**6)
EOF
chmod 755 /opt/lab/agent
w=$(( RANDOM % 3 + 1 ))
for i in 1 2 3; do
  mode=idle; [ $i = $w ] && mode=writer
  systemd-run -q --unit=lab-agent$i -p User=backup /opt/lab/agent $mode
done
systemctl show -p MainPID --value lab-agent$w > /var/lib/lab/io-pid
rm -f /home/student/io-pid.txt
sleep 2
```

```bash check
want=$(cat /var/lib/lab/io-pid)
[ -f /home/student/io-pid.txt ] || fail "Нет ~/io-pid.txt"
got=$(tr -d '[:space:]' < /home/student/io-pid.txt)
[ "$got" = "$want" ] || fail "В ~/io-pid.txt «$got» — этот процесс пишет на диск не больше всех"
ok "на диск пишет PID $want"
```

```text hint
1. Обычный top не показывает диск. Есть утилиты «top для ввода-вывода» и поштучная статистика процессов из пакета sysstat с ключом «диск».
2. Процессы принадлежат другому пользователю — их счётчики ввода-вывода видны только администратору.
3. Смотрите колонку записи (kB_wr/s или DISK WRITE) за несколько секунд, а не один мгновенный снимок.
```

```bash solution
sudo pidstat -d 1 3 | tail -8
# -h: одна строка на процесс, колонки: время, UID, PID, kB_rd/s, kB_wr/s, ...
sudo pidstat -d -h 2 1 | awk '$NF == "python3" {print $3, $5}' | sort -k2 -nr | head -1 | awk '{print $1}' > ~/io-pid.txt
```

```text review
Эталон: `sudo iotop -o` или `sudo pidstat -d 1`.

- Порядок при «всё тормозит»: `uptime` (load average) → `top` (смотрим `wa` — ожидание диска) → `iostat -xz 1` (какой диск, `%util`, `await`) → `pidstat -d 1` / `iotop -o` (какой процесс).
- `iostat -x`: `await` — сколько миллисекунд ждёт запрос (для SSD норма — единицы), `%util` близкий к 100% — диск занят всё время.
- Счётчики конкретного процесса — в `/proc/PID/io` (`write_bytes`). Читать чужие может только root.
- Список «60 секунд на диагностику» Брендана Грегга: `uptime`, `dmesg -T | tail`, `vmstat 1`, `mpstat -P ALL 1`, `pidstat 1`, `iostat -xz 1`, `free -m`, `sar -n DEV 1`, `sar -n TCP,ETCP 1`, `top`.
```

### Сколько соединений держит сервис

Сервис на порту `8088` жалуется на нехватку соединений. Узнайте, сколько **установленных** (ESTABLISHED) TCP-соединений он сейчас обслуживает — со стороны сервера, то есть с локальным портом 8088, — и запишите число в `~/conn.txt`.

```bash setup
lab_unit lab-conn-server; lab_unit lab-conn-client
rm -f /home/student/conn.txt
cat > /opt/lab/conn-server <<'EOF'
#!/usr/bin/env python3
import socket, threading
s = socket.socket(); s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(("127.0.0.1", 8088)); s.listen(100)
conns = []
while True:
    c, _ = s.accept(); conns.append(c)
EOF
cat > /opt/lab/conn-client <<'EOF'
#!/usr/bin/env python3
import socket, sys, time
socks = [socket.create_connection(("127.0.0.1", 8088)) for _ in range(int(sys.argv[1]))]
time.sleep(10**6)
EOF
chmod 755 /opt/lab/conn-server /opt/lab/conn-client
systemd-run -q --unit=lab-conn-server /opt/lab/conn-server
sleep 0.5
n=$(( RANDOM % 20 + 11 ))
systemd-run -q --unit=lab-conn-client /opt/lab/conn-client $n
sleep 1
```

```bash check
want=$(ss -Htn state established '( sport = :8088 )' | wc -l)
[ "$want" -gt 0 ] || fail "Соединений с сервисом нет — начните задачу заново"
[ -f /home/student/conn.txt ] || fail "Нет ~/conn.txt"
got=$(tr -d '[:space:]' < /home/student/conn.txt)
[ "$got" = "$want" ] || fail "В ~/conn.txt «$got», а установленных соединений с локальным портом 8088 — другое число (каждое соединение на этой машине видно дважды: со стороны клиента и сервера)"
ok "сервис на 8088 держит $want соединений"
```

```text hint
1. Утилита для сокетов умеет фильтровать по состоянию соединения и по локальному порту.
2. Клиент работает на той же машине — каждое соединение видно дважды: с локальным портом 8088 (сервер) и с портом 8088 удалённой стороны (клиент). Нужно первое.
3. Убрать заголовок и посчитать строки.
```

```bash solution
ss -tn state established '( sport = :8088 )' | head -5
ss -Htn state established '( sport = :8088 )' | wc -l > ~/conn.txt
```

```text review
Эталон: `ss -Htn state established '( sport = :8088 )' | wc -l`.

- `ss -s` — сводка по состояниям; `ss -tan | awk '{print $1}' | sort | uniq -c` — сколько соединений в каждом состоянии.
- Много `TIME-WAIT` — нормально после коротких соединений; много `CLOSE-WAIT` — приложение не закрывает сокеты (ошибка в коде, утечка); много `SYN-RECV` — SYN-флуд или перегрузка.
- Фильтры ss: `sport`/`dport` — порты, `src`/`dst` — адреса, `state` — состояние.
```

## Тест

### Что означает колонка r в выводе vmstat?
- [ ] Прочитанные с диска блоки
- [x] Число процессов в очереди на выполнение на CPU
- [ ] Свободная память
- [ ] Число перезагрузок
> Если r стабильно больше числа ядер — процессору не хватает мощности.

### Какая колонка vmstat показывает процессы, ожидающие ввода-вывода?
= b
> Это процессы в состоянии D.

### Какой командой посмотреть загрузку дисков: IOPS, задержки и %util?
= iostat -xz 1
= iostat -x 1
> `-x` — расширенная статистика, `-z` — скрыть неактивные устройства.

### В iostat у диска w_await = 250 мс и %util = 99%. Что это значит?
- [ ] Диск простаивает
- [x] Диск перегружен: операции записи стоят в очереди и выполняются очень долго
- [ ] Это нормальные значения для SSD
- [ ] Проблема с сетью
> Ищите, кто пишет: `pidstat -d 1` или `iotop`.

### Как узнать, какой процесс больше всех читает и пишет на диск?
- [x] pidstat -d 1
- [x] sudo iotop
- [ ] free -m
- [ ] ss -s
> Обе утилиты показывают ввод-вывод по процессам.

### Чем полезен sar по сравнению с vmstat и iostat?
- [ ] Он быстрее работает
- [x] Он сохраняет историю метрик, и можно посмотреть, что было с сервером в прошлом, например ночью
- [ ] Он показывает логи приложений
- [ ] Он умеет перезапускать службы
> История лежит в /var/log/sysstat или /var/log/sa.

### Как с помощью mpstat увидеть, что одно ядро загружено на 100%, а остальные свободны?
= mpstat -P ALL 1
> Типично для однопоточного приложения, которое упирается в одно ядро.

### Какая команда первой из списка «60 секунд» покажет ошибки ядра — OOM, сбои дисков?
- [ ] uptime
- [x] dmesg -T | tail
- [ ] free -m
- [ ] sar -n DEV 1
> Ошибки ядра часто сразу объясняют проблему.

### Как получить сводку по TCP-соединениям в разных состояниях?
- [x] ss -s
- [ ] iostat -n
- [ ] free -s
- [ ] vmstat -t
> Много CLOSE-WAIT обычно означает, что приложение не закрывает соединения.

### Какие колонки vmstat нужно смотреть, чтобы понять, активно ли используется swap?
- [ ] bi и bo
- [x] si и so
- [ ] in и cs
- [ ] us и sy
> bi и bo — обычный дисковый ввод-вывод.

### Для чего нужен perf?
- [ ] Для проверки сетевого соединения
- [x] Для профилирования: показывает, в каких функциях программы и ядра процессор проводит время
- [ ] Для измерения свободного места
- [ ] Для ротации логов
> Результат удобно смотреть в виде flame graph.

- [x] Utilization — загрузку
