# Сломанный сервер — диски

С дисками ошибаться дороже всего: неверная команда стирает данные, ошибка в `/etc/fstab` оставляет сервер незагружаемым. Поэтому здесь особенно важно сначала смотреть, потом менять.

## Алгоритм

1. **Что видит система:** `lsblk -f` (устройства, ФС, UUID, точки монтирования), `findmnt` (что смонтировано), `blkid`.
2. **Место:** `df -h` и `df -i`; кто съел — `du -xh --max-depth=1 / | sort -h`, удалённые открытые файлы — `lsof +L1`.
3. **fstab:** `findmnt --verify` и `mount -a` после **любой** правки — до перезагрузки. Для некритичных дисков — `nofail`.
4. **Удалять — точечно:** сначала посмотреть, что удаляется (`find ... -print`), потом `-delete`. Данные приложения не трогать.

## Частые поломки

| Симптом | Причина | Что делать |
| --- | --- | --- |
| `mount -a`: «can't find UUID=…» | в fstab неверный UUID (диск пересоздали, опечатка) | `blkid` → правильный UUID в fstab → `mount -a` |
| сервер ушёл в emergency mode | обязательный диск из fstab не монтируется | в консоли: `mount -o remount,rw /`, исправить fstab, `nofail` |
| «No space left on device» | место кончилось | `du`, старые бэкапы/логи/дампы ядра, ротация |
| то же, но `df -h` свободно | кончились inode или удалённый открытый файл | `df -i`, `lsof +L1` |
| диск «только для чтения» | ФС перемонтирована из-за ошибок | `dmesg`, `fsck` в отмонтированном виде |

## Лаборатория

```bash lib
export LVM_SUPPRESS_FD_WARNINGS=1
DISKS=/var/lib/lab-disks
# Убрать всё, что могли оставить прошлые задачи с дисками: монтирования, массивы, тома, loop-устройства
lab_disks_reset() {
  for m in $(findmnt -rn -o TARGET | grep -E '^/mnt/(data|app|busy|raid|xfs-lab|ramcache|lab-[a-z]+)$|^/srv/overlay/merged$' | sort -r); do umount -l "$m"; done
  mdadm --stop --scan >/dev/null 2>&1
  for vg in data labvg; do vgremove -qq -ff "$vg" >/dev/null 2>&1; done
  for l in $(losetup -nO NAME,BACK-FILE 2>/dev/null | awk -v d="$DISKS" 'index($2, d) == 1 {print $1}'); do
    pvremove -qq -ff "$l" >/dev/null 2>&1; wipefs -qa "$l" >/dev/null 2>&1; losetup -d "$l"
  done
  rm -f /dev/lab-*; rm -rf "$DISKS"; mkdir -p "$DISKS"
  sed -i -E '\#[[:space:]]/mnt/(data|app|raid|xfs-lab|ramcache)[[:space:]]#d' /etc/fstab
  true
}
# lab_disk имя размер → пустой «диск» /dev/lab-имя (ссылка на loop-устройство)
lab_disk() {
  truncate -s "$2" "$DISKS/$1.img"
  ln -sf "$(losetup -f --show "$DISKS/$1.img")" "/dev/lab-$1"
}
lab_unit() { systemctl stop "$1" 2>/dev/null; systemctl reset-failed "$1" 2>/dev/null; true; }
```

### Перед перезагрузкой

Админ добавил в `/etc/fstab` новый архивный диск (`/dev/lab-archive`, точка монтирования `/mnt/archive`), но `mount -a` выдаёт ошибку. Ночью плановая перезагрузка — с такой записью сервер может не загрузиться. Почините так, чтобы `mount -a` проходил без ошибок, а диск монтировался в `/mnt/archive` по записи в fstab. Данные на диске должны сохраниться.

```bash setup
for i in 1 2 3 4 5 6 7 8; do mountpoint -q /mnt/archive || break; umount -l /mnt/archive; done
lab_disks_reset
sed -i '\#/mnt/archive#d' /etc/fstab
lab_disk archive 64M
mkfs.ext4 -q -F /dev/lab-archive
mkdir -p /mnt/archive
mount /dev/lab-archive /mnt/archive && echo "архив 2025" > /mnt/archive/2025.txt && umount /mnt/archive
real=$(blkid -s UUID -o value /dev/lab-archive)
fake=$(echo "$real" | sed 's/^\(.\{8\}\)/deadbeef/')
echo "UUID=$fake /mnt/archive ext4 defaults 0 2" >> /etc/fstab
systemctl daemon-reload
```

```bash check
dev=$(readlink -f /dev/lab-archive); uuid=$(blkid -s UUID -o value $dev)
mount -a 2>/tmp/lab-mount.err || fail "mount -a выдаёт ошибку: $(head -1 /tmp/lab-mount.err)"
[ "$(findmnt -no SOURCE --mountpoint /mnt/archive | tail -1)" = "$dev" ] || fail "/mnt/archive не смонтирован с архивного диска"
line=$(grep -E '[[:space:]]/mnt/archive[[:space:]]' /etc/fstab | grep -v '^\s*#')
[ "$(echo "$line" | grep -c .)" = 1 ] || fail "Для /mnt/archive в fstab $(echo "$line" | grep -c .) активных строк"
echo "$line" | grep -q "UUID=$uuid" || fail "В fstab для /mnt/archive не UUID этого диска"
grep -q 'архив 2025' /mnt/archive/2025.txt 2>/dev/null || fail "Данные на диске пропали"
ok "$line"
```

```text hint
1. Прочитать ошибку mount -a: какое устройство не найдено.
2. Сравнить с тем, что реально есть у диска, — утилита атрибутов блочных устройств или lsblk с колонкой UUID.
3. Исправить строку в fstab (форматировать ничего не нужно!), попросить systemd перечитать конфигурацию и снова выполнить mount -a. Для некритичного архивного диска уместен флаг «не обязательно».
```

```bash solution
sudo mount -a || true
sudo blkid /dev/lab-archive
uuid=$(sudo blkid -s UUID -o value "$(readlink -f /dev/lab-archive)")
sudo sed -i "s#^UUID=[^ ]* /mnt/archive .*#UUID=$uuid /mnt/archive ext4 defaults,nofail 0 2#" /etc/fstab
sudo findmnt --verify
sudo systemctl daemon-reload
sudo mount -a
findmnt /mnt/archive
```

```text review
Причина: в fstab вписан неверный UUID — такого устройства нет. При загрузке systemd ждал бы его 90 секунд и отправил сервер в emergency mode (запись без `nofail`).

- UUID — только из `blkid`/`lsblk -f`, копированием, а не руками.
- `findmnt --verify` и `mount -a` после **каждой** правки fstab — обязательный ритуал, иначе ошибку найдёт ночная перезагрузка.
- systemd строит из fstab mount-юниты и не перечитывает файл сам. Без `systemctl daemon-reload` старый юнит ждёт устройство со старым UUID и сразу размонтирует то, что смонтировал `mount -a`, — `findmnt --verify` предупреждает: «systemd still uses the old version».
- `nofail` для всего, без чего система загрузится; на облачных ВМ без консоли это вопрос «будет ли доступ к серверу вообще».
- Если уже в emergency mode: войти под root, `mount -o remount,rw /`, поправить fstab, `systemctl daemon-reload`, `reboot`.
```

```text notes
mkfs => Диск форматировался заново — данные на нём уничтожены. Чинить нужно запись в fstab, а не диск.
```

### База не запускается

Служба **`lab-labdb`** хранит данные на отдельном разделе `/var/lib/labdb` и перестала запускаться. Поднимите её. Файлы данных (`/var/lib/labdb/data/`) трогать **нельзя**; из резервных копий (`/var/lib/labdb/backups/`) нужно **оставить самую свежую**.

```bash setup
lab_unit lab-labdb
lab_disks_reset
lab_disk labdb 64M
mkfs.ext4 -q -F /dev/lab-labdb
mkdir -p /var/lib/labdb && mount /dev/lab-labdb /var/lib/labdb
mkdir -p /var/lib/labdb/data /var/lib/labdb/backups
head -c 6000000 /dev/urandom > /var/lib/labdb/data/table1.dat
head -c 4000000 /dev/urandom > /var/lib/labdb/data/table2.dat
md5sum /var/lib/labdb/data/* > /var/lib/lab/labdb.md5
for d in 01 02 03 04 05 06 07 08 09; do
  f=/var/lib/labdb/backups/labdb-2026-11-$d.bak
  head -c 9000000 /dev/urandom > $f 2>/dev/null || break
  touch -d "2026-11-$d 03:00" $f
done
dd if=/dev/zero of=/var/lib/labdb/fill bs=1M count=200 status=none 2>/dev/null; rm -f /var/lib/labdb/fill
ls -t /var/lib/labdb/backups/ | head -1 > /var/lib/lab/labdb-newest
cat > /opt/lab-labdb.sh <<'EOF'
#!/bin/bash
# «база»: при старте пишет журнал на 8 МБ; без места — падает
head -c 8000000 /dev/zero > /var/lib/labdb/data/wal.log || { echo "FATAL: could not write WAL: No space left on device" >&2; exit 1; }
echo "labdb started"
exec sleep infinity
EOF
chmod 755 /opt/lab-labdb.sh
cat > /etc/systemd/system/lab-labdb.service <<'EOF'
[Unit]
Description=Lab DB
[Service]
ExecStart=/opt/lab-labdb.sh
EOF
systemctl daemon-reload
systemctl start lab-labdb >/dev/null 2>&1; true
```

```bash check
(cd / && md5sum -c --quiet /var/lib/lab/labdb.md5 >/dev/null 2>&1) || fail "Файлы данных в /var/lib/labdb/data изменены или удалены"
newest=$(cat /var/lib/lab/labdb-newest)
[ -f /var/lib/labdb/backups/$newest ] || fail "Самая свежая резервная копия $newest удалена"
[ "$(systemctl is-active lab-labdb)" = active ] || fail "Служба lab-labdb не работает: $(journalctl -u lab-labdb -n 1 --no-pager -o cat)"
ok "lab-labdb работает; свободно $(df -h --output=avail /var/lib/labdb | tail -1 | tr -d ' ')"
```

```text hint
1. Почему служба падает — в её журнале.
2. Посмотреть заполнение раздела и что на нём занимает место, по каталогам.
3. Удалить старые резервные копии, оставив самую новую (сортировка по времени изменения), и перезапустить службу.
```

```bash solution
journalctl -u lab-labdb -n 3 --no-pager
df -h /var/lib/labdb
sudo du -sh /var/lib/labdb/*
cd /var/lib/labdb/backups
ls -lt
ls -t | tail -n +2 | sudo xargs -r rm -v
sudo systemctl restart lab-labdb
systemctl is-active lab-labdb
```

```text review
Причина: раздел `/var/lib/labdb` заполнен резервными копиями — новые клались рядом с базой и никогда не удалялись. Служба при старте не смогла записать журнал.

- Бэкапы на том же диске, что и данные, — не бэкапы: умрёт диск — умрут оба. Их выносят на другой сервер или в S3 и хранят по политике (7 ежедневных, 4 недельных…).
- Удаляя «старое», смотрите, что удаляете: `ls -t | tail -n +2` сначала без `rm`.
- Мониторинг места (алерт на 80–85%) и прогноз заполнения (`predict_linear(node_filesystem_avail_bytes[6h], 24*3600) < 0`) находят это раньше, чем база ляжет.
```

```text notes
rm\s+[^\n]*/var/lib/labdb/data => Удалялись файлы из data/ — это данные базы, их трогать нельзя.
```

## Тест

### После правки fstab mount -a ругается «can't find UUID». Чем это грозит?
- [ ] Ничем, при загрузке Linux сам найдёт диск
- [x] При загрузке systemd будет ждать устройство и, если запись без nofail, уйдёт в emergency mode
- [ ] Диск будет отформатирован
- [ ] Сервер загрузится, но без сети
> Обязательная запись fstab, которую нельзя смонтировать, останавливает загрузку.

### Какой командой проверить fstab на ошибки без перезагрузки?
= findmnt --verify
= mount -a
> `findmnt --verify` проверяет синтаксис и существование устройств, `mount -a` — пробует смонтировать всё.

### Как узнать UUID файловой системы на устройстве?
= blkid
= lsblk -f
> UUID берут из вывода `blkid` или `lsblk -f`, а не набирают руками.

### Что значит опция nofail в fstab?
- [ ] Диск не может сломаться
- [x] Если устройства нет или оно не монтируется, загрузка продолжается
- [ ] Проверять ФС при каждой загрузке
- [ ] Монтировать только для чтения
> Для некритичных дисков (архивы, бэкапы, данные приложения) — must have.

### Служба пишет «No space left on device». Какие две команды дают картину по месту?
- [ ] free и top
- [x] df -h (раздел) и du (кто занял)
- [ ] lsblk и blkid
- [ ] mount и umount
> `df` — сколько свободно на разделе, `du -xh --max-depth=1` — какие каталоги занимают.

### Как удалить все файлы в каталоге, кроме самого нового по времени изменения?
- [ ] rm -rf *
- [x] ls -t | tail -n +2 | xargs rm
- [ ] find . -newer -delete
- [ ] rm $(ls | head -1)
> `ls -t` сортирует от новых к старым, `tail -n +2` пропускает первый — самый новый.

### Почему хранить бэкапы базы на том же диске, что и базу, — плохо?
- [ ] Бэкапы медленно читаются
- [x] При отказе диска пропадут и данные, и бэкапы; к тому же они съедают место базы
- [ ] Так нельзя по лицензии PostgreSQL
- [ ] Это нормальная практика
> Бэкап должен жить отдельно: другой сервер, S3, другая площадка.

### Сервер в emergency mode из-за fstab. Как получить возможность править файлы на корне?
= mount -o remount,rw /
> В emergency mode корень часто смонтирован только для чтения.

### df -h показывает 40% свободно, но файлы не создаются. Что проверить следующим?
- [ ] Права на /
- [x] df -i — свободные inode
- [ ] Температуру диска
- [ ] free -m
> Кончились inode — частая причина при миллионах мелких файлов.

### Диск внезапно стал «Read-only file system». Где искать причину?
- [ ] В /etc/hosts
- [x] В журнале ядра: dmesg / journalctl -k — ошибки ввода-вывода или ФС
- [ ] В crontab
- [ ] В ~/.bashrc
> Ядро перемонтирует ФС в read-only при ошибках, чтобы не испортить данные.

### Какой алерт заранее предупредит, что диск заполнится в ближайшие сутки?
- [ ] up == 0
- [x] predict_linear по свободному месту на горизонт 24 часа меньше нуля
- [ ] rate(node_cpu_seconds_total[5m])
- [ ] node_load1 > 4
> Прогноз по тренду срабатывает раньше, чем фиксированный порог.

### Что сделать перед удалением файлов командой find ... -delete?
- [ ] Ничего
- [x] Запустить ту же команду с -print и посмотреть список
- [ ] Перезагрузить сервер
- [ ] Отмонтировать раздел
> Сначала увидеть, что попадёт под удаление, — потом удалять.
