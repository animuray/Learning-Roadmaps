# Файловые системы

Диск — это просто последовательность блоков. **Файловая система** (ФС) организует их в файлы и каталоги: где лежат данные, какие блоки свободны, кому принадлежит файл, какие у него права.

## Журналирование

Если сервер выключить в момент записи, метаданные ФС могут остаться в противоречивом состоянии. **Журналируемая** ФС сначала записывает в журнал, что собирается сделать, а потом делает. После сбоя достаточно «доиграть» или откатить журнал, а не проверять весь диск часами. ext4, xfs и btrfs — журналируемые (btrfs обеспечивает целостность через copy-on-write).

## Основные файловые системы

| ФС | Где по умолчанию | Сильные стороны | Ограничения |
| --- | --- | --- | --- |
| **ext4** | Debian, Ubuntu | Надёжная, универсальная, хорошо изучена, можно уменьшить (в отмонтированном виде) | Число inode фиксируется при создании |
| **xfs** | RHEL, Rocky, AlmaLinux | Отлично работает с большими файлами и параллельным вводом-выводом, inode выделяются динамически | **Нельзя уменьшить**, только увеличить |
| **btrfs** | Fedora, openSUSE | Снапшоты, сжатие, copy-on-write, контрольные суммы данных | Сложнее, некоторые режимы RAID не рекомендуются |
| **tmpfs** | `/run`, `/dev/shm`, часто `/tmp` | Живёт в оперативной памяти — очень быстро | Содержимое пропадает при перезагрузке; размер ограничен |
| **overlay** | Docker, containerd, Kubernetes | Слоёная ФС: несколько слоёв «только для чтения» плюс один слой для записи | Особенности с inode и переименованием каталогов |
| vfat | Раздел EFI (ESP) | Понимают все ОС и UEFI | Нет прав Unix, файлы до 4 ГБ |
| nfs | Сетевые хранилища | Общий доступ к файлам по сети | Зависит от сети, возможны «зависания» в состоянии D |

```bash
df -hT                 # тип ФС у смонтированных разделов
lsblk -f               # тип ФС у всех устройств
cat /proc/filesystems  # какие ФС поддерживает ядро
```

## Создание, проверка, изменение размера

```bash
sudo mkfs.ext4 /dev/sdb1          # создать ext4
sudo mkfs.xfs /dev/sdb1           # создать xfs
sudo fsck -f /dev/sdb1            # проверить ext4 — ТОЛЬКО на отмонтированной ФС!
sudo xfs_repair /dev/sdb1         # проверить xfs — тоже на отмонтированной
sudo resize2fs /dev/sdb1          # расширить ext4 до размера раздела (можно на смонтированной)
sudo xfs_growfs /mnt/data         # расширить xfs (по точке монтирования)
sudo tune2fs -l /dev/sdb1         # параметры ext4: число inode, резерв блоков и т. д.
```

> [!warning] fsck только на отмонтированной ФС
> Проверка смонтированной файловой системы может её повредить. Корень проверяют при загрузке или из rescue-режима.

## tmpfs

```bash
sudo mount -t tmpfs -o size=512M tmpfs /mnt/ram
df -h /mnt/ram
```

tmpfs хранит данные в RAM (и при нехватке памяти может уйти в swap). Подходит для временных файлов, сокетов, кэшей, которые не жалко потерять. В Docker и Kubernetes на tmpfs монтируют каталоги для секретов, чтобы они не попадали на диск.

## overlayfs — основа образов контейнеров

OverlayFS накладывает несколько каталогов друг на друга и показывает их как один:

- **lowerdir** — один или несколько слоёв «только для чтения» (слои образа);
- **upperdir** — слой для записи (слой контейнера);
- **workdir** — служебный каталог;
- **merged** — то, что видит процесс.

```bash
mkdir -p /tmp/ov/{lower,upper,work,merged}
echo "из образа" > /tmp/ov/lower/a.txt
sudo mount -t overlay overlay -o lowerdir=/tmp/ov/lower,upperdir=/tmp/ov/upper,workdir=/tmp/ov/work /tmp/ov/merged
echo "изменено" | sudo tee /tmp/ov/merged/a.txt
cat /tmp/ov/lower/a.txt    # оригинал не изменился
ls /tmp/ov/upper           # изменённая копия попала в верхний слой
```

- При изменении файла из нижнего слоя он сначала **копируется наверх** (copy-up), а нижний слой остаётся нетронутым.
- Удаление файла из нижнего слоя отмечается в верхнем специальным файлом-«затиркой» (**whiteout**).
- Поэтому десятки контейнеров из одного образа используют одни и те же слои на диске, а у каждого контейнера — только свой тонкий слой изменений. Подробнее — в разделе Docker.

## Лаборатория

```bash setup
export LVM_SUPPRESS_FD_WARNINGS=1
DISKS=/var/lib/lab-disks
# Убрать всё, что могли оставить прошлые задачи с дисками: монтирования, массивы, тома, loop-устройства
lab_disks_reset() {
  for m in $(findmnt -rn -o TARGET | grep -E '^/mnt/(data|app|busy|raid|xfs-lab|ramcache|lab-[a-z]+)$|^/srv/overlay/merged$' | sort -r); do umount -l "$m"; done
  mdadm --stop --scan >/dev/null 2>&1
  for vg in data labvg; do vgremove -qq -ff "$vg" >/dev/null 2>&1; done
  for l in $(losetup -nO NAME,BACK-FILE 2>/dev/null | awk -v d="$DISKS" 'index($2, d) == 1 {print $1}'); do
    pvremove -qq -ff "$l" >/dev/null 2>&1; wipefs -qa "$l" >/dev/null 2>&1; losetup -d "$l"
  done
  rm -f /dev/lab-*; rm -rf "$DISKS"; mkdir -p "$DISKS"
  sed -i -E '\#[[:space:]]/mnt/(data|app|raid|xfs-lab|ramcache)[[:space:]]#d' /etc/fstab
  true
}
# lab_disk имя размер → пустой «диск» /dev/lab-имя (ссылка на loop-устройство)
lab_disk() {
  truncate -s "$2" "$DISKS/$1.img"
  ln -sf "$(losetup -f --show "$DISKS/$1.img")" "/dev/lab-$1"
}
```

### Раздел xfs для логов

Подключён пустой диск `/dev/lab-logs` (320 МБ). Создайте на нём файловую систему **xfs** с меткой `logs` и смонтируйте её в `/mnt/lab-logs`.

```bash setup
lab_disks_reset
lab_disk logs 320M
```

```bash check
dev=$(readlink -f /dev/lab-logs)
[ "$(blkid -s TYPE -o value "$dev" 2>/dev/null)" = xfs ] || fail "На /dev/lab-logs нет файловой системы xfs"
[ "$(blkid -s LABEL -o value "$dev")" = logs ] || fail "Метка файловой системы — «$(blkid -s LABEL -o value "$dev")»"
[ "$(findmnt -no SOURCE /mnt/lab-logs 2>/dev/null)" = "$dev" ] || fail "Диск не смонтирован в /mnt/lab-logs"
ok "$(findmnt -no SOURCE,FSTYPE,SIZE /mnt/lab-logs) — метка logs"
```

```text hint
1. Утилита создания ФС для xfs — mkfs с суффиксом; метку задают ключом при создании.
2. Создать каталог и смонтировать. Монтировать можно и по метке.
```

```bash solution
sudo mkfs.xfs -q -L logs /dev/lab-logs
sudo mkdir -p /mnt/lab-logs
sudo mount LABEL=logs /mnt/lab-logs
df -hT /mnt/lab-logs
```

```text review
Эталон: `mkfs.xfs -L logs /dev/lab-logs` → `mount LABEL=logs /mnt/lab-logs`.

- xfs — ФС по умолчанию в RHEL/Rocky: хороша для больших файлов и параллельной записи, inode выделяет динамически. Но её **нельзя уменьшить** — только расширить (`xfs_growfs`). ext4 — по умолчанию в Debian/Ubuntu, умеет и уменьшаться (в отмонтированном виде).
- Метка (`-L`) читается человеком; в fstab надёжнее UUID — метки могут совпасть у двух дисков.
- Посмотреть ФС всех устройств: `lsblk -f`; параметры xfs — `xfs_info /mnt/lab-logs`.
```

### Быстрый кэш в памяти

Приложению нужен каталог для временных файлов в **оперативной памяти**. Смонтируйте **tmpfs** размером **64 МБ** в `/mnt/ramcache` и пропишите его в `/etc/fstab`, чтобы он создавался при загрузке.

```bash setup
lab_disks_reset
```

```bash check
[ "$(findmnt -no FSTYPE /mnt/ramcache 2>/dev/null)" = tmpfs ] || fail "В /mnt/ramcache не смонтирован tmpfs"
sz=$(findmnt -bno SIZE /mnt/ramcache)
[ "$sz" = 67108864 ] || fail "Размер tmpfs — $((sz / 1024 / 1024)) МБ"
awk '$2 == "/mnt/ramcache" && $3 == "tmpfs"' /etc/fstab | grep -q . || fail "В /etc/fstab нет строки tmpfs для /mnt/ramcache"
ok "tmpfs 64 МБ в /mnt/ramcache, в fstab есть"
```

```text hint
1. tmpfs не нужен диск: «устройство» — просто слово tmpfs, тип — tmpfs, размер — опция монтирования.
2. Строку в таблице монтирования составить так же, как для диска; проверить, смонтировав каталог по одной лишь записи из fstab.
```

```bash solution
sudo mkdir -p /mnt/ramcache
echo 'tmpfs /mnt/ramcache tmpfs size=64M,mode=1777 0 0' | sudo tee -a /etc/fstab >/dev/null
sudo mount /mnt/ramcache
df -h /mnt/ramcache
```

```text review
Эталон: строка `tmpfs /mnt/ramcache tmpfs size=64M,mode=1777 0 0` → `mount /mnt/ramcache`.

- tmpfs живёт в оперативной памяти (и своп): очень быстрый, но **пропадает при перезагрузке**. Подходит для кэшей, сокетов, временных файлов сборки.
- Память берётся по мере заполнения, `size` — лишь потолок. Без `size` — половина ОЗУ.
- В системе tmpfs уже много: `/run`, `/dev/shm`, часто `/tmp`. Посмотреть: `findmnt -t tmpfs`.
- `mode=1777` — права как у `/tmp`: писать могут все, удалять — только свои файлы.
```

### Слои overlayfs

Так устроены слои Docker. В `/srv/overlay/lower` лежит «образ»: `app.conf` и `old.conf`. Смонтируйте **overlayfs** в `/srv/overlay/merged` (верхний слой — `/srv/overlay/upper`, рабочий — `/srv/overlay/work`). Затем **через merged**: допишите в `app.conf` строку `mode=prod` и удалите `old.conf`. Нижний слой должен остаться нетронутым.

```bash setup
lab_disks_reset
rm -rf /srv/overlay
mkdir -p /srv/overlay/lower
printf 'listen=8080\n' > /srv/overlay/lower/app.conf
printf 'legacy=true\n' > /srv/overlay/lower/old.conf
md5sum /srv/overlay/lower/* > /var/lib/lab/overlay-lower.md5
```

```bash check
o=/srv/overlay
[ "$(findmnt -no FSTYPE $o/merged 2>/dev/null)" = overlay ] || fail "В $o/merged не смонтирован overlayfs"
(cd / && md5sum -c --quiet /var/lib/lab/overlay-lower.md5 >/dev/null 2>&1) && [ -f $o/lower/old.conf ] || fail "Нижний слой изменён — так ломают образ для всех контейнеров"
grep -qx 'mode=prod' $o/merged/app.conf || fail "В merged/app.conf нет строки mode=prod"
[ -e $o/merged/old.conf ] && fail "old.conf всё ещё виден в merged"
grep -qx 'mode=prod' $o/upper/app.conf 2>/dev/null || fail "Изменённого app.conf нет в верхнем слое"
[ -c $o/upper/old.conf ] || fail "В верхнем слое нет пометки об удалении old.conf"
ok "upper: $(ls -l $o/upper | awk 'NR>1 {print $1, $NF}' | tr '\n' ';')"
```

```text hint
1. Создать верхний, рабочий и объединённый каталоги.
2. Смонтировать ФС типа overlay, указав в опциях три каталога: нижний (только чтение), верхний (куда пойдут изменения) и рабочий (служебный, на той же ФС, что верхний).
3. Все правки делать в объединённом каталоге и затем посмотреть, что появилось в верхнем слое.
```

```bash solution
o=/srv/overlay
sudo mkdir -p $o/upper $o/work $o/merged
sudo mount -t overlay overlay -o lowerdir=$o/lower,upperdir=$o/upper,workdir=$o/work $o/merged
echo 'mode=prod' | sudo tee -a $o/merged/app.conf >/dev/null
sudo rm $o/merged/old.conf
ls -l $o/upper
```

```text review
Эталон: `mount -t overlay overlay -o lowerdir=...,upperdir=...,workdir=... merged`.

- Чтение идёт сквозь слои сверху вниз, запись — только в upper. Изменённый файл целиком **копируется** наверх (copy-up) — поэтому правка большого файла в контейнере дорогая.
- Удаление — это не удаление из lower, а **whiteout**: символьное устройство 0/0 с тем же именем в upper. Поэтому `RUN rm` в отдельном слое Dockerfile не уменьшает образ.
- Docker: слои образа — несколько `lowerdir`, слой контейнера — `upperdir`. Посмотреть: `docker inspect -f '{{json .GraphDriver.Data}}' <контейнер>`, `mount | grep overlay`.
```
