# Память в Linux

Классическая паника новичка: «у сервера 16 ГБ памяти, свободно 300 МБ — срочно добавить память!». Чаще всего с памятью всё в порядке: Linux занимает свободную память под **кэш файлов** и мгновенно отдаёт её приложениям, когда нужно.

## free -h

```
$ free -h
               total        used        free      shared  buff/cache   available
Mem:            15Gi       5.2Gi       312Mi       180Mi       9.9Gi       9.8Gi
Swap:          2.0Gi        64Mi       1.9Gi
```

| Колонка | Значение |
| --- | --- |
| total | Вся память |
| used | Занято приложениями и ядром |
| **free** | Вообще ничем не занято |
| shared | Разделяемая память (tmpfs, общая память процессов) |
| **buff/cache** | Буферы и **page cache** — кэш содержимого файлов |
| **available** | Оценка, сколько памяти можно отдать новым приложениям без свопинга: free + та часть кэша, которую можно быстро освободить |

**Смотрите на `available`, а не на `free`.** В примере выше «свободно» 312 МБ, но доступно 9,8 ГБ — памяти достаточно.

## Page cache

Когда программа читает файл, его содержимое остаётся в памяти. Повторное чтение берётся из RAM, а не с диска, — это в тысячи раз быстрее. Когда приложению нужна память, ядро вытесняет кэш. Поэтому «занятая кэшем» память — это не потеря, а ускорение системы.

```bash
sync; echo 3 | sudo tee /proc/sys/vm/drop_caches   # сбросить кэш — только для экспериментов!
```

Сбрасывать кэш на продакшене не нужно: вы только замедлите систему, пока кэш не наполнится снова.

## Память процесса: VSZ и RSS

| Метрика | Где видно | Что это |
| --- | --- | --- |
| **VSZ / VIRT** | `ps`, `top` | Виртуальная память: всё, что процесс зарезервировал или отобразил (включая ещё не тронутое и файлы). Обычно сильно больше реальной |
| **RSS / RES** | `ps`, `top`, `VmRSS` в `/proc/PID/status` | Сколько страниц процесса сейчас реально лежит в RAM |
| SHR | `top` | Часть RSS, разделяемая с другими процессами (библиотеки) |
| PSS | `smem`, `/proc/PID/smaps_rollup` | RSS, где общие страницы поделены между процессами поровну — честная доля |

Общие библиотеки входят в RSS каждого процесса, поэтому сумма RSS всех процессов бывает больше всей физической памяти. Для точного подсчёта используют PSS.

```bash
ps -eo pid,rss,vsz,cmd --sort=-rss | head
grep -E 'VmRSS|VmSize|VmSwap' /proc/1234/status
```

## Swap

**Swap** — область на диске (раздел или файл), куда ядро выгружает редко используемые страницы памяти, чтобы освободить RAM.

- Swap — не «дополнительная память»: диск в тысячи раз медленнее. Если система **активно** читает и пишет swap, всё начинает тормозить.
- Немного занятого swap — нормально: ядро выгрузило то, что давно не трогали.
- Тревожный признак — постоянный обмен: ненулевые колонки `si` и `so` в `vmstat 1`.
- `vm.swappiness` (0–100+, по умолчанию 60) — насколько охотно ядро выгружает память приложений в swap по сравнению с вытеснением кэша файлов.

```bash
swapon --show
vmstat 1 5                       # колонки si/so — swap in/out в секунду
# Создать swap-файл на 2 ГБ
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

> [!note] Kubernetes и swap
> Исторически Kubernetes требовал отключать swap на нодах: лимиты памяти контейнеров и OOM должны работать предсказуемо. В новых версиях поддержка swap появилась, но по умолчанию на нодах его обычно отключают.

## Когда памяти действительно не хватает

- `available` близко к нулю;
- в `vmstat` постоянно ненулевые `si`/`so`, растёт `wa`;
- в журнале ядра появляются записи OOM Killer: `journalctl -k | grep -i oom`;
- RSS процесса растёт без остановки — похоже на **утечку памяти**.

Что делать: найти потребителя (`top -o %MEM`), ограничить его (лимиты systemd или контейнера), исправить утечку, добавить памяти или swap как временную подушку.

## Практика

- [ ] Выполнить `free -h` и объяснить каждую колонку; сравнить с `/proc/meminfo` (MemFree, MemAvailable, Cached)
- [ ] Прочитать большой файл (`cat bigfile > /dev/null`) дважды и замерить время через `time`; посмотреть, как изменился buff/cache
- [ ] Найти пять процессов с наибольшим RSS и сравнить их VSZ и RSS
- [ ] Посмотреть swap: `swapon --show`; создать swap-файл на тестовой ВМ и подключить его
- [ ] Запустить `vmstat 1` и создать нагрузку на память; понаблюдать за колонками free, cache, si, so

## Тест

### В free -h колонка free показывает 300 МБ, а available — 9 ГБ. Хватает ли системе памяти?
- [ ] Нет, осталось всего 300 МБ
- [x] Да: большая часть памяти занята кэшем файлов, который ядро мгновенно отдаст приложениям
- [ ] Нужно срочно сбросить кэш
- [ ] Это признак утечки памяти
> Ориентироваться нужно на `available`.

### Что такое page cache?
- [ ] Область swap на диске
- [x] Кэш содержимого файлов в оперативной памяти, который ускоряет повторное чтение
- [ ] Память ядра для страниц сайта
- [ ] Таблица страниц процесса
> Ядро вытесняет кэш, когда приложениям нужна память.

### Что показывает колонка available в free?
- [ ] Совсем свободную память
- [x] Оценку памяти, которую можно отдать новым приложениям без свопинга
- [ ] Размер swap
- [ ] Память, занятую ядром
> Берётся из MemAvailable в /proc/meminfo.

### Чем RSS отличается от VSZ?
- [x] RSS — память процесса, реально находящаяся в RAM
- [x] VSZ — весь виртуальный адресный объём процесса, включая ещё не использованное и отображённые файлы
- [ ] RSS всегда больше VSZ
- [ ] Это одно и то же
> Для оценки реального потребления смотрите на RSS (а точнее — на PSS).

### Почему сумма RSS всех процессов может быть больше всей физической памяти?
- [ ] Из-за ошибки ps
- [x] Общие библиотеки и разделяемая память учитываются в RSS каждого процесса, который их использует
- [ ] Из-за swap
- [ ] Из-за page cache
> Честную долю показывает PSS (утилита smem).

### Что такое swap?
- [ ] Быстрая кэш-память процессора
- [x] Область на диске, куда ядро выгружает редко используемые страницы памяти
- [ ] Резервная копия оперативной памяти
- [ ] Раздел для временных файлов
> Swap — подушка безопасности, а не замена RAM.

### По каким признакам видно, что системе действительно не хватает памяти?
- [x] available близко к нулю
- [x] В vmstat постоянно ненулевые si и so (активный обмен со swap)
- [x] В журнале ядра есть записи OOM Killer
- [ ] Колонка buff/cache большая
> Большой buff/cache — признак здоровой системы.

### Стоит ли регулярно сбрасывать кэш через drop_caches на продакшене?
- [ ] Да, это освобождает память
- [x] Нет: кэш и так освобождается по требованию, а сброс только замедлит систему
- [ ] Да, раз в час через cron
- [ ] Только на серверах баз данных
> drop_caches полезен разве что для экспериментов с производительностью.

### Какие колонки vmstat показывают активность swap?
- [ ] us и sy
- [x] si и so
- [ ] bi и bo
- [ ] r и b
> si — swap in (с диска в память), so — swap out. bi и bo — обычный дисковый ввод-вывод.

### Что регулирует параметр vm.swappiness?
- [ ] Размер swap
- [x] Насколько охотно ядро выгружает память приложений в swap по сравнению с вытеснением файлового кэша
- [ ] Скорость диска
- [ ] Лимит памяти процессов
> Для серверов баз данных его часто понижают.

### RSS процесса приложения медленно и постоянно растёт неделями, пока его не убивает OOM Killer. На что это похоже?
- [ ] На нормальную работу кэша
- [x] На утечку памяти в приложении
- [ ] На нехватку места на диске
- [ ] На проблему с сетью
> Временные меры — лимит памяти и регулярный перезапуск. Настоящее решение — найти утечку.

### Какие права должны быть у swap-файла?
= 600
> Иначе другие пользователи смогут прочитать из него содержимое чужой памяти; swapon предупредит о небезопасных правах.
