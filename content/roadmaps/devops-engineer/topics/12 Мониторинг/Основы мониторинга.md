# Основы мониторинга

Мониторинг отвечает на два вопроса: **что сломалось** (или вот-вот сломается) и **почему**. Без него о проблемах узнают от пользователей, а разбор инцидента превращается в гадание.

## Три сигнала наблюдаемости

| Сигнал | Что это | Пример | Инструменты |
| --- | --- | --- | --- |
| **Метрики** | Числа во времени, дешёвые, агрегируются | Запросов в секунду, % CPU, задержка p95 | Prometheus, VictoriaMetrics |
| **Логи** | Записи о событиях с подробностями | `ERROR db timeout user=42` | Loki, ELK/OpenSearch |
| **Трейсы** | Путь одного запроса через сервисы | api → auth → db: 340 мс, из них 300 — db | Jaeger, Tempo, OpenTelemetry |

**Наблюдаемость** (observability) — способность понять, что происходит внутри системы, по её внешним сигналам. Метрики говорят «что-то не так», логи и трейсы помогают найти «что именно».

## Метрика как временной ряд

```
http_requests_total{method="GET", status="500", instance="api-1:8080"}  1027  @1764230400
└──── имя ────────┘└─────────────── метки (labels) ───────────────────┘ значение время
```

Каждая уникальная комбинация имени и меток — отдельный **временной ряд**. Метки дают срезы: ошибки по сервису, по эндпоинту, по поду.

**Кардинальность** — число рядов. Метка с неограниченными значениями (`user_id`, `request_id`, полный URL с параметрами) создаёт миллионы рядов и роняет систему мониторинга. Такие данные — в логи и трейсы, а не в метки.

## Pull и push

| | Pull | Push |
| --- | --- | --- |
| Как | Сервер мониторинга сам опрашивает цели по HTTP | Агент или приложение отправляет данные на сервер |
| Примеры | **Prometheus** | Graphite, InfluxDB/Telegraf, Zabbix-агент (активный режим), OTLP |
| Плюсы | Сразу видно, что цель недоступна (`up == 0`); централизованный контроль частоты | Работает за NAT/файрволом, подходит для коротких задач |
| Минусы | Сервер должен дотягиваться до целей | Тишину сложно отличить от «умер» |

Для коротких задач (cron, батчи), которые завершаются раньше, чем их опросят, у Prometheus есть **Pushgateway**.

## White-box и black-box

- **White-box** — метрики изнутри: приложение само отдаёт счётчики запросов, ошибок, размер пула.
- **Black-box** — проверка снаружи, как пользователь: открывается ли сайт, отвечает ли порт, не истекает ли TLS-сертификат (blackbox_exporter, внешние uptime-чекеры).

Нужны оба: black-box ловит то, что видят пользователи, white-box объясняет причину.

## Четыре золотых сигнала (Google SRE)

Если можно измерять только четыре вещи у пользовательского сервиса — эти:

1. **Latency** — задержка ответа. Считать успешные и ошибочные запросы отдельно (быстрая ошибка 500 «улучшает» среднюю задержку). Смотреть перцентили (p95, p99), а не среднее.
2. **Traffic** — нагрузка: запросы в секунду, сообщения, сессии.
3. **Errors** — доля неуспешных запросов: 5xx, таймауты, неверные ответы.
4. **Saturation** — насколько ресурс «заполнен»: очередь, загрузка CPU, память, пул соединений; часто — ранний признак будущих проблем.

## USE — для ресурсов (Brendan Gregg)

Для **каждого ресурса** (CPU, память, диск, сеть, пул соединений) проверить:

- **Utilization** — какой % времени ресурс занят (CPU 85%);
- **Saturation** — сколько работы ждёт в очереди (load average > ядер, swap, очередь диска `iowait`);
- **Errors** — ошибки (ошибки диска, сетевые drops/errors, OOM).

## RED — для сервисов (Tom Wilkie)

Для **каждого сервиса**:

- **Rate** — запросов в секунду;
- **Errors** — ошибок в секунду (или доля);
- **Duration** — распределение длительности (p50, p95, p99).

Правило: **USE — про здоровье машин, RED — про счастье пользователей**. RED + Saturation ≈ четыре золотых сигнала.

## Симптомы и причины, хорошие алерты

- Алертить по **симптомам** («ошибок 5xx > 2% 5 минут», «p99 > 1 с»), а не по каждой причине («CPU 90%» — может, это нормально). Исключение — то, что предсказуемо приведёт к аварии: диск заполнится через 4 часа, сертификат истекает через 7 дней.
- Каждый алерт, который будит человека, должен требовать **действия** и иметь **runbook**. Шумные алерты приучают их игнорировать.
- Важно (будит ночью) → `critical`; можно утром → `warning`; информация → дашборд, не алерт.

## SLI, SLO, SLA

- **SLI** (индикатор) — измеряемая величина: доля успешных запросов, доля запросов быстрее 300 мс.
- **SLO** (цель) — желаемое значение SLI: 99.9% успешных за 30 дней.
- **SLA** (соглашение) — обещание клиенту с последствиями (компенсация), обычно мягче SLO.
- **Error budget** — допустимая «ненадёжность»: 99.9% за 30 дней = ~43 минуты простоя. Бюджет кончился — меньше рискованных релизов.

## Практика

- [ ] Для своего проекта (веб-приложение + база + сервер) выписать метрики по четырём золотым сигналам
- [ ] Составить чек-лист USE для своего сервера: какой командой Linux смотреть utilization, saturation и errors для CPU, памяти, диска и сети
- [ ] Выписать RED-метрики для своего API и подумать, какие метки нужны (method, route, status) и каких меток нельзя добавлять
- [ ] Сформулировать SLI и SLO для своего сервиса и посчитать error budget в минутах за месяц
- [ ] Придумать пять алертов: какие из них по симптомам, какие по причинам, что из этого должно будить ночью
- [ ] Настроить внешний uptime-чек своего сайта (любой бесплатный сервис или blackbox_exporter)

## Тест

### Чем метрики отличаются от логов?
- [x] Метрики — числовые значения во времени, дешёвые в хранении и удобные для агрегации и алертов
- [x] Логи — записи о конкретных событиях с подробностями, нужны для разбора причин
- [ ] Логи заменяют метрики полностью
- [ ] Метрики хранят текст ошибок
> Трейсы дополняют их, показывая путь одного запроса через сервисы.

### Что такое временной ряд в Prometheus?
- [ ] Таблица в базе
- [x] Последовательность значений во времени для уникального сочетания имени метрики и меток
- [ ] Файл лога
- [ ] Дашборд Grafana
> Изменение значения любой метки даёт новый ряд.

### Почему нельзя добавлять в метки user_id или request_id?
- [ ] Prometheus не поддерживает числа в метках
- [x] Это создаёт огромную кардинальность — миллионы временных рядов, которые съедают память и ломают систему мониторинга
- [ ] Это нарушает GDPR
- [ ] Метки должны быть только на английском
> Такие идентификаторы — в логи и трейсы.

### Какие четыре золотых сигнала мониторинга описаны в книге Google SRE?
- [x] Latency
- [x] Traffic
- [x] Errors
- [x] Saturation
- [ ] Uptime
> Если можно измерять только четыре метрики пользовательского сервиса — эти.

### Что означает метод USE?
- [ ] Users, Sessions, Errors
- [x] Utilization, Saturation, Errors — для каждого ресурса: CPU, память, диск, сеть
- [ ] Uptime, Speed, Efficiency
- [ ] Update, Scale, Evaluate
> Метод Брендана Грегга для анализа ресурсов.

### Что означает метод RED и для чего он?
- [x] Rate, Errors, Duration — метрики для каждого сервиса, обрабатывающего запросы
- [ ] Ресурсы, Ёмкость, Диски
- [ ] Метод для анализа логов
- [ ] Метод только для баз данных
> USE — про машины, RED — про пользователей сервиса.

### Чем pull-модель отличается от push?
- [x] При pull сервер мониторинга сам периодически опрашивает цели — так работает Prometheus
- [x] При push агенты или приложения сами отправляют данные на сервер
- [ ] Pull работает только в облаке
- [ ] Push не поддерживает метрики
> Для коротких задач у Prometheus есть Pushgateway.

### Почему для задержки смотрят перцентили, а не среднее?
- [ ] Среднее нельзя посчитать
- [x] Среднее скрывает «хвост»: при средней 100 мс часть пользователей может ждать секунды; p95 и p99 показывают худший опыт
- [ ] Перцентили занимают меньше места
- [ ] Так требует Grafana
> p99 = 99% запросов быстрее этого значения.

### Что такое black-box мониторинг?
- [ ] Метрики, которые приложение отдаёт изнутри
- [x] Проверка системы снаружи, как её видит пользователь: доступность сайта, порта, срок сертификата
- [ ] Мониторинг закрытого кода
- [ ] Шифрование метрик
> Пример — blackbox_exporter или внешний uptime-чекер.

### Какой алерт лучше будить дежурного ночью?
- [ ] CPU на одном сервере 85%
- [x] Доля ошибок 5xx у API больше 2% уже 5 минут
- [ ] Свободной памяти 30%
- [ ] Новый релиз выкачен
> Алертить нужно по симптомам, которые видят пользователи и которые требуют действий.

### Как соотносятся SLI, SLO и SLA?
- [x] SLI — измеряемый показатель, например доля успешных запросов
- [x] SLO — целевое значение SLI, например 99.9% за 30 дней
- [x] SLA — договорное обещание клиенту с последствиями при нарушении
- [ ] Это синонимы
> Error budget — допустимая доля сбоев в рамках SLO.

### Сколько примерно минут простоя в месяц (30 дней) допускает SLO 99.9%?
- [ ] 4 минуты
- [x] Около 43 минут
- [ ] 7 часов
- [ ] 3 дня
> 30 дней × 24 ч × 60 мин × 0.001 ≈ 43 минуты.
