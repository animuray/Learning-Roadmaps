# Практика — мониторинг своего проекта

Цель: по одному взгляду на дашборд понимать, всё ли хорошо с вашим проектом, и узнавать о проблемах из Telegram раньше пользователей. Всё описано как код и лежит в Git.

## Что должно получиться

```
monitoring/
├── docker-compose.yml
├── prometheus/
│   ├── prometheus.yml
│   └── rules/
│       ├── node.yml

├── alertmanager/
│   └── alertmanager.yml
├── blackbox/
│   └── blackbox.yml

    │   ├── datasources/prometheus.yml
    │   └── dashboards/default.yml
    └── dashboards/
        ├── overview.json

```

## Шаг 1 — стек в Compose

```yaml

      - ./prometheus:/etc/prometheus:ro
```

> [!note] Версии образов
> Закрепляйте версии тегами (как выше) и обновляйте осознанно, сверяясь с актуальными релизами на GitHub и Docker Hub. `latest` в мониторинге — путь к внезапно сломанным дашбордам.

Порты Prometheus и Alertmanager слушают только `127.0.0.1` — смотреть их через SSH-туннель или за reverse proxy с авторизацией. Grafana — за Nginx с HTTPS. Файлы с секретами (`*.env`, `grafana_admin.txt`, токен бота) — в `.gitignore`.

## Шаг 2 — что опрашивать

| Слой | Источник | Ключевые метрики |
| --- | --- | --- |
| Сервер | node_exporter | CPU, память, диск, сеть, load (USE) |
| Контейнеры | cAdvisor | CPU и память каждого контейнера, рестарты |
| База | postgres_exporter (роль pg_monitor) | `pg_up`, соединения, размер, блокировки, репликация |
| Приложение | `/metrics` через клиентскую библиотеку | RED: запросы, ошибки, гистограмма задержки |
| Снаружи | blackbox_exporter | доступность сайта, код ответа, срок сертификата |
| Сам мониторинг | Prometheus, Alertmanager, Grafana | `up`, ошибки отправки уведомлений |

## Шаг 3 — дашборд «Обзор»

Один главный дашборд, на который смотрят первым:

1. **Ряд «Пользователи» (RED / золотые сигналы)**: RPS, доля 5xx, p50/p95/p99 задержки, доступность снаружи (`probe_success`), дней до истечения сертификата.
2. **Ряд «Ресурсы» (USE)**: CPU, память, диск (% и прогноз), сеть, load average.
3. **Ряд «База»**: соединения против `max_connections`, транзакции в секунду, размер базы, долгие запросы.
4. **Ряд «Контейнеры»**: CPU и память по контейнерам, перезапуски.

Переменные: `instance`, `job`. Единицы и пороги — на каждой панели. Аннотации деплоев из CI. Подробные дашборды (Node Exporter Full и т. п.) — отдельно, для расследований.

## Шаг 4 — алерты

Минимальный набор:

- `InstanceDown` — любая цель `up == 0` 2 минуты (critical);
- `SiteDown` — `probe_success == 0` 2 минуты (critical);
- `HighErrorRate` — доля 5xx > 2% 5 минут (critical);
- `HighLatency` — p95 выше целевого 10 минут (warning);
- `DiskWillFill` — `predict_linear` на 4 часа (warning), меньше 5% (critical);
- `HighMemory` — MemAvailable < 10% 10 минут (warning);
- `PostgresDown`, `PostgresTooManyConnections` — `pg_up == 0`, соединений > 80% от максимума;
- `CertExpiresSoon` — меньше 14 дней (warning);
- `BackupTooOld` — последний бэкап старше 26 часов (critical);
- `Watchdog` — всегда горит, для проверки самого мониторинга.

У каждого critical — runbook. Уведомления: critical — в чат дежурного, warning — в общий канал.

## Шаг 5 — проверка, что всё работает

Мониторинг, который не проверяли, может молчать в самый неподходящий момент. Устройте «учения»:

1. Остановить приложение → пришёл `SiteDown`/`InstanceDown`, на дашборде видно падение.
2. Нагрузить API (`hey`, `ab`, `k6`) с частью запросов на несуществующий маршрут, который отдаёт 500 → пришёл `HighErrorRate`.
3. Заполнить диск большим файлом (`fallocate -l`) на тестовой ВМ → пришёл `DiskWillFill`.
4. Остановить postgres → `PostgresDown`, а у приложения выросли ошибки.
5. Остановить Alertmanager → как вы об этом узнаете? (внешний dead man's switch).
6. Создать silence на «плановые работы» и убедиться, что уведомлений нет.

Запишите, сколько времени прошло от поломки до уведомления.

## Лаборатория

Prometheus — служба `prometheus` (`http://localhost:9090`), конфиг `/etc/prometheus/prometheus.yml`, применяется через `curl -X POST localhost:9090/-/reload`. Учебное приложение shop-app — служба `lab-shop-exporter`, метрики на `127.0.0.1:8099/metrics` (`http_requests_total{path, status}`).

```bash lib
# Prometheus 2.45 из пакетов Ubuntu: служба prometheus (порт 9090), node-exporter (9100), alertmanager (9093).
# Учебное приложение shop-app отдаёт метрики на 127.0.0.1:8099/metrics: счётчики растут с постоянной скоростью.
lab_shop_exporter() {
  [ "$(systemctl is-active lab-shop-exporter 2>/dev/null)" = active ] && return
  mkdir -p /opt/lab
  cat > /opt/lab/shop-exporter.py <<'EOF'
import math, time
from http.server import BaseHTTPRequestHandler, HTTPServer
START = time.time()
RATES = {('/api', '200'): 10, ('/api', '500'): 1, ('/login', '200'): 2, ('/login', '404'): 0.5}
BUCKETS = [('0.1', 5), ('0.25', 8), ('0.5', 10), ('1', 11.5), ('+Inf', 13.5)]
class H(BaseHTTPRequestHandler):
    def do_GET(self):
        t = time.time() - START
        out = ['# HELP http_requests_total Requests by path and status', '# TYPE http_requests_total counter']
        for (p, s), r in RATES.items():
            out.append(f'http_requests_total{{path="{p}",status="{s}"}} {r * t:.3f}')
        out += ['# HELP request_duration_seconds Request latency', '# TYPE request_duration_seconds histogram']
        for le, r in BUCKETS:
            out.append(f'request_duration_seconds_bucket{{le="{le}"}} {r * t:.3f}')
        out += [f'request_duration_seconds_sum {3 * t:.3f}', f'request_duration_seconds_count {13.5 * t:.3f}',
                '# HELP queue_size Orders waiting in queue', '# TYPE queue_size gauge', f'queue_size {int(50 + 40 * math.sin(t / 60))}']
        body = ("\n".join(out) + "\n").encode()
        self.send_response(200); self.send_header("Content-Type", "text/plain; version=0.0.4"); self.end_headers(); self.wfile.write(body)
    def log_message(self, *a): pass
HTTPServer(("127.0.0.1", 8099), H).serve_forever()
EOF
  systemctl reset-failed lab-shop-exporter 2>/dev/null
  systemd-run -q --unit=lab-shop-exporter python3 /opt/lab/shop-exporter.py
}
# lab_prom_base [с_shop] — исходный prometheus.yml (prometheus + node; с аргументом — и shop-app), правила из /etc/prometheus/rules
lab_prom_base() {
  pkill -u student -f 'ssh .*-L *([^ ]*:)?9090:' 2>/dev/null
  mkdir -p /etc/prometheus/rules
  cat > /etc/prometheus/prometheus.yml <<'EOF'
global:
  scrape_interval: 15s
  evaluation_interval: 15s

alerting:
  alertmanagers:
    - static_configs:
        - targets: ['localhost:9093']

rule_files: []

scrape_configs:
  - job_name: prometheus
    scrape_interval: 5s
    static_configs:
      - targets: ['localhost:9090']
  - job_name: node
    static_configs:
      - targets: ['localhost:9100']
EOF
  if [ -n "$1" ]; then
    printf '  - job_name: shop-app\n    scrape_interval: 5s\n    static_configs:\n      - targets: ["127.0.0.1:8099"]\n' >> /etc/prometheus/prometheus.yml
    sed -i 's#^rule_files: \[\]#rule_files:\n  - /etc/prometheus/rules/*.yml#' /etc/prometheus/prometheus.yml
  fi
  chown root:root /etc/prometheus/prometheus.yml; chmod 644 /etc/prometheus/prometheus.yml
  sed -i 's/^ARGS=.*/ARGS="--web.enable-lifecycle"/' /etc/default/prometheus
  systemctl enable -q prometheus prometheus-node-exporter 2>/dev/null
  systemctl restart prometheus-node-exporter prometheus
  for i in $(seq 40); do curl -s localhost:9090/-/ready | grep -qi ready && break; sleep 0.25; done
}
# lab_promq 'запрос' [время] — значение запроса через HTTP API (JSON)
lab_promq() { curl -s --get localhost:9090/api/v1/query --data-urlencode "query=$1" ${2:+--data-urlencode "time=$2"}; }
# lab_promcmp файл_с_запросом 'эталонный запрос' — сравнить результаты в один момент времени
lab_promcmp() {
  python3 - "$1" "$2" <<'EOF'
import json, sys, time, urllib.parse, urllib.request
path, ref = sys.argv[1], sys.argv[2]
try:
    q = open(path).read().strip()
except OSError:
    print(f"✗ Нет файла {path}"); sys.exit(1)
if not q:
    print(f"✗ Файл {path} пуст"); sys.exit(1)
t = time.time()
def run(query):
    u = "http://localhost:9090/api/v1/query?" + urllib.parse.urlencode({"query": query, "time": t})
    try:
        d = json.load(urllib.request.urlopen(u, timeout=10))
    except urllib.error.HTTPError as e:
        d = json.load(e)
    if d.get("status") != "success":
        return None, d.get("error", "ошибка")
    res = d["data"]["result"]
    if d["data"]["resultType"] == "scalar":
        return {(): float(res[1])}, None
    return {tuple(sorted((k, v) for k, v in r["metric"].items() if k != "__name__")): float(r["value"][1]) for r in res}, None
got, err = run(q)
if got is None:
    print(f"✗ Prometheus не может выполнить запрос: {err}"); sys.exit(1)
want, _ = run(ref)
if not want:
    print("✗ Данных ещё мало — подождите полминуты и проверьте снова"); sys.exit(1)
if set(got) != set(want):
    print(f"✗ Запрос возвращает не тот набор рядов: {len(got)} шт. с метками {sorted(dict(k) for k in got)[:3]}"); sys.exit(1)
for k, v in want.items():
    if abs(got[k] - v) > max(abs(v) * 0.03, 1e-6):
        print(f"✗ Значение {got[k]:.4g} для {dict(k) or 'результата'} неверное"); sys.exit(1)
print("✓ " + "; ".join(f"{dict(k) or 'итог'}: {v:.4g}" for k, v in sorted(got.items())))
EOF
}
lab_prom_wait() { for i in $(seq ${1:-20}); do curl -s localhost:9090/-/ready 2>/dev/null | grep -qi ready && return 0; sleep 0.5; done; return 1; }
lab_promn() { lab_promq "$1" | jq -r 'if .status == "success" then (.data.result | length) else -1 end' 2>/dev/null; }
# lab_alert имя — правило алерта из /api/v1/rules (JSON) или пусто
lab_alert() { curl -s localhost:9090/api/v1/rules | jq -c --arg n "$1" '[.data.groups[].rules[] | select(.type == "alerting" and .name == $n)][0] // empty'; }
```

### Мониторинг shop-app

Подключите shop-app к мониторингу так, как это делают для своего проекта:

1. Prometheus собирает метрики приложения задачей **`shop-app`**.
2. Правила алертов — в файле **`/etc/prometheus/rules/app.yml`**, и Prometheus их загружает:
   - **`ShopAppDown`** — приложение недоступно для сбора метрик дольше **1 минуты**; важность `critical`; у алерта есть аннотация `summary`;
   - **`ShopHighErrorRate`** — доля ответов **5xx** от всех запросов за 5 минут выше **5%**; важность `warning`.

Проверка остановит приложение на несколько секунд и посмотрит, что выражение `ShopAppDown` это видит.

```bash setup
lab_shop_exporter
lab_prom_base
rm -f /etc/prometheus/rules/*
curl -s -X POST localhost:9090/-/reload >/dev/null
```

```bash check
[ "$(systemctl is-active prometheus)" = active ] && lab_prom_wait || fail "Prometheus не работает"
lab_shop_exporter
for i in $(seq 20); do [ "$(lab_promn 'up{job="shop-app"} == 1')" = 1 ] && break; sleep 0.5; done
[ "$(lab_promn 'up{job="shop-app"}')" -ge 1 ] 2>/dev/null || fail "В Prometheus нет цели задачи shop-app"
[ "$(lab_promn 'up{job="shop-app"} == 1')" = 1 ] || fail "Цель shop-app недоступна"
[ -f /etc/prometheus/rules/app.yml ] || fail "Нет файла /etc/prometheus/rules/app.yml"
promtool check rules /etc/prometheus/rules/app.yml >/dev/null 2>&1 || fail "Файл правил с ошибками: $(promtool check rules /etc/prometheus/rules/app.yml 2>&1 | grep -iE 'err|fail' | head -1)"
d=$(lab_alert ShopAppDown); [ -n "$d" ] || fail "Алерт ShopAppDown не загружен в Prometheus"
e=$(lab_alert ShopHighErrorRate); [ -n "$e" ] || fail "Алерт ShopHighErrorRate не загружен в Prometheus"
[ "$(echo "$d" | jq -r .labels.severity)" = critical ] || fail "У ShopAppDown важность не critical"
[ "$(echo "$e" | jq -r .labels.severity)" = warning ] || fail "У ShopHighErrorRate важность не warning"
[ -n "$(echo "$d" | jq -r '.annotations.summary // empty')" ] || fail "У ShopAppDown нет аннотации summary"
[ "$(echo "$d" | jq -r '.duration')" -ge 60 ] 2>/dev/null || fail "ShopAppDown сработает раньше чем через минуту недоступности"
[ "$(echo "$d" | jq -r '.duration')" -le 300 ] 2>/dev/null || fail "ShopAppDown ждёт дольше 5 минут — о падении узнают слишком поздно"
qd=$(echo "$d" | jq -r .query); qe=$(echo "$e" | jq -r .query)
echo "$qe" | grep -q '\[5m\]' || fail "ShopHighErrorRate считает долю ошибок не за 5 минут"
[ "$(lab_promn "$qe")" -ge 1 ] 2>/dev/null || fail "Выражение ShopHighErrorRate сейчас ничего не возвращает, а 5xx у shop-app около 7%"
[ "$(lab_promn "$qd")" = 0 ] || fail "Выражение ShopAppDown что-то возвращает, хотя shop-app работает"
systemctl stop lab-shop-exporter
for i in $(seq 30); do [ "$(lab_promn 'up{job="shop-app"} == 0')" = 1 ] && break; sleep 0.5; done
n=$(lab_promn "$qd")
lab_shop_exporter
[ "${n:-0}" -ge 1 ] 2>/dev/null || fail "shop-app остановили, а выражение ShopAppDown ничего не вернуло"
ok "shop-app собирается, ShopAppDown видит падение, ShopHighErrorRate видит 5xx"
```

```text hint
1. В основной конфиг добавить задачу сбора с адресом приложения и указать, откуда читать файлы правил; проверить конфиг утилитой и применить без перезапуска.
2. Алерт недоступности строится на служебной метрике, которую Prometheus сам пишет для каждой цели: единица — собрал, ноль — не смог. Время ожидания перед срабатыванием задаётся отдельным полем.
3. Доля ошибок — скорость роста счётчика по ответам 5xx, делённая на скорость роста по всем ответам, обе части агрегированы одинаково; сравнить с порогом. Проверить файл правил утилитой и выполнить выражения вручную.
```

```bash solution
sudo tee -a /etc/prometheus/prometheus.yml >/dev/null <<'EOF'
  - job_name: shop-app
    scrape_interval: 5s
    static_configs:
      - targets: ['127.0.0.1:8099']
EOF
sudo sed -i 's#^rule_files: \[\]#rule_files:\n  - /etc/prometheus/rules/*.yml#' /etc/prometheus/prometheus.yml
sudo tee /etc/prometheus/rules/app.yml >/dev/null <<'EOF'
groups:
  - name: shop-app
    rules:
      - alert: ShopAppDown
        expr: up{job="shop-app"} == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "shop-app недоступен ({{ $labels.instance }})"
          description: "Prometheus не может собрать метрики дольше минуты."

      - alert: ShopHighErrorRate
        expr: |
          sum(rate(http_requests_total{job="shop-app", status=~"5.."}[5m]))
            / sum(rate(http_requests_total{job="shop-app"}[5m])) > 0.05
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Доля 5xx у shop-app {{ $value | humanizePercentage }}"
EOF
promtool check config /etc/prometheus/prometheus.yml
curl -s -X POST localhost:9090/-/reload
sleep 12
curl -s localhost:9090/api/v1/rules | jq -r '.data.groups[].rules[] | "\(.name) \(.health) \(.state)"'
```

```text review
Эталон — в «Решении»: задача сбора shop-app, `rule_files` с маской каталога правил, два алерта.

- `up{job="..."} == 0` — базовый алерт для **каждой** задачи сбора. Если приложение пропадёт из service discovery совсем, `up` пропадёт тоже — на этот случай `absent(up{job="shop-app"})`.
- `for: 1m` отсекает единичный неудачный сбор (сеть, долгий ответ); слишком большой `for` — узнаете о падении от пользователей.
- Доля ошибок: `sum(rate(5xx)) / sum(rate(всех))`. `{{ $value | humanizePercentage }}` в аннотации показывает значение в процентах прямо в уведомлении.
- Важность определяет маршрут в Alertmanager: `critical` — дежурному сразу, `warning` — в рабочий чат. У каждого `critical` должна быть аннотация `runbook_url` с инструкцией.
- Конфиг и правила — как код: в Git, с `promtool check config` и `promtool check rules` (а лучше `promtool test rules`) в CI.
```
