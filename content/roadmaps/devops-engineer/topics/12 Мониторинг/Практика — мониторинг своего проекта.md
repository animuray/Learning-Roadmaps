# Практика — мониторинг своего проекта

Цель: по одному взгляду на дашборд понимать, всё ли хорошо с вашим проектом, и узнавать о проблемах из Telegram раньше пользователей. Всё описано как код и лежит в Git.

## Что должно получиться

```
monitoring/
├── docker-compose.yml
├── prometheus/
│   ├── prometheus.yml
│   └── rules/
│       ├── node.yml
│       ├── app.yml
│       └── postgres.yml
├── alertmanager/
│   └── alertmanager.yml
├── blackbox/
│   └── blackbox.yml
└── grafana/
    ├── provisioning/
    │   ├── datasources/prometheus.yml
    │   └── dashboards/default.yml
    └── dashboards/
        ├── overview.json
        └── node.json
```

## Шаг 1 — стек в Compose

```yaml
services:
  prometheus:
    image: prom/prometheus:v3.5.0
    command:
      - --config.file=/etc/prometheus/prometheus.yml
      - --storage.tsdb.retention.time=30d
      - --web.enable-lifecycle
    volumes:
      - ./prometheus:/etc/prometheus:ro
      - prometheus-data:/prometheus
    ports:
      - "127.0.0.1:9090:9090"
    restart: unless-stopped

  alertmanager:
    image: prom/alertmanager:v0.28.1
    volumes:
      - ./alertmanager:/etc/alertmanager:ro
    ports:
      - "127.0.0.1:9093:9093"
    restart: unless-stopped

  grafana:
    image: grafana/grafana-oss:12.2.0
    environment:
      GF_SECURITY_ADMIN_PASSWORD__FILE: /run/secrets/grafana_admin
    volumes:
      - ./grafana/provisioning:/etc/grafana/provisioning:ro
      - ./grafana/dashboards:/var/lib/grafana/dashboards:ro
      - grafana-data:/var/lib/grafana
    secrets:
      - grafana_admin
    ports:
      - "3000:3000"
    restart: unless-stopped

  node-exporter:
    image: prom/node-exporter:v1.10.2
    command: ["--path.rootfs=/host", "--collector.systemd", "--collector.processes"]
    network_mode: host
    pid: host
    volumes:
      - /:/host:ro,rslave
    restart: unless-stopped

  cadvisor:
    image: gcr.io/cadvisor/cadvisor:v0.52.1
    volumes:
      - /:/rootfs:ro
      - /var/run:/var/run:ro
      - /sys:/sys:ro
      - /var/lib/docker:/var/lib/docker:ro
    restart: unless-stopped

  postgres-exporter:
    image: quay.io/prometheuscommunity/postgres-exporter
    env_file: ./postgres-exporter.env
    restart: unless-stopped

  blackbox:
    image: prom/blackbox-exporter
    volumes:
      - ./blackbox:/config:ro
    command: ["--config.file=/config/blackbox.yml"]
    restart: unless-stopped

volumes:
  prometheus-data:
  grafana-data:

secrets:
  grafana_admin:
    file: ./grafana_admin.txt
```

> [!note] Версии образов
> Закрепляйте версии тегами (как выше) и обновляйте осознанно, сверяясь с актуальными релизами на GitHub и Docker Hub. `latest` в мониторинге — путь к внезапно сломанным дашбордам.

Порты Prometheus и Alertmanager слушают только `127.0.0.1` — смотреть их через SSH-туннель или за reverse proxy с авторизацией. Grafana — за Nginx с HTTPS. Файлы с секретами (`*.env`, `grafana_admin.txt`, токен бота) — в `.gitignore`.

## Шаг 2 — что опрашивать

| Слой | Источник | Ключевые метрики |
| --- | --- | --- |
| Сервер | node_exporter | CPU, память, диск, сеть, load (USE) |
| Контейнеры | cAdvisor | CPU и память каждого контейнера, рестарты |
| База | postgres_exporter (роль pg_monitor) | `pg_up`, соединения, размер, блокировки, репликация |
| Приложение | `/metrics` через клиентскую библиотеку | RED: запросы, ошибки, гистограмма задержки |
| Снаружи | blackbox_exporter | доступность сайта, код ответа, срок сертификата |
| Сам мониторинг | Prometheus, Alertmanager, Grafana | `up`, ошибки отправки уведомлений |

## Шаг 3 — дашборд «Обзор»

Один главный дашборд, на который смотрят первым:

1. **Ряд «Пользователи» (RED / золотые сигналы)**: RPS, доля 5xx, p50/p95/p99 задержки, доступность снаружи (`probe_success`), дней до истечения сертификата.
2. **Ряд «Ресурсы» (USE)**: CPU, память, диск (% и прогноз), сеть, load average.
3. **Ряд «База»**: соединения против `max_connections`, транзакции в секунду, размер базы, долгие запросы.
4. **Ряд «Контейнеры»**: CPU и память по контейнерам, перезапуски.

Переменные: `instance`, `job`. Единицы и пороги — на каждой панели. Аннотации деплоев из CI. Подробные дашборды (Node Exporter Full и т. п.) — отдельно, для расследований.

## Шаг 4 — алерты

Минимальный набор:

- `InstanceDown` — любая цель `up == 0` 2 минуты (critical);
- `SiteDown` — `probe_success == 0` 2 минуты (critical);
- `HighErrorRate` — доля 5xx > 2% 5 минут (critical);
- `HighLatency` — p95 выше целевого 10 минут (warning);
- `DiskWillFill` — `predict_linear` на 4 часа (warning), меньше 5% (critical);
- `HighMemory` — MemAvailable < 10% 10 минут (warning);
- `PostgresDown`, `PostgresTooManyConnections` — `pg_up == 0`, соединений > 80% от максимума;
- `CertExpiresSoon` — меньше 14 дней (warning);
- `BackupTooOld` — последний бэкап старше 26 часов (critical);
- `Watchdog` — всегда горит, для проверки самого мониторинга.

У каждого critical — runbook. Уведомления: critical — в чат дежурного, warning — в общий канал.

## Шаг 5 — проверка, что всё работает

Мониторинг, который не проверяли, может молчать в самый неподходящий момент. Устройте «учения»:

1. Остановить приложение → пришёл `SiteDown`/`InstanceDown`, на дашборде видно падение.
2. Нагрузить API (`hey`, `ab`, `k6`) с частью запросов на несуществующий маршрут, который отдаёт 500 → пришёл `HighErrorRate`.
3. Заполнить диск большим файлом (`fallocate -l`) на тестовой ВМ → пришёл `DiskWillFill`.
4. Остановить postgres → `PostgresDown`, а у приложения выросли ошибки.
5. Остановить Alertmanager → как вы об этом узнаете? (внешний dead man's switch).
6. Создать silence на «плановые работы» и убедиться, что уведомлений нет.

Запишите, сколько времени прошло от поломки до уведомления.

## Вариант для Kubernetes

Установить `kube-prometheus-stack` через Helm (тема Helm), описать опрос приложения ресурсом `ServiceMonitor`, правила — `PrometheusRule`, дашборды — ConfigMap с меткой для sidecar Grafana, получателей Alertmanager — через values и Secret.

### Какие метрики должны быть в первом ряду главного дашборда?
- [ ] Версии всех пакетов
- [x] То, что видят пользователи: запросы в секунду, доля ошибок, задержка, доступность снаружи
- [ ] Температура процессора
- [ ] Список всех процессов
> Ресурсы (USE) — следующий уровень, они объясняют причину.

### Почему порты Prometheus и Alertmanager лучше публиковать только на 127.0.0.1?
- [ ] Иначе они не запустятся
- [x] У них нет встроенной полноценной авторизации, а данные и управление (silences, reload) не должны быть доступны из интернета
- [ ] Так быстрее
- [ ] Grafana не сможет подключиться иначе
> Доступ — через SSH-туннель или reverse proxy с авторизацией.

### Почему в стеке мониторинга нужно закреплять версии образов, а не использовать latest?
- [ ] latest не существует
- [x] Новая мажорная версия может прийти неожиданно и сломать конфигурацию, дашборды или алерты в момент, когда никто этого не ждёт
- [ ] Закреплённые версии быстрее скачиваются
- [ ] Так требует Docker Compose
> Обновляйте осознанно, читая release notes.

### Как убедиться, что алерты действительно работают?
- [ ] Достаточно, что promtool не показал ошибок
- [x] Провести учения: намеренно сломать приложение, базу или диск на тестовом стенде и проверить, что уведомление пришло вовремя
- [ ] Посмотреть на дашборд
- [ ] Подождать реальной аварии
> Засеките время от поломки до уведомления.

### Как узнать, что сломался сам Alertmanager?
- [ ] Он пришлёт уведомление о себе
- [x] Через внешний dead man's switch: постоянно горящий алерт Watchdog перестаёт приходить во внешний сервис, и тот поднимает тревогу
- [ ] Никак
- [ ] Через Grafana автоматически
> Мониторинг мониторинга — обязательная часть.

### Где хранить конфигурацию стека мониторинга?
- [ ] Только в интерфейсе Grafana
- [x] В Git: prometheus.yml, правила, alertmanager.yml, provisioning и JSON дашбордов
- [ ] На рабочем ноутбуке
- [ ] В переменных окружения
> Секреты — вне Git, через .env, secrets или хранилище секретов.

### Как алертить о том, что бэкап базы давно не выполнялся?
- [ ] Это невозможно в Prometheus
- [x] Скрипт бэкапа отдаёт время последнего успеха (например, через textfile collector), а правило сравнивает его с текущим временем
- [ ] Смотреть размер диска
- [ ] Проверять логи вручную каждое утро
> Например, time() - backup_last_success_timestamp_seconds > 26 часов.

### Какие ресурсы Prometheus Operator используют в Kubernetes вместо ручной правки prometheus.yml?
- [x] ServiceMonitor или PodMonitor — что опрашивать
- [x] PrometheusRule — правила алертов и recording rules
- [ ] Ingress
- [ ] CronJob
> Их ставит kube-prometheus-stack.

### Что из перечисленного — хороший критичный алерт для проекта?
- [x] Сайт недоступен снаружи 2 минуты
- [x] Доля ошибок 5xx больше 2% в течение 5 минут
- [ ] Загрузка CPU 60%
- [ ] Новый пользователь зарегистрировался
> Critical — то, что затрагивает пользователей и требует немедленных действий.

### Зачем держать отдельно главный обзорный дашборд и подробные дашборды?
- [ ] Grafana не позволяет много панелей
- [x] Обзорный за секунды отвечает «всё ли хорошо», а подробные нужны для расследования конкретного слоя
- [ ] Подробные дашборды не нужны
- [ ] Так меньше нагрузка на диск
> Перегруженный дашборд никто не читает.
