# Сломанный сервер — мониторинг

Самая опасная поломка мониторинга — тихая: дашборды пустые, алерты молчат, и все думают, что всё хорошо. Поэтому мониторинг проверяют так же, как приложение: после каждой правки — что конфиг принят, цели собираются, правила загружены и выражения что-то возвращают.

## Алгоритм «мониторинг не работает»

1. **Prometheus жив?** `systemctl status prometheus`, `journalctl -u prometheus -n 20`. Конфиг проверяется **до** перезапуска: `promtool check config /etc/prometheus/prometheus.yml`.
2. **Цели:** Status → Targets (или `curl -s localhost:9090/api/v1/targets`). Колонка Error объясняет: `connection refused` (не тот порт/хост), `404` (не тот `metrics_path`), `context deadline exceeded` (тайм-аут).
3. **Метрика есть?** Запрос `up{job="..."}`, затем сама метрика. Нет рядов — проверьте имя: `count by (__name__) ({job="shop-app"})`.
4. **Правила:** Status → Rules (или `/api/v1/rules`) — загружен ли файл, `health`, `lastError`. Проверка файла — `promtool check rules файл.yml`.
5. **Алерт молчит?** Выполните его `expr` вручную в Graph. Пусто — ошибка в выражении (часто опечатка в имени метрики: Prometheus не ругается на несуществующие метрики). Есть результат — смотрите `for` и Alertmanager.
6. Применение без перезапуска: `curl -X POST localhost:9090/-/reload` (нужен `--web.enable-lifecycle`) или `systemctl reload prometheus`.

## Частые поломки

| Симптом | Причина |
| --- | --- |
| Prometheus не стартует | ошибка YAML, длительность без единицы (`5` вместо `5s`), неверный ключ |
| Цель `DOWN`, connection refused | не тот порт или адрес |
| Цель `DOWN`, 404 | неверный `metrics_path` |
| Правила не появились в Rules | файл не попал под маску `rule_files` (`*.yml` vs `.yaml`), не сделан reload |
| Алерт всегда inactive | опечатка в имени метрики или метке; неверный порог |

## Лаборатория

Prometheus — служба `prometheus` (`http://localhost:9090`), конфиг `/etc/prometheus/prometheus.yml`. Учебное приложение shop-app отдаёт метрики на `127.0.0.1:8099/metrics`.

```bash lib
# Prometheus 2.45 из пакетов Ubuntu: служба prometheus (порт 9090), node-exporter (9100), alertmanager (9093).
# Учебное приложение shop-app отдаёт метрики на 127.0.0.1:8099/metrics: счётчики растут с постоянной скоростью.
lab_shop_exporter() {
  [ "$(systemctl is-active lab-shop-exporter 2>/dev/null)" = active ] && return
  mkdir -p /opt/lab
  cat > /opt/lab/shop-exporter.py <<'EOF'
import math, time
from http.server import BaseHTTPRequestHandler, HTTPServer
START = time.time()
RATES = {('/api', '200'): 10, ('/api', '500'): 1, ('/login', '200'): 2, ('/login', '404'): 0.5}
BUCKETS = [('0.1', 5), ('0.25', 8), ('0.5', 10), ('1', 11.5), ('+Inf', 13.5)]
class H(BaseHTTPRequestHandler):
    def do_GET(self):
        t = time.time() - START
        out = ['# HELP http_requests_total Requests by path and status', '# TYPE http_requests_total counter']
        for (p, s), r in RATES.items():
            out.append(f'http_requests_total{{path="{p}",status="{s}"}} {r * t:.3f}')
        out += ['# HELP request_duration_seconds Request latency', '# TYPE request_duration_seconds histogram']
        for le, r in BUCKETS:
            out.append(f'request_duration_seconds_bucket{{le="{le}"}} {r * t:.3f}')
        out += [f'request_duration_seconds_sum {3 * t:.3f}', f'request_duration_seconds_count {13.5 * t:.3f}',
                '# HELP queue_size Orders waiting in queue', '# TYPE queue_size gauge', f'queue_size {int(50 + 40 * math.sin(t / 60))}']
        body = ("\n".join(out) + "\n").encode()
        self.send_response(200); self.send_header("Content-Type", "text/plain; version=0.0.4"); self.end_headers(); self.wfile.write(body)
    def log_message(self, *a): pass
HTTPServer(("127.0.0.1", 8099), H).serve_forever()
EOF
  systemctl reset-failed lab-shop-exporter 2>/dev/null
  systemd-run -q --unit=lab-shop-exporter python3 /opt/lab/shop-exporter.py
}
# lab_prom_base [с_shop] — исходный prometheus.yml (prometheus + node; с аргументом — и shop-app), правила из /etc/prometheus/rules
lab_prom_base() {
  pkill -u student -f 'ssh .*-L *([^ ]*:)?9090:' 2>/dev/null
  mkdir -p /etc/prometheus/rules
  cat > /etc/prometheus/prometheus.yml <<'EOF'
global:
  scrape_interval: 15s
  evaluation_interval: 15s

alerting:
  alertmanagers:
    - static_configs:
        - targets: ['localhost:9093']

rule_files: []

scrape_configs:
  - job_name: prometheus
    scrape_interval: 5s
    static_configs:
      - targets: ['localhost:9090']
  - job_name: node
    static_configs:
      - targets: ['localhost:9100']
EOF
  if [ -n "$1" ]; then
    printf '  - job_name: shop-app\n    scrape_interval: 5s\n    static_configs:\n      - targets: ["127.0.0.1:8099"]\n' >> /etc/prometheus/prometheus.yml
    sed -i 's#^rule_files: \[\]#rule_files:\n  - /etc/prometheus/rules/*.yml#' /etc/prometheus/prometheus.yml
  fi
  chown root:root /etc/prometheus/prometheus.yml; chmod 644 /etc/prometheus/prometheus.yml
  sed -i 's/^ARGS=.*/ARGS="--web.enable-lifecycle"/' /etc/default/prometheus
  systemctl enable -q prometheus prometheus-node-exporter 2>/dev/null
  systemctl restart prometheus-node-exporter prometheus
  for i in $(seq 40); do curl -s localhost:9090/-/ready | grep -qi ready && break; sleep 0.25; done
}
# lab_promq 'запрос' [время] — значение запроса через HTTP API (JSON)
lab_promq() { curl -s --get localhost:9090/api/v1/query --data-urlencode "query=$1" ${2:+--data-urlencode "time=$2"}; }
# lab_promcmp файл_с_запросом 'эталонный запрос' — сравнить результаты в один момент времени
lab_promcmp() {
  python3 - "$1" "$2" <<'EOF'
import json, sys, time, urllib.parse, urllib.request
path, ref = sys.argv[1], sys.argv[2]
try:
    q = open(path).read().strip()
except OSError:
    print(f"✗ Нет файла {path}"); sys.exit(1)
if not q:
    print(f"✗ Файл {path} пуст"); sys.exit(1)
t = time.time()
def run(query):
    u = "http://localhost:9090/api/v1/query?" + urllib.parse.urlencode({"query": query, "time": t})
    try:
        d = json.load(urllib.request.urlopen(u, timeout=10))
    except urllib.error.HTTPError as e:
        d = json.load(e)
    if d.get("status") != "success":
        return None, d.get("error", "ошибка")
    res = d["data"]["result"]
    if d["data"]["resultType"] == "scalar":
        return {(): float(res[1])}, None
    return {tuple(sorted((k, v) for k, v in r["metric"].items() if k != "__name__")): float(r["value"][1]) for r in res}, None
got, err = run(q)
if got is None:
    print(f"✗ Prometheus не может выполнить запрос: {err}"); sys.exit(1)
want, _ = run(ref)
if not want:
    print("✗ Данных ещё мало — подождите полминуты и проверьте снова"); sys.exit(1)
if set(got) != set(want):
    print(f"✗ Запрос возвращает не тот набор рядов: {len(got)} шт. с метками {sorted(dict(k) for k in got)[:3]}"); sys.exit(1)
for k, v in want.items():
    if abs(got[k] - v) > max(abs(v) * 0.03, 1e-6):
        print(f"✗ Значение {got[k]:.4g} для {dict(k) or 'результата'} неверное"); sys.exit(1)
print("✓ " + "; ".join(f"{dict(k) or 'итог'}: {v:.4g}" for k, v in sorted(got.items())))
EOF
}
lab_prom_wait() { for i in $(seq ${1:-20}); do curl -s localhost:9090/-/ready 2>/dev/null | grep -qi ready && return 0; sleep 0.5; done; return 1; }
# lab_promn 'запрос' — число рядов в результате (-1 — ошибка запроса)
lab_promn() { lab_promq "$1" | jq -r 'if .status == "success" then (.data.result | length) else -1 end' 2>/dev/null; }
```

### Метрики приложения пропали

После вчерашних правок `/etc/prometheus/prometheus.yml` на дашборде shop-app пусто. Почините так, чтобы Prometheus работал и собирал метрики shop-app (задача `shop-app`), а также остальные цели, что были в конфиге.

```bash setup
lab_shop_exporter
lab_prom_base shop
c=/etc/prometheus/prometheus.yml
sed -i '0,/scrape_interval: 5s/s//scrape_interval: 5/' $c
sed -i 's#targets: \["127.0.0.1:8099"\]#targets: ["127.0.0.1:8089"]#' $c
sed -i 's#^  - job_name: shop-app#  - job_name: shop-app\n    metrics_path: /metric#' $c
systemctl restart prometheus >/dev/null 2>&1; true
```

```bash check
[ "$(systemctl is-active prometheus)" = active ] && lab_prom_wait || fail "Prometheus не работает"
for i in $(seq 20); do [ "$(lab_promn 'up{job="shop-app"} == 1')" = 1 ] && break; sleep 0.5; done
[ "$(lab_promn 'up{job="shop-app"}')" -ge 1 ] 2>/dev/null || fail "В Prometheus нет цели задачи shop-app"
[ "$(lab_promn 'up{job="shop-app"} == 1')" = 1 ] || fail "Цель shop-app недоступна: $(curl -s localhost:9090/api/v1/targets | jq -r '.data.activeTargets[] | select(.labels.job == "shop-app") | .lastError' | head -1)"
[ "$(lab_promn 'http_requests_total{job="shop-app"}')" -ge 4 ] 2>/dev/null || fail "Метрики http_requests_total от shop-app не собираются"
for j in prometheus node; do [ "$(lab_promn "up{job=\"$j\"} == 1")" = 1 ] || fail "Цель $j недоступна или пропала"; done
ok "Prometheus работает, shop-app, node и prometheus — UP"
```

```text hint
1. Сначала сам Prometheus: состояние службы и последние строки её журнала. Конфиг можно проверить утилитой из комплекта Prometheus без перезапуска.
2. Когда Prometheus запустился, открыть список целей: у недоступной цели есть текст ошибки — по нему видно, что не так с адресом или путём.
3. Сравнить адрес и путь в конфиге с тем, где приложение на самом деле отдаёт метрики; применить конфиг и подождать один интервал сбора.
```

```bash solution
systemctl status prometheus --no-pager | head -5
promtool check config /etc/prometheus/prometheus.yml || true
sudo sed -i 's/scrape_interval: 5$/scrape_interval: 5s/' /etc/prometheus/prometheus.yml
promtool check config /etc/prometheus/prometheus.yml
sudo systemctl restart prometheus
sleep 8
curl -s localhost:9090/api/v1/targets | jq -r '.data.activeTargets[] | "\(.labels.job) \(.health) \(.lastError)"'
sudo sed -i '/metrics_path: \/metric$/d; s/127.0.0.1:8089/127.0.0.1:8099/' /etc/prometheus/prometheus.yml
promtool check config /etc/prometheus/prometheus.yml
curl -s -X POST localhost:9090/-/reload
sleep 8
curl -s localhost:9090/api/v1/targets | jq -r '.data.activeTargets[] | "\(.labels.job) \(.health)"'
```

```text review
Три поломки, по одной на каждом шаге:

1. `scrape_interval: 5` — длительность без единицы: `not a valid duration string`. Prometheus не стартует при любой ошибке конфига — и весь мониторинг слеп.
2. `targets: ["127.0.0.1:8089"]` — не тот порт: в Targets `connection refused`.
3. `metrics_path: /metric` — приложение отдаёт `/metrics`: `server returned HTTP status 404`.

- `promtool check config` — до каждого перезапуска. В репозитории с конфигами — в CI, в Kubernetes — так делает prometheus-operator при применении.
- `reload` (через `/-/reload` или `SIGHUP`) при ошибке в конфиге **не уронит** работающий Prometheus — он продолжит со старым конфигом и напишет ошибку в журнал. `restart` с ошибкой — уронит.
- Мониторинг мониторинга: алерт на `up == 0` по каждой задаче и внешний «dead man's switch» для самого Prometheus.
```

### Алерт молчит

У shop-app сейчас около 7–9% ответов с ошибкой 5xx, а алерт **`ShopHighErrorRate`** (порог — 5% за минуту) не срабатывает. Правила лежат в `/etc/prometheus/rules/`. Почините так, чтобы алерт был загружен и срабатывал на текущую ситуацию. Название, порог и важность алерта не меняйте.

```bash setup
lab_shop_exporter
lab_prom_base shop
rm -f /etc/prometheus/rules/*
cat > /etc/prometheus/rules/shop.yaml <<'EOF'
groups:
  - name: shop
    rules:
      - alert: ShopHighErrorRate
        expr: sum(rate(http_request_total{status=~"5.."}[1m])) / sum(rate(http_request_total[1m])) > 0.05
        for: 30s
        labels:
          severity: critical
        annotations:
          summary: "Доля ответов 5xx выше 5%"
EOF
curl -s -X POST localhost:9090/-/reload >/dev/null
```

```bash check
[ "$(systemctl is-active prometheus)" = active ] && lab_prom_wait || fail "Prometheus не работает"
r=$(curl -s localhost:9090/api/v1/rules | jq -c '[.data.groups[].rules[] | select(.type == "alerting" and .name == "ShopHighErrorRate")][0] // empty')
[ -n "$r" ] || fail "Алерт ShopHighErrorRate не загружен в Prometheus"
[ "$(echo "$r" | jq -r .health)" != err ] || fail "Правило ShopHighErrorRate с ошибкой: $(echo "$r" | jq -r .lastError)"
[ "$(echo "$r" | jq -r .labels.severity)" = critical ] || fail "Важность алерта изменена"
q=$(echo "$r" | jq -r .query)
echo "$q" | grep -qE '0\.05|\b5\b' || fail "Порог алерта изменён: $q"
echo "$q" | grep -q '5\.\.\|"5' || fail "Алерт не про ответы 5xx: $q"
for i in $(seq 20); do [ "$(lab_promn "$q")" -ge 1 ] 2>/dev/null && break; sleep 0.5; done
[ "$(lab_promn "$q")" -ge 1 ] 2>/dev/null || fail "Выражение алерта сейчас ничего не возвращает — алерт не сработает"
ok "ShopHighErrorRate загружен, выражение срабатывает: $(lab_promq "$q" | jq -r '.data.result[0].value[1]' | cut -c1-6)"
```

```text hint
1. Посмотреть в интерфейсе Prometheus, какие правила загружены. Если алерта нет — сравнить имя файла правил с маской в основном конфиге.
2. Когда правило загрузилось, выполнить его выражение вручную. Пустой результат — разобрать выражение по частям: возвращает ли что-нибудь каждая метрика по отдельности.
3. Сверить имя метрики с тем, что приложение реально отдаёт. Проверить файл правил утилитой из комплекта Prometheus и применить конфигурацию.
```

```bash solution
grep -A2 rule_files /etc/prometheus/prometheus.yml
ls /etc/prometheus/rules/
sudo mv /etc/prometheus/rules/shop.yaml /etc/prometheus/rules/shop.yml
curl -s 'localhost:9090/api/v1/query?query=count%20by%20(__name__)%20(%7Bjob%3D%22shop-app%22%7D)' | jq -r '.data.result[].metric.__name__'
sudo sed -i 's/http_request_total/http_requests_total/g' /etc/prometheus/rules/shop.yml
promtool check rules /etc/prometheus/rules/shop.yml
curl -s -X POST localhost:9090/-/reload
sleep 3
curl -s localhost:9090/api/v1/rules | jq -r '.data.groups[].rules[] | "\(.name) \(.health) \(.state)"'
```

```text review
Две тихие поломки — ни одна не даёт ошибки:

1. Файл `shop.yaml`, а в `rule_files` маска `/etc/prometheus/rules/*.yml` — файл просто не читался.
2. В выражении `http_request_total` вместо `http_requests_total`. Prometheus не знает, какие метрики «должны» быть, и опечатку не замечает: выражение возвращает пустоту, алерт навсегда `inactive`.

- Любое новое правило проверяют, выполнив его `expr` вручную на текущих данных, и в идеале — тестом: `promtool test rules` с заданными рядами и ожидаемыми алертами.
- `absent(http_requests_total{job="shop-app"})` — отдельный алерт на то, что метрика пропала (переименовали в новой версии приложения).
- Для «доли ошибок» делят `rate` по 5xx на `rate` всех запросов, суммируя одинаково (`sum` / `sum` или `sum by (path)` / `sum by (path)`), иначе метки не совпадут и деление вернёт пустоту.
```

## Тест

### Prometheus не стартует после правки конфига. Какой командой проверить конфиг без запуска?
= promtool check config
= promtool check config /etc/prometheus/prometheus.yml
> promtool проверяет синтаксис и значения, в том числе файлы правил из rule_files.

### В конфиге `scrape_interval: 5`. Что будет?
- [ ] Сбор каждые 5 секунд
- [ ] Сбор каждые 5 минут
- [x] Ошибка «not a valid duration string» — Prometheus не примет конфиг
- [ ] Значение будет проигнорировано
> Длительности в Prometheus всегда с единицей: 5s, 1m, 2h.

### Чем reload отличается от restart, если в новом конфиге ошибка?
- [ ] Ничем
- [x] reload отклонит конфиг и продолжит работать со старым; restart с ошибкой — Prometheus не поднимется
- [ ] reload удалит старые данные
- [ ] restart проверяет конфиг, reload нет
> Поэтому применять изменения на работающем сервере лучше через reload.

### Цель в Targets — DOWN с ошибкой «server returned HTTP status 404 Not Found». Что не так?
- [ ] Неверный порт
- [x] Неверный metrics_path — по этому пути метрик нет
- [ ] Приложение не запущено
- [ ] Сеть недоступна
> Сервер ответил — значит, адрес и порт верные; не тот путь.

### Цель DOWN с «connection refused». Что проверить?
- [ ] metrics_path
- [x] Адрес и порт цели: слушает ли приложение именно там
- [ ] Правила алертов
- [ ] Retention
> На этом адресе и порту никто не принимает соединения.

### Файл правил лежит в каталоге, но в Status → Rules его нет. Частая причина?
- [ ] Prometheus не поддерживает много файлов правил
- [x] Файл не попадает под маску rule_files (например, .yaml при маске *.yml) или не сделан reload
- [ ] Неверный scrape_interval
- [ ] Не запущен Alertmanager
> rule_files — маска путей; что не совпало, то не загружено.

### Алерт загружен, health ok, но всегда inactive при явной проблеме. С чего начать?
- [ ] Перезапустить Alertmanager
- [x] Выполнить expr алерта вручную — скорее всего, он ничего не возвращает (опечатка в метрике или метке)
- [ ] Увеличить for
- [ ] Удалить и создать алерт заново
> Prometheus не проверяет, существует ли метрика; пустое выражение — тихий отказ.

### Какой алерт сообщит, что метрика приложения вообще перестала поступать?
- [ ] rate(http_requests_total[5m]) == 0
- [x] absent(http_requests_total{job="shop-app"})
- [ ] up == 1
- [ ] count(http_requests_total) > 0
> absent возвращает 1, если рядов нет совсем.

### Как проверить файл правил на ошибки?
= promtool check rules
= promtool check rules файл.yml
> Проверяет синтаксис YAML и выражения PromQL.

### Как применить новый конфиг Prometheus без перезапуска?
- [ ] kill -9 и запустить снова
- [x] POST на /-/reload (с --web.enable-lifecycle) или SIGHUP / systemctl reload
- [ ] Удалить каталог данных
- [ ] Это невозможно
> Конфиг и правила перечитываются на лету.

### Чем полезен promtool test rules?
- [ ] Ускоряет вычисление правил
- [x] Проверяет алерты на заданных тестовых рядах: срабатывают ли они там, где должны
- [ ] Отправляет тестовое уведомление
- [ ] Проверяет доступность целей
> Тесты правил ловят опечатки и неверные пороги до продакшена.

### Деление `sum by (path) (rate(...{status=~"5.."}[5m])) / sum(rate(...[5m]))` вернуло пустой результат. Почему?
- [ ] Нет ошибок 5xx
- [x] У левой части есть метка path, у правой нет — ряды не сопоставились
