# Тома и хранение данных

Слой записи контейнера **живёт и умирает вместе с контейнером**. Удалили контейнер базы — удалили базу. Кроме того, запись в overlay-слой медленнее и раздувает `/var/lib/docker`. Поэтому всё, что должно пережить контейнер, хранят **вне** его слоя.

## Три способа монтирования

| | **Volume** | **Bind mount** | **tmpfs** |
| --- | --- | --- | --- |
| Где данные | `/var/lib/docker/volumes/имя/_data`, управляет Docker | Любой путь на хосте | Оперативная память |
| Синтаксис | `-v pgdata:/var/lib/postgresql/data` | `-v /srv/app/conf:/etc/app:ro` или `-v ./conf:/etc/app` | `--tmpfs /tmp` |
| Переживает контейнер | Да | Да (это файлы хоста) | Нет |
| Типичное применение | Базы данных, данные приложений | Конфиги, исходники при разработке, сокеты | Временные файлы, кэши, секреты, которые нельзя писать на диск |
| Переносимость | Хорошая: не зависит от структуры хоста | Зависит от путей на хосте | — |

## Volumes

```bash
docker volume create pgdata
docker volume ls
docker volume inspect pgdata
docker run -d --name db -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:16
docker rm -f db                         # контейнер удалён...
docker run -d --name db -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:16   # ...данные на месте
docker volume rm pgdata
```

- Если пустой том монтируется в каталог, где в образе уже есть файлы, Docker **копирует** их в том (с bind mount такого нет — каталог образа просто перекрывается).
- **Анонимные тома** (`-v /data` или `VOLUME` в Dockerfile) получают случайное имя и копятся — `docker volume prune` удалит неиспользуемые.
- `docker rm -v` удаляет контейнер вместе с его анонимными томами.

Синтаксис `--mount` длиннее, но явный — рекомендуется в скриптах:

```bash
docker run --mount type=volume,src=pgdata,dst=/var/lib/postgresql/data postgres:16
docker run --mount type=bind,src=/srv/nginx/nginx.conf,dst=/etc/nginx/nginx.conf,readonly nginx
docker run --mount type=tmpfs,dst=/tmp,tmpfs-size=64m myapp
```

## Bind mounts

```bash
docker run -d -p 8080:80 \
  -v "$(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro" \
  -v "$(pwd)/site:/usr/share/nginx/html:ro" nginx
```

- `:ro` — только чтение: контейнер не сможет испортить конфиг.
- Удобно в разработке: код на хосте, изменения сразу видны в контейнере.
- С `-v` несуществующий путь на хосте **создаётся как каталог** (частая ошибка: хотели смонтировать файл, опечатались — получили пустую папку). `--mount` в этом случае выдаёт ошибку.

### Права и UID

Внутри контейнера и на хосте одни и те же **числовые UID**. Если приложение в контейнере работает как UID 10001, а файлы на хосте принадлежат UID 1000 — будет `Permission denied`. Решения: `chown 10001` на хосте, запуск с `--user $(id -u):$(id -g)`, или именованный том вместо bind mount.

## Бэкап и перенос тома

```bash
docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine tar czf /backup/pgdata.tgz -C /data .
docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine tar xzf /backup/pgdata.tgz -C /data
```

Для работающей базы копия файлов может быть несогласованной — для PostgreSQL правильнее `pg_dump` (тема про бэкапы баз).

## Read-only контейнер

```bash
docker run --read-only --tmpfs /tmp --tmpfs /run -v appdata:/data myapp
```

Корневая ФС контейнера только для чтения, записывать можно только в явно указанные места — злоумышленник не сможет подменить файлы приложения.

## Логи контейнеров на диске

Логи `docker logs` хранятся драйвером `json-file` в `/var/lib/docker/containers/ID/ID-json.log` и **по умолчанию не ротируются** — частая причина забитого диска. Ограничение в `/etc/docker/daemon.json`:

```json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
```

Или драйвер `local`, `journald`. Настройки применяются к **новым** контейнерам.

## Практика

- [ ] Запустить PostgreSQL с именованным томом, создать таблицу, пересоздать контейнер — данные сохранились
- [ ] Запустить PostgreSQL без тома, создать таблицу, удалить контейнер — убедиться, что данные потеряны
- [ ] Запустить nginx со своим `nginx.conf` и каталогом статики через bind mount в режиме `:ro`, поменять HTML на хосте и обновить страницу
- [ ] Сделать бэкап тома в tar-архив через временный контейнер alpine и восстановить его в новый том
- [ ] Запустить контейнер с `--read-only` и найти, какие каталоги приложению нужны на запись
- [ ] Настроить ротацию логов в `daemon.json` и проверить `docker inspect -f '{{.HostConfig.LogConfig}}'` у нового контейнера

## Тест

### Что произойдёт с данными PostgreSQL в контейнере без тома после docker rm?
- [ ] Они сохранятся в образе
- [x] Они будут удалены вместе со слоем записи контейнера
- [ ] Они сохранятся в /var/lib/postgresql на хосте
- [ ] Docker спросит, сохранить ли данные
> Данные баз всегда храните в томах.

### Чем volume отличается от bind mount?
- [x] Volume хранится в области, управляемой Docker, и не зависит от структуры каталогов хоста
- [x] Bind mount монтирует любой указанный путь хоста
- [ ] Volume хранится в оперативной памяти
- [ ] Bind mount удаляется вместе с контейнером
> Для конфигов и разработки удобен bind mount, для данных — volume.

### Где по умолчанию лежат данные именованного тома?
- [ ] /tmp/docker
- [x] /var/lib/docker/volumes/имя/_data
- [ ] /home/docker
- [ ] Внутри образа
> Но работать с ними лучше через контейнеры, а не напрямую.

### Для чего подходит tmpfs-монтирование?
- [ ] Для данных базы данных
- [x] Для временных файлов и чувствительных данных, которые не должны попадать на диск: хранится в памяти и исчезает после остановки
- [ ] Для конфигов nginx
- [ ] Для логов
> Размер ограничивают через tmpfs-size.

### Что означает суффикс :ro в -v ./nginx.conf:/etc/nginx/nginx.conf:ro?
- [ ] Root only
- [x] Монтирование только для чтения
- [ ] Remove on exit
- [ ] Rotate output
> Контейнер не сможет изменить файл.

### Приложение в контейнере работает от UID 10001 и получает Permission denied на bind mount. Почему?
- [ ] Bind mount не поддерживает запись
- [x] Файлы на хосте принадлежат другому UID, а права проверяются по числовому UID, общему для хоста и контейнера
- [ ] Нужно перезапустить Docker
- [ ] Контейнеры не могут писать на хост
> Решение — chown на хосте, `--user` или именованный том.

### Что произойдёт, если через -v указать несуществующий путь на хосте?
- [ ] Ошибка
- [x] Docker создаст на хосте пустой каталог с этим именем
- [ ] Docker скопирует файл из образа на хост
- [ ] Монтирование будет пропущено
> `--mount type=bind` в этом случае выдаст ошибку — это безопаснее.

### Как удалить все неиспользуемые тома?
= docker volume prune
> Осторожно: это данные.

### Почему диск сервера с Docker может забиться логами контейнеров?
- [ ] Docker пишет логи в /tmp
- [x] Драйвер json-file по умолчанию не ротирует логи; нужно задать max-size и max-file в daemon.json
- [ ] docker logs сохраняет копию на диск
- [ ] Логи хранятся в образе
> Настройки применяются только к новым контейнерам.

### Что даёт запуск контейнера с --read-only?
- [ ] Контейнер не может пользоваться сетью
- [x] Корневая ФС контейнера доступна только для чтения, запись возможна только в явно смонтированные тома и tmpfs
- [ ] Контейнер нельзя остановить
- [ ] Образ нельзя удалить
> Это мешает злоумышленнику подменить файлы приложения.

### Что произойдёт при монтировании пустого именованного тома в каталог, где в образе уже есть файлы?
- [ ] Файлы образа будут удалены
- [x] Docker скопирует файлы из образа в том
- [ ] Будет ошибка
- [ ] Том останется пустым, а файлы образа скроются
> Скрытие файлов образа происходит при bind mount.

### Как сделать бэкап именованного тома в архив?
- [ ] docker volume backup pgdata
- [x] Запустить временный контейнер с этим томом и каталогом хоста и упаковать данные через tar
- [ ] docker commit
- [ ] docker save pgdata
> `docker save` сохраняет образы, а не тома.
