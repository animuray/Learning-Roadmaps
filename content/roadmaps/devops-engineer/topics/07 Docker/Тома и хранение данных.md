# Тома и хранение данных

Слой записи контейнера **живёт и умирает вместе с контейнером**. Удалили контейнер базы — удалили базу. Кроме того, запись в overlay-слой медленнее и раздувает `/var/lib/docker`. Поэтому всё, что должно пережить контейнер, хранят **вне** его слоя.

## Три способа монтирования

| | **Volume** | **Bind mount** | **tmpfs** |
| --- | --- | --- | --- |
| Где данные | `/var/lib/docker/volumes/имя/_data`, управляет Docker | Любой путь на хосте | Оперативная память |
| Синтаксис | `-v pgdata:/var/lib/postgresql/data` | `-v /srv/app/conf:/etc/app:ro` или `-v ./conf:/etc/app` | `--tmpfs /tmp` |
| Переживает контейнер | Да | Да (это файлы хоста) | Нет |
| Типичное применение | Базы данных, данные приложений | Конфиги, исходники при разработке, сокеты | Временные файлы, кэши, секреты, которые нельзя писать на диск |
| Переносимость | Хорошая: не зависит от структуры хоста | Зависит от путей на хосте | — |

## Volumes

```bash
docker volume create pgdata
docker volume ls
docker volume inspect pgdata
docker run -d --name db -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:16
docker rm -f db                         # контейнер удалён...
docker run -d --name db -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:16   # ...данные на месте
docker volume rm pgdata
```

- Если пустой том монтируется в каталог, где в образе уже есть файлы, Docker **копирует** их в том (с bind mount такого нет — каталог образа просто перекрывается).
- **Анонимные тома** (`-v /data` или `VOLUME` в Dockerfile) получают случайное имя и копятся — `docker volume prune` удалит неиспользуемые.
- `docker rm -v` удаляет контейнер вместе с его анонимными томами.

Синтаксис `--mount` длиннее, но явный — рекомендуется в скриптах:

```bash
docker run --mount type=volume,src=pgdata,dst=/var/lib/postgresql/data postgres:16
docker run --mount type=bind,src=/srv/nginx/nginx.conf,dst=/etc/nginx/nginx.conf,readonly nginx
docker run --mount type=tmpfs,dst=/tmp,tmpfs-size=64m myapp
```

## Bind mounts

```bash
docker run -d -p 8080:80 \
  -v "$(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro" \
  -v "$(pwd)/site:/usr/share/nginx/html:ro" nginx
```

- `:ro` — только чтение: контейнер не сможет испортить конфиг.
- Удобно в разработке: код на хосте, изменения сразу видны в контейнере.
- С `-v` несуществующий путь на хосте **создаётся как каталог** (частая ошибка: хотели смонтировать файл, опечатались — получили пустую папку). `--mount` в этом случае выдаёт ошибку.

### Права и UID

Внутри контейнера и на хосте одни и те же **числовые UID**. Если приложение в контейнере работает как UID 10001, а файлы на хосте принадлежат UID 1000 — будет `Permission denied`. Решения: `chown 10001` на хосте, запуск с `--user $(id -u):$(id -g)`, или именованный том вместо bind mount.

## Бэкап и перенос тома

```bash
docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine tar czf /backup/pgdata.tgz -C /data .
docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine tar xzf /backup/pgdata.tgz -C /data
```

Для работающей базы копия файлов может быть несогласованной — для PostgreSQL правильнее `pg_dump` (тема про бэкапы баз).

## Read-only контейнер

```bash
docker run --read-only --tmpfs /tmp --tmpfs /run -v appdata:/data myapp
```

Корневая ФС контейнера только для чтения, записывать можно только в явно указанные места — злоумышленник не сможет подменить файлы приложения.

## Логи контейнеров на диске

Логи `docker logs` хранятся драйвером `json-file` в `/var/lib/docker/containers/ID/ID-json.log` и **по умолчанию не ротируются** — частая причина забитого диска. Ограничение в `/etc/docker/daemon.json`:

```json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
```

Или драйвер `local`, `journald`. Настройки применяются к **новым** контейнерам.

## Практика

- [ ] Запустить PostgreSQL с именованным томом, создать таблицу, пересоздать контейнер — данные сохранились
- [ ] Запустить PostgreSQL без тома, создать таблицу, удалить контейнер — убедиться, что данные потеряны
- [ ] Запустить nginx со своим `nginx.conf` и каталогом статики через bind mount в режиме `:ro`, поменять HTML на хосте и обновить страницу
- [ ] Сделать бэкап тома в tar-архив через временный контейнер alpine и восстановить его в новый том
- [ ] Запустить контейнер с `--read-only` и найти, какие каталоги приложению нужны на запись
- [ ] Настроить ротацию логов в `daemon.json` и проверить `docker inspect -f '{{.HostConfig.LogConfig}}'` у нового контейнера

### Данные переживают контейнер

Запустите PostgreSQL в контейнере **`pg`** (образ `postgres:16-alpine`, пароль суперпользователя — через переменную `POSTGRES_PASSWORD`) с **именованным томом `pgdata`** для каталога данных. Создайте в базе таблицу `notes` и добавьте в неё хотя бы одну строку. Затем **удалите контейнер и создайте `pg` заново** с тем же томом — данные должны остаться.

```bash setup
lab_drm pg
docker volume rm -f pgdata >/dev/null 2>&1; true
```

```bash check
[ "$(docker inspect -f '{{.State.Running}}' pg 2>/dev/null)" = true ] || fail "Контейнер pg не запущен"
docker inspect -f '{{range .Mounts}}{{.Type}} {{.Name}} {{.Destination}}{{println}}{{end}}' pg | grep -qx 'volume pgdata /var/lib/postgresql/data' || fail "У pg каталог данных не подключён из тома pgdata"
for i in $(seq 20); do docker exec pg pg_isready -q -U postgres 2>/dev/null && break; sleep 0.5; done
n=$(docker exec pg psql -U postgres -tAc 'select count(*) from notes' 2>/dev/null)
[ -n "$n" ] && [ "$n" -ge 1 ] || fail "В базе нет таблицы notes со строками"
created=$(docker volume inspect -f '{{.CreatedAt}}' pgdata); started=$(docker inspect -f '{{.Created}}' pg)
[ "$(date -d "$started" +%s)" -gt $(( $(date -d "$created" +%s) + 2 )) ] || fail "Контейнер pg создан одновременно с томом — его не пересоздавали"
ok "pgdata пережил пересоздание: строк в notes — $n"
```

```text hint
1. Запуск контейнера с базой: имя, переменная окружения с паролем, подключение тома по имени к каталогу данных PostgreSQL (он указан в описании образа). Том создастся сам.
2. Дождаться готовности и выполнить SQL через psql внутри контейнера.
3. Удалить контейнер принудительно и запустить такой же снова — с тем же томом.
```

```bash solution
docker run -d --name pg -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:16-alpine
until docker exec pg pg_isready -q -U postgres; do sleep 1; done
sleep 2
docker exec pg psql -U postgres -c "create table notes (id serial, body text)" -c "insert into notes (body) values ('persist me')"
docker rm -f pg
sleep 3
docker run -d --name pg -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:16-alpine
until docker exec pg pg_isready -q -U postgres; do sleep 1; done
docker exec pg psql -U postgres -c "select * from notes"
```

```text review
Эталон: `docker run -v pgdata:/var/lib/postgresql/data ...` → данные → `docker rm -f pg` → тот же `run`.

- Без тома данные живут в верхнем слое контейнера и исчезают с `docker rm`. Том живёт отдельно: `docker volume ls`, `docker volume inspect pgdata` (лежит в `/var/lib/docker/volumes/`).
- Именованный том — для данных, которыми управляет Docker; bind mount (`-v /srv/pg:/var/lib/...`) — когда важно, где именно на хосте лежат файлы.
- `docker compose down -v` и `docker volume prune` удаляют тома — самые дорогие ошибки с Docker. Тома — не бэкап: для базы нужен `pg_dump`.
```

### Бэкап тома

В томе **`appdata`** лежат данные приложения. Сделайте бэкап тома в архив **`~/appdata-backup.tar.gz`** с помощью временного контейнера, а затем **восстановите** его в новый том **`appdata-restored`** — содержимое должно совпасть.

```bash setup
docker volume rm -f appdata appdata-restored >/dev/null 2>&1
docker volume create appdata >/dev/null
docker run --rm -v appdata:/data alpine:3.20 sh -c 'mkdir -p /data/uploads /data/config && echo "listen=8080" > /data/config/app.conf && for i in $(seq 1 20); do head -c 2000 /dev/urandom > /data/uploads/file$i.bin; done'
rm -f /home/student/appdata-backup.tar.gz
```

```bash check
[ -s /home/student/appdata-backup.tar.gz ] || fail "Нет ~/appdata-backup.tar.gz"
tar -tzf /home/student/appdata-backup.tar.gz >/dev/null 2>&1 || fail "~/appdata-backup.tar.gz — не архив tar.gz"
tar -tzf /home/student/appdata-backup.tar.gz | grep -q 'config/app.conf' || fail "В архиве нет данных тома (config/app.conf)"
docker volume inspect appdata-restored >/dev/null 2>&1 || fail "Тома appdata-restored нет"
a=$(docker run --rm -v appdata:/d:ro alpine:3.20 sh -c 'cd /d && find . -type f | sort | xargs md5sum')
b=$(docker run --rm -v appdata-restored:/d:ro alpine:3.20 sh -c 'cd /d && find . -type f | sort | xargs md5sum')
[ "$a" = "$b" ] || fail "Содержимое appdata-restored отличается от appdata (файлов: $(echo "$b" | grep -c .) из $(echo "$a" | grep -c .); пути внутри архива должны быть от корня тома)"
ok "бэкап и восстановление: $(echo "$a" | grep -c .) файлов совпадают"
```

```text hint
1. Временный контейнер с маленьким образом подключает том (только чтение) и каталог хоста для архива, а внутри упаковывает содержимое тома, перейдя в его корень.
2. Восстановление — наоборот: новый том и тот же каталог хоста, распаковка в корень тома.
3. Контейнеры удаляются сами после выполнения.
```

```bash solution
docker run --rm -v appdata:/data:ro -v ~/:/backup alpine:3.20 tar -czf /backup/appdata-backup.tar.gz -C /data .
docker volume create appdata-restored
docker run --rm -v appdata-restored:/data -v ~/:/backup:ro alpine:3.20 tar -xzf /backup/appdata-backup.tar.gz -C /data
docker run --rm -v appdata-restored:/data alpine:3.20 find /data -type f | head -3
```

```text review
Эталон: `docker run --rm -v appdata:/data:ro -v ~/:/backup alpine tar -czf /backup/... -C /data .` и обратно.

- Паттерн «временный контейнер + два монтирования» — универсальный способ работать с томами: бэкап, перенос на другой сервер, просмотр содержимого.
- Для баз так делают только с **остановленной** базой — иначе файлы в архиве будут несогласованы. Для живой базы — `docker exec pg pg_dump`.
- `-C /data .` — пути в архиве от корня тома; без этого внутри окажется `data/...`, и при распаковке получится лишний уровень.
```

### Статика с хоста только на чтение

Запустите nginx в контейнере **`static`** (порт **8182** хоста → 80), который раздаёт файлы из каталога `~/site` на хосте через **bind mount**, подключённый **только на чтение**. Изменения в `~/site` на хосте должны сразу видеться в браузере.

```bash setup
lab_drm static
rm -rf /home/student/site && mkdir -p /home/student/site
echo "<h1>static v1</h1>" > /home/student/site/index.html
chown -R student:student /home/student/site
```

```bash check
[ "$(docker inspect -f '{{.State.Running}}' static 2>/dev/null)" = true ] || fail "Контейнер static не запущен"
m=$(docker inspect -f '{{range .Mounts}}{{if eq .Destination "/usr/share/nginx/html"}}{{.Type}} {{.Source}} {{.RW}}{{end}}{{end}}' static)
[ -n "$m" ] || fail "К /usr/share/nginx/html в контейнере ничего не подключено"
set -- $m
[ "$1" = bind ] && [ "${2%/}" = /home/student/site ] || fail "Подключено «$m» — нужен bind mount каталога ~/site"
[ "$3" = false ] || fail "Каталог подключён с правом записи"
echo "<h1>static v$RANDOM</h1>" > /home/student/site/index.html; v=$(cat /home/student/site/index.html)
[ "$(curl -s --max-time 3 http://127.0.0.1:8182/)" = "$v" ] || fail "localhost:8182 не отдаёт актуальный ~/site/index.html"
ok "static: ~/site → /usr/share/nginx/html (ro), порт 8182"
```

```text hint
1. Bind mount — подключение каталога хоста по абсолютному пути в каталог контейнера; режим «только чтение» указывается суффиксом после второго двоеточия.
2. Каталог, который раздаёт nginx в официальном образе, указан в его документации.
3. Поменять файл на хосте и обновить страницу.
```

```bash solution
docker run -d --name static -p 8182:80 -v ~/site:/usr/share/nginx/html:ro nginx:1.27-alpine
sleep 1
curl -s localhost:8182
```

```text review
Эталон: `docker run -d --name static -p 8182:80 -v ~/site:/usr/share/nginx/html:ro nginx:1.27-alpine`.

- `:ro` — взломанный или ошибающийся контейнер не испортит файлы на хосте. Так подключают конфиги и статику.
- Bind mount удобен в разработке (код на хосте, сразу виден в контейнере), а в проде лучше запекать файлы в образ: образ — единица поставки и отката.
- Права: файлы bind mount видны в контейнере с UID хоста. Если процесс в контейнере работает под другим UID, он может не иметь доступа — частая причина «Permission denied» с томами.
- Длинный синтаксис понятнее: `--mount type=bind,source=$HOME/site,target=/usr/share/nginx/html,readonly`.
```

## Тест

### Что произойдёт с данными PostgreSQL в контейнере без тома после docker rm?
- [ ] Они сохранятся в образе
- [x] Они будут удалены вместе со слоем записи контейнера
- [ ] Они сохранятся в /var/lib/postgresql на хосте
- [ ] Docker спросит, сохранить ли данные
> Данные баз всегда храните в томах.

### Чем volume отличается от bind mount?
- [x] Volume хранится в области, управляемой Docker, и не зависит от структуры каталогов хоста
- [x] Bind mount монтирует любой указанный путь хоста
- [ ] Volume хранится в оперативной памяти
- [ ] Bind mount удаляется вместе с контейнером
> Для конфигов и разработки удобен bind mount, для данных — volume.

### Где по умолчанию лежат данные именованного тома?
- [ ] /tmp/docker
- [x] /var/lib/docker/volumes/имя/_data
- [ ] /home/docker
- [ ] Внутри образа
> Но работать с ними лучше через контейнеры, а не напрямую.

### Для чего подходит tmpfs-монтирование?
- [ ] Для данных базы данных
- [x] Для временных файлов и чувствительных данных, которые не должны попадать на диск: хранится в памяти и исчезает после остановки
- [ ] Для конфигов nginx
- [ ] Для логов
> Размер ограничивают через tmpfs-size.

### Что означает суффикс :ro в -v ./nginx.conf:/etc/nginx/nginx.conf:ro?
- [ ] Root only
- [x] Монтирование только для чтения
- [ ] Remove on exit
- [ ] Rotate output
> Контейнер не сможет изменить файл.

### Приложение в контейнере работает от UID 10001 и получает Permission denied на bind mount. Почему?
- [ ] Bind mount не поддерживает запись
- [x] Файлы на хосте принадлежат другому UID, а права проверяются по числовому UID, общему для хоста и контейнера
- [ ] Нужно перезапустить Docker
- [ ] Контейнеры не могут писать на хост
> Решение — chown на хосте, `--user` или именованный том.

### Что произойдёт, если через -v указать несуществующий путь на хосте?
- [ ] Ошибка
- [x] Docker создаст на хосте пустой каталог с этим именем
- [ ] Docker скопирует файл из образа на хост
- [ ] Монтирование будет пропущено
> `--mount type=bind` в этом случае выдаст ошибку — это безопаснее.

### Как удалить все неиспользуемые тома?
= docker volume prune
> Осторожно: это данные.

### Почему диск сервера с Docker может забиться логами контейнеров?
- [ ] Docker пишет логи в /tmp
- [x] Драйвер json-file по умолчанию не ротирует логи; нужно задать max-size и max-file в daemon.json
- [ ] docker logs сохраняет копию на диск
- [ ] Логи хранятся в образе
> Настройки применяются только к новым контейнерам.

### Что даёт запуск контейнера с --read-only?
- [ ] Контейнер не может пользоваться сетью
- [x] Корневая ФС контейнера доступна только для чтения, запись возможна только в явно смонтированные тома и tmpfs
- [ ] Контейнер нельзя остановить
- [ ] Образ нельзя удалить
> Это мешает злоумышленнику подменить файлы приложения.

### Что произойдёт при монтировании пустого именованного тома в каталог, где в образе уже есть файлы?
- [ ] Файлы образа будут удалены
- [x] Docker скопирует файлы из образа в том
- [ ] Будет ошибка
- [ ] Том останется пустым, а файлы образа скроются
> Скрытие файлов образа происходит при bind mount.

### Как сделать бэкап именованного тома в архив?
- [ ] docker volume backup pgdata
- [x] Запустить временный контейнер с этим томом и каталогом хоста и упаковать данные через tar
- [ ] docker commit
- [ ] docker save pgdata
> `docker save` сохраняет образы, а не тома.
