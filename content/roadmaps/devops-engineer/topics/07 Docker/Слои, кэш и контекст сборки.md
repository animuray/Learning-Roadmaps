# Слои, кэш и контекст сборки

## Слои образа

Образ — это **стопка слоёв только для чтения**. Слой создают инструкции, меняющие файлы: `RUN`, `COPY`, `ADD`. Остальные (`ENV`, `CMD`, `EXPOSE`, `WORKDIR`, `LABEL`) меняют только метаданные.

```
 ┌──────────────────────────┐  ← слой контейнера (запись), удаляется вместе с контейнером
 ├──────────────────────────┤
 │ COPY . .          (2 МБ) │
 │ RUN pip install  (80 МБ) │  ← слои образа (только чтение), общие для всех
 │ COPY requirements (1 КБ) │     контейнеров и образов с тем же базовым слоем
 │ FROM python:3.12-slim    │
 └──────────────────────────┘
```

- Слои объединяются в одну ФС драйвером хранения **overlay2** (overlayfs ядра).
- **Copy-on-write:** при изменении файла из нижнего слоя он сначала копируется в слой контейнера.
- Слои **переиспользуются**: десять образов на одном `python:3.12-slim` хранят базовые слои один раз, и при `pull` скачиваются только недостающие.
- **Удаление файла в следующем слое не уменьшает образ** — файл остаётся в предыдущем слое, сверху только «метка удаления» (whiteout).

```dockerfile
# ПЛОХО: архив 500 МБ остаётся в образе навсегда
RUN curl -o /tmp/big.tar.gz https://example.com/big.tar.gz
RUN tar xzf /tmp/big.tar.gz -C /opt && rm /tmp/big.tar.gz

# ХОРОШО: скачать, распаковать и удалить в ОДНОМ слое
RUN curl -fsSL https://example.com/big.tar.gz | tar xz -C /opt
```

Посмотреть слои: `docker history образ`, подробно — утилита **dive**.

## Кэш сборки

При повторной сборке Docker проверяет каждую инструкцию: если она и её входные данные не изменились — берёт готовый слой из кэша (`CACHED` в выводе).

Кэш **инвалидируется**, когда:

- изменился текст инструкции;
- для `COPY`/`ADD` — изменилось содержимое или метаданные копируемых файлов;
- изменился любой **предыдущий** слой — тогда пересобирается всё, что ниже.

Для `RUN` Docker смотрит только на текст команды: `RUN apt-get update` закэшируется и не обновится, пока строка не изменится. Поэтому `apt-get update` всегда пишут в одной строке с `install`.

### Порядок инструкций — главное правило

От редко меняющегося к часто меняющемуся:

```dockerfile
# ПЛОХО: любое изменение кода → заново ставятся все зависимости
COPY . .
RUN pip install -r requirements.txt

# ХОРОШО: зависимости пересобираются только при изменении requirements.txt
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
```

Для Node.js — `COPY package.json package-lock.json ./` → `RUN npm ci` → `COPY . .`. Для Go — `go.mod`/`go.sum` → `go mod download` → код.

### Кэш-маунты BuildKit

```dockerfile
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt
```

Кэш пакетного менеджера сохраняется между сборками, но **не попадает в образ**.

### Управление кэшем

```bash
docker build --no-cache -t myapp .        # собрать без кэша
docker build --pull -t myapp .            # проверить свежесть базового образа
docker builder prune                      # очистить кэш сборки
docker buildx build --cache-from type=registry,ref=registry/app:cache --cache-to type=registry,ref=registry/app:cache,mode=max .
```

В CI каждый раз чистая машина — кэш передают через реестр (`--cache-from`/`--cache-to`).

## Контекст сборки и .dockerignore

`docker build .` отправляет демону **весь каталог** — это контекст. Если там `node_modules`, `.git`, дампы баз и логи — сборка медленная, а `COPY . .` тащит мусор и секреты в образ и ломает кэш.

**.dockerignore** в корне контекста исключает файлы:

```
.git
node_modules
__pycache__
*.log
.env
Dockerfile
docker-compose*.yml
dist
coverage
```

> [!warning] .env и ключи
> Если `.env` или `id_rsa` не исключены, `COPY . .` положит их в образ, а образ может уйти в публичный реестр.

## Тест

### Какие инструкции Dockerfile создают слои с файлами?
- [x] RUN
- [x] COPY
- [x] ADD
- [ ] ENV и CMD
> ENV, CMD, EXPOSE, LABEL меняют только метаданные образа.

### Вы скачали архив в одном RUN и удалили его в следующем. Уменьшился ли образ?
- [ ] Да, файл удалён
- [x] Нет: файл остался в предыдущем слое, новый слой только помечает его удалённым
- [ ] Да, если включён BuildKit
- [ ] Образ увеличится в два раза
> Скачивайте, используйте и удаляйте в одном RUN — или используйте multi-stage.

### Когда инвалидируется кэш для инструкции COPY?
- [ ] Каждый раз
- [x] Когда изменилось содержимое или метаданные копируемых файлов либо изменился один из предыдущих слоёв
- [ ] Только при --no-cache
- [ ] Никогда
> Docker считает контрольные суммы файлов.

### Что происходит со всеми инструкциями ниже, если кэш одной инструкции инвалидирован?
- [ ] Они берутся из кэша
- [x] Они тоже выполняются заново
- [ ] Сборка падает
- [ ] Пересобирается только эта инструкция
> Поэтому часто меняющиеся шаги ставят в конец.

### Как правильно расположить шаги для Python-приложения, чтобы зависимости не ставились при каждом изменении кода?
- [ ] COPY . . → RUN pip install -r requirements.txt
- [x] COPY requirements.txt . → RUN pip install -r requirements.txt → COPY . .
- [ ] RUN pip install → COPY requirements.txt
- [ ] Порядок не влияет на кэш
> Зависимости пересоберутся только при изменении requirements.txt.

### Почему apt-get update пишут в одном RUN с apt-get install?
- [ ] Так требует синтаксис
- [x] Иначе слой с apt-get update закэшируется со старыми списками пакетов, и install может упасть или поставить устаревшие версии
- [ ] Так быстрее скачиваются пакеты
- [ ] apt-get update нельзя запускать в Docker
> Для RUN кэш проверяет только текст команды.

### Что такое контекст сборки?
- [ ] Базовый образ
- [x] Набор файлов (обычно каталог), который отправляется сборщику и из которого можно копировать в образ
- [ ] Переменные окружения сборки
- [ ] Список слоёв
> В `docker build .` точка — это контекст.

### Как называется файл для исключения файлов из контекста сборки?
= .dockerignore
= dockerignore
> Синтаксис похож на .gitignore.

### Почему важно исключить .env и .git из контекста сборки?
- [x] Иначе COPY . . может положить секреты и всю историю репозитория в образ
- [x] Большой контекст замедляет сборку
- [x] Изменения в этих файлах ломают кэш COPY . .
- [ ] Docker не умеет копировать скрытые файлы
> Образ может попасть в реестр, где его скачают другие.

### Какой драйвер хранения Docker используется по умолчанию в современных Linux?
= overlay2
> Он основан на overlayfs ядра.

### Что означает copy-on-write в контексте контейнеров?
- [ ] Каждый контейнер получает полную копию образа
- [x] Файл из слоя образа копируется в слой контейнера только при первой попытке его изменить
- [ ] Запись в контейнере запрещена
- [ ] Файлы копируются на хост
> Благодаря этому контейнеры стартуют мгновенно и занимают мало места.

### Как кэш сборки передают между запусками в CI, где каждый раз чистая машина?
- [ ] Это невозможно
- [x] Через реестр: docker buildx build --cache-from и --cache-to
- [ ] Через docker commit
- [ ] Через .dockerignore
> Кэш хранится как специальный образ в реестре.

### Что делает RUN --mount=type=cache,target=/root/.cache/pip?
- [ ] Монтирует том в запущенный контейнер
- [x] Сохраняет кэш pip между сборками, не включая его в итоговый образ
- [ ] Отключает кэш
- [ ] Копирует кэш в образ
> Ускоряет повторную установку зависимостей.
