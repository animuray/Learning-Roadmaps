# Слои, кэш и контекст сборки

## Слои образа

Образ — это **стопка слоёв только для чтения**. Слой создают инструкции, меняющие файлы: `RUN`, `COPY`, `ADD`. Остальные (`ENV`, `CMD`, `EXPOSE`, `WORKDIR`, `LABEL`) меняют только метаданные.

```
 ┌──────────────────────────┐  ← слой контейнера (запись), удаляется вместе с контейнером
 ├──────────────────────────┤
 │ COPY . .          (2 МБ) │
 │ RUN pip install  (80 МБ) │  ← слои образа (только чтение), общие для всех
 │ COPY requirements (1 КБ) │     контейнеров и образов с тем же базовым слоем
 │ FROM python:3.12-slim    │
 └──────────────────────────┘
```

- Слои объединяются в одну ФС драйвером хранения **overlay2** (overlayfs ядра).
- **Copy-on-write:** при изменении файла из нижнего слоя он сначала копируется в слой контейнера.
- Слои **переиспользуются**: десять образов на одном `python:3.12-slim` хранят базовые слои один раз, и при `pull` скачиваются только недостающие.
- **Удаление файла в следующем слое не уменьшает образ** — файл остаётся в предыдущем слое, сверху только «метка удаления» (whiteout).

```dockerfile
# ПЛОХО: архив 500 МБ остаётся в образе навсегда
RUN curl -o /tmp/big.tar.gz https://example.com/big.tar.gz
RUN tar xzf /tmp/big.tar.gz -C /opt && rm /tmp/big.tar.gz

# ХОРОШО: скачать, распаковать и удалить в ОДНОМ слое
RUN curl -fsSL https://example.com/big.tar.gz | tar xz -C /opt
```

Посмотреть слои: `docker history образ`, подробно — утилита **dive**.

## Кэш сборки

При повторной сборке Docker проверяет каждую инструкцию: если она и её входные данные не изменились — берёт готовый слой из кэша (`CACHED` в выводе).

Кэш **инвалидируется**, когда:

- изменился текст инструкции;
- для `COPY`/`ADD` — изменилось содержимое или метаданные копируемых файлов;
- изменился любой **предыдущий** слой — тогда пересобирается всё, что ниже.

Для `RUN` Docker смотрит только на текст команды: `RUN apt-get update` закэшируется и не обновится, пока строка не изменится. Поэтому `apt-get update` всегда пишут в одной строке с `install`.

### Порядок инструкций — главное правило

От редко меняющегося к часто меняющемуся:

```dockerfile
# ПЛОХО: любое изменение кода → заново ставятся все зависимости
COPY . .
RUN pip install -r requirements.txt

# ХОРОШО: зависимости пересобираются только при изменении requirements.txt
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
```

Для Node.js — `COPY package.json package-lock.json ./` → `RUN npm ci` → `COPY . .`. Для Go — `go.mod`/`go.sum` → `go mod download` → код.

### Кэш-маунты BuildKit

```dockerfile
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt
```

Кэш пакетного менеджера сохраняется между сборками, но **не попадает в образ**.

### Управление кэшем

```bash
docker build --no-cache -t myapp .        # собрать без кэша
docker build --pull -t myapp .            # проверить свежесть базового образа
docker builder prune                      # очистить кэш сборки
docker buildx build --cache-from type=registry,ref=registry/app:cache --cache-to type=registry,ref=registry/app:cache,mode=max .
```

В CI каждый раз чистая машина — кэш передают через реестр (`--cache-from`/`--cache-to`).

## Контекст сборки и .dockerignore

`docker build .` отправляет демону **весь каталог** — это контекст. Если там `node_modules`, `.git`, дампы баз и логи — сборка медленная, а `COPY . .` тащит мусор и секреты в образ и ломает кэш.

**.dockerignore** в корне контекста исключает файлы:

```
.git
node_modules
__pycache__
*.log
.env
Dockerfile
docker-compose*.yml
dist
coverage
```

> [!warning] .env и ключи
> Если `.env` или `id_rsa` не исключены, `COPY . .` положит их в образ, а образ может уйти в публичный реестр.

### Огромный контекст сборки

Сборка образа из `~/ctx` каждый раз начинается с долгой передачи **контекста**: в каталоге проекта лежат `.git`, `node_modules`, логи и выгрузки базы. В образ нужен только код (`app.py`). Сделайте так, чтобы контекст сборки стал **меньше 1 МБ**, а образ по-прежнему собирался и содержал `app.py`. Dockerfile менять не нужно.

```bash setup
rm -rf /home/student/ctx
mkdir -p /home/student/ctx/.git/objects /home/student/ctx/node_modules/big /home/student/ctx/logs /home/student/ctx/dumps
echo 'print("ctx app")' > /home/student/ctx/app.py
printf 'FROM python:3.12-slim\nWORKDIR /app\nCOPY . .\nCMD ["python3", "app.py"]\n' > /home/student/ctx/Dockerfile
head -c 30000000 /dev/urandom > /home/student/ctx/node_modules/big/blob.bin
head -c 20000000 /dev/urandom > /home/student/ctx/.git/objects/pack.bin
head -c 10000000 /dev/urandom > /home/student/ctx/dumps/db.sql
for i in $(seq 1 50); do echo "log line $i" > /home/student/ctx/logs/app-$i.log; done
chown -R student:student /home/student/ctx
```

```bash check
out=$(su - student -c 'docker build --progress=plain --no-cache -t lab-ctx-check ~/ctx' 2>&1) || fail "Образ из ~/ctx не собирается: $(echo "$out" | tail -2 | tr '\n' ' ')"
size=$(echo "$out" | grep -oE 'transferring context: [0-9.]+[kMG]?B' | tail -1 | awk '{print $3}')
[ -n "$size" ] || fail "Не удалось определить размер контекста"
bytes=$(echo "$size" | awk '/kB$/ {print $1*1000; next} /MB$/ {print $1*1000000; next} /GB$/ {print $1*1e9; next} {print $1+0}' | cut -d. -f1)
[ "$bytes" -lt 1000000 ] || fail "Контекст сборки — $size"
docker run --rm lab-ctx-check ls /app | grep -qx app.py || fail "В образе нет app.py"
docker run --rm lab-ctx-check ls -a /app | grep -qxE 'node_modules|\.git|dumps' && fail "В образ попали лишние каталоги"
docker rmi -f lab-ctx-check >/dev/null 2>&1
ok "контекст сборки: $size"
```

```text hint
1. Собрать образ с подробным выводом и найти строку о передаче контекста — сколько сейчас уходит демону.
2. Рядом с Dockerfile можно положить файл исключений: шаблоны путей, которые не попадут в контекст, — по строке на шаблон, синтаксис как у .gitignore.
3. Исключить служебные и тяжёлые каталоги и логи, пересобрать и сравнить.
```

```bash solution
cd ~/ctx
printf '.git\nnode_modules\nlogs\ndumps\n*.log\n' > .dockerignore
docker build --progress=plain -t ctx-app . 2>&1 | grep 'transferring context'
```

```text review
Эталон: `.dockerignore` с `.git`, `node_modules`, `logs`, `dumps`.

- Контекст — всё содержимое каталога сборки, его целиком отправляют сборщику **до** первой инструкции. Сотни мегабайт контекста = медленная сборка даже с кэшем.
- `.dockerignore` защищает и от утечек: `COPY . .` без него затащит в образ `.git` (вся история), `.env` с паролями и ключи.
- Обычный набор: `.git`, `node_modules`, `__pycache__`, `.venv`, `*.log`, `.env`, `Dockerfile*`, `docs/`. Можно наоборот: `*` и потом `!app.py`, `!requirements.txt` — разрешить только нужное.
```

### Порядок инструкций и кэш

В `~/cacheapp` — приложение и Dockerfile. Каждый раз, когда меняется хоть строка в `app.py`, сборка заново устанавливает зависимости — а это самая долгая часть. Переставьте инструкции так, чтобы при изменении **только кода** шаг установки зависимостей брался **из кэша**. Образ должен работать как раньше.

```bash setup
rm -rf /home/student/cacheapp
mkdir -p /home/student/cacheapp
echo 'print("cache app v1")' > /home/student/cacheapp/app.py
printf '# зависимости приложения (для учебного примера список пуст)\n' > /home/student/cacheapp/requirements.txt
cat > /home/student/cacheapp/Dockerfile <<'EOF'
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install --no-cache-dir -r requirements.txt && echo "зависимости установлены"
CMD ["python3", "app.py"]
EOF
chown -R student:student /home/student/cacheapp
```

```bash check
d=/home/student/cacheapp
grep -qE '^\s*RUN\s+.*pip install' $d/Dockerfile || fail "Из Dockerfile пропала установка зависимостей"
su - student -c "docker build -q -t lab-cache-check $d" >/dev/null 2>&1 || fail "Образ из ~/cacheapp не собирается"
cp $d/app.py /tmp/lab-app.py.bak
echo "# изменение кода $RANDOM" >> $d/app.py
out=$(su - student -c "docker build --progress=plain -t lab-cache-check $d" 2>&1)
cp /tmp/lab-app.py.bak $d/app.py; chown student:student $d/app.py
step=$(echo "$out" | grep -E '^#[0-9]+ \[[0-9/ ]+\] RUN .*pip install' | head -1 | awk '{print $1}')
[ -n "$step" ] || fail "Не нашёл шаг установки зависимостей в выводе сборки"
echo "$out" | grep -qx "$step CACHED" || fail "После изменения app.py зависимости устанавливаются заново — шаг не берётся из кэша"
docker run --rm lab-cache-check | grep -q "cache app" || fail "Образ собирается, но приложение не запускается"
docker rmi -f lab-cache-check >/dev/null 2>&1
ok "при изменении кода установка зависимостей — CACHED"
```

```text hint
1. Кэш шага сбрасывается, если изменились файлы, скопированные в образ до него, — и тогда пересобираются все следующие шаги.
2. Значит, сначала копируют только файл со списком зависимостей и устанавливают их, а весь остальной код — потом.
3. Собрать дважды, изменив код между сборками, и посмотреть в подробном выводе, какие шаги помечены как взятые из кэша.
```

```bash solution
cat > ~/cacheapp/Dockerfile <<'EOF'
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt && echo "зависимости установлены"
COPY . .
CMD ["python3", "app.py"]
EOF
docker build -q -t cacheapp ~/cacheapp
```

```text review
Эталон: `COPY requirements.txt .` → `RUN pip install ...` → `COPY . .`.

- Правило: сначала то, что меняется **редко** (базовый образ, системные пакеты, зависимости), в конце — то, что меняется **часто** (код).
- Docker сравнивает инструкцию и контрольные суммы скопированных файлов. Изменился файл в `COPY` — этот шаг и все после него пересобираются.
- Для Node.js то же: `COPY package*.json .` → `RUN npm ci` → `COPY . .`; для Go — `COPY go.mod go.sum .` → `RUN go mod download` → `COPY . .`.
- В CI кэш между сборками на разных машинах не живёт сам: `--cache-from`/`--cache-to type=registry`.
```

### Удалённый файл всё равно в образе

Dockerfile в `~/fatimg` скачивает «дистрибутив» на 80 МБ, распаковывает из него одну маленькую утилиту и удаляет архив. Но образ всё равно весит на 80 МБ больше базового. Исправьте Dockerfile так, чтобы образ **`fatimg:slim`** был больше `alpine:3.20` **не более чем на 10 МБ**, а утилита `/usr/local/bin/tool` в нём осталась.

```bash setup
docker rmi -f fatimg:slim >/dev/null 2>&1
rm -rf /home/student/fatimg && mkdir -p /home/student/fatimg
cat > /home/student/fatimg/Dockerfile <<'EOF'
FROM alpine:3.20
# «скачиваем» большой архив
RUN mkdir /dist && head -c 80000000 /dev/urandom > /dist/archive.bin && printf '#!/bin/sh\necho tool ok\n' > /dist/tool
# забираем из него утилиту
RUN install -m 755 /dist/tool /usr/local/bin/tool
# удаляем архив
RUN rm -rf /dist
CMD ["tool"]
EOF
chown -R student:student /home/student/fatimg
true
```

```bash check
docker image inspect fatimg:slim >/dev/null 2>&1 || fail "Образа fatimg:slim нет"
base=$(docker image inspect -f '{{.Size}}' alpine:3.20); s=$(docker image inspect -f '{{.Size}}' fatimg:slim)
d=$(( (s - base) / 1024 / 1024 ))
[ $d -le 10 ] || fail "fatimg:slim больше alpine:3.20 на $d МБ"
[ "$(docker run --rm fatimg:slim)" = "tool ok" ] || fail "Утилита /usr/local/bin/tool в образе не работает"
ok "fatimg:slim: +$d МБ к alpine"
```

```text hint
1. Каждая инструкция RUN — отдельный слой. Удаление в следующем слое лишь прячет файл, но байты остаются в предыдущем слое.
2. Скачать, забрать нужное и удалить мусор нужно в одной инструкции — тогда большой файл не попадёт ни в один слой.
3. Посмотреть размер слоёв можно в истории образа.
```

```bash solution
cat > ~/fatimg/Dockerfile <<'EOF'
FROM alpine:3.20
RUN mkdir /dist \
 && head -c 80000000 /dev/urandom > /dist/archive.bin \
 && printf '#!/bin/sh\necho tool ok\n' > /dist/tool \
 && install -m 755 /dist/tool /usr/local/bin/tool \
 && rm -rf /dist
CMD ["tool"]
EOF
docker build -q -t fatimg:slim ~/fatimg
docker history fatimg:slim | head -4
```

```text review
Эталон: всё в одном `RUN ... && ... && rm -rf /dist`.

- Слои только добавляются: `RUN rm` создаёт новый слой с пометкой «удалено» (whiteout), а файл остаётся в слое ниже. `docker history` показывает размер каждого слоя.
- Классика: `RUN apt-get update && apt-get install -y --no-install-recommends ... && rm -rf /var/lib/apt/lists/*` — в одной инструкции.
- Ещё лучше — **multi-stage**: всё тяжёлое в этапе сборки, в итоговый образ копируется только результат (следующая тема).
- Секреты, удалённые в следующем слое, тоже остаются в образе — их можно достать из любого слоя.
```

- [x] Сохраняет кэш pip между сборками, не включая его в итоговый образ
- [ ] Отключает кэш
- [ ] Копирует кэш в образ
> Ускоряет повторную установку зависимостей.
