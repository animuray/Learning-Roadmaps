# Best practices Dockerfile

Хороший образ — **маленький, воспроизводимый, безопасный и быстро собирается**. Ниже — правила, которые проверяют на ревью и спрашивают на собеседованиях.

## 1. Минимальный и официальный базовый образ

- Берите официальные образы (`python`, `node`, `nginx`) или образы проверенных издателей.
- Варианты: `-slim` (урезанный Debian), `-alpine` (~5 МБ), `distroless`, `scratch`.
- **Alpine — не всегда лучший выбор:** в нём musl вместо glibc. Python-пакеты с C-расширениями могут собираться из исходников (медленно) или вести себя иначе. Для Python чаще берут `-slim`.

## 2. Фиксируйте версии

```dockerfile
FROM python:3.12.7-slim-bookworm        # не python:latest
FROM nginx:1.27-alpine@sha256:...       # максимум воспроизводимости — по digest
```

`latest` сегодня и через месяц — разные образы, и сборка внезапно ломается. Версии пакетов приложения фиксируйте lock-файлами (`requirements.txt` с версиями, `package-lock.json`, `go.sum`).

## 3. Порядок слоёв для кэша

Редко меняющееся — выше: системные пакеты → зависимости → код. Подробно — в теме про кэш.

## 4. Меньше слоёв и чистка в том же RUN

```dockerfile
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*
```

- `--no-install-recommends` — не ставить рекомендуемые пакеты;
- `rm -rf /var/lib/apt/lists/*` — удалить списки пакетов в том же слое;
- `pip install --no-cache-dir`, `apk add --no-cache`, `npm ci && npm cache clean --force`.

## 5. Multi-stage

Инструменты сборки не должны попадать в итоговый образ.

## 6. Не запускайте от root

```dockerfile
RUN groupadd --system app && useradd --system --gid app --uid 10001 app
COPY --chown=app:app . .
USER app
```

Если злоумышленник получит выполнение кода в контейнере от root, а изоляция неидеальна, он ближе к root на хосте. В Kubernetes политика `runAsNonRoot` вообще не даст запустить такой контейнер. Порты ниже 1024 непривилегированный пользователь слушать не может — слушайте 8080.

## 7. .dockerignore

Исключите `.git`, `node_modules`, `.env`, логи — меньше контекст, нет утечек, стабильнее кэш.

## 8. Один процесс — одна задача

Контейнер = одно приложение. Не запихивайте nginx + приложение + базу + cron в один образ через supervisord: их нельзя масштабировать, обновлять и перезапускать по отдельности, а логи смешиваются.

## 9. Корректный PID 1 и сигналы

- `CMD`/`ENTRYPOINT` в exec-форме.
- В entrypoint-скрипте — `exec "$@"`.
- Если приложение порождает дочерние процессы и не умеет их «пожинать» (зомби), используйте `docker run --init` или **tini** как ENTRYPOINT.
- Приложение должно корректно обрабатывать SIGTERM: закончить запросы, закрыть соединения.

## 10. Логи в stdout/stderr

Не пишите логи в файлы внутри контейнера — Docker и Kubernetes собирают stdout/stderr. Официальный образ nginx делает симлинки `/var/log/nginx/access.log → /dev/stdout`.

## 11. Конфигурация через окружение, секреты — не в образе

Один образ для dev, stage и prod; различия — в переменных окружения и смонтированных конфигах (принцип 12-factor). Никаких паролей в Dockerfile, ENV и ARG.

## 12. Метаданные и HEALTHCHECK

```dockerfile
LABEL org.opencontainers.image.source="https://gitlab.com/team/app" \
      org.opencontainers.image.version="1.4.2"
HEALTHCHECK CMD wget -qO- http://localhost:8080/health || exit 1
```

## 13. Сканирование и линтинг

```bash
hadolint Dockerfile                    # линтер Dockerfile
trivy image myapp:1.0                  # уязвимости в пакетах образа
docker scout cves myapp:1.0
```

Регулярно пересобирайте образы, чтобы подтянуть исправления безопасности базового образа (`docker build --pull`).

## Плохой и хороший Dockerfile

```dockerfile
FROM node:latest
COPY . .
RUN npm install
CMD npm start
```

Проблемы: плавающая версия, огромный образ, кэш ломается при любом изменении, dev-зависимости в проде, root, shell-форма CMD, нет .dockerignore.

```dockerfile
FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

FROM node:22-alpine
ENV NODE_ENV=production
WORKDIR /app
COPY --from=deps --chown=node:node /app/node_modules ./node_modules
COPY --chown=node:node . .
USER node
EXPOSE 3000
CMD ["node", "server.js"]
```

## Практика

- [ ] Взять плохой Dockerfile из примера выше, собрать его и записать размер и время пересборки
- [ ] Исправить его по всем пунктам и сравнить размер, время пересборки после изменения кода и `id` внутри контейнера
- [ ] Прогнать оба Dockerfile через hadolint и разобрать предупреждения
- [ ] Просканировать оба образа через trivy и сравнить число уязвимостей
- [ ] Проверить, как приложение реагирует на `docker stop`: завершается ли сразу или ждёт 10 секунд

## Тест

### Почему не стоит использовать тег latest в FROM?
- [ ] latest всегда самая старая версия
- [x] Под latest со временем оказываются разные образы — сборка перестаёт быть воспроизводимой и может внезапно сломаться
- [ ] latest запрещён в Docker Hub
- [ ] latest медленнее скачивается
> Фиксируйте версию, а для максимальной точности — digest.

### Зачем запускать контейнер не от root?
- [x] При компрометации приложения у атакующего будет меньше прав внутри контейнера и меньше шансов выбраться на хост
- [x] Многие политики безопасности (например, runAsNonRoot в Kubernetes) запрещают запуск от root
- [ ] Так контейнер быстрее работает
- [ ] Root не может слушать порты
> Пользователя создают в Dockerfile и переключаются через USER.

### Как правильно установить пакеты через apt в Dockerfile?
- [ ] RUN apt-get update, отдельной строкой RUN apt-get install -y curl
- [x] Одним RUN: apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/*
- [ ] RUN apt-get upgrade -y
- [ ] ADD с пакетами
> Чистка в том же слое действительно уменьшает образ.

### Почему alpine не всегда лучший базовый образ для Python?
- [ ] Alpine не поддерживает Python
- [x] В alpine используется musl вместо glibc: многие пакеты с C-расширениями приходится собирать из исходников, сборка медленнее, возможны отличия в поведении
- [ ] Alpine больше slim
- [ ] В alpine нет оболочки
> Для Python часто выбирают `python:3.x-slim`.

### Почему не стоит запускать nginx, приложение и базу в одном контейнере?
- [ ] Docker это запрещает
- [x] Их нельзя масштабировать, обновлять и перезапускать независимо, а при падении одного процесса контейнер может продолжать считаться живым
- [ ] Это увеличивает размер образа в 10 раз
- [ ] Контейнеры не поддерживают несколько портов
> Один контейнер — одна ответственность; связывайте их через Compose или Kubernetes.

### Для чего нужен флаг docker run --init или tini?
- [ ] Для инициализации базы данных
- [x] Чтобы PID 1 корректно передавал сигналы и забирал завершившиеся дочерние процессы (зомби)
- [ ] Для ускорения запуска
- [ ] Для включения systemd в контейнере
> Обычные приложения не рассчитаны работать как init.

### Куда приложение в контейнере должно писать логи?
- [ ] В файл /var/log/app.log внутри контейнера
- [x] В stdout и stderr — их собирает Docker или Kubernetes
- [ ] В базу данных
- [ ] Никуда
> Файлы в контейнере пропадут вместе с ним и заполняют слой записи.

### Как называется популярный линтер для Dockerfile?
= hadolint
> Он также проверяет shell-команды в RUN через ShellCheck.

### Какой инструмент сканирует образ на известные уязвимости пакетов?
- [x] trivy
- [x] docker scout
- [ ] hadolint
- [ ] dive
> dive показывает содержимое слоёв, hadolint — линтер Dockerfile.

### Как правильно передавать разную конфигурацию для dev, stage и prod?
- [ ] Собирать отдельный образ под каждое окружение с разными файлами
- [x] Использовать один образ, а различия передавать через переменные окружения, смонтированные конфиги и секреты
- [ ] Хранить все пароли в образе и выбирать нужный по ENV
- [ ] Менять файлы через docker exec после запуска
> Тот же образ, что прошёл тесты, уходит в прод.

### Зачем добавлять --no-install-recommends к apt-get install?
- [ ] Чтобы пакеты ставились без подтверждения
- [x] Чтобы не ставить рекомендуемые, но необязательные пакеты и не раздувать образ
- [ ] Чтобы использовать кэш
- [ ] Чтобы отключить обновления безопасности
> Подтверждение отключает флаг `-y`.

### Почему образы нужно регулярно пересобирать, даже если код не менялся?
- [ ] Образы портятся со временем
- [x] Чтобы получить исправления уязвимостей в базовом образе и системных пакетах
- [ ] Реестр удаляет старые образы
- [ ] Чтобы сбросить кэш
> Используйте `docker build --pull` и сканирование в CI.

### Какие проблемы в Dockerfile FROM node:latest / COPY . . / RUN npm install / CMD npm start?
- [x] Плавающая версия базового образа
- [x] Кэш зависимостей ломается при любом изменении кода
- [x] Контейнер работает от root, а CMD в shell-форме
- [ ] Нет проблем
> Плюс dev-зависимости в проде и большой базовый образ.
