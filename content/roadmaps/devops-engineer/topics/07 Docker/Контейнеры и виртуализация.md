# Контейнеры и виртуализация

Главная задача контейнеров — **упаковать приложение со всеми зависимостями** так, чтобы оно одинаково запускалось на ноутбуке разработчика, в CI и на сервере. Больше никакого «у меня работает». В практике Linux вы руками ставили Python, библиотеки и версии Node.js — контейнер делает это один раз в образе.

## Виртуальная машина и контейнер

```
   Виртуальные машины                      Контейнеры
┌────────┐ ┌────────┐ ┌────────┐     ┌────────┐ ┌────────┐ ┌────────┐
│  App   │ │  App   │ │  App   │     │  App   │ │  App   │ │  App   │
│ Libs   │ │ Libs   │ │ Libs   │     │ Libs   │ │ Libs   │ │ Libs   │
│Гост.ОС │ │Гост.ОС │ │Гост.ОС │     └────────┘ └────────┘ └────────┘
│ (ядро) │ │ (ядро) │ │ (ядро) │     ┌──────────────────────────────┐
└────────┘ └────────┘ └────────┘     │ Container runtime (Docker…)  │
┌──────────────────────────────┐     ├──────────────────────────────┤
│ Гипервизор (KVM, VMware…)    │     │ ОС хоста — ОДНО общее ядро   │
├──────────────────────────────┤     ├──────────────────────────────┤
│ Железо                        │     │ Железо                        │
└──────────────────────────────┘     └──────────────────────────────┘
```

| | Виртуальная машина | Контейнер |
| --- | --- | --- |
| Что виртуализируется | Железо — у каждой ВМ своё ядро и полноценная ОС | ОС — все контейнеры используют **ядро хоста** |
| Изоляция | Сильная, на уровне гипервизора | Слабее: механизмы ядра (namespaces, cgroups) |
| Размер | Гигабайты | Мегабайты — десятки мегабайт |
| Запуск | Десятки секунд — минуты | Доли секунды |
| Другая ОС | Можно (Windows на Linux) | Только с тем же ядром: Linux-контейнеры на Linux |
| Плотность | Единицы-десятки на сервер | Сотни на сервер |

Контейнеры и ВМ не конкурируют, а дополняют друг друга: в облаке контейнеры обычно работают **внутри** виртуальных машин.

## Как устроен контейнер

Контейнер — это **обычный процесс Linux**, которому ядро:

- **namespaces** — даёт изолированный взгляд на систему: свои PID (приложение — PID 1), сеть и порты, файловую систему, имя хоста, пользователей;
- **cgroups** — ограничивает ресурсы: CPU, память, число процессов;
- **корневая ФС из образа** (через overlayfs) — свой набор файлов и библиотек;
- **capabilities, seccomp, AppArmor/SELinux** — урезанные права даже для root внутри.

Подробно это разбиралось в теме «OOM Killer, cgroups и namespaces». Отсюда следствие: уязвимость ядра или запуск контейнера с `--privileged` может дать доступ к хосту.

## Образ и контейнер

- **Образ** (image) — неизменяемый шаблон: слои файловой системы + метаданные (команда запуска, переменные, порты).
- **Контейнер** — запущенный экземпляр образа с тонким слоем для записи сверху.

Аналогия: образ — класс, контейнер — объект. Из одного образа можно запустить сколько угодно контейнеров.

## OCI — стандарты

**Open Container Initiative** (2015, Docker и другие компании) описывает три спецификации:

- **image-spec** — формат образа;
- **runtime-spec** — как запускать контейнер из распакованного образа (эталонная реализация — **runc**);
- **distribution-spec** — API реестров для `push` и `pull`.

Благодаря OCI образ, собранный Docker, запускается в Podman, containerd и Kubernetes.

## Экосистема инструментов

| Инструмент | Роль |
| --- | --- |
| **Docker** | Всё в одном: сборка, запуск, реестр, Compose. Демон `dockerd` + CLI |
| **containerd** | Среда выполнения контейнеров уровнем ниже — используется внутри Docker и напрямую в Kubernetes |
| **runc** / crun | Низкоуровневый runtime: создаёт namespaces и cgroups и запускает процесс |
| **Podman** | Альтернатива Docker **без демона**, контейнеры без root по умолчанию, совместимый CLI (`alias docker=podman`) |
| **Buildah** | Сборка образов без демона (используется и в Podman) |
| CRI-O | Runtime специально для Kubernetes |

> [!note] Kubernetes и Docker
> Kubernetes больше не использует Docker Engine напрямую — он работает с containerd или CRI-O через интерфейс CRI. Но образы, собранные Docker, работают там без изменений: это всё OCI-образы.

## Практика

- [ ] Установить Docker Engine по официальной инструкции для своего дистрибутива и выполнить `docker run hello-world`
- [ ] Запустить `docker run --rm -it alpine sh` и посмотреть внутри `ps`, `hostname`, `ip a`, `cat /etc/os-release`; сравнить с хостом
- [ ] Найти процесс контейнера на хосте (`docker inspect -f '{{.State.Pid}}' имя` и `ps -fp PID`) и убедиться, что это обычный процесс
- [ ] Посмотреть namespaces контейнера: `sudo ls -l /proc/PID/ns` и сравнить с namespaces своей оболочки
- [ ] Установить Podman и запустить тот же образ без sudo: `podman run --rm alpine echo hi`

## Лаборатория

Docker установлен на стенде, пользователь `student` в группе `docker` — команды `docker` работают без sudo.

```bash setup
lab_drm() { docker rm -f "$@" >/dev/null 2>&1; true; }
# образ есть локально или скачивается (если ученик почистил образы через prune)
lab_img() { for i in "$@"; do docker image inspect "$i" >/dev/null 2>&1 || docker pull -q "$i" >/dev/null; done; }
# lab_wait_http URL [строка] — дождаться ответа
lab_wait_http() { for i in $(seq 60); do curl -s --max-time 1 "$1" 2>/dev/null | grep -q "${2:-.}" && return 0; sleep 0.25; done; return 1; }
lab_img alpine:3.20
```

### Контейнер — это процесс хоста

Запущен контейнер `lab-sleeper`. Найдите **PID главного процесса контейнера на хосте** (стенде) и запишите его в `~/container-pid.txt`.

```bash setup
lab_drm lab-sleeper
docker run -d --name lab-sleeper alpine:3.20 sleep 100000 >/dev/null
rm -f /home/student/container-pid.txt
```

```bash check
want=$(docker inspect -f '{{.State.Pid}}' lab-sleeper 2>/dev/null)
[ -n "$want" ] && [ "$want" != 0 ] || fail "Контейнер lab-sleeper не запущен — начните задачу заново"
[ -f /home/student/container-pid.txt ] || fail "Нет ~/container-pid.txt"
got=$(tr -d '[:space:]' < /home/student/container-pid.txt)
[ "$got" = "$want" ] || fail "В ~/container-pid.txt «$got» — это не PID процесса контейнера на хосте (внутри контейнера у него PID 1, но на хосте номер другой)"
ok "lab-sleeper — это процесс $want на хосте: $(ps -o user=,args= -p $want)"
```

```text hint
1. Команда подробной информации о контейнере выводит его состояние, в том числе PID процесса на хосте. Можно попросить только это поле шаблоном формата.
2. Убедиться, что такой процесс виден в обычном списке процессов хоста.
```

```bash solution
docker inspect -f '{{.State.Pid}}' lab-sleeper > ~/container-pid.txt
ps -fp "$(cat ~/container-pid.txt)"
```

```text review
Эталон: `docker inspect -f '{{.State.Pid}}' lab-sleeper`.

- Контейнер — не виртуальная машина: это обычный процесс хоста, изолированный namespaces и ограниченный cgroups. Его видно в `ps` и `top` хоста, у него свой PID на хосте и PID 1 внутри.
- Отсюда: ядро общее (уязвимость ядра — общая для всех контейнеров), а root в контейнере без user namespaces — это root хоста с урезанными правами.
- `docker top lab-sleeper` — процессы контейнера с PID хоста; `docker inspect` — вся конфигурация (сети, тома, переменные, лимиты).
```

### Заглянуть в сеть контейнера с хоста

В минимальных образах нет сетевых утилит. Узнайте **IP-адрес контейнера** `lab-sleeper` изнутри его сетевого пространства имён, используя утилиты **хоста** (`nsenter`), и запишите адрес в `~/container-ip.txt`.

```bash setup
lab_drm lab-sleeper
docker run -d --name lab-sleeper alpine:3.20 sleep 100000 >/dev/null
rm -f /home/student/container-ip.txt
```

```bash check
want=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' lab-sleeper)
[ -f /home/student/container-ip.txt ] || fail "Нет ~/container-ip.txt"
got=$(grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' /home/student/container-ip.txt | head -1)
[ "$got" = "$want" ] || fail "В ~/container-ip.txt «$got» — у контейнера другой адрес"
ok "IP lab-sleeper: $want"
```

```text hint
1. Узнать PID процесса контейнера на хосте.
2. Утилита nsenter запускает команду в пространствах имён указанного процесса — нужно только сетевое. Команда — привычная ip с выводом адресов. Нужны права root.
```

```bash solution
pid=$(docker inspect -f '{{.State.Pid}}' lab-sleeper)
sudo nsenter -t "$pid" -n ip -4 -o addr show eth0
sudo nsenter -t "$pid" -n ip -4 -o addr show eth0 | awk '{print $4}' | cut -d/ -f1 > ~/container-ip.txt
```

```text review
Эталон: `sudo nsenter -t <PID> -n ip addr`.

- `nsenter -n` — только сетевой namespace, а утилиты (ip, ss, tcpdump, curl) берутся с хоста. Так отлаживают сеть контейнера без утилит внутри: `sudo nsenter -t <PID> -n ss -ltn`, `... tcpdump -i eth0`.
- Флаги: `-n` сеть, `-m` файловая система, `-p` PID, `-u` hostname. `nsenter -t PID -a` — во все сразу (почти как `docker exec`).
- Альтернатива — отладочный контейнер в той же сети: `docker run --rm -it --network container:lab-sleeper nicolaka/netshoot`.
```

## Тест

### Главное отличие контейнера от виртуальной машины?
- [ ] Контейнер всегда безопаснее
- [x] Контейнеры используют общее ядро хоста, а у каждой ВМ своё ядро и полноценная гостевая ОС
- [ ] Контейнеры работают только в облаке
- [ ] ВМ запускаются быстрее
> Поэтому контейнеры легче и быстрее, но изолированы слабее.

### На каких механизмах ядра Linux построены контейнеры?
- [x] namespaces — изоляция того, что видит процесс
- [x] cgroups — ограничение ресурсов
- [ ] Гипервизор KVM
- [ ] Отдельное ядро на каждый контейнер
> Плюс overlayfs для файловой системы образа и capabilities/seccomp для ограничения прав.

### Можно ли запустить Linux-контейнер с ядром, отличным от ядра хоста?
- [ ] Да, всегда
- [x] Нет: контейнер использует ядро хоста; другое ядро требует виртуальной машины
- [ ] Да, если указать --kernel
- [ ] Только в Podman
> Docker Desktop на macOS и Windows запускает Linux-контейнеры внутри скрытой ВМ с Linux.

### Чем образ отличается от контейнера?
- [ ] Это одно и то же
- [x] Образ — неизменяемый шаблон из слоёв, контейнер — запущенный экземпляр образа со своим слоем для записи
- [ ] Контейнер хранится в реестре, образ — нет
- [ ] Образ — это запущенный процесс
> Из одного образа можно запустить много контейнеров.

### Что стандартизирует Open Container Initiative (OCI)?
- [x] Формат образа (image-spec)
- [x] Запуск контейнера (runtime-spec)
- [x] API реестров для загрузки и выгрузки образов (distribution-spec)
- [ ] Формат docker-compose.yaml
> Благодаря этому образ Docker работает в Podman и Kubernetes.

### Чем Podman отличается от Docker?
- [ ] Podman не совместим с образами Docker
- [x] Podman работает без постоянного демона и по умолчанию запускает контейнеры без root, при этом CLI совместим с Docker
- [ ] Podman работает только на Windows
- [ ] Podman — это реестр образов
> Можно даже сделать `alias docker=podman`.

### Что такое runc?
- [ ] Реестр образов
- [x] Низкоуровневый runtime по спецификации OCI, который создаёт namespaces и cgroups и запускает процесс контейнера
- [ ] Графический интерфейс Docker
- [ ] Формат образа
> Docker → containerd → runc — цепочка запуска контейнера.

### Какая эталонная реализация OCI runtime-spec передана Docker в OCI?
= runc
> Альтернатива — crun.

### Почему запуск контейнера с --privileged опасен?
- [ ] Он работает медленнее
- [x] Контейнер получает почти полный доступ к устройствам и возможностям ядра хоста, и изоляция фактически снимается
- [ ] Он не может использовать сеть
- [ ] Он удаляет образ после запуска
> Используйте только когда без этого никак, и понимайте риски.

### Использует ли современный Kubernetes Docker Engine для запуска контейнеров?
- [ ] Да, всегда
- [x] Нет, он работает с containerd или CRI-O через интерфейс CRI, но образы Docker запускаются там без изменений
- [ ] Kubernetes вообще не использует контейнеры
- [ ] Только в облаках
> Все эти инструменты работают с OCI-образами.

### Почему контейнер запускается за доли секунды, а виртуальная машина — гораздо дольше?
- [ ] Контейнеры кэшируются в оперативной памяти
- [x] Контейнеру не нужно загружать ядро и ОС: это просто процесс с изоляцией на уже работающем ядре
- [ ] Контейнеры не используют диск
- [ ] Виртуальные машины всегда работают в облаке
> ВМ проходит полную загрузку: прошивка, загрузчик, ядро, init.
