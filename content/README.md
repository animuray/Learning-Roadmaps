# Контент: как писать роадмапы, конспекты и тесты

Папка `content/` — это **хранилище Obsidian**. Откройте её в Obsidian через «Open folder as vault» и пишите как обычные заметки. Сайт сам соберёт из них карту роадмапа, страницы тем, практику и тесты.

```
content/
├── README.md                ← эта инструкция
├── _templates/Тема.md       ← шаблон темы (плагин Templates в Obsidian)
└── roadmaps/
    └── devops/              ← адрес роадмапа: /roadmaps/devops (латиница, цифры, дефис)
        ├── roadmap.md       ← карта: разделы и порядок тем
        └── topics/          ← заметки-темы, можно раскладывать по любым подпапкам
            └── 01 Основы ИТ/
                ├── Устройство компьютера.md
                └── ...
```

## 1. Карта роадмапа — `roadmap.md`

```markdown
---
title: DevOps — от нуля до L2
description: Короткое описание для карточки роадмапа.
mode: sequential     # sequential — темы открываются по порядку; free — всё открыто сразу
passScore: 80        # процент для зачёта теста по умолчанию
order: 1             # порядок в списке роадмапов
---

## Название раздела
Описание раздела одной строкой.

- [[Устройство компьютера]]
	- Подтема
	- Ещё подтема
- [[BGP]] #optional
```

- `## Раздел` — раздел на карте.
- `- [[Заметка]]` — тема. Порядок пунктов = порядок прохождения.
- Вложенные пункты — подтемы: показываются на карте и в шапке темы.
- `#optional` — необязательная тема: открыта всегда и не блокирует следующие.
- `- [[Заметка|Другое название]]` — показать тему под другим именем.
- Если заметки ещё нет (ссылка в Obsidian «пустая»), тема всё равно появится на сайте с пометкой «нет конспекта», и её можно будет отметить изученной вручную. Кликните по ссылке в Obsidian — заметка создастся.

## 2. Тема — отдельная заметка

Начните с шаблона `_templates/Тема.md`. Поля в начале заметки (frontmatter):

| Поле | Зачем |
| --- | --- |
| `title` | Название темы (иначе — имя файла) |
| `slug` | Адрес темы и ключ прогресса в базе. **Задайте один раз и не меняйте** — иначе прогресс по теме потеряется. Без slug адрес строится из имени файла |
| `description` | Подзаголовок темы |
| `duration` | Сколько минут занимает тема |
| `level` | Уровень: Основы, Продвинутый… |
| `quizSize` | Сколько вопросов давать за попытку (случайно из банка) |
| `passScore` | Процент для зачёта, если отличается от роадмапа |
| `materials` | Список ссылок `title` + `url` (+ `type`, `note`) |
| `aliases` | Другие названия заметки для ссылок `[[...]]` |
| `draft: true` | Пометить тему черновиком |

Всё, что написано в заметке, становится **конспектом**, кроме специальных разделов второго уровня:

- `## Практика` — пункты `- [ ] ...` превращаются в чек-лист, который отмечается на сайте.
- `## Материалы` — строки `- [Название](https://...) — комментарий`.
- `## Тренажёр` — задачи SQL-тренажёра, которые решаются прямо на сайте (формат ниже).
- `## Лаборатория` — задачи в настоящем терминале Linux на учебном стенде (формат ниже).
- `## Тест` — вопросы (формат ниже).

Работают ссылки `[[Другая тема]]`, картинки `![[схема.png]]` (файл кладите в любую папку внутри `content/`), `==выделение==`, таблицы, код с подсветкой и callout-блоки `> [!tip]`, `> [!warning]`, `> [!note]`, `> [!danger]`.

## 3. Тест

```markdown
## Тест

### Вопрос с одним ответом?
- [ ] неверно
- [x] верно
> Пояснение после сдачи.

### Вопрос с несколькими ответами?
- [x] верно
- [x] верно
- [ ] неверно

### Какой командой посмотреть таблицу маршрутов?
= ip route
= ip r
```

- Один `[x]` — один ответ (радиокнопки), несколько `[x]` — несколько ответов (чекбоксы).
- Строки `= ответ` — вопрос с вводом текста; можно перечислить все допустимые варианты.
- `> текст` — пояснение. Показывается только после успешной сдачи, чтобы тест нельзя было пройти «по подсказкам».
- Вопросы и варианты перемешиваются при каждой попытке. Если вопросов больше, чем `quizSize`, каждый раз выпадает случайный набор — делайте банк вопросов побольше.
- Пишите вопросы **не только по конспекту, а по всему важному в теме**: понимание, команды, диагностика, «что сделать, если…».

## 4. Тренажёр SQL

Задачи, в которых нужно написать запрос. На сайте он выполняется в изолированной базе-песочнице: перед запросом создаются таблицы задачи, после проверки всё откатывается.

``````markdown
## Тренажёр

```sql seed
CREATE TABLE products (id integer PRIMARY KEY, name text, price integer);
INSERT INTO products VALUES (1, 'Чай', 50), (2, 'Кофе', 150);
```

### Дорогие товары
Выведите название и цену товаров дороже 100.

```sql check
SELECT name, price FROM products WHERE price > 100;
```

```text hint
Оставить товары, где цена больше 100 → показать название и цену.
```

```sql solution
SELECT name, price FROM products WHERE price > 100;
```
``````

- Каждая задача начинается с `### Название`. Текст под заголовком — условие.
- `` ```sql seed `` — таблицы и данные. Блок **до первой задачи** — общий для всех задач темы; задача со своим seed использует свой.
- `` ```sql check `` — эталонный запрос: результат ученика сравнивается с его результатом (порядок строк неважен, порядок столбцов важен, имена столбцов неважны).
- `` ```sql check ordered `` — то же, но порядок строк важен (задачи на ORDER BY).
- `` ```sql check state `` — для INSERT/UPDATE/DELETE/CREATE: после запроса ученика выполняется контрольный запрос, задача решена, если он вернул хотя бы одну строку.
- `` ```text hint `` и `` ```sql solution `` — подсказка и решение, ученик открывает их кнопками.
- Подсказка — **русский псевдокод**, а не SQL: шаги «взять → оставить → посчитать → отсортировать» и предупреждение о ловушке (деление нацело, NULL, приоритет И/ИЛИ). Не пишите в подсказке код и названия команд — готовый запрос ученик видит по кнопке «Решение».
- В условии явно называйте нужные столбцы и их порядок, а для вычислений — способ округления: `round(price * 0.9)` и `price * 0.9` дают разный результат.

Проверка задач: `npm run sql:check` (или `npm run sql:check -- sql` для одного роадмапа) выполняет решение каждой задачи в песочнице и убеждается, что оно проходит проверку, а пустой запрос — нет.

## 5. Лаборатория (терминал)

Задачи, которые решаются в терминале учебного стенда (Ubuntu 24.04, пользователь `student` с sudo). Проверяется **результат** — состояние системы, а не набранные команды, поэтому засчитывается любое рабочее решение. Чем решение отличается от принятого на практике, объясняют замечания и разбор.

````markdown
## Лаборатория

```bash lib
# общие функции и переменные темы (необязательно)
lab_user_reset() { userdel -r "$1" 2>/dev/null; true; }
```

```bash setup
# общая подготовка для всех задач темы (необязательно), от root
```

### Создать пользователя deploy
Создайте пользователя `deploy` с домашним каталогом и оболочкой bash.

```bash setup
lab_user_reset deploy
```

```bash check
id deploy >/dev/null 2>&1 || fail "Пользователя deploy нет"
[ -d /home/deploy ] || fail "У deploy нет домашнего каталога"
ok "$(id deploy)"
```

```text hint
Создать пользователя одной командой: сразу с домашним каталогом и нужной оболочкой.
```

```bash solution
sudo useradd -m -s /bin/bash deploy
```

```text review
Эталон: `useradd -m -s /bin/bash deploy`. Почему именно так и какие есть варианты…
```

```text notes
useradd\s+(?![^\n]*-m) => Пользователь создавался без -m: домашний каталог не появится сам.
```
````

- `` ```bash lib `` — общие функции и переменные темы (до первой задачи, необязательно). Вставляется перед **каждым** setup и **каждой** check темы: проверка выполняется отдельным процессом и не видит ни функций, ни переменных из setup. Сюда кладут повторяющиеся куски (`lab_net_reset`, `lab_kns`, `lab_s3` и т.п.) — без вывода и побочных эффектов при простом подключении.
- `` ```bash setup `` — приводит стенд в исходное состояние задачи (от root). Выполняется кнопкой «Начать задачу», поэтому должен быть **повторяемым**: удалить то, что мог оставить прошлый запуск. Блок до первой задачи выполняется перед каждой задачей темы.
- `` ```bash check `` — проверка от root: код 0 — решено. Функции `fail "сообщение"` (вывести ✗ и завершить с ошибкой) и `ok "сообщение"`. Пишите в `fail`, **что именно не так** в текущем состоянии стенда («Группы devops нет», «Служба не запустится при загрузке»). Ученик видит этот текст, в том числе когда нажал «Проверить», ничего не сделав, поэтому в `fail` не бывает команд, способа решения («добавьте в .gitignore», «Подсказка: …») и готового ответа («Ожидалось: …»): для этого есть подсказка и решение.
- `` ```bash solution `` — эталонное решение, выполняется от `student`; не должно быть интерактивным (никаких vim — только `tee`, `sed`, here-doc).
- `` ```text review `` — разбор после решения: почему эталон такой, какие есть варианты и подводные камни на работе.
- `` ```text notes `` — замечания: `регулярка => объяснение`, по строке на правило. Регулярка проверяется по командам, которые ученик ввёл в терминале после «Начать задачу» (без учёта регистра, `^`/`$` — границы одной команды). Так тренажёр объясняет, чем рабочее, но неудачное решение хуже эталона (`chmod 777`, `usermod -G` без `-a`, правка пакетного unit-файла). Замечания показываются только после решения задачи.
- `` ```text hint `` — русский псевдокод, как в SQL-тренажёре.
- Файлы ученика — в `/home/student`; создавая их из setup (root), не забудьте `chown student:student`. Репозитории Git для задачи создавайте от имени ученика: `su - student -c 'bash -s' <<'EOF' … EOF`. Служебные данные проверки (правильный ответ и т.п.) — в `/var/lib/lab/`, ученику он недоступен.
- Скрипты setup, check и solution выполняются из временного файла с **пустым stdin** (login-оболочка `bash -l`). Поэтому команды, читающие stdin (`rabbitmqctl`, `docker compose exec`, `ssh`, `su -c …`), не «съедают» остаток скрипта. Если команда ждёт ввода, она получит конец файла — данные передавайте явно (here-doc, `-T`, аргументы).
- Проверка ограничена **минутой**, setup — тремя. Ожидания в check (поды, синхронизация Argo CD, сбор метрик) делайте циклом с потолком по времени, а не `sleep 60`.
- Разбор аварий «Сломанный сервер» — отдельная тема в конце раздела (перед «… на собеседовании»): в условии симптом, а не причина; в задаче обычно две-три поломки, вторая видна после исправления первой; в `fail` — только наблюдаемое состояние.

Проверка: `npm run lab:check` (или `npm run lab:check -- devops-engineer "Git"`) на работающем стенде выполняет для каждой задачи setup, убеждается, что проверка **не** проходит до решения, выполняет эталон и проверяет, что теперь проходит.

## 6. Проверка

```bash
npm run content:check
```

Покажет, сколько тем с конспектами и тестами, и найдёт ошибки: вопросы без правильного ответа, `quizSize` больше банка вопросов.
